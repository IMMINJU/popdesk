# 첫 묶음 사전 부검

> 첫 묶음(v0.1)을 내고 석 달 뒤 일이 틀어졌다고 가정하고, 어떻게 틀어졌을지와 막을 장치를 적는다. 이 묶음은 마이그레이션, 고객사 경계, 개인정보, 공개 계약을 모두 건드려서 전체 경로다(`process.md`).
> 후보는 수용 기준을 쓴 탭(s0-acc)이 넘겼다. 기술 쪽 셋(1~3절)은 별도 탭이 내장 PostgreSQL 16, pgjdbc 42.7, Flyway 12.4로 직접 실험했다. 나머지 일곱(4~10절)은 문서 정합, 프레임워크 동작, 반례 세 갈래로 나눠 조사한 뒤 메인이 근거를 다시 열어 확인했다.
> "옮길 곳"은 장치를 적을 문서다. 수용 기준 ID가 아직 없는 것은 계약 단계 전에 `acceptance.md`에 더한다. 묶음이 끝나면 이 파일은 `design/archive/0-first/`로 간다.

표시: [실험]은 직접 돌려 본 것, [소스]는 라이브러리 소스나 공식 문서로 본 것, [추론]은 확인하지 않은 판단이다.

## 1. 단순하게 짠 첨부 저장은 384MB 힙에서 동시 올리기·내려받기를 견디지 못한다

| 항목 | 내용 |
|---|---|
| 장면 | 고객 열 명이 동시에 10MB 첨부를 올리고 상담원이 내려받자 앱이 메모리 부족으로 죽었다. 재시작 뒤 같은 일이 되풀이됐다 |
| 원인 | `MultipartFile.getBytes()` → 엔티티 `byte[]` → JPA로 짜면 요청 하나가 약 30MB를 잡는다. pgjdbc는 한 연결에서 같은 SQL의 처음 5번을 hex 글자로 받아 3배를 쓰고, Hibernate는 `byte[]`를 한 벌 더 복사한다. pgjdbc로는 bytea 값 하나를 흘려 읽을 방법이 없다 [실험][소스] |
| 막는 법 | 첨부 내용은 메타데이터와 다른 테이블(`attachment_content`)에 두고 JPA 엔티티에 `byte[]` 칸을 두지 않는다. 쓰기는 `setBinaryStream(in, 길이)`. 읽기는 `substring(data from ? for ?)` 1MB 조각을 응답에 바로 쓴다. 안전망으로 올리기·내려받기 동시 수를 각각 16으로 막고 넘으면 503과 `Retry-After`. multipart 상한은 10MB보다 조금 크게, `file-size-threshold`는 0 |
| 확인 테스트 | S0-AC-64를 실제 앱 이미지, `-Xmx384m`, 운영 GC 옵션으로 돈다. 앱을 막 띄운 직후(연결마다 첫 실행)에도 돈다. 내려받은 내용의 해시가 같은지, 힙 최대값을 기록한다. ArchUnit: 엔티티에 `byte[]`·`@Lob` 칸 없음, 첨부 쓰기 코드가 `setBytes`를 부르지 않음 |
| 옮길 곳 | `architecture.md` 첨부 저장, S0-AC-59·64, 새 기준(동시 수 상한과 503) |
| 남은 것 | 앱이 평소 쥐는 힙은 아직 모른다(실험은 150MB로 가정했다). 첫 뼈대를 띄워 잰다. 0.5GB 컨테이너에서는 JVM이 Serial GC를 고를 수 있어 부하 테스트는 운영과 같은 GC로 돈다 |

## 2. 잠금 순서가 엇갈리면 같은 고객사의 동시 등록이 교착으로 실패한다

| 항목 | 내용 |
|---|---|
| 장면 | 월말에 한 고객사에서 문의가 몰리자 일부 등록이 500으로 실패했다. 로그에는 deadlock(40P01)만 남았다 |
| 원인 | 문서대로(순번을 트랜잭션 맨 끝에 `UPDATE … RETURNING`) 짜면 교착이 없다. 그러나 세 경우에 교착이 났다: 순번이나 문의 행을 `SELECT … FOR UPDATE`로 잠글 때, 자식 행을 넣은 뒤 부모를 `FOR UPDATE`로 잠글 때, 순번 칸에 유니크 색인이 걸릴 때. 외래 키 INSERT가 부모에 `FOR KEY SHARE`를 걸고, 이것이 `FOR UPDATE`와만 부딪히기 때문이다 [실험][소스] |
| 막는 법 | 한 트랜잭션의 잠금 순서를 고정한다: ① 있는 문의 행 `FOR NO KEY UPDATE`(어떤 INSERT보다 먼저) → ② 첨부 행 조건부 UPDATE(ID 오름차순) → ③ 새 행 INSERT(문의, 댓글, 보내기 대기, 감사) → ④ 고객사 순번 `UPDATE … RETURNING` → ⑤ (1번 묶음부터) 감사 사슬 머리 행. `FOR UPDATE`는 쓰지 않는다. 순번 칸에 유니크 색인을 두지 않는다. 첨부 ①(`pending` 커밋)과 ②(저장소 쓰기)는 업무 트랜잭션을 열기 전에 끝내고 `REQUIRES_NEW`로 부르지 않는다. 문의 ID는 앱에서 먼저 정하고 첨부의 외래 키를 `DEFERRABLE INITIALLY DEFERRED`로 두어, 문의 번호 칸에 NOT NULL을 건다. DB 연결에 `lock_timeout` 5초를 걸고, 40P01·55P03이면 한 번만 다시 시도한다. 팀 총량 한도는 잠그지 않고 동시 업로드로 조금 넘는 것을 받아들인다 |
| 확인 테스트 | 같은 고객사에 첨부 섞은 등록 20건 동시: 모두 성공, 순번 1~20 빈칸 없음, 40P01 없음(S0-AC-44). 같은 문의에 댓글 20건과 첨부 20건 동시(S0-AC-51·56). 두 테스트의 SQL 로그에 `NO KEY` 없는 `FOR UPDATE`가 없다. 순번 직전 실패 주입: 순번이 쓰이지 않고 첨부는 `pending`으로 남는다(S0-AC-63). 정리 작업과 ③이 같은 `pending` 행을 두고 겨루면 하나만 이긴다. 스키마 테스트: 순번 칸에 유니크 색인 없음 |
| 옮길 곳 | `architecture.md` 동시성 절, S0-AC-44·51·56·63, `conventions.md`(재시도 규칙) |

## 3. Flyway 기본 설정과 Boot 기동 순서는 수용 기준 둘과 맞지 않는다

| 항목 | 내용 |
|---|---|
| 장면 | 두 번째 릴리스의 `CREATE INDEX CONCURRENTLY` 마이그레이션이 끝나지 않아 업그레이드가 멈췄다. 상태 확인은 마이그레이션 내내 연결을 거부했는데 문서는 "liveness UP"이라고 적고 있었다 |
| 원인 | Flyway 12.4는 기본으로 마이그레이션마다 트랜잭션 advisory lock을 잡고, 마이그레이션 SQL은 다른 연결에서 돈다. `CONCURRENTLY`는 잠금을 쥔 연결의 트랜잭션이 끝나길 기다리고, 그 연결은 `CONCURRENTLY`를 기다린다. DB는 이것을 교착으로 보지 않는다 [실험]. Boot는 Flyway가 도는 동안 HTTP 포트를 열지 않는다 [소스]. 앱 잠금 없이 두 대가 겹쳐 뜨면 둘 다 "관리자 없음"을 읽고 첫 관리자를 넣으려 한다 [실험] |
| 막는 법 | 순서: 앱 단일 인스턴스 잠금 → Flyway → 첫 관리자. 앱 잠금은 `FlywayMigrationStrategy` 안에서, 풀 밖 전용 연결, autocommit, 두 int 키로 잡는다(Flyway의 bigint 키와 겹치지 않는다). `spring.flyway.postgresql.transactional-lock=false`. Flyway는 Boot가 관리하는 12.4를 쓴다. 첫 관리자는 마이그레이션 뒤 한 트랜잭션에서 "관리자가 없으면 만들기"로 하고, 실패해도 예외로 끝내지 않고 readiness DOWN을 남긴다. 컨테이너 안 CLI 명령(복구 명령, 백업·복원)도 앱 잠금을 잡는다. S0-AC-09는 "마이그레이션 중에는 상태 확인이 연결을 거부하고, compose `start_period`와 쿠버네티스 `startupProbe`로 기다린다"로 고친다 |
| 확인 테스트 | 같은 DB에 앱 둘 동시 기동: 하나만 뜨고 다른 하나는 Flyway 전에 멈춘다. 관리자 1명, 감사 행 1건(S0-AC-01·11). 먼저 뜬 쪽을 죽이면 뒤 쪽이 넘겨받는다. 실패 마이그레이션 픽스처 둘(트랜잭션 안 실패, `CONCURRENTLY` 실패): 앱이 뜨지 않고 실패 버전과 복구 절차를 로그에 남기며 관리자 행이 없다(S0-AC-08). `CONCURRENTLY` 픽스처가 30초 안에 끝난다. `pg_locks`에 앱 잠금이 두 int 키로 보인다 |
| 옮길 곳 | `architecture.md` 기동 순서, S0-AC-01·02·08·09·11, `docs/operate/` 상태 확인 설명 |
| 남은 것 | 앱 잠금을 못 잡을 때 다시 시도할 시간과 TCP keepalive 값. 호스트가 갑자기 꺼지면 DB가 세션 잠금을 늦게 푼다 |

## 4. 유니크 위반 예외가 이메일 원문을 로그에 남긴다

| 항목 | 내용 |
|---|---|
| 장면 | 운영자가 오류 로그를 바깥 지원 채널에 붙였는데, 그 안에 고객 이메일 원문이 있었다 |
| 원인 | pgjdbc는 기본값(`logServerErrorDetail=true`)에서 서버 오류의 DETAIL(`Key (email)=(kim@a.com) already exists.`)을 예외 메시지에 넣는다. Hibernate `SqlExceptionHelper`가 이 메시지를 WARN으로 남기고, Spring 예외 메시지에도 이어진다 [소스]. S0-AC-86의 로그 검사는 정상 흐름 E2E를 지나므로 409·500 경로를 거치지 않는다 |
| 막는 법 | JDBC URL에 `logServerErrorDetail=false`. 오류 처리기는 DB 예외를 제약 이름으로 `code`에 옮기고 `getMessage()`를 로그·응답에 쓰지 않는다. `SqlExceptionHelper` 로거는 WARN에서 끈다. 로그 출력 단계에 이메일 모양을 가리는 필터를 마지막 방어선으로 둔다(스택 추적 포함). 로그 규칙은 PII-2 하나로 맞췄다(`AGENTS.md`도 고침) |
| 확인 테스트 | S0-AC-86의 로그 검사에 중복 초대 409, 고객사 코드 중복 409, 일부러 낸 500 경로를 더한다. 원문, 퍼센트 인코딩(`%40`), JSON 이스케이프 세 형태를 모두 찾는다. 스택 추적 필드까지 본다 |
| 옮길 곳 | S0-AC-85·86, `architecture.md` 로그 절, `docs/operate/configuration.md`(JDBC URL 기본값) |

## 5. 모르는 Host 안내가 형식을 정하지 않으면 반사 XSS가 된다

| 항목 | 내용 |
|---|---|
| 장면 | 보안 점검에서 `Host: <svg onload=…>` 요청에 HTML로 해석되는 안내가 돌아왔다 |
| 원인 | S0-AC-14는 받은 Host 값을 이스케이프한다고만 적었고 응답 형식은 정하지 않았다. 템플릿 없이 문자열을 돌려주면 Spring은 이스케이프하지 않고, `Accept: text/html`과 협상돼 HTML로 나갈 수 있다 [소스·추론]. 받은 Host를 보여 주는 것은 부검 1의 목적(프록시가 Host를 바꿔 넘길 때 원인을 보이기)이라 빼지 않는다. 프로젝트 부검 1의 "감출 것이 없다"는 받은 Host를 생각하지 않은 문장이다 |
| 막는 법 | 응답 형식을 `text/plain; charset=utf-8`로 고정하고(`produces`), nosniff와 CSP를 이 응답에도 붙인다(S0-AC-16 "모든 응답") |
| 확인 테스트 | `Host: <svg onload=1>`과 따옴표·줄바꿈 섞인 값으로 요청: 404, `Content-Type: text/plain`, nosniff·CSP 있음, 본문에 받은 값이 글자 그대로 |
| 옮길 곳 | S0-AC-14, 프로젝트 `premortem.md` 1절 문장 |

## 6. 이름 패턴으로 만든 tenant_id 예외는 업무 테이블을 몰래 뺀다

| 항목 | 내용 |
|---|---|
| 장면 | 여러 팀을 열려고 보니 보내기 대기 테이블에 `tenant_id`가 없었다. 관문은 한 번도 실패한 적이 없었다 |
| 원인 | `scripts/ci/check-tenant-id.py`는 마이그레이션 글을 정규식으로 읽는다. 예외는 정확한 이름 넷(`flyway_schema_history`, `spring_session`, `spring_session_attributes`, `tenant`)이라 지금은 괜찮다. 그러나 `CREATE TABLE … (LIKE x)`, 파티션 자식, 함수 안에서 만든 테이블은 글 검사로 놓칠 수 있다 [추론]. "업무 테이블"의 정의는 문서에 없다 |
| 막는 법 | 정의: 예외 목록에 이름이 있는 테이블 말고는 모두 업무 테이블이다(감사, 보내기 대기, 정리 기록, 운영 경보 포함). 예외는 이름을 하나씩 적고 이유를 붙이며, 패턴을 쓰지 않는다. 글 검사에 더해, 마이그레이션을 다 돌린 실제 스키마의 `information_schema.columns`를 검사하는 테스트를 둔다 |
| 확인 테스트 | 부정 픽스처: `tenant_id` 없는 테이블, `DROP NOT NULL`, `(LIKE x)`로 만든 테이블을 넣으면 두 관문이 모두 실패한다 |
| 옮길 곳 | S0-AC-05, `architecture.md` 팀 절(정의와 예외 목록), D-18 문구 |

## 7. 토큰을 담은 응답 하나가 캐시나 액세스 로그에 남는다

| 항목 | 내용 |
|---|---|
| 장면 | 공용 PC에서 관리자가 초대 링크를 복사한 뒤, 다른 사람이 뒤로 가기로 그 링크를 다시 봤다. 프록시 액세스 로그에는 수락 주소의 토큰이 남아 있었다 |
| 원인 | Spring Security는 모든 응답에 `no-store`를 붙이지만, 컨트롤러가 `Cache-Control`을 직접 쓰면 쓰지 않는다 [소스]. S0-AC-38은 링크 복사 응답만 정했고, 초대 API가 링크를 바로 줄 때와 수락 화면은 정하지 않았다. 토큰이 경로나 쿼리에 있으면 프록시 로그에 남는다 |
| 막는 법 | 초대 토큰은 URL 조각(`#` 뒤)에만 둔다. 수락 API는 토큰을 본문으로 받는다. 토큰을 담거나 받는 모든 응답에 `Cache-Control: no-store`. 화면은 토큰을 읽은 뒤 주소창에서 지운다(`history.replaceState`) |
| 확인 테스트 | 토큰이 오가는 모든 엔드포인트(초대, 링크 복사, 수락)의 `Cache-Control` 단언. 모든 `/api` 응답에 `no-store`가 있는지 묶어서 단언. E2E 뒤 액세스 로그에 토큰이 없다 |
| 옮길 곳 | S0-AC-33·38, 수락 기준, TM-44, `screens.md` P-2 |

## 8. 업그레이드 틀은 v0.1에서 늘 통과해서 틀려 있어도 모른다

| 항목 | 내용 |
|---|---|
| 장면 | v0.2를 낼 때 업그레이드 틀을 처음 제대로 돌렸는데, 틀의 단언이 틀려 있어서 깨진 마이그레이션을 통과시켰다 |
| 원인 | v0.1에는 옛 버전이 없어 마이그레이션이 0건 돈다. 그래서 "마이그레이션이 돌았는지" 단언이 틀려도 통과한다. 견본 덤프를 지금 코드로 만들면 옛 버전의 데이터 모양을 담지 못한다 |
| 막는 법 | 틀의 자기 시험: v0.1에서 일부러 깨뜨린 V999를 넣으면 틀이 실패해야 한다. 견본 덤프는 고정한 이미지 다이제스트로 만들고 만든 이미지를 기록한다. 견본에는 경계값(255자 파일 이름, `purging` 첨부, `failed` 대기 행)을 넣는다. v0.1을 낼 때 v0.1 견본 덤프를 릴리스 산출물로 보관한다 |
| 확인 테스트 | V999 부정 픽스처로 틀이 실패한다. v0.1 이미지 → 같은 이미지로 복원·기동이 통과한다(S0-AC-95·96) |
| 옮길 곳 | S0-AC-95·96, `process.md` 릴리스 단계(견본 덤프 보관) |

## 9. 감사 행의 모양을 지금 고정하지 않으면 1번 묶음의 사슬 계산이 v0.1 행에서 끊긴다

| 항목 | 내용 |
|---|---|
| 장면 | 1번 묶음에서 해시 사슬을 켜자 무결성 확인이 v0.1 구간 전체를 "변조"로 보고했다. 변조는 없었고, 직렬화 방식이 바뀌어 있었다 |
| 원인 | AUDIT-6은 "정해진 JSON"의 해시를 쓰지만 그 직렬화 규칙(칸 순서, null, 시각 정밀도, 숫자 표기)이 정해져 있지 않다. v0.1 행은 사슬 없이 쌓이고, 1번 묶음이 이미 있는 행까지 계산한다(`acceptance.md` 2.3절) |
| 막는 법 | 0번 묶음에서 감사 행의 저장 모양과 정해진 JSON 규칙(키 정렬, null 칸 생략 여부, 시각은 UTC 마이크로초 ISO-8601, 사람은 `{accountId, name, email}`)을 정하고, 정답 값을 미리 박아 둔 테스트로 고정한다. 1번 묶음의 소급 계산과 실시간 계산은 같은 함수 하나를 쓴다. 소급 계산은 앱 잠금을 쥔 마이그레이션 안에서 하고, 사슬 머리 행을 같은 트랜잭션에서 만든다. `sha256(bytea)`는 PostgreSQL 11부터 내장이다 [소스]. v0.1 구간은 사슬이 생기기 전이라 그동안의 변조는 찾을 수 없다는 한계를 위협 모델에 적는다 |
| 확인 테스트 | 정해진 JSON 정답 값 테스트(입력 감사 행 → 바이트 열과 sha256). 1번 묶음: v0.1 견본 덤프로 업그레이드 틀을 돌린 뒤 무결성 확인이 통과한다 |
| 옮길 곳 | 새 수용 기준(감사 행 직렬화), S0-AC-83, AUDIT-6, TM-29 |

## 10. 첨부를 ID로만 찾으면 다른 고객사 문의나 내부 첨부가 샌다

| 항목 | 내용 |
|---|---|
| 장면 | B사 고객이 첨부 주소의 숫자를 바꿔 A사 문의의 첨부를 받았다. 다른 날에는 고객이 올리기 한도 오류를 보고 내부 첨부의 크기를 짐작했다 |
| 원인 | 첨부 API의 경로 모양이 정해져 있지 않다. 내려받기는 404로 정했지만 지우기, HEAD, 범위 요청, `pending` 재시도는 정하지 않았다. 문의당 50MB 한도가 내부 첨부까지 세면 400이 나는 지점으로 내부 첨부 크기가 드러난다. 저장소 계층을 서비스가 바로 부르면 S0-AC-84의 저장소 메서드 규칙을 건너뛴다 [추론] |
| 막는 법 | 첨부 경로는 문의 아래(`/api/{앱}/issues/{key}/attachments/{id}`)에 두고, 문의를 볼 수 있는지 거르는 조건과 내부 댓글 조건을 첨부 조회와 같은 쿼리에 붙인다. 없는 ID, 볼 수 없는 문의, 내부 첨부, `pending`·`purging`·`purged`는 모두 같은 404로 답한다(본문과 헤더까지 같게). 저장소 읽기는 범위가 걸린 첨부 서비스 한 곳에서만 부른다(ArchUnit). 문의당 50MB 한도는 공개 첨부만 세고, 내부 첨부는 팀 총량 한도에만 센다. 첨부 ID는 추측할 수 없게 짓되(ATT-7) 권한 검사를 대신하지 않는다 |
| 확인 테스트 | S0-AC-92 픽스처로 첨부 엔드포인트 전부(내려받기, 지우기, HEAD, 범위 요청)를 돌려 상태 코드와 본문이 "없는 ID"와 같은지 비교한다. 같은 고객사 동료가 남의 비공개 문의 첨부를 받으면 404. 내부 첨부가 섞인 문의에서 고객의 50MB 경계 테스트 |
| 옮길 곳 | S0-AC-57·59·60·84·92, ATT-2, `conventions.md`(첨부 경로) |

## 11. 이 부검으로 정한 것

사용자가 2026-10-08에 확인했다.

- S0-AC-09는 "마이그레이션 중에는 연결을 거부하고 startup probe로 기다린다"로 고친다(3절).
- 문의 ID는 앱에서 먼저 정하고 첨부 외래 키를 `DEFERRABLE`로 둔다(2절).
- 첨부 내용은 다른 테이블, 흘려 쓰기, 1MB 조각 읽기, 동시 수 상한 16과 503(1절).
- `spring.flyway.postgresql.transactional-lock=false`, Flyway는 Boot가 관리하는 버전(3절).
- `lock_timeout` 5초, 교착·잠금 시간 초과는 한 번 다시 시도(2절).
- 팀 총량 한도는 잠그지 않는다(2절).
- 로그의 이메일은 PII-2대로 가려서만 남기고 `AGENTS.md`를 맞췄다(4절).
- 초대 토큰은 URL 조각에만 둔다(7절).
- 문의당 50MB 한도는 공개 첨부만 센다(10절).
