# 5b 묶음 사전 부검

> 이 묶음이 나간 뒤 생길 수 있는 사고를 먼저 적고, 무엇이 막는지를 기준 ID로 잇는다. 막는 것이 없으면 기준을 더하거나 받아들인다고 적는다.
> `design/premortem.md` 6절의 다섯 이야기 가운데 5번 묶음 몫 넷을 여기서 받는다.
> 상태: **메인이 정함, 사용자 확인 전**(2026-10-14).

## 1. 컨테이너를 다시 만들었더니 첨부가 다 사라졌다

`disk`로 바꾸고 폴더를 다른 곳으로 정했는데 볼륨을 붙이지 않았다. 파일은 컨테이너 안에 쌓였고 이미지를 올리며 컨테이너가 새로 만들어졌다.

| 까닭이 될 것 | 막는 것 |
|---|---|
| 빈 폴더에 그대로 뜬다 | S5B-AC-21: 그 자리를 가리키는 행이 있는데 표지가 없으면 뜨지 않는다. 더 쓰지 않게는 막지만 **이미 잃은 파일은 돌아오지 않는다** |
| 처음부터 볼륨 없이 시작한 것을 모른다 | 릴리스 compose는 `/data/attachments`에 볼륨을 늘 붙인다 [소스: `compose.yml:59`]. 폴더를 바꾼 설치는 문서가 말한다(S5B-AC-51). 폴더가 볼륨인지 앱이 가리는 것은 넣지 않는다. **받아들인다** |
| 표지를 뜰 때마다 새로 써서 검사가 늘 지난다 | S5B-AC-20: 가리키는 행이 없을 때만 쓴다. 센 검증을 받는다(틀린 구현: 표지를 늘 새로 쓰기) |

## 2. 설정을 바꿨더니 옛 첨부가 열리지 않는다

`S3_BUCKET`을 바꿨다. 또는 `s3`에서 `disk`로 돌아오며 S3 키를 지웠다.

| 까닭이 될 것 | 막는 것 |
|---|---|
| 읽기가 늘 지금 저장소로 간다 | S5B-AC-10: 행에 적힌 곳에서 읽는다. 바꾸는 길 다섯을 테스트가 본다 |
| 지우기와 정리 작업이 지금 저장소에서 지운다(없으니 지운 것으로 치고 파일이 남는다) | S5B-AC-10, 12. 테스트가 옛 자리에서 파일이 사라진 것을 본다 |
| S3 키를 지워 옛 첨부가 하나씩 500이 된다 | S5B-AC-22: 뜨지 않고 빠진 키를 말한다 |
| 옛 버킷을 지웠다 | S5B-AC-21: 표지가 없어 뜨지 않는다 |
| 운영자가 "바꾸면 옮겨 주겠지"라고 여긴다 | S5B-AC-11, 51: 옮기지 않는다고 문서가 말한다 |

## 3. 복원했더니 DB가 가리키는 파일이 없다

DB 덤프보다 파일 백업이 먼저였다. 또는 파일 백업을 빠뜨렸다.

| 까닭이 될 것 | 막는 것 |
|---|---|
| 얼마나 없는지 알 길이 없다 | S5B-AC-40~43: `popdesk attachments check` |
| 없는 파일의 내려받기가 빈 파일로 내려온다 | S5B-AC-31: 500 |
| 차례를 모른다 | 문서: DB를 먼저 뜨고 파일을 뒤에 뜬다 [소스: `configuration.md:266`]. 복원 뒤 명령으로 확인하는 절차를 더한다(S5B-AC-51) |
| 다른 설치의 볼륨을 붙였다(표지는 있다) | 뜰 때는 못 가린다. 명령이 가린다. **받아들인다**(`acceptance.md` 5절 13) |

## 4. 주인 없는 파일이나 지우지 못한 파일이 쌓인다

| 까닭이 될 것 | 막는 것 |
|---|---|
| 저장소에 쓴 뒤 DB가 되돌려졌다 | 앞 묶음: `pending` 행을 먼저 커밋한다 [소스: `AttachmentService.writePending`]. 5b는 그 행의 자리에서 지운다(S5B-AC-12) |
| S3가 다 받고 답만 잃었다 | 같다. `pending` 행이 남아 1시간 뒤 지운다 |
| 정리 작업이 행을 끝낸 뒤에 늦은 쓰기가 닿았다 | 앞 묶음: 올리기가 ③에서 진 것을 알면 지운다 [소스: `upload`의 `stored == null`] |
| `.part` 파일이 남는다 | `design.md` 0절 10: 지우기는 두 이름을 다 지운다 |
| S3가 죽어 `purging` 행이 쌓인다(5번에서 넘긴 것) | S5B-AC-33: 다음 회에 다시. 첨부 정리는 지우지 못한 것이 있으면 그 회를 실패로 끝낸다 [소스: `AttachmentCleanup.run`]. 실패한 회는 기록되지 않아 시스템 상태의 "마지막으로 돈 시각"이 멈추고 로그에 WARN이 남는다(`design.md` 6절 2). 하루 넘게 돌지 않을 때의 경보는 7번 묶음이다. **그때까지는 받아들인다** |
| S3가 죽은 동안 정리 스레드가 `purging` 행마다 시간 제한까지 기다려 세션 정리와 경보 검토가 밀린다 | S5B-AC-35: 닿지 못하면 그 회를 멈춘다 |
| 저장소를 훑어 주인 없는 파일을 지우는 작업을 넣는다 | 넣지 않는다(ATT-11). 복원 직후에 산 파일을 지울 수 있다 |

## 5. 권한 검사를 건너뛰어 파일이 읽혔다

| 까닭이 될 것 | 막는 것 |
|---|---|
| 내려받기가 저장소 주소로 돌려보낸다. 그 주소가 채팅으로 샌다 | S5B-AC-06, TM-54 |
| 버킷이 공개다 | 설치하는 쪽의 일이다. 문서가 비공개로 두라고 말한다(S5B-AC-51). 객체 키는 추측하기 어려운 ID지만 권한 검사가 아니다. **받아들인다** |
| 올린 이름 `../../etc/x`가 경로가 된다 | S5B-AC-03, TM-20. 센 검증을 받는다 |
| 서버의 다른 사용자가 폴더를 읽는다 | 컨테이너에는 앱의 사용자뿐이다 [소스: `Dockerfile`]. 호스트에서 볼륨을 읽는 것은 DB 볼륨과 같은 처지다. **받아들인다** |

## 6. 비밀 키가 새었다

| 까닭이 될 것 | 막는 것 |
|---|---|
| 뜨지 않을 때 설정을 통째로 적는다 | S5B-AC-25: 키의 이름만 적는다 |
| SDK 예외의 글을 로그에 쓴다 | `design.md` 2절: 클래스 이름과 S3의 오류 코드만. 테스트가 뜨지 않는 경우의 로그도 본다 |
| SDK의 요청 로그가 켜진다 | 기본은 꺼져 있다 [추론]. 테스트가 로그에서 키의 값을 원문과 퍼센트 인코딩으로 찾는다(S0-AC-86의 방법) |
| `S3_ENDPOINT`가 `http`라 키로 서명한 요청과 파일이 평문으로 간다 | S5B-AC-26: 받되 경고한다(D-51). 같은 compose 안에 둔 S3 호환 서버가 흔해 막지 않는다 |

## 7. 저장소 때문에 헬프데스크가 멈췄다

| 까닭이 될 것 | 막는 것 |
|---|---|
| S3가 답하지 않아 올리기 16자리가 다 잡혔다 | S5B-AC-34: 시간 제한. 그 뒤 요청은 지금처럼 503 `SERVER_BUSY` |
| 디스크가 찼다 | S5B-AC-30: 500. 팀 총량(ATT-3)과 80% 경보, 볼륨의 남은 공간 지표가 이미 있다 [소스: `OpsMetrics`] |
| S3가 잠깐 죽은 때 앱을 다시 띄웠더니 뜨지 않는다 | S5B-AC-24. **받아들인다**: compose가 다시 띄우고 S3가 돌아오면 뜬다. 그사이 글만 쓰는 일도 못 한다. 대안(떠서 올리기만 막기)은 "돌아왔는가"를 보는 상태가 하나 는다 |
| 묶어 붙인 폴더의 주인이 root다 | S5B-AC-24: 뜨지 않고 사용자 번호를 말한다 |
| 뜰 때의 검사가 행이 많아 오래 걸린다 | 묶어 세는 쿼리 하나와 자리마다 요청 한둘이다. 파일마다 보지 않는다(그것은 명령이 한다) |

## 8. 앞 묶음의 테스트가 깨졌다

| 까닭이 될 것 | 막는 것 |
|---|---|
| "`disk`와 `s3`는 뜨지 않는다"를 고정한 테스트 | 없다(조사: 레포와 숨긴 저장소에서 0건, `design.md` 6절 6) |
| 저장소 인터페이스가 바뀌어 `ScopedReadRulesTest`와 `AttachmentArchitectureTest`의 규칙이 어긋난다 | 테스트 탭이 두 파일을 먼저 읽고 알린다. 규칙이 이름에 묶여 있으면 그 이름을 지키게 구현 지시서에 적는다 |
| 올리기의 세 걸음의 차례를 문장 로그로 보는 테스트(`AttachmentStatementLogTest`) | `db` 컨텍스트에서 그대로 돈다. `db`의 문장을 바꾸지 않는다(읽기에 "없으면 예외"를 넣을 때 조심한다) |
| 컨텍스트가 둘 늘어 서버 잡의 힙이 모자란다 | CI는 힙 1024m이다 [소스: 운영 노트]. `local-ci.sh`는 다섯 묶음으로 나눠 돈다. 새 클래스는 컨텍스트 둘에 모은다(`acceptance.md` 4절) |
| S3 대역 컨테이너가 이 PC의 메모리를 넘긴다 | 서버 테스트는 `heavy.sh`로 하나씩 돈다. versitygw 하나가 더 뜨고 20MiB를 쓴다 [잼] |
| 새 의존성이 있는 라이브러리의 판을 바꾼다 | SDK는 `slf4j-api`와 `reactive-streams`만 함께 쓴다 [잼: jar 목록]. C-4에서 `dependency:tree`로 판이 그대로인지 본다 |

## 9. 받아들이는 것

- 저장소 사이에 파일을 옮기는 도구가 없다.
- 서버 쪽 암호화와 버킷 정책은 설치하는 쪽의 일이다(위협 모델 83줄).
- 운영자가 표지를 손으로 만들면 뜰 때의 검사를 지난다. 파일을 잃은 것을 알고 띄우는 길로 문서에 적는다.
- S3의 내려받기는 10MB 파일 하나에 요청이 열 번까지 간다.
- 다른 popdesk 볼륨을 잘못 붙인 것은 명령을 돌려야 안다.
