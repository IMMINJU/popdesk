## 1. 저장소를 고르는 곳

- 지금 인터페이스는 ID만 받아 읽고 지운다 [소스: `AttachmentStorage.read`, `delete`]. 저장소가 하나라는 전제다. 5b에서는 "저장소 종류와 자리"마다 저장소 하나가 있고, 읽기와 지우기와 있는지 보기는 행에 적힌 종류와 자리로 저장소를 골라서 한다. 쓰기만 지금 저장소로 간다.
- 고르는 곳은 하나다(이름은 구현이 정한다). 뜰 때 "지금 저장소"와 "행이 가리키는 저장소들"을 만들어 둔다. 뜬 뒤에 새로 생기는 자리는 지금 저장소뿐이라, 뜬 뒤에 모르는 자리를 만날 일은 없다.
- 읽기와 지우기를 부르는 곳 [소스]: `AttachmentService`의 내려받기 둘(`download`, `downloadTemporaryImage`), 지우기 넷(`upload`와 `uploadImage`의 늦은 지우기, `discardEnded`, `removeFiles`), `AttachmentCleanup.run`, `TemporaryImageCleanup.delete`. 여덟 곳이 행의 `storage`와 `storage_location`을 같이 넘겨야 한다. `AttachmentRow`와 정리 작업의 조회에 두 칸이 는다.
- 저장소 클래스는 Spring 없이 만들 수 있어야 한다. 명령은 Spring 없는 JVM에서 돈다 [소스: `deploy/image/popdesk`, `PopdeskCommand`]. 설정 읽기(`_FILE` 키 포함)는 앱과 명령이 같은 코드를 쓴다 [추론: `SecretFiles`가 Spring의 `Environment`에 묶여 있으면 명령 쪽에 얇은 길이 하나 든다. 구현 탭이 본다].
- 내용을 읽는 것은 `AttachmentService`뿐이라는 규칙(S5B-AC-60)은 그대로다. 정리 작업과 명령이 쓰는 문에는 읽기가 없게 한다 [추론: `ScopedReadRulesTest`가 메서드 이름으로 보는지 타입으로 보는지는 테스트 탭이 읽고 알린다].

## 2. 뜰 때의 검사

마이그레이션이 끝난 뒤, 요청을 받기 전에 이 차례로 한다.

1. 설정의 꼴(S5B-AC-23). 빠진 키를 한 번에 모두 적는다.
2. `purged`가 아닌 행을 저장소와 자리로 묶어 센다. 설정도 행도 `db`뿐이면 여기서 끝난다(S5B-AC-27).
3. 행이 가리키는 `s3` 자리가 있는데 S3 키가 없으면 끝낸다(S5B-AC-22).
4. 행이 가리키는 자리마다 표지가 있는지 본다. 없으면 종류, 자리, 행의 수를 적고 끝낸다(S5B-AC-21).
5. 지금 저장소의 자리에 표지가 없으면(4를 지났으니 가리키는 행이 없다) 표지를 남긴다(S5B-AC-20).
6. 지금 저장소에 작은 것을 하나 쓰고 지워 본다(S5B-AC-24).

- 3~6은 자리마다 10초 안에 끝나게 한다.
- 닿지 못한 것("답이 없다")과 없는 것("표지가 없다고 답했다")은 로그의 글을 다르게 쓴다. 둘 다 뜨지 않는다.
- 예외의 `getMessage()`는 로그에 쓰지 않는다 [소스: `architecture.md` "로그"]. SDK의 예외 글에는 주소와 버킷이, 서명 오류에는 요청 머리글이 들 수 있다. 예외의 클래스 이름과 S3의 오류 코드(`NoSuchBucket`, `AccessDenied`, `InvalidAccessKeyId`, `SignatureDoesNotMatch`)만 적는다.
- 운영자가 파일을 잃은 것을 알고도 띄우려면 표지를 손으로 만든다(`touch`). 문서에 그 길과 "그 뒤 그 파일들의 내려받기는 500"을 적는다. 따로 키나 명령을 두지 않는다.

## 3. 탈 났을 때의 답

- 쓰기 실패(S5B-AC-30): 지금도 ②에서 던진 예외는 500이 되고 `pending` 행이 남는다 [소스: `AttachmentService.writePending`]. `disk`는 `.part`를, `s3`는 아무것도 남기지 않거나 다 쓴 객체를 남긴다(답만 잃은 경우). 어느 쪽이든 1시간 뒤 첨부 정리 작업이 행의 자리에서 지운다.
- 없는 파일(S5B-AC-31): `db` 구현은 지금 내용 행이 없으면 빈 바이트를 준다 [소스: `DatabaseAttachmentStorage.read`]. 그러면 `Content-Length`만큼 오지 않는 응답이 된다 [추론: 6절 3에서 본다]. 세 저장소 모두 "없다"를 예외로 알리고, 내려받기는 응답을 쓰기 전에 첫 조각을 읽는다.
- 올리기 자리(S5B-AC-34): 올리기와 내려받기는 16개씩이다 [소스: `conventions.md` 168줄]. S3가 답하지 않으면 자리 하나가 길게는 60초 잡힌다.
- 정리 작업(S5B-AC-35): 두 정리 작업은 지우다가 저장소에 닿지 못하면(연결 실패, 시간 초과) 그 회를 거기서 멈춘다. 객체 하나의 오류(권한, 없는 버킷의 답)는 지금처럼 세고 다음 행으로 간다. 첨부 정리는 멈춘 회를 실패로 끝내 1분 뒤 다시 돈다 [소스: `Housekeeping.RETRY_FAILED_JOB`]. 한 회가 길어도 연결 시간 제한 한 번이다.

## 4. 명령

- `PopdeskCommand`의 갈래 하나다 [소스: `backup`, `restore`, `admin`]. `stored` 행을 ID 차례로 훑어 자리마다 있는지와 크기를 본다: `db`는 `octet_length(data)`, `disk`는 파일 크기, `s3`는 `HeadObject`.
- 행이 많아도 메모리에 다 올리지 않는다(쪽으로 나눠 읽는다). S3는 행마다 요청 하나다. 1만 개면 몇 분이 걸린다 [추론]. 문서에 적는다.
- 끝 코드와 출력의 꼴은 계약 단계에서 다른 명령의 것에 맞춘다.

## 5. 문서와 배포

- `configuration.md`: `POPDESK_STORAGE` 줄, 설정 표 아래의 "옮기지 않는다" 문단, "Attachments" 절, "Commands" 절(S5B-AC-51). `upgrade.md`의 "다음 판" 절에 "새 키 없음, 마이그레이션 없음, `disk`와 `s3`를 쓸 수 있다"를 적는다.
- `compose.yml`: 앱의 환경에 S3 키 여섯(S5B-AC-50). 지금은 `POPDESK_STORAGE`와 `POPDESK_STORAGE_DIR`만 넘긴다 [소스: `compose.yml:38~39`].
- `architecture.md`(spec) 84줄과 백업 절은 그대로 맞다. 표지와 뜰 때의 검사를 한 줄씩 더한다(구현이 합쳐질 때 메인이 더한다).
- 위협 모델: TM-54를 더했다(버킷이나 폴더에 직접 닿아 권한 검사를 건너뛴다). 68~83줄의 "앱 ↔ S3는 https"에 "`http` 주소는 경고와 함께 받는다"를 맞춘다(메인이 구현 뒤에).
- 견본 생성기(`make-sample.py`)는 그대로다. 새 표가 없다. 0.5.0 견본은 `db` 저장소로 만든다(업그레이드 테스트는 덤프만 올린다 [소스: `deploy/upgrade/README.md`를 가리키는 `process.md` D절]).

## 7. 일하는 차례

1. 계약 앞에 볼 것 1~4(메인).
2. 계약(C-4): API와 화면이 그대로라 작다. 메인이 `pom.xml`에 의존성을 넣고(빌드 파일은 탭이 못 고친다), 명령의 이름과 끝 코드와 출력의 꼴, `configuration.md`의 새 글을 정한다. 이미지를 빌드해 6절 5를 잰다.
3. 테스트(C-5): 서버 탭 하나(`disk` 컨텍스트, `s3` 컨텍스트, 뜰 때의 검사, 설정 바꾸기, 명령, compose 파일의 키). 숨긴 E2E 하나(릴리스 compose로 띄워 `db`→`disk`→`s3`로 바꿔 가며 쓰고, 볼륨을 떼고 다시 띄워 뜨지 않는 것을 본다).
4. 실패 확인과 잠금(C-6), 점검(C-7). 틀린 구현의 목록: 읽기를 늘 지금 저장소에서 하기, 지우기를 늘 지금 저장소에서 하기, 표지가 없어도 뜨기, 표지를 늘 새로 쓰기, 올린 이름으로 경로 짓기, 없는 파일에 빈 200, 서명된 주소로 돌려보내기, 예외의 글을 로그에 쓰기.
5. 구현(C-9): 서버 탭 하나(고르는 곳과 `db`의 새 인터페이스 → `disk` → 뜰 때의 검사 → `s3` → 명령 → compose와 문서). 웹 탭은 없다.
6. 검증(C-10): `local-ci.sh`, 숨긴 E2E, 변이 테스트(순수 계산 셋), 브라우저로 `disk`와 `s3` 설치에서 첨부와 본문 이미지를 한 번씩. `verify.md`에 "CI 없이 이 PC에서 본 것"과 단계마다 걸린 시간을 적는다.

## 8. 계약 (C-4, 2026-10-14 메인이 정함)

API 계약 파일 둘과 화면은 그대로다. 이 묶음의 계약은 의존성, 명령, 설정 키의 동작이다.

### 의존성

`server/pom.xml`에 `software.amazon.awssdk:s3`와 `url-connection-client` 2.55.15를 넣었다. 런타임 의존성이 144개에서 175개가 됐고(31개: SDK 30개와 `reactive-streams`), 있던 144개의 판은 하나도 바뀌지 않았다 [잼: `dependency:list`를 넣기 전과 뒤로 견줌].

### 명령 `popdesk attachments check`

- 인자가 없다. 다른 인자가 붙으면 다른 명령처럼 쓰는 법을 적고 1로 끝난다 [소스: `PopdeskCommand`의 `Failed`는 표준 오류에 `popdesk: …`를 적고 끝 코드가 1이다].
- 표준 출력의 줄은 셋 가운데 하나다. 차례는 파일 줄이 먼저(첨부 ID 차례), 요약 줄이 끝이다.

| 줄 | 꼴 | 뜻 |
|---|---|---|
| 파일 줄 | `missing {저장소} {첨부 ID}` | `stored`인 행의 파일이 행에 적힌 곳에 없다 |
| 파일 줄 | `wrong-size {저장소} {첨부 ID}` | 있지만 크기가 행과 다르다 |
| 요약 줄 | `{저장소} {자리}: checked {n}, missing {n}, wrong size {n}` | `stored`인 행이 있는 자리마다 한 줄. 저장소 이름, 자리 차례 |

- `stored`인 행이 하나도 없으면 `no stored attachments` 한 줄이고 0으로 끝난다.
- 끝 코드: 0(모두 맞다), 2(끝까지 보았고 없거나 다른 것이 있다), 1(DB나 저장소에 닿지 못했다, 설정이 빠졌다, 쓰는 법이 틀렸다). 1일 때 표준 오류에 `popdesk: `로 시작하는 까닭 한 줄이 있다.
- 감사 로그를 남기지 않는다. `configuration.md`의 "Each one is recorded in the audit log" 문장을 "데이터를 바꾸거나 꺼내는 명령은"으로 고친다.
- 쓰는 법 글(`USAGE`)에 한 줄이 는다.

### 뜰 때의 로그

테스트는 글자를 통째로 고정하지 않는다. 뜨지 않을 때의 로그에 이것이 있는지만 본다: 걸린 키의 이름(S5B-AC-22, 23), 저장소 종류와 자리와 행의 수(S5B-AC-21), 사용자 번호 `10001`(S5B-AC-24의 `disk`). 새 저장소에 표지를 남길 때(S5B-AC-20)는 INFO 한 줄에 저장소 종류와 자리가 있다. `http` 주소의 경고(S5B-AC-26)는 WARN 한 줄에 `S3_ENDPOINT`가 있다.

### 표지와 파일의 자리

테스트가 폴더와 버킷을 들여다볼 때 쓰는 이름이다(0절 2~4): 표지 `.popdesk-storage`, `disk`의 파일 `{폴더}/{ID 앞 두 글자}/{ID}`, `s3`의 키 `popdesk/{ID}`와 `popdesk/.popdesk-storage`, 행의 자리 `{버킷}/popdesk`.
