# 1b 묶음의 규칙 (spec에서 옮긴 것)

> `design/spec/features.md` 14절을 그대로 옮겼다. 수용 기준(`acceptance.md`)의 괄호 안 규칙 ID가 가리키는 글이다.
> AUDIT-1·2의 남기기는 첫 묶음과 1a에서 했다. 익명화에 따른 재계산(AUDIT-6 끝부분, AUDIT-7의 구간 나누기, PII-5)은 10번 묶음으로 미뤘다(2026-10-11 사람이 정함).

| ID | 규칙 |
|---|---|
| AUDIT-1 | 남기는 일: 초대·다시 보내기·취소(고객사 담당자가 한 것 포함), 정지·해제, 역할·이름 변경, 비밀번호 초기화, 익명화, 내보내기(계정·고객사·감사 로그), 고객사 만들기·고치기·상태 변경, 소속·배정 더하고 빼기, 고객사 담당자 지정·해제, SLA 정책·업무 시간 변경, 브랜딩 변경, 라벨 만들기·고치기·지우기, 문의 삭제·복구·영구 삭제(사람이 한 것), 비밀번호 찾기로 바꾼 비밀번호(요청은 남기지 않는다), 관리자 복구 명령(ACCT-6), 초대 링크 복사(INVITE-6), 보내기 `failed` 다시 보내기와 시험 메일(OPS-3), 담당 비우기(ACCT-7). 로그인 성공·실패와 잠금도 남긴다 |
| AUDIT-2 | 항목: 일의 종류, 한 사람(시스템은 0), 대상(종류와 ID), 바뀐 값(전과 뒤, 비밀번호·토큰은 넣지 않는다), 시각. 바꾼 내용과 같은 트랜잭션에 저장한다(로그인 실패는 따로) |
| AUDIT-3 | 관리자만 본다. 최신순이고 일의 종류·한 사람·대상·기간으로 거른다. 쪽 나누기는 COM-4 |
| AUDIT-4 | 고치거나 지우는 API는 없다. `POPDESK_AUDIT_RETENTION`(기본 365일)이 지난 항목은 시스템이 하루 한 번 지운다. 값이 `P30D`보다 짧으면 앱이 뜨지 않고 이유를 남긴다. 지우기와 사슬 시작점 기록(AUDIT-6)은 한 트랜잭션이다(지운 뒤 시작점을 남기기 전에 죽어 무결성 확인이 늘 실패하지 않게) |
| AUDIT-5 | 문의 이력(HIST)과는 따로다. 문의의 상태·담당자 같은 업무 변경은 이력에만 남는다 |
| AUDIT-6 | 변조 탐지: 항목마다 `hash = SHA-256(앞 항목의 hash ‖ 이 항목의 정해진 JSON)`을 저장한다. 항목은 한 번에 하나씩 순서대로 붙인다(사슬이 갈라지지 않게): 사슬 머리 행(마지막 hash를 든 행 하나)을 잠그고 붙인 뒤 머리를 고친다. `prev_hash`에 유니크 제약을 둔다(그래도 둘이 같은 앞 hash를 읽으면 하나는 실패한다). 정해진 JSON 규칙(RFC 8785 표기, `null` 칸을 빼지 않음, UTC 마이크로초 시각, 사람은 `{accountId, name, email}`)은 첫 묶음에서 정답 값 테스트로 고정했다(S0-AC-100). 이미 있는 행의 소급 계산과 새 행의 계산은 같은 함수 하나를 쓰고, 소급 계산은 앱 잠금을 쥔 마이그레이션 안에서 사슬 머리 행과 같은 트랜잭션으로 한다. 보관 기간이 지나 앞 항목을 지울 때는 지운 마지막 항목의 hash를 사슬의 시작점으로 남긴다. 익명화(PII-5)로 값을 바꿀 때는 사슬 머리를 잠근 채 한 트랜잭션으로 그 뒤 사슬을 다시 계산하고, 다시 계산했다는 항목을 남긴다(중간에 죽으면 통째로 되돌아간다). 바깥 사본(AUDIT-9)에도 재계산 이벤트(바뀐 구간과 새 hash)를 보낸다 |
| AUDIT-7 | 관리자는 "무결성 확인"을 돌려 사슬이 처음 끊긴 항목을 본다. 확인은 재계산 항목을 경계로 구간을 나눠 본다(재계산 앞의 옛 hash와 맞지 않는 것을 변조로 보지 않게). 이것은 고친 흔적을 찾아낼 뿐 막지는 못한다: DB를 고칠 수 있는 사람은 사슬 전체를 다시 쓸 수 있다. 그래서 AUDIT-9의 바깥 사본과 함께 쓰라고 문서에 적는다 |
| AUDIT-8 | 내보내기: 관리자가 거른 결과(AUDIT-3)를 CSV나 JSON Lines로 받는다. hash 칸도 함께 나가서 밖에서도 사슬을 확인할 수 있다. 내보내기 자체를 감사 로그에 남긴다 |
| AUDIT-9 | 바깥 사본(선택): `AUDIT_FORWARD_URL`이 있으면 항목마다 JSON 한 건을 그 주소로 POST한다. 보내기 대기 테이블로 나가므로 최소 한 번 보내기다(중복이 올 수 있어 항목 ID를 함께 보낸다). 받는 쪽은 SIEM이나 로그 수집기다 |
