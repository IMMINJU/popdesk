## 1. 데이터 (마이그레이션 V6, V7)

| 바뀌는 것 | 내용 | 까닭 |
|---|---|---|
| `audit_log` | 칸 셋을 더한다: `seq bigint`(유니크), `prev_hash text`(유니크), `hash text`. V6에서는 null을 허용하고 V7이 채운 뒤 `NOT NULL`을 건다 | `prev_hash` 유니크는 사슬이 갈라지는 것의 마지막 방어선이다(AUDIT-6). `NOT NULL`이라 해시 없이 넣는 코드는 INSERT에서 실패한다(부검 3) |
| 새 테이블 `audit_chain` | 행 하나. 머리(`head_seq`, `head_hash`)와 시작점(`anchor_seq`, `anchor_hash`), `tenant_id` | 붙일 때마다 이 행을 잠근다. 시작점은 보관 기간으로 지운 마지막 항목의 번호와 해시다. 아무것도 지우지 않았으면 0과 `0` 64개다 |
| `audit_log` 색인 | 종류, 한 사람(`actor->>'accountId'`), 대상(`target`의 종류와 ID)에 하나씩. 지금 있는 시각 색인은 둔다 | 필터(S1B-AC-03~06). 10만 건으로 실행 계획을 보고 필요 없는 것은 뺀다 |
| `outbox` | `channel` 제약에 `AUDIT_FORWARD`를 더하고, `audit_id bigint` 칸을 더한다 | 바깥 사본 행은 감사 항목 ID만 든다. 본문은 보낼 때 읽는다(메일이 주소를 보낼 때 읽는 것과 같다) [소스: V3] |
| `delivery_status` | `channel` 제약에 `AUDIT_FORWARD`를 더한다 | 시스템 상태(S1B-AC-33) |
| 정리 작업 | `audit-retention` 하나를 더한다. 기록은 `cleanup_run` | S1B-AC-19 |

- V6은 SQL(칸과 테이블 더하기), V7은 Java 마이그레이션(소급 계산, `NOT NULL`, 유니크)이다. V7은 `db/migration` 패키지에 두고 정적 함수만 쓴다(Flyway가 직접 만드는 클래스라 스프링 빈을 받지 못한다). 한 트랜잭션이라 중간에 죽으면 통째로 되돌아가고, 실패 행이 남지 않아 다음에 처음부터 다시 한다(S1B-AC-13, 실험 4).
- V7은 커서로 읽고(2,000건씩) 묶음마다 `update … from unnest(…)` 한 문장으로 쓴다. 이 PC에서 100만 건에 26초, 10만 건에 2.6초, 힙 최대 152MB였다(`-Xmx384m`, 실험 2). 행마다 UPDATE하면 51초다.
- 한 트랜잭션으로 둔다(메인이 정함). 소급 계산은 0.1.0이나 1a에서 올라올 때 한 번만 돌고, 0.1.0은 이미지를 밖에 내지 않아 감사 행이 많은 설치가 없다. 묶음마다 커밋하면 `NOT NULL`과 유니크를 나중에 걸어야 하고 반쯤 채운 상태를 다뤄야 한다. `upgrade.md`에는 잰 값과 "시작 확인 시간을 늘릴 것"을 적는다.
- 표가 하나 늘어나므로 `deploy/upgrade/make-sample.py`가 `audit_chain`을 채우게 한다(S1B-AC-41).
- 옛 이미지는 이 스키마에서 뜨지 않는다(D-46). 릴리스 노트에 되돌릴 수 없는 마이그레이션으로 표시한다(D-24).

## 2. 해시 사슬

### 계산은 한 곳에서 한다

- "행 → 정해진 JSON → 해시"는 함수 하나다. 새 행 붙이기, 소급 계산, 무결성 확인, 내보내기가 모두 이 함수를 지난다(AUDIT-6).
- 이 함수의 입력은 DB에 든 값을 읽은 것이다. 새 행은 넣을 JSON 글자를 DB에 한 번 다녀오게 해서(`select cast(? as jsonb)::text`, 붙일 항목들을 한 문장으로) 그 글자로 계산한다. 넣을 글자를 앱에서 다시 읽는 것만으로는 모자랐다(실험 1): `jsonb`는 `1e19` 이상의 소수를 긴 정수로 바꿔 적고, 짝 없는 대리 글자를 `?`로 저장하고, `\u0000`은 받지 않는다.
- 감사 값의 숫자는 정수만 받는다(`Integer`, `Long`, `Short`). `Double`, `Float`, `BigDecimal`, `BigInteger`가 오면 `record`가 예외를 낸다. 지금 남기는 26곳의 값은 `String`, `Long`, `Boolean`, `List<String>`, `Instant`, `{from, to}`, `null`뿐이라 걸리는 곳이 없다(실험 1). `conventions.md`의 해시 규칙에 "값에 소수가 없다"를 적는다.
- DB에서 읽은 숫자는 `Integer`로 올 수 있다. 계정 ID는 `Number.longValue()`로 받는다.
- `CanonicalAuditJson`은 고치지 않는다 [소스: 클래스 머리말]. 정답 값 테스트(S0-AC-100)가 잠겨 있다.
- 종류 이름은 한 곳(enum)에 모은다. 지금은 서비스마다 글자로 흩어져 있다 [소스]. API의 종류 필터가 이 목록으로 400을 낸다(S1B-AC-03).

### 붙이기

1. `AuditLog.record`는 항목을 트랜잭션에 묶인 목록에 넣기만 한다. 시각은 이때 정한다.
2. 커밋 직전(`TransactionSynchronization.beforeCommit`)에 `audit_chain` 행을 `FOR NO KEY UPDATE`로 잠근다.
3. 목록의 항목마다 번호와 해시를 계산해 INSERT하고, 바깥 사본이 켜져 있으면 보내기 대기 행도 넣는다.
4. `audit_chain`의 머리를 고친다. 이 뒤로는 아무것도 잠그지 않는다.

- 트랜잭션이 되돌아가면 목록도 버려진다. 커밋이 실패하면 머리도 같이 되돌아간다(S1B-AC-11).
- 로그인 실패는 지금처럼 따로 여는 트랜잭션에서 남는다 [소스: `SignInService`]. 같은 길로 붙는다.
- 컨테이너 안 명령(비밀번호 복구, 백업, 복원)은 스프링 없이 JDBC 연결로 감사 행을 직접 넣는다 [소스: `CommandDatabase.auditBySystem`]. 붙이는 코드를 "연결 하나를 받아 잠그고 붙이는" 한 곳에 두고 앱과 명령이 같이 쓴다. 복원 명령은 옛 덤프(해시 칸이 없는 스키마)를 복원한 직후에도 행을 넣으므로, 칸이 없으면 예전처럼 넣고 V7이 뒤에 채운다. 명령이 남긴 항목도 사본이 켜져 있으면(명령은 앱과 같은 컨테이너의 환경 변수를 읽는다) 보내기 대기에 넣고, 앱의 보내기 루프가 보낸다. 새 스키마의 덤프를 복원한 뒤 남기는 `DATABASE_RESTORED`는 복원된 사슬의 머리에 잇는다.
- `architecture.md` 잠금 순서 5번을 "감사 사슬 머리 행을 잠그고, 감사 행과 바깥 사본 대기 행을 넣고, 머리를 고친다"로 고친다. 보내기 대기에는 외래 키가 없어 다른 행을 잠그지 않는다 [소스: V3 주석].

### 무결성 확인

- 읽기 전용 `REPEATABLE READ` 트랜잭션 하나에서 시작점부터 `seq` 순서로 흘려 읽는다. 도는 동안 새 항목이 붙거나 보관 작업이 돌아도 같은 시점의 사슬을 본다. 사슬을 잠그지 않는다.
- 보는 것: 번호가 비지 않았는지, 앞 해시가 앞 항목의 해시인지, 해시가 다시 계산한 값과 같은지, 마지막 항목의 해시가 머리와 같은지.
- 한 번에 하나만 도는 것은 앱 안의 잠금 하나로 한다(인스턴스가 하나다, D-23). 요청이 끊겨도 계산은 끝까지 돌고 그동안 409다.
- 답: 맞음과 확인한 건수, 아니면 처음 끊긴 항목의 ID·시각·종류. 맨 끝이 머리와 다르면 따로 구별해 준다(S1B-AC-42).

### 보관 기간

- 하루 한 번, 한 트랜잭션에서: 머리 행을 잠근다 → 시작점 다음부터 `seq` 순서로 보며 기간이 지난 항목이 이어지는 데까지 지운다 → 지운 마지막 항목의 번호와 해시를 시작점에 적는다(S1B-AC-21).
- `POPDESK_AUDIT_RETENTION`은 뜰 때 다른 설정 키와 같은 곳에서 검사한다(S1B-AC-20).
- 보내기 대기에 남은 바깥 사본 행이 가리키는 항목이 지워졌으면, 보낼 때 그 행을 버린다. 보관 기간은 30일 이상이고 대기 행은 8일 안에 없어지므로 실제로는 생기지 않는다.

## 3. 보기, 내보내기, 바깥 사본

- 보기의 순서는 시각 내림차순, 같으면 `seq` 내림차순이다. 쪽 나누기는 COM-4(`page`, `size`).
- 응답의 바뀐 값은 저장된 꼴 그대로다: `{칸: {from, to}}` [소스: `AccountService.change`]. 해시에 들어간 값이라 이름을 바꿔 줄 수 없다(내보낸 파일로 다시 계산해야 한다). 화면이 `from`과 `to`가 있는 값을 "전 → 뒤"로 보인다. 값이 바뀌는 일을 새로 남길 때는 이 꼴을 쓴다고 `conventions.md`에 적는다. 1a에서 넘어온 "전·뒤 방향을 테스트가 보지 않는다"는 이 묶음의 테스트가 종류마다 본다(S1B-AC-07).
- 내보내기: ① 짧은 트랜잭션에서 지금의 머리 번호와 조건에 맞는 건수를 읽고 `AUDIT_EXPORTED`를 남긴다 ② 머리 번호까지만 `seq` 오름차순으로 커서로 흘려 보낸다. 그래서 파일에 자기 자신의 내보내기 항목은 없다.
- JSON Lines 한 줄: `id`, `seq`, `prevHash`, `hash`, `action`, `actor`, `target`, `changes`, `occurredAt`. CSV는 첫 줄이 머리글이고 칸 이름이 같다. `actor`는 세 칸(`actorAccountId`, `actorName`, `actorEmail`)으로 펴고 `target`·`changes`는 JSON 글자 한 칸이다. CSV는 사람이 읽는 용도이고 사슬 확인은 JSON Lines로 한다. CSV 파일 앞에는 BOM을 넣는다(엑셀에서 한글 이름이 깨지지 않게. C-9에서 정함).
- 동시 수 2는 프로필 사진과 같은 꼴이다(`Semaphore`, 503과 `Retry-After`) [소스: `PhotoService`]. 응답은 `Cache-Control: no-store`. 자리를 먼저 잡고 그 뒤에 `AUDIT_EXPORTED`를 남긴다. 거절된 내보내기는 항목을 남기지 않는다(C-5의 `AuditExportLimitTest`가 이 순서에 기댄다).
- CSV의 수식 막기에서 탭과 줄바꿈으로 시작하는 값은 API로 넣을 길이 없다(이름 입력이 앞뒤 공백을 지운다). 이 둘은 구현 쪽 단위 테스트가 본다.
- 화면은 받기 전에 같은 주소를 `HEAD`로 먼저 부른다(첨부와 같다) [소스: `attachments.ts`]. `HEAD`는 감사 항목을 남기지 않는다.
- 사본의 본문은 감사 로그 항목, 내보내기 JSON Lines 한 줄과 칸 이름이 같다: `id`, `seq`, `prevHash`, `hash`, `action`, `actor`, `target`, `changes`, `occurredAt`. `Content-Type`은 `application/json`이다.
- `failed`가 된 사본 행을 다시 보내는 API는 이 묶음에 없다(콘솔 계약의 시스템 상태는 읽기뿐이다. 다시 보내기는 OPS-3이 들어오는 묶음에서 한다). 그때까지 `failed`가 된 구간은 내보내기로 옮긴다고 문서에 적는다.
- 바깥 사본은 웹훅 보내기와 같은 틀(`Sender`, 보내기 루프)을 쓴다. 리다이렉트를 따라가지 않는다(토큰이 다른 호스트로 가지 않게). 시간 제한은 웹훅과 같다. 2xx만 성공이다.
- `POPDESK_SANDBOX=true`면 주소가 있어도 꺼진 것으로 본다(D-46).
- `deploy/compose.yml`은 앱에 넘길 환경 변수를 키마다 적는다. `AUDIT_FORWARD_URL`, `AUDIT_FORWARD_TOKEN`과 두 키의 `_FILE`, `POPDESK_AUDIT_RETENTION`이 거기 없으면 더한다(compose 파일은 공개 계약이다). `outbox.audit_id`에는 외래 키를 두지 않고 `audit_log`에 트리거를 두지 않는다.

## 4. 새 결정 D-54 (2026-10-11 사람이 정함)
