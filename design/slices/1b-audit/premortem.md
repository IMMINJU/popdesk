# 1b 묶음 사전 부검

> 1b 묶음(감사 로그)을 내고 석 달 뒤 일이 틀어졌다고 가정하고, 어떻게 틀어졌을지와 막을 장치를 적는다. 마이그레이션, 공개 계약(API, 설정 키), 개인정보(감사 항목의 이름과 이메일이 밖으로 나간다)를 건드려서 전체 경로다(`process.md`).
> 표시: [소스]는 레포의 코드나 마이그레이션에서 본 것, [추론]은 확인하지 않은 판단이다. "먼저 확인할 것"은 `design.md` 6절의 실험 넷이다. 결과가 나오면 여기에 적는다.
> 장치는 `acceptance.md`와 `design.md`에 옮긴다. 묶음이 끝나면 이 파일은 `design/archive/1b-audit/`로 간다.
> 상태: 사용자가 확인했다(2026-10-11).

## 1. 올린 첫날부터 무결성 확인이 "고쳐졌다"고 했다

| 항목 | 내용 |
|---|---|
| 장면 | 0.2.0으로 올린 설치에서 관리자가 무결성 확인을 누르자 아무도 손대지 않은 항목이 끊긴 곳으로 나왔다. 그 뒤로 이 기능을 아무도 믿지 않았다 |
| 원인 | 해시를 계산할 때의 값과 다시 읽은 값이 다르면 생긴다. `jsonb`는 숫자를 고쳐 적고(`1.0`, `1e2`) 키 순서를 바꾼다 [추론]. 붙일 때는 메모리의 값으로, 확인할 때는 DB에서 읽은 값으로 계산하면 어긋난다. 첫 묶음이 시각을 정해진 글자 꼴로 저장하게 해 둔 것은 이 때문이다 [소스: `AuditLog` 머리말] |
| 막는 법 | 계산하는 함수를 하나로 두고, 입력은 늘 DB에 든 값을 읽은 것으로 한다(`design.md` 2절). 새 행도 넣을 JSON 글자를 같은 방법으로 읽어 계산한다 |
| 확인 테스트 | 지금 남기는 모든 종류를 한 번씩 일으킨 뒤 무결성 확인이 맞다(S1B-AC-14). v0.1.0 견본 덤프를 올린 뒤 맞다(S1B-AC-40). 내보낸 파일을 따로 짠 스크립트로 확인해 맞다(S1B-AC-24) |
| 먼저 확인할 것 | 실험 1 |
| 옮길 곳 | S1B-AC-09·12·14·24·40, `design.md` 2절 |

## 2. 큰 설치가 올린 뒤 뜨지 않았다

| 항목 | 내용 |
|---|---|
| 장면 | 감사 행이 150만 건인 설치를 올리자 소급 계산이 몇 분 걸렸다. 쿠버네티스가 시작 확인 시간을 넘겼다고 앱을 죽였고, 다시 뜨면 처음부터 계산해 또 죽었다 |
| 원인 | 소급 계산이 한 트랜잭션이면 죽을 때마다 통째로 되돌아간다 [추론]. 마이그레이션이 도는 동안 포트는 열리지 않는다 [소스: `architecture.md` 기동 순서]. 로그인 성공·실패가 감사 행이라 고객 3,000명인 설치는 한 해에 100만 건쯤 쌓일 수 있다 [추론: 산수] |
| 막는 법 | 걸리는 시간을 재서 정한다. 100만 건이 30초 안이면 한 트랜잭션으로 둔다. 넘으면 묶음마다 커밋하고 머리 행에 어디까지 했는지 남겨 이어서 한다. 어느 쪽이든 계산은 스트림으로 읽어 힙에 다 올리지 않는다. 릴리스 노트와 `docs/operate/upgrade.md`에 "감사 행 N건에 몇 초"를 적고 시작 확인 시간을 늘리라고 안내한다 |
| 확인 테스트 | 소급 계산 중에 앱을 죽이고 다시 띄우면 끝까지 가고 무결성 확인이 맞다(S1B-AC-13). 업그레이드 테스트(S1B-AC-40) |
| 먼저 확인할 것 | 실험 2 |
| 옮길 곳 | S1B-AC-13, `design.md` 1절, 릴리스 노트 |

## 3. 컨테이너 안 명령을 돌린 뒤 사슬이 끊겼다

| 항목 | 내용 |
|---|---|
| 장면 | 관리자가 비밀번호 복구 명령을 돌렸다. 그 뒤 무결성 확인이 그 항목에서 끊겼다고 했다. 또는 명령이 오류로 끝나 복구를 못 했다 |
| 원인 | 비밀번호 복구, 백업, 복원 명령은 앱의 `AuditLog`를 거치지 않고 JDBC로 `audit_log`에 직접 INSERT한다 [소스: `CommandDatabase.auditBySystem`]. 이 코드를 그대로 두면 해시 없는 행이 들어가거나, `NOT NULL` 제약에 걸려 명령이 실패한다. 복구 명령은 앱이 떠 있는 동안 돈다 [소스: D-46] |
| 막는 법 | 붙이는 코드를 연결 하나를 받는 한 곳에 두고 앱과 명령이 같이 쓴다. 명령도 머리 행을 잠근다. 복원 명령은 옛 덤프를 복원한 직후 해시 칸이 없는 스키마에 행을 넣으므로, 칸이 없으면 예전처럼 넣고 V7이 채운다. `audit_log`에 INSERT하는 곳이 한 클래스뿐인지 아키텍처 테스트로 본다 |
| 확인 테스트 | 앱이 떠 있는 채로 복구 명령과 백업 명령을 돌린 뒤 무결성 확인이 맞다. v0.1.0 덤프를 복원 명령으로 넣고 올린 뒤 맞다. 수용 기준에 없어서 S1B-AC-43으로 더한다 |
| 옮길 곳 | 새 기준 S1B-AC-43, `design.md` 2절 |

## 4. 아침에 로그인이 몰리자 로그인이 실패했다

| 항목 | 내용 |
|---|---|
| 장면 | 월요일 아침 로그인이 몰리자 몇 사람이 "잠시 뒤 다시 하세요"를 봤다. 또는 관리 작업 둘이 같은 때 돌아 사슬이 갈라졌다 |
| 원인 | 감사 항목마다 머리 행 하나를 잠근다. 로그인 성공도 감사 항목이다 [소스: `SignInService`]. 잠금을 오래 쥐면 뒤의 로그인이 `lock_timeout` 5초에 걸린다 [추론]. 잠그지 않고 머리를 읽으면 둘이 같은 앞 해시를 쓴다 |
| 막는 법 | 머리 행은 커밋 직전에만 잠근다(`design.md` 2절). 쥐는 동안 하는 일은 해시 계산과 INSERT 몇 개다. 갈라지는 것은 잠금이 막고 `prev_hash` 유니크가 마지막에 막는다. 교착이나 잠금 시간 초과는 이미 있는 규칙대로 한 번 다시 한다 [소스: `architecture.md`] |
| 확인 테스트 | 로그인 50개를 같은 때 보내면 모두 성공하고, 뒤에 무결성 확인이 맞고, 같은 앞 해시를 가진 항목이 없다(S1B-AC-10) |
| 먼저 확인할 것 | 실험 3 |
| 옮길 곳 | S1B-AC-10·11, `architecture.md` 잠금 순서 5번 |

## 5. 보관 기간 작업이 돈 다음 날 사슬이 끊겼다

| 항목 | 내용 |
|---|---|
| 장면 | 설치한 지 1년이 지나 보관 작업이 처음 항목을 지웠다. 다음 날 무결성 확인이 첫 항목에서 끊겼다고 했다 |
| 원인 | (가) 시각이 기간을 넘은 행만 골라 지우면, 사슬 순서와 시각 순서가 어긋난 자리에서 가운데가 빠진다 [추론]. (나) 지운 뒤 시작점을 적기 전에 죽으면 시작점이 옛 값이다(AUDIT-4가 이미 한 트랜잭션으로 정했다). (다) 무결성 확인이 도는 중에 지우면 읽던 행이 없어진다 |
| 막는 법 | 사슬의 앞에서부터 이어진 구간만 지운다. 지우기와 시작점 적기는 머리 행을 잠근 한 트랜잭션이다. 무결성 확인은 한 시점의 스냅숏을 읽는다 |
| 확인 테스트 | 시각 순서와 붙은 순서가 어긋난 항목을 만들어 놓고 보관 작업을 돌린 뒤 무결성 확인이 맞다(S1B-AC-17·21). 기간 안의 항목은 남는다(S1B-AC-22). 모든 항목이 지워진 뒤에도 맞다고 답하고 새 항목이 이어 붙는다 |
| 옮길 곳 | S1B-AC-17·21·22, `design.md` 2절 |

## 6. 바깥 사본이 비었거나 엉뚱한 곳으로 갔다

| 항목 | 내용 |
|---|---|
| 장면 | (가) 수집기가 주말 동안 죽어 있었고, 그 이틀 치 사본이 없다는 것을 감사 때 알았다. (나) 운영 DB를 복사한 시험 설치가 운영 수집기로 항목을 보냈다. (다) 수집기 주소가 다른 호스트로 리다이렉트했고 토큰이 그쪽으로 갔다. (라) 사본을 켜고 "이제 다 밖에 있다"고 믿었는데 켜기 전 2년 치는 가지 않았다. (마) 오류 로그에 토큰이 든 주소가 찍혔다 |
| 원인 | (가) 24시간 뒤 `failed`가 되면 더 보내지 않는다 [소스: D-39]. (나) 설정을 그대로 복사하면 생긴다. (다) HTTP 클라이언트가 리다이렉트를 따라가면 생긴다 [추론]. (라) 대기 행은 항목이 생길 때만 들어간다. (마) 예외 문구를 그대로 남기면 생긴다. 지금 대기 행은 오류의 종류만 남긴다 [소스: V3 `last_error_kind`] |
| 막는 법 | (가) `failed`가 되면 운영 경보를 남기고(S1B-AC-30) 시스템 상태에서 다시 보낼 수 있다. (나) `POPDESK_SANDBOX=true`면 끈다(D-46). (다) 리다이렉트를 따라가지 않는다. (라) 문서에 적고, 그 전 항목은 내보내기로 옮기라고 안내한다. (마) 주소와 토큰은 로그·응답·지표에 넣지 않고 오류는 종류만 남긴다(S1B-AC-32) |
| 확인 테스트 | 받는 쪽이 500을 주다가 살아나면 항목이 온다. 24시간 뒤 경보가 선다(S1B-AC-30). 샌드박스에서 대기에 아무것도 없다. 받는 쪽이 302를 주면 따라가지 않고 실패로 센다. 실패를 일으킨 뒤 로그에 주소와 토큰이 없다(S1B-AC-32) |
| 옮길 곳 | S1B-AC-29~34, `threat-model.md`(새 줄: 사본 토큰이 새는 길), `docs/operate/` |
| 남은 것 | 사본에는 사람 이름과 이메일이 든다. 한번 나간 사본은 익명화(10번 묶음)로 지우지 못한다. 문서에 적는다 |

## 7. 내보낸 파일이 문제를 일으켰다

| 항목 | 내용 |
|---|---|
| 장면 | (가) 누군가 이름을 `=HYPERLINK(...)`로 바꿔 두었고, 관리자가 CSV를 엑셀로 열자 수식이 돌았다. (나) 항목 100만 건을 내보내다 앱이 메모리 부족으로 죽었다. (다) 내보낸 파일로 사슬을 확인하려 했는데 문서대로 계산해도 값이 맞지 않았다 |
| 원인 | (가) 이름과 고객사 이름은 사용자가 넣는 값이고 감사 항목에 그대로 든다 [소스: `AccountService`]. (나) 결과를 목록으로 모으면 생긴다. (다) 문서의 계산 규칙과 서버의 코드가 어긋나면 생긴다 |
| 막는 법 | (가) `=`, `+`, `-`, `@`, 탭, 줄바꿈으로 시작하는 값 앞에 `'`를 붙이고 모든 칸을 따옴표로 싼다(S1B-AC-25). (나) 커서로 흘려 보내고 한 번에 둘까지만 돈다(S1B-AC-27·28). (다) 문서에 확인 스크립트를 붙이고 테스트가 그 스크립트로 내보낸 파일을 확인한다 |
| 확인 테스트 | 수식 꼴 이름을 가진 계정의 항목을 CSV로 받아 그 칸이 `'`로 시작한다. 10만 건을 `-Xmx384m`에서 내보낸다. 내보낸 JSON Lines를 스크립트로 확인한다 |
| 먼저 확인할 것 | 실험 2 |
| 옮길 곳 | S1B-AC-23~28 |

## 8. "모두 맞습니다"를 너무 믿었다

| 항목 | 내용 |
|---|---|
| 장면 | DB를 고칠 수 있는 사람이 항목을 고치고 그 뒤 사슬을 통째로 다시 계산해 넣었다. 무결성 확인은 "모두 맞습니다"라고 했고, 회사는 그것을 근거로 고쳐지지 않았다고 답했다 |
| 원인 | 해시 사슬은 고친 흔적을 찾을 뿐이고, 사슬 전체를 다시 쓰는 것은 막지 못한다(AUDIT-7, D-30). 화면의 말이 그 한계를 가리면 생긴다 |
| 막는 법 | 결과 띠에 한계를 같이 적는다(`screens.md`). 문서에 바깥 사본과 같이 쓰라고 적는다. 사본에는 해시와 앞 해시가 같이 가므로 밖의 사본과 안의 사슬을 견줄 수 있다 |
| 확인 테스트 | 화면 테스트: 맞음 결과에 한계 문구가 있다(S1B-AC-37) |
| 옮길 곳 | `screens.md`, `docs/operate/`, `threat-model.md` TM-29 |

## 9. 살펴봤지만 장치를 더하지 않은 것

- 무결성 확인이 앞단 프록시의 시간 제한(흔히 60초)에 걸리는 것: 100만 건에 얼마나 걸리는지 재서 문서에 적는다(실험 2). 백그라운드 작업으로 바꾸지 않는다(사용자가 정함, 5절 3). 화면은 연결이 끊기면 그 까닭을 한 줄로 보인다.
- 무결성 확인을 돌린 일을 남기지 않는 것: 읽기만 한다(사용자가 정함, 5절 5).
- 기본 목록이 로그인 기록으로 채워지는 것: 종류 고르기에 "로그인 기록 빼고"를 둔다(사용자가 정함, 5절 6).
- 로그인 실패를 일부러 쏟아 감사 표를 키우는 것: 로그인에는 이미 요청 수 제한과 잠금이 있다. 그대로 둔다.
- 익명화로 항목의 이름을 바꾸면 사슬이 달라지는 것: 10번 묶음으로 미뤘다(roadmap).
- 앱이 둘 뜨는 것: 인스턴스 잠금이 막는다(D-23). 머리 행 잠금은 DB에서 걸리므로 둘이 떠도 사슬은 갈라지지 않는다.
- 사본을 받는 쪽이 느려 보내기 루프가 밀리는 것: 채널마다 루프가 따로라 메일과 웹훅은 밀리지 않는다 [소스: D-39].
