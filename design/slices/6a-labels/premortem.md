# 6a 묶음 사전 부검

> 이 묶음이 나간 뒤 생길 수 있는 사고를 먼저 적고, 무엇이 막는지를 기준 ID로 잇는다. 막는 것이 없으면 기준을 더하거나 받아들인다고 적는다.
> 상태: **메인이 정함, 사용자 확인 전**(2026-10-14).

## 1. 다른 고객사의 분류가 보였다

A사에만 배정된 상담원이 B사 라벨의 ID를 알아내(옛 링크, 연속된 정수) 목록 필터나 붙이기에 넣었다. 라벨 이름("계약 해지 예정")이 B사의 사정을 말한다.

| 까닭이 될 것 | 막는 것 |
|---|---|
| 라벨 목록이 상담원의 배정을 보지 않는다 | S6A-AC-11: 없는 고객사와 같은 404 |
| 붙이기가 라벨의 고객사를 보지 않아 A사 문의에 B사 라벨이 붙고, 응답이 그 이름을 돌려준다 | S6A-AC-22: 고객사 조건이 넣는 문장 안에 있다(`design.md` 0절 4). 없는 ID와 같은 400 |
| 고치기·지우기가 라벨 ID로만 찾는다 | S6A-AC-12: 경로의 고객사와 다르면 404 |
| `label` 필터가 범위 밖의 문의를 낸다 | S6A-AC-52: 범위 조건과 같은 `WHERE`(`design.md` 4절) |

라벨 ID가 연속 정수라 "있다"는 것은 알 수 있다(404와 400의 차이는 없다). 이름과 붙은 문의는 새지 않는다. 받아들인다(`design.md` 0절 2).

센 검증을 받는다(`acceptance.md` 3절).

## 2. 고객이 내부 분류를 봤다

라벨 "불만 고객", 마감일이 고객의 포털이나 메일에 나왔다.

| 까닭이 될 것 | 막는 것 |
|---|---|
| 포털 응답에 콘솔 타입을 쓴다 | D-41(따로 둔 타입), S6A-AC-40: 포털의 모든 응답을 본다 |
| 메일 본문이 문의의 칸을 모아 넣는다 | 지금 메일은 키·제목·고객사 코드만 싣는다 [소스: `IssueFacts.java:17`]. S6A-AC-40이 메일도 본다 |
| 포털 목록이 `label`로 거르는 길을 연다(있다 없다로 라벨을 알아낸다) | S6A-AC-42: 지금처럼 400 |

## 3. 마감일이 하루 어긋났다

서울의 설치가 `POPDESK_TIMEZONE=KST`(받지 않는 값)로 떠서 UTC로 판정했다. 오전 9시 전에 정한 "오늘"이 400이 되거나, 어제 날짜가 지나지 않은 것으로 보였다.

| 까닭이 될 것 | 막는 것 |
|---|---|
| 틀린 값이 조용히 UTC가 된다(0.4.0의 동작) | S6A-AC-70: 요청을 받지 않고 로그에 설정 이름을 적는다 |
| 오늘을 UTC로 셈한다 | S6A-AC-34: 시간대 둘로 시험한다(`acceptance.md` 4절). 센 검증 |
| 화면이 브라우저의 시간대로 "지남"을 판정한다 | S6A-AC-35, 81: 서버의 `overdue`를 쓴다 |
| 0.4.0에서 틀린 값으로 돌던 설치가 올린 뒤 요청을 받지 않는다 | 받아들인다. 올리기 노트와 `configuration.md`에 적는다(`acceptance.md` 5절 14). 로그가 무엇을 고칠지 말한다 |

## 4. 지운 라벨이 남았다, 닫은 문의가 바뀌었다

| 까닭이 될 것 | 막는 것 |
|---|---|
| 붙이기와 라벨 지우기가 겹쳐 지운 라벨의 행이 남거나 외래 키 오류로 500 | S6A-AC-25, `design.md` 0절 3·4 |
| 종료와 같은 때 온 붙이기가 닫힌 문의를 바꾼다 | S6A-AC-23: 문의 행을 잠그고 `CLOSED`를 다시 본다(STATUS-7). 센 검증 |
| 같은 이름 둘이 같은 때 만들어진다 | 유니크 색인에서 409(`design.md` 0절 1) |

## 5. 목록이 느려졌다

라벨 필터와 마감일순이 더해지며 쿼리가 늘었고, 10만 건에서 첫 쪽이 1초가 됐다.

| 까닭이 될 것 | 막는 것 |
|---|---|
| 필터가 문의마다 라벨을 묻는다 | `design.md` 4절: `exists`와 `(label_id, issue_id)` 색인, 쪽의 라벨은 한 번에 읽는다 |
| 마감일순에 맞는 색인이 없다 | S6A-AC-55: C-10에서 잰다. 구현 탭이 고치기 전후를 잰다 |

S6A-AC-55는 테스트로 고정하지 않는다. CI의 기계마다 숫자가 다르다. 받아들인다.

## 6. 앞 묶음의 테스트와 화면이 깨졌다

| 까닭이 될 것 | 막는 것 |
|---|---|
| 문의 응답에 칸이 늘어 견본을 통째로 견주는 잠긴 테스트가 깨진다 | `design.md` 10절: 계약 뒤 같은 푸시에서 테스트 탭이 맞춘다 |
| Storybook 실행기가 처음 돌며 앞 묶음 story 수십 개가 실패해 묶음이 멈춘다 | `design.md` 8절: 계약 단계에서 한 번 돌려 실패 수를 먼저 안다. 테스트 쪽이 story를, 구현 쪽이 컴포넌트를 고친다 |
| 실행기가 느려 local-ci가 길어진다 | `acceptance.md` 5절 13: 5분을 넘으면 다시 정한다 |
| `TestMail`의 시간대가 바뀌어 4b의 시험 메일 테스트가 깨진다 | 같은 값을 읽는 곳을 하나로 모을 뿐 동작은 같다(틀린 값만 달라진다). 4b의 시험 메일 테스트를 구현 뒤 돈다 |

## 7. 받아들이는 것

- 라벨 ID가 추측 가능한 정수다(1절).
- 목록 성능은 C-10에서 한 번 잰다(5절).
- 틀린 `POPDESK_TIMEZONE`으로 돌던 설치는 올린 뒤 고쳐야 다시 요청을 받는다(3절).
- 라벨 이름을 고쳐도 이력의 옛 이름은 그대로라 이력과 지금 라벨의 이름이 다를 수 있다(`acceptance.md` 5절 6).
