# 10a 묶음 수용 기준: 계정 내보내기와 익명화

> `roadmap.md` 10번의 앞 조각이다(5절 1). 묶음이 끝나면 `design/archive/10a-privacy/`로 간다(D-27).
> 전체 경로다: 개인정보 흐름(내보내기 파일, 익명화), 마이그레이션(계정에 칸 하나), 공개 계약(새 경로 둘, 계정 응답의 새 칸, 새 감사 종류, 바깥 확인 스크립트의 규칙), 감사 사슬을 다시 쓰는 일. 사전 부검은 같은 폴더의 `premortem.md`다.
> 규칙 ID의 글은 같은 폴더 `rules.md`에 있다. 기준 ID는 `S10A-AC-nn`이다.
> 관계있는 결정(`adr.md`): D-18, D-20, D-25, D-43, D-49, D-52, D-57, D-62(새). 위협 모델: TM-05, TM-30, TM-67(새).
> 상태: **메인이 정함, 사용자 확인 전**(2026-10-18). 규칙에 없던 것을 메인이 넣은 곳은 5절에 모았다.

## 1. 넣는 것과 미루는 것

지금: 내보내기와 익명화 코드는 없다. 계정 정지(세션 끝내기, 마지막 관리자 막기, 담당 비우기), 감사 사슬(머리 행 잠금, `prev_hash` 유니크, 보관 작업의 시작점), 감사 내보내기(흘려 쓰기, 동시 둘), 무결성 확인, 바깥 사본(보낼 때 본문을 DB에서 읽음)은 있다. 감사 값에서 사람은 한 사람(`actor`)이 `{accountId, name, email}` 구조이고, 대상 계정은 `target.accountId`, 대상 계정의 이름·이메일은 `changes`의 `name`·`email` 칸에 글자로 들어 있다.

|---|---|---|---|

| PII-7 | `docs/operate/privacy.md`(절차, 남는 것, 저장 항목) | 보관 기간 표와 문의 자동 정리 절 | 10b |
| PII-6, 8 | – | 문의 자동 정리, 고객사 내보내기 | 10b |

## 2. 수용 기준

말의 뜻:

- "익명 계정"은 익명화한 계정이다. "익명 이름"은 설치 언어(`POPDESK_LOCALE`)로 `ko`면 "삭제된 사용자", `en`이면 "Deleted user"이고, "익명 이메일"은 `deleted-{id}@invalid`다.
- "그 사람의 감사 항목"은 `actor.accountId` 또는 `target.accountId`가 그 계정 ID인 항목이다. "사람 칸"은 `actor`의 `name`·`email`과, `target.accountId`가 그 계정인 항목의 `changes` 맨 위 `name`·`email`(글자이거나 `{from, to}`)이다.

### 2.3 감사 사슬

| ID | 기준 |
|---|---|
| S10A-AC-17 | When 계정을 익명화하면, the system shall 그 사람의 감사 항목의 사람 칸을 익명 값으로 바꾼다. 다른 칸, 다른 계정의 항목, 같은 이름을 가진 다른 계정의 항목은 그대로다. (PII-5) |
| S10A-AC-18 | When 감사 값을 바꾸면, the system shall 바뀐 첫 항목부터 사슬 머리까지 `prev_hash`와 `hash`를 다시 계산하고, 바로 다음 항목(seq `toSeq + 1`, `ACCOUNT_ANONYMIZED`보다 앞)으로 감사 `AUDIT_RECHAINED` 하나를 남긴다: 대상 `{type: AUDIT_LOG}`, 바뀐 값 `fromSeq`, `toSeq`, `headHash` `{from, to}`(재계산 전과 뒤의 `toSeq` 항목 hash). 바뀐 항목이 없으면 다시 계산하지 않고 이 항목도 남기지 않는다(이 경우는 HTTP로 만들 수 없어 C-10의 `AuditAnonymizer` 단위 테스트로 본다). (AUDIT-6) |
| S10A-AC-19 | When 익명화가 끝난 뒤 관리자가 무결성 확인을 돌리면, the system shall 사슬이 맞다고 답한다. 재계산 중 앱이 죽으면 익명화 전체가 되돌아가고 무결성 확인도 맞다고 답한다. (AUDIT-6, AUDIT-7) |
| S10A-AC-20 | When 익명화와 다른 감사 남기기(로그인, 관리 작업)가 함께 오면, the system shall 둘 다 끝내고 사슬을 하나로 둔다(갈라지지 않고 무결성 확인이 맞다). 감사 항목 10만 건이 있는 설치에서 익명화가 도는 동안 다른 요청(로그인 20번)이 모두 성공한다(사슬 머리는 익명화가 시작된 뒤 붙은 항목을 이어 계산하는 동안만 잡는다, 5절 2). (AUDIT-6) |
| S10A-AC-21 | If 다른 익명화가 돌고 있으면, then the system shall 409 `ANONYMIZATION_RUNNING`으로 답하고 아무것도 바꾸지 않는다. (5절 3) |
| S10A-AC-35 | When 익명화가 커밋되기 전에 값을 만든 그 사람의 감사 항목(그 사람의 로그인 실패 따위)이 커밋 뒤에 붙으면, the system shall 그 항목의 사람 칸도 익명 값으로 붙인다. 익명화 뒤에 그 사람을 대상으로 붙는 모든 감사 항목도 같다. (PII-5, 5절 2) |
| S10A-AC-22 | When 감사 보관 작업(AUDIT-4)이 익명화와 같은 때 돌면, the system shall 어떤 한 순서로 한 것과 같게 끝낸다(무결성 확인이 맞다). (AUDIT-4, AUDIT-6) |
| S10A-AC-23 | When 바깥 사본(AUDIT-9)이 켜져 있으면, the system shall 아직 보내지 않은 그 사람의 감사 사본을 익명 값과 새 hash로 보내고, `AUDIT_RECHAINED` 항목도 다른 항목처럼 보낸다. 이미 보낸 사본은 다시 보내지 않는다. (PII-5, AUDIT-6) |
| S10A-AC-24 | When `docs/integrate/audit-verify.py`가 재계산 앞에 받은 사본과 뒤에 받은 사본이 섞인 JSON Lines를 읽으면, the system shall `AUDIT_RECHAINED` 항목(seq R, 구간 F~T)을 경계로 구간을 나눠 본다: 항목의 `prevHash`가 앞 항목의 hash와 다른 곳이 F~T 안이거나 R이면 끊긴 곳이 아니라 "다시 계산됨, seq F~T"로 적는다. 다만 R의 `prevHash`는 `headHash.to`와 같아야 하고, 각 항목의 hash는 그 항목 자신의 값과 `prevHash`로 다시 계산해 맞아야 한다. 그 밖의 어긋남은 지금처럼 끊긴 곳으로 알린다. 같은 seq가 두 번 오면(최소 한 번 보내기) hash가 같으면 하나로 보고, 다르면 그 seq가 뒤에 오는 어느 재계산 구간 안일 때만 뒤의 것을 쓴다. 재계산 구간이 겹쳐도 각 경계를 따로 본다. `AUDIT_RECHAINED` 항목 자신의 seq가 뒤의 재계산 구간 안에 들면 그 항목의 "`prevHash` = `headHash.to`" 검사는 하지 않고 뒤 구간의 이음으로 본다. (AUDIT-7) |

| S10A-AC-30 | When 관리자가 "익명화"를 고르면, the system shall 위험 확인 대화상자에 되돌릴 수 없다는 것과 바뀌는 것(이름·이메일, 사진·세션 지움, 쓴 글은 남음), 그 사람이 담당인 열린 문의·작업 수와 담당 비우기 선택(정지와 같은 꼴)을 보이고, 그 사람의 이메일을 쳐 넣어야(앞뒤 공백을 자르고 대소문자는 가리지 않는다) "익명화" 단추가 눌린다. (PII-4, ACCT-7, 5절 5) |
| S10A-AC-31 | When 익명화가 끝나면, the system shall 목록을 다시 읽어 그 줄을 익명 이름, 익명 이메일, "익명화됨" 표시로 바꾸고 "익명화했습니다"를 알린다(비운 담당이 있으면 정지와 같은 꼴로 수를 덧붙인다). 400·409면 대화상자 안에 까닭을 보이고 닫지 않는다. (PII-4) |
| S10A-AC-36 | When 계정 목록을 `anonymized=false`로 부르면, the system shall 익명 계정을 빼고 준다(값이 없으면 거르지 않는다). C-9 고객사 상세의 고객 찾기는 이 값으로 불러 익명 계정을 보이지 않는다. (PII-4, S10A-AC-13) |
| S10A-AC-32 | The system shall 구성원 목록에서 익명 계정을 "익명화됨" 표시로 정지 계정과 구분한다(상태 필터는 지금처럼 `SUSPENDED`에 든다). (PII-4) |

일부러 틀린 구현(C-7 점검 지시서에 넣음): 감사 값을 이름 글자로 찾아 바꿈(동명이인이 바뀜), `actor`만 바꾸고 `changes`의 `name`·`email`을 둠, 사슬을 다시 계산하지 않고 값만 바꿈, 바뀐 항목만 다시 계산하고 그 뒤를 둠, 재계산을 두 트랜잭션으로 나눔, 세션을 지우지 않음, 메일 대기 행을 둠, 내보내기에 담당자 이름을 넣음, 내보내기에 영구 삭제한 문의를 넣음, 익명 계정의 정지 해제를 받음, 마지막 관리자 검사를 잠금 없이 함, 붙이기에서 익명 계정을 다시 보지 않음(S10A-AC-35), 비밀번호를 `null`로 지움.

순수 계산 클래스(C-8 목록 후보, `design.md` 3절): 서버 `AuditAnonymizer`(감사 행 하나와 계정 ID, 익명 값을 받아 바꾼 행을 돌려줌). 바깥 확인 스크립트의 구간 나누기는 `AuditVerifyScriptTest`가 본다(파이썬이라 PIT 밖). 웹은 이메일 맞춤 검사(대소문자, 앞뒤 공백)가 판단이 걸린 곳이라 Stryker를 받는다.
