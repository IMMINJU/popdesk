# 5번 묶음 수용 기준: 본문 이미지와 첨부 이력

> `roadmap.md` 6절 5번의 앞쪽 절반이다. 뒤쪽 절반(저장소 `disk`·`s3`, ATT-9)은 5b 묶음으로 가른다(5절 1). 묶음이 끝나면 `design/archive/5-attachments/`로 간다(D-27).
> 전체 경로다. 마이그레이션(첨부 표에 칸 하나, 제약 하나), 고객사 경계(남의 이미지를 묶거나 읽기), 공개 계약(새 경로 둘, 요청 칸 하나, 새 오류 코드, 이력의 새 `field`), 공용 컴포넌트 API(편집기와 마크다운 보기)를 건드린다. 사전 부검은 같은 폴더의 `premortem.md`다.
> 규칙 ID의 글은 같은 폴더 `rules.md`에 있다. 기준 ID는 `S5-AC-nn`이다.
> 관계있는 결정(`adr.md`): D-14, D-38, D-43, D-47, D-57, D-59(새 결정). 위협 모델: TM-19, TM-26, TM-33, TM-34, TM-39.
> 상태: **메인이 정함, 사용자 확인 전**(2026-10-13). 규칙에 없던 것을 메인이 넣은 곳은 5절에 모았다.

## 2. 수용 기준

"임시 이미지"는 올렸지만 아직 어느 글에도 묶이지 않은 이미지다. "묶는다"는 임시 이미지를 문의(와 댓글)의 첨부로 만드는 것이다. "본문 이미지"는 묶인 것이다. "글"은 문의 본문과 댓글이다.

### 2.1 임시 이미지 올리기

| ID | 기준 |
|---|---|
| S5-AC-01 | When 로그인한 사람이 이미지를 올리면, the system shall 임시 이미지를 만들고 그 ID를 준다. 문의 없이 올린다(등록 화면에는 아직 문의가 없다). 두 앱 모두에 경로가 있다. (ATT-6) |
| S5-AC-02 | If 파일의 앞 바이트가 PNG, JPEG, GIF, WebP 가운데 어느 것도 아니면, then the system shall 400으로 답한다. 파일 이름의 확장자와 요청이 말한 형식은 보지 않는다. (ATT-6, TM-19) |
| S5-AC-03 | The system shall 이미지의 형식(`Content-Type`)을 앞 바이트로 정해 적고, 내려줄 때 그 값을 쓴다. 요청이 말한 형식은 쓰지 않는다. (TM-19, 5절 3) |
| S5-AC-04 | If 파일이 0바이트거나 10MB를 넘거나 이름이 1~255자가 아니면, then the system shall 첨부 올리기와 같은 400으로 답한다. (ATT-2, S0-AC-57) |
| S5-AC-05 | If 올리면 그 사람의 임시 이미지가 20개를 넘거나 합이 50MB를 넘게 되면, then the system shall 400으로 답한다. 묶인 이미지와 만료된 이미지는 세지 않는다. (ATT-7, TM-26) |
| S5-AC-06 | The system shall 임시 이미지를 팀 총량 한도에 센다. 넘게 되면 첨부 올리기와 같은 400이다. (ATT-3, S0-AC-58, 5절 4) |
| S5-AC-07 | The system shall 임시 이미지 올리기를 첨부 올리기와 같은 횟수 제한과 같은 "한 번에 16건"에 센다. (S0-AC-59의 꼴, `conventions.md`) |
| S5-AC-08 | The system shall 임시 이미지의 ID를 추측할 수 없는 값(UUID)으로 짓는다. (ATT-7) |

### 2.2 임시 이미지 읽기

| ID | 기준 |
|---|---|
| S5-AC-10 | When 올린 사람이 자기 임시 이미지를 읽으면, the system shall 내용을 준다(미리보기에 쓴다). 머리글은 첨부 내려받기와 같다(`Content-Disposition: attachment`, `nosniff`). (ATT-7, TM-19) |
| S5-AC-11 | If 다른 사람이 그 임시 이미지를 읽으면(관리자도), then the system shall 없는 ID와 같은 404로 답한다. (ATT-7, TM-34) |
| S5-AC-12 | If 임시 이미지가 묶였거나 만료됐거나 지워졌으면, then the system shall 임시 이미지 경로에서 없는 ID와 같은 404로 답한다. 묶인 이미지는 문의 아래의 첨부 경로로만 읽는다. (ATT-7, S0-AC-102) |

### 2.3 묶기

| ID | 기준 |
|---|---|
| S5-AC-20 | When 문의 등록, 대리 등록, 문의 고치기, 댓글 달기, 댓글 고치기 요청이 이미지 ID들을 함께 보내면, the system shall 그 글의 저장과 같은 트랜잭션에서 그 이미지들을 그 문의(댓글이면 그 댓글)의 첨부로 묶는다. 글이 저장되지 않으면 하나도 묶이지 않는다. (ATT-6) |
| S5-AC-21 | If 보낸 ID 가운데 하나라도 호출한 사람이 올린 것이 아니거나, 이미 묶였거나, 만료됐거나, 임시 이미지가 아니거나(보통 첨부), 없는 ID면, then the system shall 글을 저장하지 않고 400으로 답한다. 어느 경우든 상태 코드와 본문이 같다. (ATT-6, TM-33) |
| S5-AC-22 | If 같은 임시 이미지를 두 요청이 같은 때 묶으려 하면, then the system shall 하나만 묶고 다른 하나는 S5-AC-21의 400으로 답한다. (ATT-7) |
| S5-AC-23 | If 묶으면 문의의 공개 첨부 합이 50MB를 넘게 되면, then the system shall 글을 저장하지 않고 첨부 올리기와 같은 400으로 답한다. 내부 댓글에 묶는 이미지는 이 합에 세지 않는다. (ATT-2, S0-AC-57) |
| S5-AC-24 | The system shall 본문 이미지를 그 문의의 첨부로 다룬다: 첨부 목록에 나오고(본문 이미지라는 표시와 함께), 문의 아래의 첨부 경로로 읽고, 올린 사람과 관리자가 지운다. 내부 댓글에 묶인 이미지는 고객에게 없는 것과 같다. (ATT-4, ATT-5, S0-AC-60, TM-39, 5절 5) |
| S5-AC-25 | The system shall 요청이 보낸 ID만 묶는다. 본문에 `attachment:{id}`가 적혀 있어도 보내지 않은 ID는 묶지 않고, 본문에 적히지 않은 ID를 보내도 거절하지 않는다. 본문의 글자는 그대로 저장한다. (ATT-6, COM-6, 5절 6) |
| S5-AC-26 | When 글을 고쳐 본문에서 이미지를 빼면, the system shall 그 이미지를 지우지 않는다. 첨부 목록에 남고 올린 사람과 관리자가 지울 수 있다. (5절 7) |
| S5-AC-27 | When 댓글을 지우면, the system shall 그 댓글에 묶인 이미지도 그 댓글의 다른 첨부와 같이 지운다. (S4-AC-14) |
| S5-AC-28 | If 문의가 `CLOSED`면, then the system shall 이미지를 묶는 요청을 그 글의 요청이 이미 그러듯 400 `ISSUE_CLOSED`로 답한다. 종료와 같은 때 온 묶기는 종료 뒤에 처리되면 묶이지 않는다. (ATT-1, S3-AC-52) |

### 2.4 만료와 정리

| ID | 기준 |
|---|---|
| S5-AC-30 | The system shall 올린 지 24시간이 지난 임시 이미지를 만료된 것으로 본다. 만료된 이미지는 묶이지 않고 읽히지 않는다(정리 작업이 아직 지우지 않았어도). (ATT-7) |
| S5-AC-31 | When 임시 이미지 정리 작업이 돌면(10분마다), the system shall 만료된 임시 이미지의 파일과 행을 지운다. 흔적을 남기지 않는다(아무에게도 보인 적이 없다). (ATT-7, ATT-10) |
| S5-AC-32 | If 정리와 묶기가 같은 이미지를 두고 겨루면, then the system shall 하나만 이기게 한다. 묶인 이미지는 지워지지 않고, 지워진 이미지는 묶이지 않는다. (ATT-7) |
| S5-AC-33 | The system shall 이 정리 작업의 마지막으로 돈 시각과 지운 수를 다른 정리 작업처럼 남기고 시스템 상태에 보인다. (OPS-2, S0-AC-82) |
| S5-AC-34 | If 파일 지우기가 실패하면, then the system shall 행을 남겨 다음 회에 다시 지운다. 그 이미지는 그사이에도 읽히지 않는다. (ATT-10) |

### 2.5 첨부 이력

| ID | 기준 |
|---|---|
| S5-AC-40 | When 이미 있는 문의에 첨부가 붙으면(문의나 댓글에 올리기, 문의 고치기·댓글 달기·댓글 고치기에서 이미지 묶기), the system shall 첨부마다 이력 항목 하나를 남긴다: 무엇이 붙었는지(첨부 ID), 누가, 언제. (ATT-8) |
| S5-AC-41 | When 첨부가 지워지면(첨부 지우기, 댓글 지우기에 딸린 것), the system shall 첨부마다 이력 항목 하나를 남긴다. (ATT-8) |
| S5-AC-42 | The system shall 문의 등록과 대리 등록에 딸린 첨부와 이미지에는 이력을 따로 남기지 않는다. `CREATED` 하나다. (5절 8) |
| S5-AC-43 | The system shall 이력 항목에 파일 이름을 적지 않는다. 첨부 ID만 적는다. (S0-AC-61: 지운 첨부의 이름은 비운다, 5절 9) |
| S5-AC-44 | The system shall 첨부의 이력으로 알림(알림함, 메일, 웹훅)을 만들지 않는다. (ATT-8) |
| S5-AC-45 | The system shall 이력 항목을 첨부를 붙이거나 지운 트랜잭션에서 남긴다. 되돌려진 요청은 이력을 남기지 않는다. (HIST-1의 꼴) |

### 2.6 그리기와 편집기 (두 앱)

| ID | 기준 |
|---|---|
| S5-AC-50 | When 본문에 `![설명](attachment:{id})`가 있고 `{id}`가 UUID 꼴이면, the system shall 그 자리에 이미지를 그린다. 주소는 그 문의의 첨부 경로다. 설명은 대체 글이다. (ATT-6) |
| S5-AC-51 | The system shall 그 밖의 이미지 문법(`http`, `https`, `data:` 주소, 날 `<img>`)을 이미지로 그리지 않는다. 지금처럼 글자로 남는다. (COM-6, D-59) |
| S5-AC-52 | If 이미지를 읽지 못하면(지워졌다, 다른 문의의 것이다, 고객에게 내부 이미지다), then the system shall 깨진 그림 대신 설명과 "이미지를 볼 수 없습니다"를 보인다. (UX, 5절 10) |
| S5-AC-53 | The system shall 이미지를 글의 폭 안에 그린다. 큰 이미지가 가로 넘침을 만들지 않는다(360px에서도). |
| S5-AC-54 | When 글 쓰는 사람이 편집기의 이미지 단추로 파일을 고르거나, 이미지를 붙여 넣거나, 끌어다 놓으면, the system shall 임시 이미지로 올리고 올라가면 커서 자리에 `![파일 이름](attachment:{id})`를 넣는다. 올리는 동안 그 편집기의 저장 단추는 눌리지 않는다. |
| S5-AC-55 | If 올리기가 실패하면, then the system shall 본문을 바꾸지 않고 까닭을 편집기 아래에 보인다(형식, 크기, 임시 이미지 한도, 팀 총량, 413, 횟수 제한, 연결 끊김). 이미 쓴 글은 남는다. (UX-11) |
| S5-AC-56 | The system shall 미리보기에서 아직 묶지 않은 이미지도 그린다(임시 이미지 경로로). |
| S5-AC-57 | When 글을 저장하면, the system shall 이 편집에서 올린 이미지 가운데 본문에 아직 남아 있는 것의 ID만 보낸다. 이미 묶인 이미지의 ID는 다시 보내지 않는다. |
| S5-AC-58 | If 저장이 S5-AC-21의 400으로 실패하면, then the system shall 글을 지우지 않고 "이미지를 다시 올려야 한다"는 것을 알린다(임시 이미지가 만료된 경우가 보통이다). |
| S5-AC-59 | The system shall 첨부 목록에서 본문 이미지를 표시로 가린다("본문 이미지"). 콘솔의 이력에는 첨부가 붙고 지워진 것을 사람과 시각과 함께 보인다. 파일 이름은 지금 첨부 목록에 있으면 그것으로, 없으면 "지워진 파일"로 보인다. |

### 2.7 함께 붙일 관문과 구조

| ID | 기준 |
|---|---|
| S5-AC-60 | 마이그레이션은 앞으로만 간다. 0.4.0 견본에서 올린 뒤 있던 첨부가 모두 "본문 이미지 아님"이고 내려받은 내용의 해시가 같다. 0.5.0 견본 생성기는 본문 이미지(묶인 것)와 임시 이미지를 하나씩 넣는다. (D-47) |
| S5-AC-61 | 서버 패키지 `attachment`와 `comment` 사이의 순환이 없어지고 기준선 파일에서 그 두 줄이 빠진다. 새 순환은 없다. (D-57, `design.md` 4절) |
| S5-AC-62 | 임시 이미지 내용을 읽는 것도 첨부 서비스 한 곳뿐이다(`ScopedReadRulesTest`의 규칙이 그대로 통과한다). |
| S5-AC-63 | 편집기의 올리기와 그리기의 주소는 앱이 인자로 준다. `@popdesk/ui`와 `@popdesk/app`은 API 클라이언트를 가져오지 않는다. 포털 빌드에 `/api/console`이 없다. (D-57) |

## 4. 테스트를 쓸 때 지킬 것

- 묶기의 거절(S5-AC-21)은 경우마다 응답을 "없는 ID"의 응답과 통째로 견준다(상태, 본문).
- 만료는 시계를 돌려 본다. 24시간의 경계 앞뒤 한 번씩.
- 겨루기(S5-AC-22, 32)는 결과를 "어떤 한 순서로 한 것과 같다"로 단언한다: 묶인 수는 0이나 1, 묶였으면 파일이 읽힌다.
- 고객에게 내부 이미지는 목록, 읽기, HEAD, 범위 요청 모두 본다(S0-AC-102의 목록).
- 웹의 가짜 응답은 계약 스키마로 검증하는 도움을 지난다(이 묶음에서 만든다).
- 새 테스트는 잠그기 전에 무작위 순서로 세 번 돈다(`process.md` C-6).

## 5. 메인이 추천대로 넣은 것 (메인이 정함, 사용자 확인 전)

| # | 정한 것 | 까닭 | 버린 대안 |
|---|---|---|---|
| 1 | 5번을 둘로 가른다: 5(본문 이미지와 이력), 5b(저장소 `disk`·`s3`) | 둘은 서로 기대지 않는다. 5는 마이그레이션과 화면, 5b는 설정 키와 새 의존성(S3 클라이언트)이다. 4번을 둘로 갈랐을 때 묶음 하나가 7시간쯤이었다 | 한 묶음 |
| 2 | 임시 이미지는 문의 없이 올리는 새 경로를 둔다 | 등록 화면에는 문의가 없다. 지금 첨부 경로는 모두 문의 키가 있어야 한다 | 등록 요청에 파일을 같이 싣기(본문에 넣을 ID를 미리 알 수 없다) |
| 3 | 형식은 앞 바이트로 서버가 정한다. 이미지를 풀어 보거나 다시 만들지 않는다 | 프로필 사진과 달리 원본을 그대로 보여 주는 것이 목적이다. `nosniff`와 맞는 형식이면 브라우저가 이미지로만 읽는다 | 풀어서 다시 인코딩(메모리, GIF 움직임이 사라진다) |
| 4 | 임시 이미지도 팀 총량에 센다 | 디스크를 쓰는 것은 같다(TM-26) | 묶을 때부터 세기 |
| 5 | 본문 이미지는 첨부 목록에 나온다(표시와 함께) | 숨기면 50MB를 채우는 보이지 않는 파일이 생기고 지울 길이 없다 | 목록에서 빼기 |
| 6 | 서버는 본문을 읽어 ID를 찾지 않는다. 보낸 ID만 묶는다 | 규칙이 그렇다(ATT-6). 서버가 마크다운을 해석해 권한을 정하면 해석의 틈이 권한의 틈이 된다 | 본문에서 ID 뽑기 |
| 7 | 본문에서 뺀 이미지는 지우지 않는다 | 문의 이력이 옛 본문을 갖고 있어 그 이미지를 가리킨다. 지우는 것은 사람이 한다 | 고칠 때 빠진 이미지 지우기 |
| 8 | 등록에 딸린 첨부는 이력을 따로 남기지 않는다 | `CREATED`가 "이때 이 상태로 생겼다"를 말한다. 줄이 스무 개 생기는 것을 피한다 | 첨부마다 한 줄 |
| 9 | 이력에는 첨부 ID만 적는다 | 지운 첨부의 이름은 비우기로 했다(이름에 개인정보가 들 수 있다). 이력에 이름을 적으면 그 약속이 깨진다 | 이름 적기 |
| 10 | 바깥 주소의 이미지는 그리지 않는다(D-59) | 글을 여는 사람의 IP와 시각이 바깥 서버에 간다. 상담원이 고객이 쓴 글을 여는 것만으로 추적된다 | 허용 목록, 프록시 |
| 11 | 새 오류 코드: 이미지 형식 아님, 묶을 수 없는 이미지, 임시 이미지 한도. 이름은 계약 탭이 `conventions.md`의 있는 이름과 견줘 정한다 | 공개 계약이다 | – |
| 12 | 메일과 웹훅의 글은 손대지 않는다 | 둘 다 글의 본문을 싣지 않는다(`design.md` 6절 2에서 확인) | – |
| 13 | 오류 코드 이름: `FILE_NOT_IMAGE`, `TEMPORARY_IMAGE_INVALID`, `TEMPORARY_IMAGE_LIMIT_EXCEEDED`. 칸 이름: `imageIds`, `inline` | 계약 탭이 있는 이름의 꼴과 견줘 정했다(`FILE_`, `…_INVALID`, `…_EXCEEDED`) | – |
| 14 | `imageIds`의 값이 UUID 꼴이 아니어도 `TEMPORARY_IMAGE_INVALID`다. 20개를 넘는 것만 `INVALID_INPUT`(`TOO_MANY`)이다 | 첨부 경로의 "UUID가 아니면 없는 ID"와 같다. 꼴 검사를 따로 답하면 경우가 하나 더 갈린다(S5-AC-21) | 칸의 `INVALID_FORMAT` |
| 15 | 본문은 그대로이고 `imageIds`만 보낸 고치기: 이미지는 묶이고 이력이 남는다. 문의의 `version`은 오르지 않고 댓글의 고친 시각은 바뀌지 않는다 | 첨부 올리기도 `version`을 올리지 않는다. `version`은 제목·내용·우선순위의 덮어쓰기를 막는 값이다 | 묶기도 고친 것으로 치기 |
| 16 | `Idempotency-Key`로 다시 보낸 등록은 `imageIds`를 보지 않는다. 첫 응답을 그대로 준다 | 다시 보낸 등록의 파일도 보지 않는다. 첫 요청이 이미 묶었으므로 다시 보면 늘 거절이 된다 | "같은 내용"의 견줌에 넣기 |
| 17 | 첨부 정리 작업(하루 한 번)이 치운 임시 이미지의 `pending` 행은 `purged`로 남고, 임시 이미지 정리가 24시간 뒤 그 행도 지운다 | 아무에게도 보인 적 없는 행이다(S5-AC-31) | 남겨 두기 |
