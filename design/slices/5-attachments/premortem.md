# 5번 묶음 사전 부검

> 이 묶음이 나간 뒤 생길 수 있는 사고를 먼저 적고, 무엇이 막는지를 기준 ID로 잇는다. 막는 것이 없으면 기준을 더하거나 받아들인다고 적는다.
> 상태: **메인이 정함, 사용자 확인 전**(2026-10-13).

## 1. 다른 사람의 파일이 내 글에 붙었다

고객이 다른 고객사 문의의 첨부 ID나 내부 댓글의 첨부 ID를 알아내(이력, 추측, 옛 링크) 자기 댓글을 쓰며 그 ID를 묶는 칸에 넣었다. 묶이면 그 파일이 자기 문의의 첨부가 되어 읽힌다.

| 까닭이 될 것 | 막는 것 |
|---|---|
| 묶기가 "올린 사람"을 보지 않는다 | S5-AC-21: 호출한 사람이 올린 임시 이미지만. 조건이 UPDATE 한 문장에 있다(`design.md` 2절) |
| 이미 묶인 첨부를 다시 묶는다(`issue_id`를 덮는다) | S5-AC-21: `issue_id IS NULL` 조건. 보통 첨부는 `inline`이 아니라 걸린다 |
| 거절의 응답이 경우마다 달라 ID가 있는지 알려 준다 | S5-AC-21: 모든 경우가 같은 400. 테스트가 응답을 통째로 견준다(4절) |
| 서버가 본문에서 ID를 뽑아 묶는다 | S5-AC-25: 보낸 ID만 묶는다 |

센 검증을 받는다(틀린 구현: 올린 사람 조건 빼기, `issue_id` 조건 빼기). `inline` 조건 빼기는 밖에서 드러나지 않는다: "파일이 다 쓰였고 문의가 없고 본문 이미지가 아닌" 행은 DB 제약이 막아 생기지 않는다(점검에서 봄).

## 2. 묶지 않은 이미지가 남에게 읽혔다

임시 이미지의 주소가 채팅이나 화면 공유로 새어, 다른 사람이 열었다.

| 까닭이 될 것 | 막는 것 |
|---|---|
| 임시 경로가 로그인만 본다 | S5-AC-11: 올린 사람만. 관리자도 404 |
| 묶인 뒤에도 임시 경로가 열려 문의 권한을 건너뛴다 | S5-AC-12: 묶이면 임시 경로는 404 |
| 내부 댓글에 묶인 이미지가 고객에게 읽힌다 | S5-AC-24: 첨부의 404 하나(S0-AC-102)를 그대로 탄다. `comment_id`가 적히므로 있는 쿼리가 거른다 [추론: 구현이 `comment_id`를 적는 것에 달렸다. 테스트가 목록, 읽기, HEAD, 범위 요청을 본다] |

## 3. 이미지가 스크립트로 열렸다

HTML이나 SVG를 `.png`로 올려 본문에 넣었다.

| 까닭이 될 것 | 막는 것 |
|---|---|
| 확장자나 요청의 형식을 믿는다 | S5-AC-02, 03: 앞 바이트로 가르고, 내려줄 형식도 서버가 정한다 |
| 앞 바이트만 PNG이고 뒤가 HTML인 파일 | `nosniff`와 이미지 형식으로 내려가므로 브라우저가 문서로 읽지 않는다. 주소를 직접 열면 내려받기가 된다(S5-AC-10, S0-AC-59) |
| 바깥 주소의 이미지가 그려져 읽는 사람이 추적된다 | S5-AC-51, D-59 |
| 마크다운의 이미지 갈래가 주소를 그대로 `src`에 넣는다 | S5-AC-50: UUID 꼴만 받고 주소는 앱의 함수가 만든다. 글에서 온 글자는 ID 자리에만 들어간다 |

## 4. 임시 이미지가 디스크를 채웠다

스크립트가 이미지를 계속 올렸다. 또는 정리 작업이 멈췄다.

| 까닭이 될 것 | 막는 것 |
|---|---|
| 사람마다의 한도가 없다 | S5-AC-05(20개·50MB), S5-AC-07(횟수 제한) |
| 여러 계정으로 올린다 | S5-AC-06: 팀 총량에 센다. 80% 경보가 이미 있다(S0-AC-58) |
| 정리 작업이 돌지 않는다 | S5-AC-33: 시스템 상태에 마지막으로 돈 시각. 하루 넘게 돌지 않을 때의 경보는 7번 묶음이다(로드맵) |
| 만료된 것이 정리 전에 한도를 차지해 진짜 사용자가 막힌다 | S5-AC-05: 만료된 것은 세지 않는다 |
| 파일 지우기가 실패한 행이 쌓인다 | S5-AC-34: 다음 회에 다시. 쌓이는 수는 시스템 상태의 지운 수로는 안 보인다. **받아들인다**(`db` 저장소에서는 행과 내용이 같은 DB라 실패할 일이 드물다. 5b에서 다시 본다) |

## 5. 앞 묶음의 테스트가 깨졌다

| 까닭이 될 것 | 막는 것 |
|---|---|
| 새 정리 작업의 기록을 `PasswordResetCleanupTest`와 `IdempotencyKeyTest`가 자기 작업으로 본다("먼저 있던 셋이 아닌 작업") | 계약 뒤 테스트 탭이 두 파일의 목록에 새 이름을 더한다(`design.md` 6절 5). 구현 탭이 첫 실행에서 이 둘을 돈다 |
| 표나 칸을 꼴로 찾는 테스트 도움이 `attachment`의 새 `boolean` 칸에 걸린다 | `process.md` C-4: `db.tables()`를 쓰는 클래스를 한 번 돈다 |
| 첨부 목록 응답에 칸이 늘어 웹의 견본이 계약과 어긋난다 | 이 묶음에서 만드는 계약 스키마 검증 도움 |
| 마크다운이 `![x](attachment:…)`를 지금은 글자 `!x`로 그리는데, 그것을 고정한 테스트 | 없다(조사: 마크다운 테스트 여섯 파일에 `![` 0건) |
| 편집기 도구가 아홉에서 열이 되어 도구 수를 세는 테스트 | 화면 초안 전에 잠긴 테스트를 읽는다(`process.md` C-1~3) |
| 댓글 외래 키를 미뤄지게 바꾸면 없는 댓글 ID의 오류가 문장이 아니라 커밋에서 난다 | 지금 올리기는 댓글을 먼저 찾고 넣는다 [소스: `AttachmentService.upload`]. 오류의 자리에 기대는 코드가 있는지 구현 탭이 `SqlStates` 쓰는 곳을 본다 |

## 6. 올린 글이 사라졌다

이미지를 여럿 넣은 긴 글을 저장했는데 400이 났다(임시 이미지 하나가 만료됐다).

| 까닭이 될 것 | 막는 것 |
|---|---|
| 실패하면 편집기가 비워진다 | S5-AC-58: 글은 남는다(앞 묶음의 "실패해도 입력을 지우지 않는다"와 같다) |
| 어느 이미지인지 모른다 | **받아들인다.** 거절은 어느 ID인지 말하지 않는다(1절). 화면은 "이미지를 다시 올려야 한다"만 말한다. 24시간 넘게 쓰는 글은 드물다 |
| 본문에서 지운 이미지의 ID를 보내 만료로 거절된다 | S5-AC-57: 본문에 남은 것만 보낸다 |

## 7. 받아들이는 것

- 악성 파일 검사는 하지 않는다(위협 모델의 받아들인 위험 그대로).
- 큰 픽셀 수의 이미지가 읽는 사람의 브라우저를 느리게 할 수 있다. 서버는 이미지를 풀지 않는다. 10MB 상한과 `loading="lazy"`가 줄인다.
- 본문에서 뺀 이미지는 사람이 지울 때까지 남는다(`acceptance.md` 5절 7).
- 동시 올리기로 임시 이미지 한도를 한두 개 넘을 수 있다.
