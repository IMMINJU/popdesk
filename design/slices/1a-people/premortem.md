# 1a 묶음 사전 부검

> 1a 묶음(사람과 고객사)을 내고 석 달 뒤 일이 틀어졌다고 가정하고, 어떻게 틀어졌을지와 막을 장치를 적는다. 권한, 고객사 경계, 개인정보, 마이그레이션을 건드려서 전체 경로다(`process.md`).
> 표시: [소스]는 레포의 코드나 마이그레이션에서 본 것, [추론]은 확인하지 않은 판단이다. 직접 돌려 본 것은 아직 없다. "먼저 확인할 것"은 계약 단계(C-4) 앞에서 작은 실험으로 본다.
> 장치는 `acceptance.md` 3.13절(S1A-AC-81~90)과 `design.md`에 옮겼다. 묶음이 끝나면 이 파일은 `design/archive/1a-people/`로 간다.
> 상태: 초안. 사용자 확인을 기다린다.

## 1. 관리자 둘이 서로를 내려 관리자가 하나도 남지 않았다

| 항목 | 내용 |
|---|---|
| 장면 | 관리자 A와 B가 같은 때 서로를 상담원으로 바꿨다. 둘 다 성공했고 설치에 관리자가 없어졌다. 복구 명령은 관리자 계정의 비밀번호만 바꾸므로 쓸 수 없었고, DB를 손으로 고쳐야 했다 |
| 원인 | "자기 자신은 못 바꾼다"(ACCT-3)는 한 사람만 본다. 두 요청이 저마다 "다른 관리자가 하나 있다"를 읽고 지나간다 [추론]. 복구 명령이 `ADMIN`만 받는 것은 S0-AC-97이 정했다 [소스] |
| 막는 법 | 정지와 역할 변경은 한 트랜잭션에서 관리자 행들을 ID 순서로 잠근 뒤 `ACTIVE` 관리자 수를 세고, 0이 되면 400 `LAST_ADMIN`. 잠금은 `FOR NO KEY UPDATE`(첫 묶음 잠금 규칙) |
| 확인 테스트 | 관리자 둘이 서로를 같은 때 내리기와 정지하기를 되풀이: 늘 하나는 400이고 `ACTIVE` 관리자가 하나 이상 남는다(S1A-AC-81) |
| 옮길 곳 | S1A-AC-81, `architecture.md` 동시성 절 |

## 2. 비밀번호 찾기가 계정을 넘겨주는 길이 됐다

| 항목 | 내용 |
|---|---|
| 장면 | (가) 공격자가 `Host` 머리글을 자기 주소로 바꿔 비밀번호 찾기를 요청했고, 피해자에게 간 메일의 링크가 공격자 주소였다. 눌러서 토큰이 넘어갔다. (나) 정지된 직원이 정지 전에 받아 둔 재설정 링크로 비밀번호를 바꿨다. (다) 누군가 남의 이메일로 찾기를 되풀이해 그 사람의 세션이 계속 끊겼다 |
| 원인 | (가) 링크를 요청의 호스트로 만들면 생긴다. 초대 링크는 설정한 공개 주소로 만든다(`PublicAddress`) [소스]. 재설정도 같은 곳을 쓰는지는 새로 짜는 코드에 달렸다. (나) 토큰을 쓸 때 계정 상태를 다시 보지 않으면 생긴다 [추론]. (다) 찾기 요청이 세션이나 비밀번호를 건드리면 생긴다 [추론] |
| 막는 법 | 링크는 `PublicAddress`로만 만든다. 토큰을 쓸 때 계정이 `ACTIVE`이고 그 앱의 계정인지 다시 본다. 초대 토큰과 재설정 토큰은 다른 테이블에 두어 섞어 쓸 수 없게 한다. 찾기 요청은 토큰과 메일만 만들고 계정은 건드리지 않는다. 토큰 비교는 해시로 찾는다(초대와 같다) |
| 확인 테스트 | `Host`·`X-Forwarded-Host`를 바꾼 요청의 메일 링크가 설정한 주소다(S1A-AC-82). 토큰 종류를 바꿔 내면 400(S1A-AC-83). 링크를 받고 정지된 계정은 400(S1A-AC-84). 찾기를 열 번 요청해도 그 계정의 세션으로 보낸 요청이 200이다(S1A-AC-85) |
| 옮길 곳 | S1A-AC-82~85, `threat-model.md`(새 줄: 재설정 링크 가로채기) |
| 남은 것 | 메일함을 가진 사람은 계정을 가진 것과 같다. 이 묶음은 그것을 막지 않는다(2단계 인증은 범위 밖). `docs/operate/`에 적는다 |

## 3. 정지한 사람이 한동안 계속 썼다

| 항목 | 내용 |
|---|---|
| 장면 | 관리자가 퇴사자를 정지했는데, 열려 있던 탭에서 몇 분 동안 문의를 계속 읽었다 |
| 원인 | 세션 지우기와 처리 중인 요청이 겹치면, 요청이 끝날 때 Spring Session이 세션 속성을 다시 쓴다. 지워진 세션 ID로 행이 다시 생기는지는 확인하지 않았다 [추론]. 첫 묶음의 `SessionFilter`는 요청마다 계정이 `ACTIVE`인지 본다(62줄) [소스]. 그 줄은 지금 테스트가 없다(서버 PIT) |
| 막는 법 | 두 겹으로 막는다. 정지·역할 변경·비밀번호 변경 때 그 계정의 세션 행을 지운다. 그리고 `SessionFilter`가 요청마다 계정 상태와 역할을 DB에서 다시 읽는 것을 기준으로 삼는다(세션이 다시 생겨도 401) |
| 확인 테스트 | 정지한 뒤 같은 쿠키로 보낸 요청이 401(S1A-AC-01). 느린 요청이 도는 중에 정지하고, 그 요청이 끝난 뒤 같은 쿠키로 다시 보내도 401(S1A-AC-86). 역할을 바꾼 뒤 옛 세션으로 관리자 API를 부르면 401 |
| 먼저 확인할 것 | Spring Session JDBC가 지워진 세션을 요청 끝에 다시 저장하는지 |
| 옮길 곳 | S1A-AC-01·03·86 |

## 4. 프로필 사진이 서버를 죽이거나 남의 정보를 흘렸다

| 항목 | 내용 |
|---|---|
| 장면 | (가) 누군가 200KB짜리 PNG를 올렸는데 풀면 2만×2만 픽셀이었고 앱이 메모리 부족으로 죽었다. (나) 정상 사진 다섯 장을 같은 때 올리자 죽었다. (다) A사 고객이 계정 번호를 바꿔 가며 사진 주소를 불러 B사에 누가 있는지 알아냈다. (라) 사진 주소를 직접 열자 브라우저가 그것을 HTML로 읽었다 |
| 원인 | (가)(나) 그림을 통째로 풀면 픽셀당 4바이트를 쓴다. 1,200만 픽셀 휴대폰 사진 한 장이 48MB이고 힙은 384MB다 [추론: 산수]. (다) 없는 계정과 볼 수 없는 계정의 응답이 다르면 생긴다. (라) 올린 내용을 그대로 내보내면 생긴다 |
| 막는 법 | 머리글만 읽어 가로×세로를 먼저 본다(2,500만 픽셀 초과는 400). 풀 때는 줄여서 읽는다(`ImageReadParam`의 건너뛰며 읽기로 긴 변이 1,024px 안팎이 되게). 같은 때 푸는 수를 2로 막고 넘으면 503과 `Retry-After`. 저장하는 것은 서버가 다시 만든 PNG뿐이고 응답 `Content-Type`은 `image/png` 고정, `nosniff`, `Cache-Control: private`. 사진 조회는 이름 조회와 같은 범위 검사를 지나고, 범위 밖과 없음은 같은 404 |
| 확인 테스트 | 2만×2만 PNG는 400이고 그 요청 뒤 힙이 늘지 않는다(S1A-AC-23). 실제 이미지에서 2MB 사진 열 장 동시 올리기를 `-Xmx384m`으로(S1A-AC-88). 저장된 바이트에 EXIF 표지가 없다(S1A-AC-21). 경계 부정 테스트에 사진 조회를 넣는다(S1A-AC-25~27, 76). 응답 머리글(S1A-AC-87) |
| 먼저 확인할 것 | WebP를 푸는 라이브러리가 머리글만 읽기와 줄여 읽기를 받는지. 안 받으면 WebP는 픽셀 상한을 낮춘다 |
| 옮길 곳 | S1A-AC-20~28·87·88, `design.md` 2절, 새 결정 D-53 |

## 5. 구성원 검색이 느려지거나 엉뚱한 사람을 찾았다

| 항목 | 내용 |
|---|---|
| 장면 | 검색 칸에 `%`를 넣자 전체가 나왔고, `_`가 든 이메일을 찾으니 다른 사람이 섞여 나왔다 |
| 원인 | 검색어를 `LIKE` 패턴에 그대로 넣으면 `%`와 `_`가 와일드카드로 읽힌다 [추론] |
| 막는 법 | 검색어의 `%`, `_`, `\`를 이스케이프한다. 값은 늘 바인드 변수로 넘긴다. 계정 수가 수천을 넘지 않는 설치를 가정해 색인은 두지 않는다(3번 묶음의 검색에서 `pg_trgm`을 붙일 때 다시 본다) |
| 확인 테스트 | 이름에 `%`와 `_`가 든 계정을 만들어 그 글자로 찾으면 그 계정만 나온다(S1A-AC-89) |
| 옮길 곳 | S1A-AC-89 |

## 6. v0.1.0에서 올린 설치에서 "정지 풀기"가 막혔다

| 항목 | 내용 |
|---|---|
| 장면 | v0.1.0을 쓰던 설치를 올린 뒤, 이미 쓰던 계정을 정지했다가 풀려니 "수락한 적 없는 계정"이라며 400이 났다 |
| 원인 | "수락한 적 있음"을 새 칸으로 두면 이미 있던 계정의 값이 비어 있다 [추론]. 지금 `account`에는 그 칸이 없고 `password_hash`가 수락 전에는 null이다 [소스] |
| 막는 법 | 새 칸을 두지 않고 `password_hash`가 있는지로 판정한다. 관리자의 비밀번호 초기화(S1A-AC-36)는 해시를 지우지 않고 못 쓰는 값으로 바꾼다(null로 두면 수락 전과 구별되지 않는다) |
| 확인 테스트 | v0.1.0 견본 덤프를 올린 뒤 이미 있던 `ACTIVE` 계정을 정지하고 풀기가 된다(S1A-AC-90, S1A-AC-80). 비밀번호를 초기화한 계정을 정지하고 풀기가 된다 |
| 옮길 곳 | S1A-AC-35·36·90, `design.md` 1절 |

## 7. 살펴봤지만 장치를 더하지 않은 것

- 소속에서 빠진 고객에게 가는 메일: 보낼 때 받는 사람이 지금 볼 수 있는지 다시 본다(S0-AC-69). 자기가 올린 문의는 계속 보므로 메일도 간다(권한 모델). 그대로 둔다.
- 로그인할 때 CSRF 토큰이 바뀌어 다른 탭의 요청이 403이 되는 것: 화면이 한 번 다시 보낸다(S1A-AC-57).
- 비밀번호 찾기의 응답 시간 차이: 계정이 있으면 DB 쓰기가 하나 더 있어 몇 ms 다르다. 로그인에서 받아들인 것과 같은 크기라 그대로 둔다(첫 묶음 verify 6절).
- 고객사를 보관한 뒤 그 고객사만 맡던 상담원: 문의는 계속 보인다(PROJ-3은 이미 있는 문의를 그대로 다룬다). 그대로 둔다.
