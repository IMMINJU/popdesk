## 1. 데이터 (마이그레이션 V5)

| 바뀌는 것 | 내용 | 까닭 |
|---|---|---|
| 새 테이블 `password_reset` | 계정 ID, 토큰 해시(유니크), 만든 시각, 만료 시각, 쓴 시각, `tenant_id` | 초대 토큰과 섞이지 않게 테이블을 나눈다(S1A 부검 2). 계정마다 살아 있는 행은 하나다(새로 만들면 앞 행을 지운다) |

| `account` | 비밀번호 바꾼 시각 칸 하나를 더한다(null 허용, 이미 있는 행은 null). 수락했는지는 새 칸 없이 `password_hash`가 있는지로 본다 | 시각 칸은 비밀번호 변경과 겹친 로그인의 세션을 막는 데 쓴다(3절). 수락 여부는 v0.1.0에서 올라온 계정도 값이 맞는다(S1A 부검 6) |
| `invitation` | 취소한 시각 칸을 더한다 | 취소된 초대를 목록에 보이고(S1A-AC-42), 정지된 계정과 구별한다 |
| `company` | 바뀌지 않는다. `status`와 세 값의 제약이 이미 있다 | 첫 묶음 V2 |

- 마이그레이션은 칸과 테이블을 더하기만 한다. 이미 있는 행을 고치지 않는다.
- 관리자의 비밀번호 초기화는 `password_hash`를 null로 두지 않고, 어떤 비밀번호와도 맞지 않는 고정 표지 값으로 바꾼다.

## 2. 프로필 사진

- 받는 형식은 PNG, JPEG, WebP다. 형식은 파일 앞머리 바이트로 가린다.
- 차례: ① 요청 크기 2MB 확인 ② 머리글에서 가로×세로 읽기(PNG·JPEG는 2,500만, WebP는 1,200만 픽셀 초과는 400) ③ 줄여 읽기로 풀기 ④ 긴 변 256px로 줄이기(비율 유지, 자르지 않음) ⑤ PNG로 다시 쓰기 ⑥ 저장.
- 같은 때 푸는 수는 2다. 넘으면 503과 `Retry-After`(첨부의 동시 수 상한과 같은 꼴).
- 움직이는 그림은 첫 장만 쓴다. EXIF의 회전 값은 적용한 뒤 버린다(세로로 찍은 사진이 눕지 않게). JDK와 라이브러리의 메타데이터는 회전 값을 주지 않으므로 JPEG는 APP1, WebP는 `EXIF` 청크에서 274번 태그를 직접 읽는다.
- WebP의 상한이 낮은 까닭: 줄여 읽기가 PNG·JPEG에서는 힙을 16MB 아래로 줄이지만, WebP는 알파가 있거나 무손실이면 다 푼 뒤에 줄인다. 1,200만 픽셀 알파 WebP 한 장에 힙 72MB, 2,500만이면 128~160MB가 들었다(실험). 라이브러리의 자체 크기 검사는 2MB 파일에서는 막지 못하므로 우리 머리글 검사가 먼저 돈다.
- WebP 리더는 `ImageIO` 검색에 기대지 않고 `WebPImageReaderSpi`로 직접 만든다(실행 jar 안에서 플러그인이 잡히는지는 확인하지 못했다).
- WebP는 푸는 데 0.7~2초가 걸려(PNG·JPEG는 0.25초) 동시 수 2에서 503이 더 자주 날 수 있다.
- 응답은 `image/png` 고정이다. 사람을 담는 응답은 사진을 바꾼 시각(`photoUpdatedAt`, 없으면 `null`)을 준다. 화면은 그 시각을 주소에 붙여 받고, 서버는 `private, no-cache`와 `ETag`로 답해 브라우저가 매번 권한을 다시 확인받는다(바뀌지 않았으면 304).
- 포털의 사람 타입에도 `photoUpdatedAt` 칸은 있다(D-44: 칸을 빼지 않는다). 상담 쪽 사람에서는 늘 `null`이다(ANON-1).

## 3. 세션과 비밀번호

- 계정의 세션을 모두 지우는 일은 한 곳(`Sessions`)에 둔다. 첫 묶음이 세션에 적어 둔 계정 ID 색인으로 찾는다(지금은 읽는 곳이 없다).
- `SessionFilter`가 요청마다 계정의 상태와 역할을 DB에서 읽는 것을 그대로 둔다. 세션 지우기가 늦어도 이 검사가 막는다(S1A 부검 3).
- 본인의 비밀번호 변경 실패 횟수는 로그인 실패 횟수(`failed_sign_ins`, `locked_until`)를 같이 쓴다. 다섯 번 틀리면 그 계정의 로그인도 15분 잠긴다.
- 재설정 링크는 초대 링크와 같은 곳(`PublicAddress`)에서 만든다.
- 실험으로 본 것: 처리 중에 지운 세션은 요청 끝에 다시 생기지 않는다(Spring Session JDBC 4.1.1, 일곱 경우). 역할도 요청마다 DB에서 읽으므로, 세션 지우기가 빠진 세션으로 관리자 API를 부르면 403이다.
- 남은 틈: 비밀번호를 바꾸는 순간에 옛 비밀번호로 보낸 로그인이 처리 중이면, 그 로그인의 새 세션이 지우기 뒤에 저장될 수 있다(소스로만 봄). 계정은 `ACTIVE`라 `SessionFilter`가 막지 못한다. 막는 법: `account`에 비밀번호 바꾼 시각 칸을 두고, `SessionFilter`가 그 시각보다 먼저 로그인한 세션을 세지 않는다(2026-10-11 사람이 정함). 비밀번호를 바꾼 본인의 지금 세션은 새로 내면서 로그인 시각도 새로 적는다(S1A-AC-02).
- 마지막 관리자 검사(S1A-AC-81)는 정지와 역할 변경이 같은 메서드 하나를 거치게 한다.

## 4. 새 결정 D-53 (2026-10-11 사람이 정함)

| | |
|---|---|
| 결정 | 프로필 사진의 WebP는 순수 Java 라이브러리 TwelveMonkeys `imageio-webp`로 푼다. 저장은 형식과 관계없이 PNG로 한다 |
| 이유 | JDK는 PNG와 JPEG만 읽는다. D-52가 WebP를 받기로 했다. 이 라이브러리는 읽기만 하고 네이티브 코드가 없어 이미지와 SBOM이 단순하다(BSD-3). JDK는 WebP를 쓰지 못하므로 저장은 PNG로 통일한다. 256px PNG는 수십 KB다 |
| 버린 대안 | WebP를 받지 않기(D-52를 고쳐야 한다. 휴대폰과 메신저에서 받은 그림이 WebP인 일이 흔하다) / libwebp 네이티브 바인딩(amd64·arm64 둘 다 맞춰야 하고, 네이티브 디코더의 취약점이 앱 프로세스에 그대로 온다) / JPEG로 저장(투명한 그림의 배경이 검게 된다) |
| 걸리는 것 | 남이 올린 그림을 푸는 코드가 의존성으로 는다(jar 여섯, 모두 같은 프로젝트, 합쳐 585KB). 보안 검사(trivy)가 이 라이브러리를 본다. 머리글만 읽기와 줄여 읽기가 되는지는 계약 단계 앞에서 실험으로 확인하고, 안 되면 이 결정을 다시 연다 |

## 5. 쓸 컴포넌트와 토큰

- 새 공용 컴포넌트: 사진 올리기(`PhotoField`: 사진이나 머리글자, 올리기·바꾸기·지우기 버튼, 오류 자리). 자르기 화면은 두지 않는다.
- 고치는 공용 컴포넌트: `Avatar`(사진 주소를 받으면 그림, 못 받으면 머리글자. 지금은 자리만 있다), `StatusBadge`(초대 취소됨, 고객사의 중지·보관).
- 새 토큰은 없다. 색과 모양은 `design/tokens.md`대로다.

## 5-1. 계약 단계(C-4)에서 정한 것

- 화면 경로: 비밀번호 찾기 `/forgot-password`, 재설정 `/reset-password`(토큰은 `#token=` 뒤), 내 정보 `/me`. 두 앱이 같은 이름을 쓴다. 서버는 재설정 링크를 `<앱 주소>/reset-password#token=…`으로 만든다.
- 로그인 뒤 돌아갈 주소(`next`)로 `/forgot-password`, `/reset-password`는 받지 않는다(`/login`, `/invite`와 같게). C-5에서 테스트로 정한다.
- 상태 배지: 고객사 말(사용 중, 중지, 보관)은 새 kind `company`에 둔다. 첫 묶음의 kind `project`("멈춤")는 C-5에서 잠긴 테스트를 `company`로 옮긴 뒤 C-9에서 지운다. "초대 취소됨"은 화면 쪽 값이고(API는 `cancelled`로 준다) 끝난 상태처럼 중립 색의 속 빈 점으로 보인다.
- `PhotoField`의 props: 이름, 사진 주소, 올리는 중, 오류, 안내 문구, `accept`, 올리기·지우기 콜백, 버튼 글자 셋. 껍데기는 콜백을 잇지 않았다.
- 문구 사전의 키는 점으로 이은 납작한 꼴이다(`passwordForgot.title`).
- 사진 응답의 404와 401은 다른 응답처럼 `no-store`다. `private, no-cache`와 `ETag`는 200과 304에만 붙는다.
- `PATCH /api/console/companies/{code}`와 `PUT …/status`는 보안 설정의 관리자 전용 목록에 아직 없다. C-9에서 넣는다. 이미 목록에 있는 경로의 "상담원은 403" 테스트는 구현 전에도 통과하므로 C-6에서 `red-allow.txt`에 올린다.

## 6. 일하는 차례

1. 계약 앞 실험: Spring Session의 지워진 세션 다시 저장(부검 3), WebP 라이브러리(부검 4). 작은 탭 하나, 30분 안쪽.
2. C-4 계약: 컨트롤러 껍데기와 계약 파일, 클라이언트, props·story 껍데기.
3. C-5 테스트: 수용 기준 절 단위로 세션을 나눈다. 서버 셋(3.1~3.4, 3.5~3.8, 3.10~3.13), 웹 하나.
4. 그 뒤는 `process.md` C-6~C-11.

`ci.yml`에 적어 둔 운영 코드 정적 검사와 중복 검사는 C-5 앞에 따로 붙인다(조사 보고 `popdesk-b1-report.md`의 추천, 새 결정 없이 되는 것).
