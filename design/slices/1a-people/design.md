# 1a 묶음 설계

> 수용 기준(`acceptance.md`)을 어떻게 만들지 가운데, 나중에 바꾸기 어려운 것만 적는다. API 경로와 응답 모양은 계약 단계(C-4)의 컨트롤러 껍데기가 정한다.
> 묶음이 끝나면 남길 것은 `spec/architecture.md`와 `adr.md`로 옮기고 이 파일은 지운다.
> 상태: 초안. 4절의 새 결정(D-53)은 사용자 확인을 기다린다.

## 1. 데이터 (마이그레이션 V5)

| 바뀌는 것 | 내용 | 까닭 |
|---|---|---|
| 새 테이블 `password_reset` | 계정 ID, 토큰 해시(유니크), 만든 시각, 만료 시각, 쓴 시각, `tenant_id` | 초대 토큰과 섞이지 않게 테이블을 나눈다(S1A 부검 2). 계정마다 살아 있는 행은 하나다(새로 만들면 앞 행을 지운다) |
| 새 테이블 `account_photo` | 계정 ID(기본 키), PNG 바이트, 크기, 바꾼 시각, `tenant_id` | 256px PNG는 수십 KB라 `bytea` 한 칸에 둔다. 첨부 저장소(db·disk·s3)를 타지 않는다. 계정 행과 나눠 계정 조회가 사진을 끌고 오지 않게 한다 |
| `account` | 칸을 더하지 않는다. 수락했는지는 `password_hash`가 있는지로 본다 | v0.1.0에서 올라온 계정도 값이 맞는다(S1A 부검 6) |
| `invitation` | 취소한 시각 칸을 더한다 | 취소된 초대를 목록에 보이고(S1A-AC-42), 정지된 계정과 구별한다 |
| `company` | 바뀌지 않는다. `status`와 세 값의 제약이 이미 있다 | 첫 묶음 V2 |
| 정리 작업 | 쓰거나 만료된 `password_reset` 행을 지우는 작업 하나를 더한다 | S1A-AC-15 |

- 마이그레이션은 칸과 테이블을 더하기만 한다. 이미 있는 행을 고치지 않는다.
- 관리자의 비밀번호 초기화는 `password_hash`를 null로 두지 않고, 어떤 비밀번호와도 맞지 않는 고정 표지 값으로 바꾼다.

## 2. 프로필 사진

- 받는 형식은 PNG, JPEG, WebP다. 형식은 파일 앞머리 바이트로 가린다.
- 차례: ① 요청 크기 2MB 확인 ② 머리글에서 가로×세로 읽기(2,500만 픽셀 초과는 400) ③ 줄여 읽기로 풀기 ④ 긴 변 256px로 줄이기(비율 유지, 자르지 않음) ⑤ PNG로 다시 쓰기 ⑥ 저장.
- 같은 때 푸는 수는 2다. 넘으면 503과 `Retry-After`(첨부의 동시 수 상한과 같은 꼴).
- 움직이는 그림은 첫 장만 쓴다. EXIF의 회전 값은 적용한 뒤 버린다(세로로 찍은 사진이 눕지 않게).
- 응답은 `image/png` 고정이다. 화면은 사진이 바뀌면 주소에 바꾼 시각을 붙여 다시 받는다.
- 포털 응답에는 상담 쪽 사람의 사진 표시 칸 자체를 두지 않는다(ANON-1). 포털과 콘솔의 응답 타입을 나눈 첫 묶음의 꼴(D-43)을 따른다.

## 3. 세션과 비밀번호

- 계정의 세션을 모두 지우는 일은 한 곳(`Sessions`)에 둔다. 첫 묶음이 세션에 적어 둔 계정 ID 색인으로 찾는다(지금은 읽는 곳이 없다).
- `SessionFilter`가 요청마다 계정의 상태와 역할을 DB에서 읽는 것을 그대로 둔다. 세션 지우기가 늦어도 이 검사가 막는다(S1A 부검 3).
- 본인의 비밀번호 변경 실패 횟수는 로그인 실패 횟수(`failed_sign_ins`, `locked_until`)를 같이 쓴다. 다섯 번 틀리면 그 계정의 로그인도 15분 잠긴다.
- 재설정 링크는 초대 링크와 같은 곳(`PublicAddress`)에서 만든다.
- 마지막 관리자 검사(S1A-AC-81)는 정지와 역할 변경이 같은 메서드 하나를 거치게 한다.

## 4. 새 결정이 하나 필요하다 (D-53, 확인 대기)

| | |
|---|---|
| 결정 | 프로필 사진의 WebP는 순수 Java 라이브러리 TwelveMonkeys `imageio-webp`로 푼다. 저장은 형식과 관계없이 PNG로 한다 |
| 이유 | JDK는 PNG와 JPEG만 읽는다. D-52가 WebP를 받기로 했다. 이 라이브러리는 읽기만 하고 네이티브 코드가 없어 이미지와 SBOM이 단순하다(BSD-3). JDK는 WebP를 쓰지 못하므로 저장은 PNG로 통일한다. 256px PNG는 수십 KB다 |
| 버린 대안 | WebP를 받지 않기(D-52를 고쳐야 한다. 휴대폰과 메신저에서 받은 그림이 WebP인 일이 흔하다) / libwebp 네이티브 바인딩(amd64·arm64 둘 다 맞춰야 하고, 네이티브 디코더의 취약점이 앱 프로세스에 그대로 온다) / JPEG로 저장(투명한 그림의 배경이 검게 된다) |
| 걸리는 것 | 남이 올린 그림을 푸는 코드가 의존성으로 하나 더 는다. 보안 검사(trivy)가 이 라이브러리를 본다. 머리글만 읽기와 줄여 읽기가 되는지는 계약 단계 앞에서 실험으로 확인하고, 안 되면 이 결정을 다시 연다 |

## 5. 쓸 컴포넌트와 토큰

- 새 공용 컴포넌트: 사진 올리기(`PhotoField`: 사진이나 머리글자, 올리기·바꾸기·지우기 버튼, 오류 자리). 자르기 화면은 두지 않는다.
- 고치는 공용 컴포넌트: `Avatar`(사진 주소를 받으면 그림, 못 받으면 머리글자. 지금은 자리만 있다), `StatusBadge`(초대 취소됨, 고객사의 중지·보관).
- 새 토큰은 없다. 색과 모양은 `design/tokens.md`대로다.

## 6. 일하는 차례

1. 계약 앞 실험: Spring Session의 지워진 세션 다시 저장(부검 3), WebP 라이브러리(부검 4). 작은 탭 하나, 30분 안쪽.
2. C-4 계약: 컨트롤러 껍데기와 계약 파일, 클라이언트, props·story 껍데기.
3. C-5 테스트: 수용 기준 절 단위로 세션을 나눈다. 서버 셋(3.1~3.4, 3.5~3.8, 3.10~3.13), 웹 하나.
4. 그 뒤는 `process.md` C-6~C-11.

`ci.yml`에 적어 둔 운영 코드 정적 검사와 중복 검사는 C-5 앞에 따로 붙인다(조사 보고 `popdesk-b1-report.md`의 추천, 새 결정 없이 되는 것).
