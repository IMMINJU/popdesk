# 2번 묶음 사전 부검

> 2번 묶음(고객사 담당자)을 내고 석 달 뒤 일이 틀어졌다고 가정하고, 어떻게 틀어졌을지와 막을 장치를 적는다. 권한과 고객사 경계, 개인정보(계정이 있는지), 마이그레이션을 건드려서 전체 경로다(`process.md`).
> 표시: [소스]는 레포의 코드나 마이그레이션에서 본 것, [추론]은 확인하지 않은 판단이다.
> 장치는 `acceptance.md`와 `design.md`에 옮겼다. 묶음이 끝나면 이 파일은 `design/archive/2-manager/`로 간다.
> 상태: **메인이 정함, 사용자 확인 전**(2026-10-12).

## 1. 담당자가 초대 기능으로 다른 고객사의 고객 명단을 맞춰 봤다

| 항목 | 내용 |
|---|---|
| 장면 | 고객사 A의 담당자가 경쟁사 B 직원들의 이메일을 하나씩 초대해 보고, 응답이나 목록이 다른 것으로 누가 popdesk 계정이 있는지 알아냈다. B가 이 지원팀의 고객이라는 사실이 새 나갔다 |
| 원인 | 두 갈래(새 이메일, 있는 이메일)가 갈리는 곳이 여럿이다: 응답 코드와 본문, 목록의 행(ID의 꼴, 이름, 상태, 순서), 다시 보내기와 빼기의 답, 한도에 걸리는 때, 응답 시간 |
| 막는 법 | 응답은 본문 없이 같다(S2-AC-15, 27, 30). 행은 계정 ID가 아닌 난수 행 ID로 가리키고 두 종류를 한 SQL로 읽어 이메일로 줄 세운다(`design.md` 0절 2, 3절). 요청 행은 담당자가 넣은 이름과 `INVITED`만 보인다(S2-AC-16). 한도와 보관 검사는 계정을 찾기 전에 한다(`design.md` 3절). 상담 쪽 계정의 이메일도 같은 길로 간다(`acceptance.md` 5절 4) |
| 남는 것 | 응답 시간. 같게 만들지 않는다. 두 갈래 모두 INSERT 두세 번이고 메일은 대기에 넣기만 해서 차이가 작다고 본다 [추론]. 분당 20번과 고객사마다 걸린 것 100개의 한도가 통계로 가르는 것을 어렵게 한다. 담당자가 한 초대는 모두 감사 로그에 남아 관리자가 뒤에 볼 수 있다 |
| 남는 것 | 수락 전인데 다른 고객사에도 소속인 구성원에게 다시 보내기를 하면 400이다(S2-AC-31). 같은 code를 수락한 사람, 정지된 사람에게도 주지만, 목록에서 `INVITED`로 보이는 행이 400이면 "다른 고객사에도 있다"는 뜻이 된다. 규칙(MGR-4)이 받아들인 것이다. 이 경우는 그 사람이 이미 이 고객사의 소속이라 관리자가 두 고객사에 함께 넣은 사람이다 |
| 확인 테스트 | 새 이메일과 있는 이메일(고객, 상담원, 정지된 계정, 수락 전 계정)의 초대 응답을 견준다. 그 뒤 목록의 두 행을 칸마다 견준다. 요청 행에 다시 보내기와 빼기를 해서 새 계정의 행과 답이 같은지 본다. 숨긴 E2E가 같은 것을 처음부터 끝까지 한 번 한다 |
| 옮길 곳 | S2-AC-10, 14~17, 27, 30, 31, `acceptance.md` 4절 |

## 2. 풀린 담당자가 계속 사람을 뺐다

| 항목 | 내용 |
|---|---|
| 장면 | 관리자가 퇴사 예정인 담당자의 지정을 풀었다. 그 사람은 열어 둔 화면에서 동료 여럿을 소속에서 뺐다 |
| 원인 | 담당자 여부를 세션이나 화면이 쥐고 있거나, 확인과 쓰기 사이에 지정이 풀린다 |
| 막는 법 | 요청마다 DB에서 읽는다. 쓰기는 같은 트랜잭션에서 자기 소속 행을 잠그고 다시 본다(`design.md` 2절). 확인은 함수 하나에 두고 구성원 엔드포인트가 모두 지난다 |
| 확인 테스트 | 지정을 푼 직후 같은 세션으로 목록, 초대, 빼기, 다시 보내기를 불러 모두 403이다(S2-AC-11). 소속에서 뺀 직후에는 404다 |
| 옮길 곳 | S2-AC-11, `design.md` 2절 |

## 3. 고객사 A의 담당자가 B의 행 ID로 B의 사람을 뺐다

| 항목 | 내용 |
|---|---|
| 장면 | 두 고객사에 소속이고 A에서만 담당자인 사람이, 경로의 고객사는 A로 두고 행 ID만 B의 것으로 바꿔 B의 구성원을 뺐다 |
| 원인 | 권한은 경로의 고객사로 보고, 지울 행은 행 ID만으로 찾는다 |
| 막는 법 | 행을 찾는 조건에 경로의 고객사를 넣는다. 다른 고객사의 행 ID는 404다(S2-AC-32). 행 ID는 난수라 맞춰 볼 수도 없다 |
| 확인 테스트 | A의 담당자가 B의 행 ID로 빼기와 다시 보내기를 하면 404이고 B의 소속은 그대로다. B의 소속이기만 한(담당자가 아닌) 사람이 B의 목록을 부르면 403이다 |
| 옮길 곳 | S2-AC-09, 32, 50 |

## 4. 담당자가 초대 메일을 아무에게나 뿌렸다

| 항목 | 내용 |
|---|---|
| 장면 | 담당자 계정이 털렸다. 공격자가 이 설치의 메일 서버로 초대 메일 수만 통을 바깥 주소로 보냈고, 지원팀의 발신 도메인이 차단 목록에 올랐다 |
| 원인 | 담당자는 고객인데 아무 주소로나 메일을 내보낼 수 있다. 분당 횟수만 막으면 하루 28,800통이다 |
| 막는 법 | 고객사마다 수락 전 소속과 걸린 요청을 합쳐 100개까지다(S2-AC-21). 다시 보내기도 분당 20번에 든다(S2-AC-20). 초대 메일의 글은 담당자가 정하지 못한다: 이름 칸만 들어가고 [소스: `MailText.invitation`], 이름은 관리자 초대와 같은 입력 규칙을 지나고(S2-AC-19), 담당자 초대에서는 줄바꿈 같은 제어 문자도 막는다(S2-AC-53). 관리자 초대는 이름의 줄바꿈을 받는다 [소스: 테스트 탭이 돌려 봄] |
| 남는 것 | 100명을 초대하고 빼고 다시 100명을 초대하는 것. 분당 20번이 막는 것이 전부다. 뺀 계정은 `SUSPENDED`로 남아 관리자의 구성원 목록에 쌓인다. 담당자가 한 일은 감사 로그에 남는다. 더 막아야 하면 뒤에 하루 한도를 DB에 세서 건다. 이름 칸 50자 안에 주소를 적어 보내는 것도 남는다 |
| 확인 테스트 | 101번째 초대는 409다. 다시 보내기 21번째는 429다. 이름에 줄바꿈을 넣은 초대는 400이다 |
| 옮길 곳 | S2-AC-19~21, 53 |

## 5. 요청이 승인됐는데 그 사람은 로그인하지 못했다

| 항목 | 내용 |
|---|---|
| 장면 | 담당자가 뺀 수락 전 계정의 이메일을 다시 초대했다. 관리자가 요청을 승인했고 담당자의 목록에는 "정지"로 나왔다. 초대 메일은 다시 가지 않았고 아무도 까닭을 몰랐다 |
| 원인 | 뺄 때 초대가 취소되어 계정이 `SUSPENDED`다. 승인은 소속만 만들고 초대를 되살리지 않는다(`acceptance.md` 5절 9) |
| 막는 법 | 관리자의 소속 요청 구역이 대상 계정의 상태를 보이고, 초대가 취소된 수락 전 계정이면 "승인한 뒤 구성원 목록에서 초대를 다시 보내세요"를 보인다(`screens.md` C-9). `docs/use/`의 담당자 안내에 적는다 |
| 확인 테스트 | 화면 테스트: 그런 계정의 요청 줄에 안내가 보인다. 서버 테스트: 승인 뒤 계정의 상태와 초대가 그대로다 |
| 옮길 곳 | S2-AC-34, `screens.md` |

## 6. 올린 뒤 구성원 화면이 비었다

| 항목 | 내용 |
|---|---|
| 장면 | 0.2.0에서 올린 설치에서 V8이 실패하거나, 있던 소속 행이 모두 같은 행 ID를 받아 유니크 제약에서 멈췄다 |
| 원인 | `ADD COLUMN … DEFAULT 함수`가 행마다 따로 계산되지 않으면 값이 같다 [추론: PostgreSQL은 변하는 함수의 기본값을 행마다 계산하지만 확인하지 않았다]. 앱의 DB 사용자에게 그 함수를 부를 권한이 없을 수 있다 |
| 막는 법 | 계약 앞에 이미지의 PostgreSQL에서 해 본다(`design.md` 7절 1). 업그레이드 테스트가 0.1.0과 0.2.0 견본을 올려 행 ID가 모두 다르고 담당자가 없는지 본다(S2-AC-51) |
| 확인 테스트 | S2-AC-51. 견본 생성기가 새 표를 채운다(S2-AC-52) |
| 옮길 곳 | S2-AC-51, 52, `design.md` 1절 |

## 7. 관리자가 요청이 온 줄 몰랐다

| 항목 | 내용 |
|---|---|
| 장면 | 담당자가 초대한 사람이 몇 주째 "수락 전"이다. 이미 다른 고객사에 계정이 있던 사람이라 소속 요청이 걸려 있었는데 관리자는 그것을 본 적이 없다 |
| 원인 | 콘솔에 알림함 화면이 없다 [소스: `web/console/src`에 알림 API를 쓰는 화면이 없다]. 요청은 고객사 상세에 들어가야 보인다 |
| 막는 법 | 고객사 목록에 고객사마다 걸린 요청 수를, 옆 메뉴의 "고객사"에 그 합을 보인다(S2-AC-48). 알림 API에도 항목을 넣어 두어 4번 묶음의 알림함이 생기면 거기에도 나온다(S2-AC-39). 담당자의 초대 대화상자가 "이미 계정이 있는 분이면 지원팀이 확인한 뒤 추가됩니다"를 미리 알린다 |
| 남는 것 | 관리자가 콘솔을 열지 않으면 모른다. 메일은 4번 묶음에서 정한다 |
| 확인 테스트 | 화면 테스트: 걸린 요청이 있으면 메뉴에 숫자가 있고 없으면 없다. 서버 테스트: 요청이 생기면 관리자마다 알림 항목이 하나다 |
| 옮길 곳 | S2-AC-39, 48 |

## 8. 감사 로그에서 담당자가 한 일을 찾지 못했다

| 항목 | 내용 |
|---|---|
| 장면 | 고객사에서 "누가 우리 직원을 뺐느냐"고 물었다. 감사 로그에는 "소속 빼기"가 있었지만 한 사람이 비어 있거나 관리자로 적혀 있었다 |
| 원인 | 있던 서비스 함수는 관리자가 부른다고 보고 짰다. 담당자가 같은 함수를 지날 때 "한 사람"을 넘기지 않으면 틀린 값이 남는다 [추론] |
| 막는 법 | 감사 항목의 한 사람은 요청한 계정에서 만든다 [소스: `CurrentAccount.actor()`]. 담당자가 한 일마다 한 사람이 그 담당자인지 테스트가 본다(S2-AC-41). 종류는 새로 만들지 않고 있던 것을 쓴다(`design.md` 0절 5) |
| 확인 테스트 | 담당자의 초대, 다시 보내기, 빼기, 요청 뒤 감사 로그의 항목마다 한 사람의 계정 ID가 담당자다. 무결성 확인이 맞다(S2-AC-43) |
| 옮길 곳 | S2-AC-41~43 |
