# 4b 묶음 설계

> 수용 기준(`acceptance.md`)을 어떻게 만들지 가운데, 나중에 바꾸기 어려운 것만 적는다. API 경로와 응답 모양은 계약 단계(C-4)의 컨트롤러 껍데기가 정한다.
> 표시: [소스]는 레포에서 본 것, [추론]은 확인하지 않은 판단이다.
> 상태: **메인이 정함, 사용자 확인 전**(2026-10-12).

## 1. 샌드박스

- 메일: 주소를 바꾸는 자리는 **SMTP에 넘기기 직전 한 곳**이다 [소스: `MailSender.attempt`의 `smtp.send(recipient.email(), …)`와 초대·재설정의 같은 길]. 보내기 직전의 확인은 그 앞에서 원래 받는 사람으로 끝낸다(S4B-AC-05). 시험 메일도 같은 자리를 지난다.
- 주소가 없는 샌드박스는 "SMTP가 없다"와 같은 가지를 탄다 [소스: `MailSender`의 SMTP 없는 가지: 로그 한 줄, 행 지움].
- 웹훅: 대기에 넣는 쪽이 넣지 않고 [소스: `OutboxWebhookQueue.queue`가 주소가 없으면 넣지 않는다], 보내는 쪽이 있던 행을 버린다 [소스: `AuditCopySender`가 샌드박스에서 버리는 꼴].
- 시스템 상태: `enabled`는 "설정이 있고 샌드박스가 끄지 않았다"다. 샌드박스인지와 주소가 있는지를 상태 응답의 새 칸으로 준다(더하기만 한다).
- 초대 링크 복사(C-10)는 `mail.enabled`를 읽는다 [소스: `getSystemStatus`의 설명]. 주소 없는 샌드박스에서는 메일이 꺼진 것이므로 링크 복사가 나온다. 주소가 있는 샌드박스에서는 초대 메일이 운영자에게 간다. 그대로 둔다.
- `POPDESK_SANDBOX_MAIL_TO`가 이메일 꼴이 아니면 앱이 뜨지 않는다(S4B-AC-06, S0-AC-10의 꼴). `POPDESK_AUDIT_RETENTION`, `POPDESK_LOCALE`처럼 뜬 채 준비 상태만 내리는 꼴이 아니다. 틀린 주소로 뜬 샌드박스는 메일이 어디로 갈지 알 수 없다(테스트 탭이 기준과 이 줄이 어긋난다고 알려 2026-10-12에 고침).

## 2. 한 시간 50통

- 수는 보내기 루프 안에서 센다. 메일 채널의 루프는 스레드 하나라 [소스: `SendLoops`] 잠금이 필요 없다. 시험 메일은 요청 스레드에서 보내므로 세는 것만 같이 쓴다(동시에 닿는 자료 구조로 둔다).
- 키는 실제로 나가는 주소(소문자로 바꾼 것)의 해시다. 주소 글자를 메모리의 키로 오래 들고 있지 않는다.
- 세는 것은 성공한 보내기의 시각 목록이고 60분이 지난 것은 버린다. 상한에 닿은 주소의 다음 행은 SMTP에 붙지 않고 바로 `failed`가 된다(다시 시도하지 않는다. 다시 시도하면 24시간 동안 대기에 쌓인다).
- 그 `failed`는 있던 길로 `DELIVERY_FAILED` 경보가 된다 [소스: `OutboxDelivery.failed`]. 하루 한 건이라 쏟아지지 않는다.

## 3. 다시 보내기와 시험 메일

- 다시 보내기는 `UPDATE outbox SET state = 'queued', attempts = 0, first_failed_at = NULL, failed_at = NULL, last_error_kind = NULL, next_attempt_at = 지금 WHERE id = ? AND state = 'failed'` 한 문장이다. 바뀐 행이 1이면 감사 항목을 남기고 루프를 깨운다 [소스: `Wakeups`]. 0이면 행을 읽어 있으면(이미 대기) 그대로 답하고 없으면 404다.
- 채널이 꺼져 있는지는 UPDATE 앞에서 본다. 감사는 잠금 순서 5의 자리다 [소스: `architecture.md`].
- 시험 메일은 대기를 거치지 않는다. 서비스가 `SmtpMail`을 바로 부른다. `SmtpMail.send`는 지금 오류의 종류만 돌려준다 [소스: `Attempt`]. 서버가 한 답의 글(`SMTPSendFailedException`의 응답, 연결 실패의 글)을 함께 돌려주는 길을 더하되, 보내기 루프가 쓰는 길의 로그와 대기 행에는 그 글을 넣지 않는다.
- 시험 메일은 트랜잭션 밖에서 보내고, 끝난 뒤 감사 항목만 따로 남긴다(SMTP가 30초 걸리는 동안 DB 연결을 쥐지 않는다).

## 4. 실패가 이어질 때의 경보

- 채널마다 "마지막 성공 시각" [소스: `delivery_status.last_success_at`]과 "대기 행 가운데 첫 실패가 한 시간 넘은 것이 있는가"로 판정한다. 살피는 자리는 있던 운영 살피기 [소스: `Housekeeping.round`]다.
- 하루 한 건과 풀기는 있던 경보의 길을 쓴다 [소스: `OpsAlertService`]. 꺼진 채널은 경보를 내지 않는다.

## 5. 쓸 컴포넌트

- 새 토큰과 새 공용 컴포넌트는 없다. C-18에 `Alert`(샌드박스 띠), `Button`, `DataTable`(정리 작업), 결과를 보일 `pre` 꼴의 글 자리를 쓴다. 자세한 것은 `screens.md`.

## 7. 일하는 차례

4a의 구현과 검증이 도는 동안 4b의 계약과 테스트를 시작한다. 서버 탭 여럿을 같이 띄우고 무거운 실행은 `heavy.sh`로 차례를 지킨다(`process.md`).

1. C-4 서버 계약과 실험. 4a의 서버 구현이 main에 합쳐진 뒤에 띄운다(같은 컨트롤러와 `MailSender`를 고친다).
2. 테스트 맞추기(있으면), C-4 웹 껍데기(C-18에 자리만).
3. C-5 테스트: 서버 둘(① 샌드박스와 한 시간 50통 ② 다시 보내기, 시험 메일, 경보, 관문)을 같이 띄운다. 웹 하나(C-18), 숨긴 E2E 하나.
4. C-6, C-7(서버와 웹 한 탭씩), C-8.
5. C-9: 서버 하나, 웹 하나.
6. C-10: 4a와 합쳐 한 번에 검증하고 푸시한다.
