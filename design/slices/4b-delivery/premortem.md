# 4b 묶음 사전 부검

> 4b 묶음(보내기 운영)을 내고 석 달 뒤 일이 틀어졌다고 가정하고, 어떻게 틀어졌을지와 막을 장치를 적는다. 공개 계약(설정 키)과 개인정보 흐름을 건드려서 전체 경로다.
> 표시: [소스]는 레포에서 본 것, [추론]은 확인하지 않은 판단이다.
> 상태: **메인이 정함, 사용자 확인 전**(2026-10-12).

## 1. 시험 설치가 진짜 고객에게 메일을 보냈다

| 항목 | 내용 |
|---|---|
| 장면 | 운영자가 장애를 재현하려고 운영 DB를 복사해 `POPDESK_SANDBOX=true`로 띄웠다. 대기에 남아 있던 메일 300통 가운데 초대와 비밀번호 재설정이 진짜 주소로 나갔다. 문의 메일은 샌드박스 주소로 왔다 |
| 원인 | 주소를 바꾸는 코드를 문의 메일의 길에만 넣었다. 초대와 재설정은 받는 사람을 다른 길로 읽는다 [소스: `MailSender`의 종류별 가지]. 0.1.0에서는 문서만 있고 구현이 없었다 |
| 막는 법 | 주소를 바꾸는 자리는 SMTP에 넘기기 직전 한 곳이다(`design.md` 1절). 설정을 읽는 곳도 한 클래스다(`design.md` 0절 7) |
| 확인 테스트 | 샌드박스 앱에서 메일 종류마다(초대, 재설정, 답변, 대리 등록, 해결, 종료, 재오픈, 멘션, 담당자, 소속 요청, 시험 메일) 한 통씩 만들어, 원래 주소의 메일함이 비었고 샌드박스 주소에 그 수만큼 왔다. 종류의 목록은 `MailKind`의 값 전부에서 만든다(새 종류가 생기면 테스트가 실패하게). C-7이 한 종류만 원래 주소로 보내는 틀린 구현을 넣어 본다 |
| 옮길 곳 | S4B-AC-01, 03, 09 |

## 2. 다시 보내기가 떠난 사람에게 메일을 되살렸다

| 항목 | 내용 |
|---|---|
| 장면 | 메일 서버가 이틀 멈췄다가 돌아왔다. 관리자가 `failed` 행 40개를 다시 보냈다. 그사이 정지된 고객과 배정에서 빠진 상담원에게도 문의 메일이 나갔다. 지워진 댓글의 "답변했습니다" 메일도 나갔다 |
| 원인 | 다시 보내기가 행을 대기로 돌리지 않고 그 자리에서 바로 SMTP로 보냈다. 보내기 직전의 확인을 지나지 않았다 |
| 막는 법 | 다시 보내기는 행의 상태만 바꾸고, 보내는 것은 늘 루프가 한다(`design.md` 3절). 확인은 루프 안에 있다 [소스: `MailSender.attempt`] |
| 확인 테스트 | `failed` 행을 만든 뒤 받는 사람을 정지하거나 배정을 빼거나 댓글을 지우고 다시 보내면 메일이 없고 행이 사라진다 |
| 옮길 곳 | S4B-AC-15 |

## 3. 시험 메일의 응답에 비밀번호가 보였다

| 항목 | 내용 |
|---|---|
| 장면 | 관리자가 시험 메일을 눌렀다. 인증에 실패한 SMTP 서버의 답이 화면에 그대로 나왔고, 그 안에 Base64로 된 사용자 이름이 있었다. 화면을 캡처해 문의에 붙였다. 다른 설치에서는 그 글이 감사 로그와 앱 로그에도 남았다 |
| 원인 | 예외의 글을 통째로 돌려줬다. 메일 라이브러리의 디버그 글이나 예외의 글에는 주고받은 줄이 섞일 수 있다 [추론: 실험 1] |
| 막는 법 | 서버가 한 답의 줄(응답 코드와 글)만 돌려주고, 설정의 사용자 이름과 비밀번호 글자(원래 꼴과 Base64 꼴)가 들어 있으면 지운다. 500자에서 자른다. 감사 로그와 앱 로그에는 오류의 종류만 남긴다(S4B-AC-24, 27, 38) |
| 확인 테스트 | 인증에 실패하게 한 뒤 응답 본문, 감사 항목, 로그 전체에서 설정에 넣은 비밀번호와 사용자 이름(Base64 꼴 포함)을 찾아 없다 |
| 옮길 곳 | S4B-AC-24, 27, 31, 38 |

## 4. 상한이 진짜 메일을 막았다

| 항목 | 내용 |
|---|---|
| 장면 | 샌드박스로 띄운 시험 설치에서 운영자가 초대 60통을 시험했다. 51번째부터 `failed`가 됐고 경보가 떴다. 운영자는 고장으로 알았다 |
| 원인 | 샌드박스에서는 모든 메일이 한 주소로 가서 합쳐 50통이다 |
| 막는 법 | 막힌 행의 오류 종류가 `RATE_LIMITED`로 보이고(`design.md` 0절 4), C-18이 그 종류를 글로 풀어 쓴다("한 주소에 한 시간 50통을 넘겼습니다"). 운영 문서에 샌드박스에서는 합쳐서 센다고 적는다 |
| 남는 것 | 상한의 값은 설정으로 바꿀 수 없다. 한 사람이 한 시간에 50통을 넘게 받는 진짜 경우는 지금 없다 [추론] |
| 확인 테스트 | 50통까지 나가고 51번째가 `RATE_LIMITED`로 `failed`다. 다른 주소는 나간다. 시계를 60분 옮기면 다시 나간다 |
| 옮길 곳 | S4B-AC-10~13 |

## 5. 앞 묶음의 테스트가 깨졌다

| 항목 | 내용 |
|---|---|
| 장면 | 시스템 상태 응답에 칸이 늘자 그 응답의 칸을 통째로 견주던 테스트가 깨졌다. 감사 종류가 둘 늘자 종류 수를 고정한 테스트가 깨졌다 |
| 원인 | 2번에서 같은 일이 있었다(`process.md` 2번 규칙) |
| 막는 법 | 계약 탭이 껍데기 앞에 찾는다(`design.md` 6절 실험 4). 테스트 쪽이 구현보다 먼저 맞춘다 |
| 옮길 곳 | `design.md` 6절 |

## 6. 받아들이는 것

- 한 시간 50통의 수는 앱이 다시 뜨면 0부터다.
- 샌드박스는 메일 받기를 끄지 않는다(메일 받기가 아직 없다. 12번에서 같이 만든다).
- 다시 보내기는 하나씩이다.
- 샌드박스에서 원래 받는 사람이 누구였는지는 계정 ID로만 안다.
