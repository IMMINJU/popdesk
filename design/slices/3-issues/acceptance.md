# 3번 묶음 수용 기준: 문의

> `roadmap.md` 6절 3번의 EARS 수용 기준이다. 묶음이 끝나면 `design/archive/3-issues/`로 간다(D-27).
> 전체 경로다. 고객사 경계(검색과 필터라는 새 옆길, 대리 등록, 담당자), 마이그레이션(V9, V10), 공개 계약(새 오류 코드, `pg_trgm` 확장)을 건드린다. 사전 부검은 같은 폴더의 `premortem.md`에 쓴다(C-3).
> 꼴은 앞 묶음과 같다. 괄호 안은 근거다. 규칙 ID의 글은 같은 폴더 `rules.md`와 `archive/1a-people/rules.md`에 있다. 기준 ID는 `S3-AC-nn`이다.
> 관계있는 결정(`adr.md`): D-12, D-13, D-18, D-24, D-34, D-36, D-41, D-43, D-44, D-47, D-49, 새 결정 D-56(`design.md` 0절). 위협 모델: TM-01, TM-02, TM-06, TM-07, TM-08, TM-32, TM-48.
> 기준 한 줄에는 밖에서 보이는 동작 하나만 적는다. 만드는 법은 설계(`design.md`)에 둔다.
> 코드와 API에서 고객사는 `company`다(`roadmap.md` 1절의 `project`는 옛 이름이다).
> 상태: **메인이 정함, 사용자 확인 전**(2026-10-12). 사용자가 남은 묶음의 설계를 메인의 추천대로 진행하라고 맡겼다. 규칙에 없던 것을 메인이 넣은 곳은 5절에 모았다.

## 2. 수용 기준

"상담 쪽"은 상담원과 관리자다. 상담원에 관한 기준은 배정된 고객사의 문의에만 해당한다. "열린 문의"는 `CLOSED`가 아닌 문의다. "올린 고객"은 문의의 올린 사람이고, 대리 등록한 문의에서는 상담원이 고른 고객이다.

### 2.1 목록의 필터 (콘솔)

| ID | 기준 |
|---|---|
| S3-AC-01 | When 상담 쪽이 문의 목록에 상태를 하나 이상 주면, the system shall 그 상태들 가운데 하나인 문의만 준다. 모르는 상태 값은 400이다. (ISSUE-5) |
| S3-AC-02 | When 상담 쪽이 문의 목록에 고객사 코드를 주면, the system shall 그 고객사의 문의만 준다. 볼 수 없는 고객사나 없는 코드는 빈 목록이다(400이나 404로 있는지를 알리지 않는다). (ISSUE-5, COM-1) |
| S3-AC-03 | When 상담 쪽이 담당자 필터에 계정 ID, "나", "없음" 가운데 하나를 주면, the system shall 그 사람이 담당인 문의, 내가 담당인 문의, 담당자가 빈 문의만 준다. (ISSUE-5) |
| S3-AC-04 | When 상담 쪽이 담당자 필터에 "볼 수 없음"을 주면, the system shall 담당자가 `ACTIVE`가 아니거나 그 고객사에 배정되지 않은 상담원인 문의만 준다. 담당자가 관리자이면 배정과 관계없이 볼 수 있는 것으로 친다. (ISSUE-11) |
| S3-AC-05 | When 상담 쪽이 올린 사람의 계정 ID를 주면, the system shall 그 사람이 올린 문의만 준다. 없는 계정이면 빈 목록이다. (ISSUE-5) |
| S3-AC-06 | The system shall 필터를 여럿 주면 모두 맞는 문의만 주고, 필터가 있어도 보는 범위(RULE-03), 최신순, COM-4의 쪽 나누기를 그대로 지킨다. `totalElements`는 거른 뒤의 수다. (ISSUE-5, TM-02) |
| S3-AC-07 | If 콘솔 문의 목록에 계약에 없는 쿼리 이름이 들어오면, then the system shall 400 `INVALID_INPUT`과 그 이름의 `UNKNOWN_PARAMETER`로 답한다. (5절 9) |

### 2.2 목록의 필터 (포털)

| ID | 기준 |
|---|---|
| S3-AC-08 | When 고객이 문의 목록에 상태(여러 개), 고객사 코드, "내가 올린 것만"을 주면, the system shall 모두 맞는 문의만 준다. 소속이 아닌 고객사 코드는 빈 목록이다. (ISSUE-5) |
| S3-AC-09 | If 고객 문의 목록에 담당자, 올린 사람의 계정 ID, 라벨, SLA, 정렬 같은 상담 쪽 전용 이름이 들어오면, then the system shall 지금처럼 400 `UNKNOWN_PARAMETER`로 답한다. (ISSUE-5, TM-07, S0-AC-48) |

### 2.3 검색

| ID | 기준 |
|---|---|
| S3-AC-11 | When 문의 목록에 검색어 `q`(1~100자)를 주면, the system shall 제목이나 내용의 화면 글자에 그 글자가 들어 있는 문의만 준다. 대소문자를 가리지 않고 낱말 단위가 아니다. 다른 필터와 함께 쓸 수 있다. 포털과 콘솔이 같다. (COM-5, ISSUE-5) |
| S3-AC-12 | The system shall 내용의 마크다운 기호(`**`, `#`, 목록 표시, 코드 울타리)와 링크·이미지의 주소는 찾는 글자에 넣지 않고, 링크의 글자와 이미지의 설명, 코드 안의 글자는 넣는다. (ISSUE-5, D-56) |
| S3-AC-13 | The system shall 검색어의 `%`, `_`, `\`를 보통 글자로 다룬다. (COM-5, TM-32) |
| S3-AC-14 | If `q`가 비었거나 100자를 넘으면, then the system shall 400과 `fields`로 답한다. 길이는 NFC로 맞춘 뒤 코드 포인트로 센다. (COM-5, conventions 글자 입력) |
| S3-AC-15 | If 한 계정이 60초 안에 검색어가 든 목록 요청을 60번 넘게 보내면, then the system shall 429와 `Retry-After`로 답한다. 문의 목록과 계정 목록을 합쳐 센다. (COM-8) |
| S3-AC-16 | When 문의의 제목이나 내용이 고쳐지면, the system shall 다음 검색부터 고친 글자로 찾는다. (ISSUE-6) |
| S3-AC-17 | The system shall 문의 검색과 계정 검색(이름, 이메일)에 `pg_trgm` 색인을 둔다. 계정 검색의 결과는 지금과 같다. (D-13, 1a `verify.md`) |

### 2.4 고치기

| ID | 기준 |
|---|---|
| S3-AC-18 | When 올린 고객이나 상담 쪽이 읽어 온 `version`과 함께 제목, 내용, 우선순위 가운데 보낸 칸을 고치면, the system shall 저장하고 `version`을 1 올려 고친 문의를 준다. 보내지 않은 칸은 그대로다. 입력 규칙은 등록과 같다. (ISSUE-6, ISSUE-2, D-44) |
| S3-AC-19 | If 보낸 `version`이 지금 값과 다르면, then the system shall 409 `VERSION_CONFLICT`로 답하고 아무것도 바꾸지 않는다. `version`이 없으면 400이다. (ISSUE-6, D-47) |
| S3-AC-20 | If 올린 사람이 아닌 같은 고객사 고객이나, 그 고객사 소속에서 빠진 올린 고객이 고치면, then the system shall 403으로 답한다. (ISSUE-6, PROJ-4, COM-2) |
| S3-AC-21 | If 문의가 `CLOSED`이면, then the system shall 고치기를 400 `ISSUE_CLOSED`로 답한다. (ISSUE-6) |
| S3-AC-22 | When 보낸 값이 모두 지금 값과 같으면, the system shall 200으로 답하고 `version`을 올리지 않고 이력을 남기지 않는다. (HIST-2) |
| S3-AC-23 | The system shall 고객이 고칠 때 제목, 내용, 우선순위 말고 다른 칸을 받지 않는다. 비공개 여부와 고객사는 누구도 고치지 못한다. (ISSUE-6, D-41) |

### 2.5 담당자

| ID | 기준 |
|---|---|
| S3-AC-24 | When 상담 쪽이 문의의 담당자를 정하거나 바꾸면, the system shall 저장하고 `version`을 1 올린다. 같은 사람으로 다시 정하면 200이고 아무것도 바뀌지 않는다. (ISSUE-7, HIST-2) |
| S3-AC-25 | If 담당자로 정하려는 계정이 `ACTIVE` 관리자도, 그 고객사에 배정된 `ACTIVE` 상담원도 아니면(고객, 수락 전, 정지, 배정되지 않은 상담원, 없는 계정), then the system shall 까닭과 관계없이 같은 400과 `fields`의 `UNKNOWN_VALUE`로 답한다. (ISSUE-7, INVITE-5) |
| S3-AC-26 | When 상담 쪽이 담당자를 비우면, the system shall 담당자를 `null`로 둔다. 이미 비어 있으면 그대로 200이다. (ISSUE-7, D-44) |
| S3-AC-27 | When 상담 쪽이 한 고객사의 담당자 후보를 요청하면, the system shall `ACTIVE` 관리자와 그 고객사에 배정된 `ACTIVE` 상담원을 계정 ID, 이름, 역할로 준다. 상담원이 배정되지 않은 고객사의 후보를 요청하면 404다. (ISSUE-7, COM-1) |
| S3-AC-28 | The system shall 콘솔의 문의 목록과 상세에 담당자(없으면 `null`)와 "담당자가 볼 수 없음" 표시를 준다. (ISSUE-11, D-44) |
| S3-AC-29 | The system shall 포털의 문의 응답에 담당자, 대리 등록한 상담원, 받은 경로, 이력, 첫 응답 시각을 넣지 않는다. 계약 스냅샷이 이것을 고정한다. (ISSUE-8, RULE-04, D-41, S0-AC-49) |
| S3-AC-30 | While 문의가 `CLOSED`여도, the system shall 담당자를 정하고 비울 수 있게 한다. (5절 7) |
| S3-AC-31 | When 담당자의 배정이 빠지거나 계정이 정지되면, the system shall 문의의 담당자 칸을 그대로 두고 그 문의를 "담당자가 볼 수 없음"으로 준다. 배정을 되돌리거나 정지를 풀면 표시가 사라진다. (PROJ-4, ISSUE-11) |

### 2.6 대리 등록

| ID | 기준 |
|---|---|
| S3-AC-32 | When 상담 쪽이 고객사, 고객 한 명, 받은 경로(`PHONE`·`OTHER`), 제목, 내용, 우선순위, 비공개 여부로 문의를 올리면, the system shall 올린 사람은 그 고객, 만든 사람은 그 상담원, 상태 `RECEIVED`인 문의를 포털 등록과 같은 규칙(키, 순번, 입력, 기본값)으로 만든다. (ISSUE-9, ISSUE-2, ISSUE-3, D-34) |
| S3-AC-33 | If 고른 계정이 그 고객사에 소속된 `ACTIVE` 고객이 아니면(다른 고객사의 고객, 수락 전, 정지, 상담 쪽 계정, 없는 계정), then the system shall 까닭과 관계없이 같은 400과 `fields`의 `UNKNOWN_VALUE`로 답한다. (ISSUE-9) |
| S3-AC-34 | If 상담원이 배정되지 않은 고객사에 대리 등록하면, then the system shall 404로 답한다. 고객사가 `ACTIVE`가 아니면 400 `COMPANY_NOT_ACTIVE`다. (ISSUE-9, COM-1, PROJ-3) |
| S3-AC-35 | If 받은 경로가 `PHONE`이나 `OTHER`가 아니면(`PORTAL`, `EMAIL`, 빈 값, 모르는 값), then the system shall 400과 `fields`로 답한다. (ISSUE-9) |
| S3-AC-36 | The system shall 콘솔의 문의 응답에 만든 상담원(대리 등록이 아니면 `null`)과 받은 경로를 주고, 포털의 문의 응답에는 "지원팀이 대신 올렸다"는 표시만 준다. 포털 응답 어디에도 그 상담원의 이름, 이메일, 계정 ID가 없다. (ISSUE-9, ANON-1, D-49) |
| S3-AC-37 | When 대리 등록이 끝나면, the system shall 올린 고객에게 메일 한 통을 대기에 넣는다. 메일은 받는 사람의 언어로 쓰고, 포털의 문의 링크를 담고, 올린 쪽을 "지원팀"으로 쓰며, 상담원의 이름과 문의 내용은 담지 않는다. 보내기 직전에 받는 사람이 그 문의를 볼 수 있는지 다시 본다. (ISSUE-9, MAIL-1, MAIL-4, ANON-1) |
| S3-AC-38 | When 대리 등록한 문의를 올린 고객이 포털에서 열면, the system shall 자기가 올린 문의와 같게 보이고 같게 다룰 수 있게 한다(고치기, 댓글, 첨부, 종료, 재오픈). 비공개이면 동료에게 404다. (D-34, ISSUE-4) |
| S3-AC-39 | The system shall 대리 등록을 포털 등록과 같은 요청 수 제한(한 계정에 60초 동안 10건)에 센다. (COM-8) |

| 권한(동료, 빠진 고객, 고객의 칸) | S3-AC-20, 23, 55, 58 |

숨긴 E2E는 하나다: 상담원이 대리 등록 → 고객이 포털에서 보고 댓글 → 상담원이 담당자를 정하고 처리 중, 해결로 → 고객이 다시 열기 → 상담원이 해결 → 고객이 해결 확인 → 콘솔 이력에 모든 일이 차례로 있고, 다른 고객사의 고객은 검색으로 이 문의를 찾지 못한다.

## 4. 테스트를 쓸 때 지킬 것

- 기준 하나에 테스트는 동작 하나꼴로 쓴다. 전이 표(S3-AC-48, 49)는 25칸을 매개변수 테스트 하나로 돈다. 도움 코드는 `support/`와 `issue` 패키지에 이미 있는 것을 쓴다.
- 상태가 다른 문의는 API로 만든다(상담 쪽이 전이를 차례로 한다). 테스트가 DB의 상태 칸을 직접 고치지 않는다. `CLOSED`를 DB로 만들던 앞 묶음의 테스트는 그대로 둔다(잠겨 있다).
- 14일과 24시간은 `TestClock`으로 옮긴다. 고정 대기를 쓰지 않는다.
- 필터와 검색의 테스트는 자기가 만든 고객사와 문의만 센다(같은 앱과 DB를 나눠 쓴다). 검색어에는 `Unique`로 만든 낱말을 넣는다.
- "까닭과 관계없이 같은 400"(S3-AC-25, 33)은 경우마다 상태 코드와 본문 전체를 견준다.
- 경합(S3-AC-44, 51, 52)은 `Concurrently`와 `HeldWrite`를 쓰고, 결과는 "어떤 한 순서의 결과"로 단언한다. 어느 쪽이 이기는지는 고정하지 않는다.
- 웹훅과 메일의 글은 스냅샷으로 고정하되, 오류 문구나 순서 같은 우연한 값은 고정하지 않는다.
- 표나 칸을 꼴로 찾는 도움(`db.tables()`)에 "그런 표는 하나뿐"이라고 기대지 않는다(1a C-11). 이 묶음은 `issue`에 칸 다섯을 더한다.
