## 1. 표 (V15)

```
task(id bigint generated by default as identity primary key,
     tenant_id bigint not null,
     issue_id uuid not null references issue(id),
     title text not null,                       -- 지우면 ''
     status text not null check (status in ('OPEN','DONE')),
     assignee_id bigint references account(id),
     due_date date,
     created_by bigint not null references account(id),
     created_at timestamptz not null,
     done_at timestamptz, done_by bigint references account(id),
     deleted_at timestamptz, deleted_by bigint references account(id))
create index task_issue_idx on task(issue_id, id);
create index task_assignee_open_idx on task(assignee_id, due_date) where status = 'OPEN' and deleted_at is null;

task_note(id bigint generated by default as identity primary key,
          tenant_id bigint not null,
          task_id bigint not null references task(id),
          kind text not null check (kind in ('NOTE','CHANGE')),
          author_id bigint not null references account(id),
          content text not null,                -- NOTE의 글, 지우면 ''. CHANGE는 ''
          field text,                            -- CHANGE: STATUS, ASSIGNEE, DUE_DATE, TITLE
          old_value text, new_value text,        -- CHANGE: 상태 이름, 계정 ID, 날짜, 제목. 작업을 지우면 null
          created_at timestamptz not null,
          edited_at timestamptz,
          deleted_at timestamptz, deleted_by bigint references account(id))
create index task_note_task_idx on task_note(task_id, id);

alter table notification add column task_id bigint;
alter table outbox add column task_id bigint;
create index notification_task_idx on notification(task_id) where task_id is not null;
```

- 휴지통이 생기면(7번) 문의를 영구 삭제할 때 작업과 기록을 지운다. 이 묶음은 외래 키를 `on delete cascade`로 두지 않는다(지금 문의를 지우는 길이 없다).
- `deploy/upgrade/make-sample.py`가 S6B-AC-95의 행을 채운다.

## 2. 경로

계약 탭(C-4)이 `conventions.md`의 꼴과 견줘 정한다. 메인의 초안:

| 하는 일 | 초안 | 답 |
|---|---|---|
| 목록 | `GET /api/console/issues/{key}/tasks` | 200 `IssueTasks{items: Task[], openCount}` |
| 만들기 | `POST /api/console/issues/{key}/tasks` `{title, assigneeId?, dueDate?}` | 201 `Task` |
| 고치기 | `PATCH /api/console/issues/{key}/tasks/{id}` `{title?, status?, assigneeId?, dueDate?}` | 200 `Task` |
| 지우기 | `DELETE /api/console/issues/{key}/tasks/{id}` | 204 |
| 기록 남기기 | `POST /api/console/issues/{key}/tasks/{id}/notes` `{content}` | 201 `TaskNote` |
| 기록 고치기 | `PATCH /api/console/issues/{key}/tasks/{id}/notes/{noteId}` `{content}` | 200 `TaskNote` |
| 기록 지우기 | `DELETE /api/console/issues/{key}/tasks/{id}/notes/{noteId}` | 204 |
| 내 작업 | `GET /api/console/tasks?status=OPEN|DONE&page&size` | 200 `PagedMyTask` |

- `Task`: `id`, `title`, `status`, `assignee`(사람 또는 `null`), `dueDate`, `overdue`, `createdBy`, `createdAt`, `doneBy`, `doneAt`, `deleted`, `deletedBy`, `deletedAt`, `notes`. 지운 작업은 `title`이 `""`, 담당자·마감일이 `null`, `notes`가 `[]`다(S6B-AC-10, D-44: 칸을 빼지 않는다).
- `TaskNote`: `id`, `kind`(`NOTE`·`CHANGE`), `author`, `content`, `field`, `oldValue`, `newValue`, `oldPerson`, `newPerson`, `createdAt`, `editedAt`, `deleted`, `deletedBy`, `deletedAt`. 담당자 항목은 `oldPerson`·`newPerson`으로 사람을 준다(문의 이력의 `ASSIGNEE`와 같은 꼴) [소스: 콘솔 `IssueHistoryEntry`].
- `MyTask`: `id`, `title`, `status`, `dueDate`, `overdue`, `doneAt`, `issue{key, title, status}`, `companyCode`, `companyName`.
- `IssueSummary`에 `openTaskCount`(정수)를 더한다. 포털 타입은 바뀌지 않는다.
- `Notification`에 `task`(`{id, title}` 또는 `null`)를 더하고 `kind`에 `TASK_ASSIGNED`를 더한다.
- `OpenAssignments`에 `tasks`(정수)를 더한다.
- 감사 종류에 `LABEL_CREATED`, `LABEL_UPDATED`, `LABEL_DELETED`를 더한다(계약의 `action` 필터 enum 포함).
- 새 오류 code: `TASK_LIMIT_EXCEEDED`, `TASK_NOTE_LIMIT_EXCEEDED`, `TASK_DELETED`, `TASK_NOTE_DELETED`(모두 400). 요청 수 제한(COM-8)에 "작업과 기록의 만들기·고치기: 60"을 더한다. 그 밖은 있는 code다(`ISSUE_CLOSED`, `FORBIDDEN`, `INVALID_INPUT`의 `REQUIRED`·`TOO_LONG`·`BLANK`·`UNKNOWN_VALUE`·`OUT_OF_RANGE`·`INVALID_FORMAT`).
- 검사 차례는 `conventions.md` "Order of checks"를 따른다: 404(문의, 작업, 기록) → 403(지우기·고치기의 사람) → 400 입력 → 400 상태(`ISSUE_CLOSED`) → 400 한도.

## 3. 쓰기의 차례와 잠금

| 쓰기 | 차례 |
|---|---|
| 작업 만들기 | 요청 수 → 문의 행 잠금(보기 범위, 404) → 입력(제목, 마감일, 담당자 자격) → `CLOSED` → 작업 수(지우지 않은 것 30, 모두 100) → INSERT → 담당자가 있고 자기가 아니면 알림함 항목과 메일 |
| 작업 고치기 | 요청 수 → 문의 행 잠금 → 작업 행(그 문의의 것, 404) → 입력(담당자 자격은 보낸 값이 지금과 다를 때만) → 지운 작업(`TASK_DELETED`) → `CLOSED` → 항목 수(1,000) → 바뀐 칸만 UPDATE → 칸마다 `CHANGE` 기록 → 담당자가 다른 사람으로 바뀌었고 자기가 아니면 알림 |
| 작업 지우기 | 문의 행 잠금 → 작업 행(404) → 만든 사람이나 관리자(403) → 이미 지웠으면 그대로 204 → 작업 UPDATE(`title = ''`, 담당자·마감일 비움, 지운 시각과 사람) → 그 작업의 사람 기록 UPDATE(`content = ''`, 지운 시각과 사람, 이미 지운 것은 그대로)와 시스템 항목 UPDATE(`old_value`·`new_value` null) → 그 작업의 알림함 항목 DELETE. `CLOSED`여도 한다 |
| 기록 남기기·고치기 | 요청 수 → 문의 행 잠금 → 작업 행(404) → 기록 행(그 작업의 것, 404, 고치기만) → 쓴 사람(403, 고치기만. 시스템 항목도 403) → 입력 → 지운 작업·지운 기록(400) → `CLOSED` → 한도(남기기만: 사람 기록 100, 모든 항목 1,000) → INSERT/UPDATE |
| 기록 지우기 | 문의 행 잠금 → 작업 행(404) → 기록 행(404) → 쓴 사람이나 관리자(403. 시스템 항목은 403) → 이미 지웠으면 204 → UPDATE. `CLOSED`여도 한다 |
| 담당 비우기(배정 빼기, 정지) | 지금의 문의 비우기와 같은 트랜잭션에서 `UPDATE task SET assignee_id = NULL … WHERE assignee_id = ? AND status = 'OPEN' AND deleted_at IS NULL AND issue_id IN (CLOSED가 아니고 [그 고객사의] 문의) RETURNING id` → 돌아온 작업마다 `CHANGE` 기록 | 

- `architecture.md` 잠금 순서 표에 위 다섯 줄을 C-10에서 더한다.
- 알림함 항목과 메일 대기 행은 4번의 `IssueNotifications` 꼴로 넣는다: 누구에게 알릴지는 그 클래스가 정하고, 받는 사람이 `ACTIVE`이고 문의를 볼 수 있는지 넣을 때와 보낼 때 본다 [소스: `IssueNotifications.java:170-183`, `MailSender.java:82-89`]. 보낼 때는 작업도 다시 본다: `notification` 모듈이 `helpdesk`의 공개 인터페이스(`IssueFacts`와 같은 꼴, 새)로 "이 작업이 남아 있고 이 사람이 담당자인가, 제목은"을 묻는다. 아니면 보내지 않는다 [소스: `IssueFacts.java`, `CommentFacts.java`].
- 담당자 정하기와 배정 빼기가 같은 때 오면 막 빠진 상담원이 담당자가 될 수 있다(`findAssignable`은 잠그지 않는다, 문의 담당자와 같은 틈). 메일은 보내기 직전 확인에서 막힌다. 받아들인다(`premortem.md` 7절).
- 작업 서비스는 `helpdesk/task`(새)에 둔다. `task` → `issue`, `company`, `account`의 공개 타입을 쓰고, 반대 방향은 두지 않는다. 문의 목록의 열린 작업 수와 담당 비우기는 `issue` 쪽이 `helpdesk`의 인터페이스로 부르고 `task`가 구현한다(`OpenAssignments`와 같은 꼴, `PackageCyclesTest`).

## 4. 목록과 내 작업

- 콘솔 문의 목록의 `openTaskCount`는 6a의 라벨처럼 쪽의 문의 ID로 한 번 더 읽는다: `select issue_id, count(*) from task where issue_id = any(?) and status = 'OPEN' and deleted_at is null group by issue_id` [소스: `ConsoleIssueController.java:169-173`].
- 내 작업: `task t join issue i on i.id = t.issue_id where t.assignee_id = 나 and t.deleted_at is null and t.status = ? and i.status <> 'CLOSED' and (보기 범위의 조건)`. 보기 범위의 조건은 문의 목록과 같은 것을 쓴다(새로 짜지 않는다). 차례: `OPEN`은 `t.due_date asc nulls last, t.created_at, t.id`, `DONE`은 `t.done_at desc, t.id desc`.
- 성능: 구현 탭이 문의 10만 건과 작업 3만 건(한 상담원에게 몇천 건)으로 내 작업 첫 쪽과 문의 목록 첫 쪽을 잰다. 기준은 150 ms(6a S6A-AC-55와 같다). 못 미치면 멈추고 숫자를 보고한다. 테스트로 고정하지 않는다.

## 5. 알림

- `IssueInbox.add`가 받는 값에 `taskId`를 더한다. 메일 대기 행에도 `task_id`를 적는다. 알림함을 읽을 때 `helpdesk`가 작업 제목을 준다(`InboxFacts`에 메서드 하나, 지운 작업이면 항목이 이미 지워졌다).
- 메일 `MailText.taskAssigned`: `aboutIssue` 꼴로 `[KEY] 작업을 맡았습니다: {작업 제목}` / `[KEY] Task assigned: {title}`. 본문에 작업 제목, 문의 제목, 링크 `origin/issues/{key}#task-{id}` [소스: `MailText.java:131-171`, `MailSender.java:105`].
- 작업 제목은 메일 제목 줄에 들어가므로 줄바꿈을 지운다(앞 묶음 제목과 같은 처리를 쓴다).

1. 계약(C-4): 서버 껍데기(경로 여덟, 칸 넷, 알림 종류, 감사 종류 셋)와 계약 파일, 웹 클라이언트. 공용 컴포넌트를 바꾸면 그 props와 story 껍데기.
2. 테스트(C-5): 서버 탭 둘(작업과 기록·경계 / 알림·내 작업·담당 비우기·라벨 감사), 웹 탭 하나(C-4 작업 구역, C-15, C-3·C-7·C-9·C-10·C-12의 바뀐 곳), 숨긴 E2E 하나(상담원이 작업을 만들어 다른 상담원에게 맡기고, 맡은 사람이 메일과 알림함으로 알고 내 작업에서 끝내고, 고객은 아무것도 못 보고, 배정에서 빠진 상담원의 내 작업에서 사라진다).
3. 실패 확인, 점검(C-7, 3절의 틀린 구현), 잠금.
4. 구현(C-9): 서버 탭 하나와 웹 탭 하나를 같은 때(6a와 같다). 서버 탭은 4절을 잰다.
5. 검증(C-10): `local-ci.sh` 전체와 이미지·deploy, 숨긴 E2E, 변이 테스트(8절), 브라우저(C-4 작업 구역, C-15, 세 폭).
