# 6b 묶음 수용 기준: 작업

> `roadmap.md` 6번의 둘째 조각이다(6a 수용 기준 5절 1). 묶음이 끝나면 `design/archive/6b-tasks/`로 간다(D-27).
> 전체 경로다. 마이그레이션(표 둘, 알림함과 보내기 대기에 칸 하나씩), 고객사 경계(다른 고객사 문의의 작업, 작업 담당자의 자격), 개인정보 흐름(작업 알림 메일), 공개 계약(새 경로, 응답의 새 칸, 알림 종류와 감사 종류)을 건드린다. 사전 부검은 같은 폴더의 `premortem.md`다.
> 규칙 ID의 글은 같은 폴더 `rules.md`에 있다. 기준 ID는 `S6B-AC-nn`이다.
> 관계있는 결정(`adr.md`): D-10, D-20, D-41, D-42, D-43, D-44, D-49, D-57. 위협 모델: TM-57(새, 다른 고객사의 작업), TM-58(새, 작업과 기록 한도).
> 상태: **메인이 정함, 사용자 확인 전**(2026-10-15). 규칙에 없던 것을 메인이 넣은 곳은 5절에 모았다.

## 2. 수용 기준

"상담 쪽"은 관리자와 상담원이다. "볼 수 있는"은 RULE-03이다(관리자는 모든 문의, 상담원은 배정된 고객사의 문의). "오늘"은 6a와 같다(`POPDESK_TIMEZONE`의 날짜). "열린 작업"은 `OPEN`이고 지우지 않은 작업이다(문의가 `CLOSED`여도 센다. 담당 비우기만 `CLOSED`가 아닌 문의의 것을 센다, S6B-AC-75).

### 2.1 작업 만들기와 고치기

| ID | 기준 |
|---|---|
| S6B-AC-01 | When 상담 쪽이 볼 수 있는 문의에 작업을 만들면(제목, 담당자와 마감일은 고를 때만), the system shall 상태 `OPEN`으로 만들고 작업을 준다. 작업에는 ID, 제목, 상태, 담당자, 마감일, `overdue`, 만든 사람과 시각, 끝낸 사람과 시각이 있다. (TASK-2) |
| S6B-AC-02 | If 제목이 비었거나(앞뒤 공백을 자른 뒤) 100자를 넘으면, then the system shall 400 `INVALID_INPUT`으로 답하고 만들지 않는다. 고치기도 같다. (TASK-2) |
| S6B-AC-03 | When 상담 쪽이 작업의 제목·상태·담당자·마감일 가운데 보낸 칸만 고치면, the system shall 그 칸만 바꾸고 작업을 준다. 빠진 칸은 그대로, 담당자와 마감일의 `null`은 비우기다. 제목과 상태의 `null`은 400이다. (TASK-2) |
| S6B-AC-04 | If 보낸 담당자가 `ACTIVE` 관리자도 그 고객사에 배정된 `ACTIVE` 상담원도 아니면, then the system shall 400 `INVALID_INPUT`(필드 `assigneeId`, `UNKNOWN_VALUE`)으로 답한다. 없는 계정, 다른 고객사의 상담원, 정지한 계정, 고객이 같은 답이다. 자격은 담당자를 보낼 때만 본다: 지금 담당자와 같은 값을 보내거나 담당자를 보내지 않으면 보지 않는다(자격을 잃은 담당자가 남은 작업의 다른 칸도 고칠 수 있다). 입력 검사라 `CLOSED`보다 먼저 본다. (TASK-6, ISSUE-7, TM-57) |
| S6B-AC-05 | If 보낸 마감일이 오늘보다 이전이거나 `YYYY-MM-DD`가 아니면, then the system shall 6a의 문의 마감일과 같은 400(`OUT_OF_RANGE`, `INVALID_FORMAT`)으로 답한다. 이미 지난 날짜와 같은 날짜를 다시 보내도 400이다(S6A-AC-35와 같다). 마감일을 보내지 않으면 지난 마감일이 있는 작업의 다른 칸도 고칠 수 있다. (TASK-6, DUE-1) |
| S6B-AC-06 | When 작업이 `DONE`이 되면, the system shall 끝낸 시각과 사람을 남긴다. When `OPEN`으로 되돌리면, the system shall 둘을 지운다. 이미 그 상태면 아무것도 바꾸지 않는다. (TASK-6) |
| S6B-AC-07 | The system shall 작업의 `overdue`를 마감일이 오늘보다 이전이고 상태가 `OPEN`일 때만 참으로 준다. (TASK-6, 5절 6) |
| S6B-AC-08 | If 문의에 지우지 않은 작업이 이미 30개거나 지운 것까지 100개면, then the system shall 만들기를 400 `TASK_LIMIT_EXCEEDED`로 답한다. (TM-58, 5절 4) |
| S6B-AC-09 | When 같은 문의에 같은 때 여러 요청이 작업이나 기록을 만들어 한도를 넘게 되면, the system shall 어떤 한 순서로 한 것과 같은 결과를 준다(작업 30개, 기록 100개를 넘지 않는다). (TM-58, STATUS-7) |
| S6B-AC-13 | If 한 계정이 60초 안에 작업과 기록의 만들기·고치기를 60번 넘게 하면, then the system shall 429로 답한다. 지우기는 세지 않는다. (COM-8, TM-58, 5절 4) |

### 2.2 지우기와 흔적

| ID | 기준 |
|---|---|
| S6B-AC-10 | When 작업을 만든 사람이나 관리자가 작업을 지우면, the system shall 작업의 제목·담당자·마감일을 지우고 지운 흔적(지운 시각과 사람)을 남긴다. 그 작업의 사람 기록은 모두 내용을 지우고, 시스템 항목도 지운다(전·뒤 값이 남지 않는다). 응답은 204다. 목록에서 지운 작업은 `deleted: true`, `title: ""`, 담당자·마감일 `null`, `overdue: false`, `notes: []`다. 이미 지운 작업을 다시 지우면 같은 204다. `CLOSED` 문의에서도 지울 수 있다. (TASK-2, COM-7, 5절 15) |
| S6B-AC-11 | If 만들지 않은 상담원이 작업을 지우려 하면, then the system shall 403 `FORBIDDEN`으로 답한다. (TASK-2) |
| S6B-AC-12 | If 지운 작업을 고치거나 거기에 기록을 남기면, then the system shall 400 `TASK_DELETED`로 답하고 아무것도 바꾸지 않는다. The system shall 지운 작업을 열린 작업 수·내 작업·알림에서 뺀다. 작업 목록에는 흔적으로 남는다. (TASK-2, 댓글의 `COMMENT_DELETED`와 같은 꼴) |

### 2.3 기록

| ID | 기준 |
|---|---|
| S6B-AC-20 | When 상담 쪽이 작업에 기록을 남기면(1~4,000자), the system shall 쓴 사람과 시각과 함께 남긴다. 비었거나(앞뒤 공백을 자른 뒤) 4,000자를 넘으면 400이다. (TASK-3) |
| S6B-AC-21 | When 쓴 사람이 기록을 고치면, the system shall 내용을 바꾸고 고친 시각을 남긴다. If 다른 사람이면(관리자 포함), then 403이다. (TASK-3) |
| S6B-AC-22 | When 쓴 사람이나 관리자가 기록을 지우면, the system shall 내용을 빈 글로 바꾸고 흔적(지운 시각과 사람)을 남긴다. 응답은 204다. 그 밖의 상담원은 403이다. 다시 지우면 같은 204, 지운 기록을 고치면 400 `TASK_NOTE_DELETED`다(작업까지 지웠으면 작업을 먼저 보아 `TASK_DELETED`, C-5에서 정함). `CLOSED` 문의에서도 지울 수 있다. (TASK-3, COM-7, 5절 15) |
| S6B-AC-23 | If 작업에 지우지 않은 사람 기록이 이미 100개면, then the system shall 기록 남기기를 400 `TASK_NOTE_LIMIT_EXCEEDED`로 답한다. If 작업의 모든 항목(지운 기록과 시스템 항목 포함)이 1,000개면, then 기록 남기기와 항목을 남길 고치기(상태·담당자·마감일·제목)를 같은 400으로 답하고 아무것도 바꾸지 않는다. (TM-58, 5절 4) |
| S6B-AC-24 | When 상담 쪽이 문의의 작업 목록을 읽으면, the system shall 작업(지운 것은 흔적으로)을 만든 차례로, 작업마다 기록과 시스템 항목을 남긴 차례로 한 번에 준다. 응답에 그 문의의 열린 작업 수가 있다. (TASK-4) |

### 2.4 시스템 항목과 알림

| ID | 기준 |
|---|---|
| S6B-AC-30 | When 작업의 상태·담당자·마감일·제목이 바뀌면, the system shall 그 작업의 기록에 시스템 항목 하나(누가, 어느 칸 `STATUS`·`ASSIGNEE`·`DUE_DATE`·`TITLE`, 전·뒤 값)를 칸마다 남긴다. 담당자는 사람으로(`oldPerson`·`newPerson`), 마감일은 날짜로, 상태는 이름으로, 제목은 글로 준다. 바뀌지 않은 칸은 남기지 않는다. (TASK-5, RULE-06, 5절 7) |
| S6B-AC-31 | The system shall 작업의 일을 문의 이력에 남기지 않고, 문의의 `version`을 올리지 않는다. (TASK-5, 5절 8) |
| S6B-AC-32 | The system shall 시스템 항목을 고치기·지우기에서 403으로 답한다. (TASK-5) |
| S6B-AC-33 | When 작업 담당자가 다른 사람으로 정해지면(만들 때 정한 것 포함), the system shall 새 담당자에게 알림함 항목 `TASK_ASSIGNED` 하나와 메일 하나를 보낸다. 항목에는 문의와 작업(ID와 제목)이 있다. 자기를 담당자로 정하면 보내지 않는다. 담당자를 비우면 보내지 않는다. 옛 담당자의 항목은 그대로 둔다. (TASK-5, INBOX-1) |
| S6B-AC-34 | The system shall 작업 알림 메일을 받는 사람의 언어로 보낸다. 제목 줄은 `[{문의 키}] 작업을 맡았습니다: {작업 제목}`(영어 `[{key}] Task assigned: {title}`), 본문에 작업 제목, 문의 제목, 그 작업으로 가는 콘솔 링크(`/issues/{key}#task-{id}`)가 있다. 기록 내용은 넣지 않는다. 제목과 링크는 보낼 때 읽는다. 보내기 직전에 받는 사람이 `ACTIVE`이고 그 문의를 볼 수 있고 아직 그 작업의 담당자인지, 작업이 지워지지 않았는지 다시 보고, 아니면 보내지 않는다. (MAIL-1~5, MAIL-4, 5절 9, 17) |
| S6B-AC-35 | The system shall 작업의 일로 웹훅을 보내지 않고, 고객에게 알림함·메일을 보내지 않는다. 기록을 남기거나 상태·마감일을 바꿔도 알리지 않는다. (TASK-5) |
| S6B-AC-36 | When 작업을 지우면, the system shall 그 작업의 알림함 항목을 지운다(댓글을 지울 때와 같다). (TASK-2, 5절 10) |

### 2.5 경계와 고객

| ID | 기준 |
|---|---|
| S6B-AC-40 | If 상담원이 배정되지 않은 고객사 문의의 작업을 읽거나 쓰려 하면, then the system shall 없는 문의와 같은 404로 답한다. (RULE-03, TM-57) |
| S6B-AC-41 | If 작업 ID가 경로의 문의에 속하지 않으면(다른 문의, 다른 고객사의 작업), then the system shall 없는 작업과 같은 404로 답하고 아무것도 바꾸지 않는다. 기록 ID도 같다. (TM-57) |
| S6B-AC-42 | If 고객이 작업 경로를 부르면, then the system shall 있는 콘솔 경로와 같은 답(포털 호스트 404, 콘솔 호스트 401)을 준다(6a S6A-AC-41과 같다, 5절 16). 포털의 문의 응답, 목록, 알림함, 메일 어디에도 작업이 나오지 않는다. (TASK-1, RULE-04, D-49) |

### 2.6 닫힌 문의와 같은 때

|---|---|

| S6B-AC-51 | When 작업 쓰기와 문의 종료가 같은 때 오면, the system shall 어떤 한 순서로 한 것과 같은 결과를 준다(종료 뒤에 작업이 바뀌지 않는다). (STATUS-7) |
| S6B-AC-52 | When 문의를 다시 열면, the system shall 작업과 기록을 그대로 두고 다시 쓸 수 있게 한다. (STATUS-4) |

### 2.7 내 작업 (C-15)

| ID | 기준 |
|---|---|
| S6B-AC-60 | When 상담 쪽이 내 작업을 읽으면, the system shall 자기가 담당인 작업을 모든 문의에 걸쳐 준다. 항목마다 작업(ID, 제목, 상태, 마감일, `overdue`, 끝낸 시각), 문의(키, 제목, 상태), 고객사(코드, 이름)가 있다. 쪽 나누기는 COM-4다. (TASK-7) |
| S6B-AC-61 | The system shall 내 작업을 `status`로 거른다. 기본은 `OPEN`이고 `DONE`도 받는다. `status`는 한 값이다. 그 밖의 값과 여러 번 준 것은 400 `INVALID_INPUT`(필드 `status`, `UNKNOWN_VALUE`), 모르는 매개변수는 `UNKNOWN_PARAMETER`다. `OPEN`은 마감일이 빠른 순(없는 것은 뒤), 같으면 만든 차례다. `DONE`은 끝낸 시각이 늦은 순이다. 쪽 경계에서 빠지거나 겹치지 않는다. (TASK-7, 5절 11) |
| S6B-AC-62 | The system shall 내 작업에서 지금 볼 수 없는 문의(배정에서 빠진 고객사)와 `CLOSED` 문의와 지운 작업을 뺀다. (TASK-7, TM-57) |
| S6B-AC-63 | When 상담 쪽이 내 작업에서 "완료"를 누르면, the system shall 작업 고치기와 같은 요청으로 `DONE`이 된다. (TASK-7) |

### 2.8 콘솔 목록과 문의 닫기

| ID | 기준 |
|---|---|
| S6B-AC-70 | The system shall 콘솔 문의 목록의 항목마다 열린 작업 수(`openTaskCount`)를 준다. 포털 목록에는 없다. (roadmap 6b, 5절 12) |
| S6B-AC-71 | When 문의를 `RESOLVED`나 `CLOSED`로 바꿀 때 열린 작업이 있으면, the system shall 막지 않고 바꾼다. 작업은 그대로 `OPEN`이다. (TASK-8) |

### 2.9 담당 비우기 (ACCT-7의 작업 몫)

| ID | 기준 |

## 4. 테스트를 쓸 때 지킬 것

- 고객사 경계의 부정 테스트는 고객사 둘(A, B)과 A에만 배정된 상담원으로 쓴다(6a와 같다).
- 알림과 메일은 자기가 만든 문의와 작업으로만 센다. 메일은 4번의 시험 메일 받는 곳(Mailpit 대역)을 쓰는 앞 묶음 도움을 쓴다.
- 날짜 판정은 6a의 `DueSteps` 꼴로 앱 시계를 쓴다. 작업 마감일의 시간대 경우(Kiritimati, Pago_Pago)는 다시 쓰지 않는다(같은 계산을 쓴다는 것을 S6B-AC-05 한 경우로 본다).
- 잠긴 앞 테스트: `C4IssueDetail.actions.test.tsx`는 해결이 묻지 않고 종료가 지금 문구로 묻는다고 단언한다. 열린 작업이 없을 때의 동작이라 그대로 맞는다. 가짜 서버(`console.ts`)의 기본 핸들러에 작업 목록(빈 `items`, `openCount: 0`)과 내 작업(빈 쪽)을 더한다(`process.md` C-4).
- 옆 메뉴를 그대로 견주는 잠긴 테스트가 있다: `layout.inbox.test.tsx` 54~55줄, `adminOnly.1b.test.tsx` 14·23줄. "내 작업"이 "문의" 다음에 들어가므로 이 묶음의 테스트 탭이 그 줄을 맞춘다(관리자 `['문의', '내 작업', '고객사', …]`, 상담원 `['문의', '내 작업']`).
