# 4번 묶음 사전 부검

> 4번 묶음(대화와 알림)을 내고 석 달 뒤 일이 틀어졌다고 가정하고, 어떻게 틀어졌을지와 막을 장치를 적는다. 개인정보 흐름, 고객사 경계, 마이그레이션, 공개 계약을 건드려서 전체 경로다(`process.md`).
> 표시: [소스]는 레포의 코드나 마이그레이션에서 본 것, [추론]은 확인하지 않은 판단이다.
> 장치는 `acceptance.md`와 `design.md`에 옮겼다. 묶음이 끝나면 이 파일은 `design/archive/4-talk/`로 간다.
> 상태: **메인이 정함, 사용자 확인 전**(2026-10-12).

## 1. 고객의 알림함에 상담원의 이름이 나왔다

| 항목 | 내용 |
|---|---|
| 장면 | 포털의 알림함 응답에 일으킨 사람의 이름과 계정 ID가 실렸다. 화면은 "지원팀"이라고 썼지만 브라우저의 개발자 도구에는 상담원의 이름이 보였다. 해결 메일에는 "○○ 님이 해결로 바꿨습니다"가 나갔다 |
| 원인 | 콘솔의 알림 타입을 포털이 같이 썼다. 댓글 행을 읽는 쿼리는 고객에게도 쓴 사람의 이름을 담아 준다 [소스: `CommentRepository.CommentRow`]. 가리는 곳은 컨트롤러의 변환 하나다 [소스: `PortalIssueController.person`] |
| 막는 법 | 포털과 콘솔의 알림 타입을 따로 둔다(D-41). 포털의 일으킨 사람은 댓글과 같은 변환을 거친다(`design.md` 4절). 새 메일은 "지원팀"만 쓰고 이름을 받는 인자가 없다(`design.md` 5절) |
| 확인 테스트 | 상담원이 답하고 해결로 바꾸고 다시 연 문의로, 포털의 알림 목록 응답과 새 메일 셋의 본문 전체에서 그 상담원의 이름, 이메일, 계정 ID를 찾아 없다(S0-AC-98의 꼴). 포털 계약 스냅샷에 상담 쪽 전용 이름 조각이 없다 |
| 옮길 곳 | S4-AC-15, 41, 46, 53, 71 |

## 2. 배정이 빠진 상담원의 알림함에 그 고객사의 문의 제목이 남았다

| 항목 | 내용 |
|---|---|
| 장면 | A사 배정에서 빠진 상담원이 알림함을 열자 A사 문의의 지금 제목이 그대로 보였다. 그 뒤에 고쳐진 제목까지 보였다. 안 읽은 수도 A사의 새 일을 계속 셌다 |
| 원인 | 알림함이 계정만 보고 읽었다 [소스: `OpsRepository`의 `listInbox`, `countUnread`]. 제목을 읽을 때 붙이므로 항목이 남아 있으면 지금 값이 나간다 |
| 막는 법 | 목록과 수 모두 지금 볼 수 있는 문의의 항목만 읽는다(`design.md` 0절 3, 4절). 넣을 때도 볼 수 없는 사람에게는 넣지 않는다(S4-AC-36). 보내기 직전의 확인은 이미 있다 [소스: `MailSender`] |
| 남는 것 | 항목은 지우지 않고 숨긴다. 배정을 되돌리면 다시 보인다. 그 사람의 항목이 가리키는 문의가 많으면 한 번의 물음이 커진다(`design.md` 7절 실험 3) |
| 확인 테스트 | 담당자로 정해 항목을 만든 뒤 배정을 빼면 목록과 안 읽은 수에서 사라지고, 되돌리면 다시 나온다. 소속에서 빠진 동료 고객, 비공개 문의도 같다. C-7 점검 탭이 수를 세는 쪽에서만 거르기를 뺀 틀린 구현을 넣어 테스트가 잡는지 본다 |
| 옮길 곳 | S4-AC-26, 42, 43, 47, 70 |

## 3. 멘션 후보로 맡지 않은 고객사의 사람을 봤다

| 항목 | 내용 |
|---|---|
| 장면 | A사에만 배정된 상담원이 B사 문의 키로 멘션 후보를 요청해 B사 문의를 올린 고객의 이름을 받았다. 다른 날에는 내부 메모에 고객을 멘션해, 고객이 "내부 댓글에서 언급됐다"는 메일을 받았다 |
| 원인 | 후보 길이 "상담 쪽이면 된다"만 봤다. 멘션 대상을 달 때의 공개 여부와 견주지 않았다 |
| 막는 법 | 후보는 문의를 범위 안에서 먼저 찾는다. 범위 밖은 404다(S4-AC-23). 멘션 대상은 서버가 다시 보고, 내부 댓글에서 올린 고객은 대상이 아니다(S4-AC-20). 후보는 이메일을 주지 않는다(S4-AC-22) |
| 확인 테스트 | 배정되지 않은 상담원의 후보 요청이 404다. 내부 댓글에 올린 고객을 멘션하면 400이고 댓글이 없고 메일과 항목이 없다. 경계 테스트 목록에 새 엔드포인트가 있다 |
| 옮길 곳 | S4-AC-20, 22, 23, 70 |

## 4. 지운 댓글의 내용이 메일로 나갔다

| 항목 | 내용 |
|---|---|
| 장면 | 상담원이 다른 고객의 전화번호를 잘못 적은 답변을 달고 10초 뒤에 지웠다. 고객은 "지원팀이 답변했습니다" 메일을 받고 포털에 들어와 지운 댓글을 봤다. 다른 설치에서는 지운 댓글의 내용이 댓글 목록 응답에 그대로 있었고 화면만 가렸다 |
| 원인 | 메일 대기 행에 댓글 칸이 있지만 보낼 때 읽지 않는다 [소스: `MailSender`, `WebhookSender`]. 지우기가 표시만 남기고 내용을 두었다 |
| 막는 법 | 지우면 내용 칸을 비운다(`design.md` 0절 8). 그 댓글의 항목을 지우고(S4-AC-16), 보내기 직전에 댓글이 지워졌는지 본다(S4-AC-55) |
| 남는 것 | 이미 나간 메일은 되돌리지 못한다. 메일에는 댓글 내용이 없고 제목과 링크뿐이다 [소스: `MailText.staffComment`]. DB 백업에는 지우기 전의 내용이 남는다 |
| 확인 테스트 | 메일을 붙잡아 둔 채(`SmtpGate` [소스]) 댓글을 지우면 풀어도 메일이 없다. 지운 댓글의 글자를 DB의 모든 표에서 찾아 없다(잠긴 테스트의 `Rows` 꼴). 포털과 콘솔의 댓글 응답에 그 글자가 없다 |
| 옮길 곳 | S4-AC-10, 16, 18, 55 |

## 5. 한 번 누른 일에 알림이 두 번, 세 번 갔다

| 항목 | 내용 |
|---|---|
| 장면 | 상담원이 고객을 멘션한 공개 답변을 달았다. 고객은 답변 메일과 멘션 메일을 같이 받았다. 댓글을 고칠 때마다 멘션된 사람 모두가 메일을 다시 받았다. 상담원 둘이 같은 때 "해결"을 눌러 고객이 해결 메일을 두 통 받았다 |
| 원인 | 댓글 알림과 멘션 알림을 따로 넣었다. 고치기가 멘션 목록 전체를 새로 알렸다. 상태 변경의 알림을 UPDATE가 행을 바꿨는지 보지 않고 넣었다 |
| 막는 법 | 받는 사람은 한 곳에서 정하고 같은 요청의 겹침은 멘션 하나로 줄인다(`design.md` 0절 2, 3절). 고치기는 새로 더한 사람만 알린다(S4-AC-24). 항목과 대기 행은 UPDATE가 행을 바꾼 뒤에만 넣는다(`design.md` 3절) |
| 남는 것 | 보내기 대기는 최소 한 번이라 메일이 두 번 갈 수 있다(D-39). 멘션을 뺐다가 다시 넣으면 다시 알린다 |
| 확인 테스트 | 멘션한 공개 답변 하나에 고객의 메일과 항목이 하나씩이다. 내용만 고치면 새 메일이 없다. 같은 전이 둘을 같은 때 보내면 항목과 메일 대기 행이 한 건이다 |
| 옮길 곳 | S4-AC-24, 35, 37, 50 |

## 6. 새 메일이 앞 묶음의 테스트와 화면을 깼다

| 항목 | 내용 |
|---|---|
| 장면 | 구현 탭이 해결 메일을 넣자 3번 묶음의 잠긴 테스트 여럿이 "고객에게 온 메일은 한 통"에서 실패했다. 구현 탭은 테스트를 고칠 수 없어 멈췄다. 웹에서는 머리가 안 읽은 수를 요청하자 화면 테스트 수백 개의 가짜 서버가 모르는 요청으로 실패했다 |
| 원인 | 앞 묶음의 테스트가 "이 일 뒤에 메일은 이것뿐", "요청은 이것뿐"을 단언한다. 새 알림은 그 수를 바꾼다 |
| 막는 법 | 계약 탭이 껍데기를 쓰기 전에 그런 단언을 찾아 목록으로 낸다(`design.md` 7절 실험 1, 2, 4, 7). 테스트 쪽 탭이 구현보다 먼저 맞춘다. 웹은 화면 초안을 쓰기 전에 잠긴 테스트와 가짜 서버를 읽는다(3번 C-11 규칙. `screens.md` 0절에 결과를 적는다) |
| 남는 것 | 숨긴 E2E 저장소의 앞 묶음 클래스도 메일 수를 셀 수 있다. E2E 탭이 같이 본다 |
| 확인 테스트 | C-6의 실패 확인에서 앞 묶음의 테스트는 모두 통과하고 새 테스트만 실패한다 |
| 옮길 곳 | `design.md` 7절, `acceptance.md` 4절, S4-AC-75 |

## 7. 안 읽은 수를 받는 요청이 앱을 느리게 했다

| 항목 | 내용 |
|---|---|
| 장면 | 상담원 50명이 콘솔을 하루 종일 열어 두었다. 탭마다 60초에 한 번 안 읽은 수를 받았고, 요청마다 그 사람의 항목 전부와 문의 범위를 읽었다. 다른 날에는 세션이 끝난 탭이 밤새 401을 받으며 요청을 보냈다 |
| 원인 | 수를 세는 길이 전체 목록과 같은 쿼리를 썼다. 화면이 실패해도 주기를 멈추지 않았다 |
| 막는 법 | 안 읽은 수는 안 읽은 항목만 읽고 그 색인을 둔다(`design.md` 1절). 탭이 보이지 않으면 받지 않고, 401이면 멈춘다(S4-AC-64, 69). 실험 3으로 시간을 잰다 |
| 남는 것 | 안 읽은 항목을 수천 건 쌓아 둔 사람은 느리다. "모두 읽음"이 있다 |
| 확인 테스트 | 화면 테스트: 탭이 숨겨진 동안 요청이 없고, 401 뒤에 요청이 없다. 서버는 실험 3의 수치를 `verify.md`에 적는다 |
| 옮길 곳 | S4-AC-43, 64, 69 |

## 8. 올린 뒤 알림함이 500이 됐다

| 항목 | 내용 |
|---|---|
| 장면 | 0.3.0에서 올린 설치의 관리자가 알림함을 열자 500이 났다. 올리기 전에 쌓인 `MEMBERSHIP_REQUESTED` 항목은 문의 칸이 비어 있었고, 새 코드는 모든 항목에 문의가 있다고 보았다 |
| 원인 | 있던 관리자 항목(문의 없음)과 새 항목(문의 있음)이 한 표에 있다. 종류 이름을 enum으로 바꾸는 곳은 모르는 이름에서 던진다 [소스: `ConsoleNotificationController`의 `valueOf`] |
| 막는 법 | 새 칸은 모두 `null`을 받고 응답도 `null`을 준다(D-44). 업그레이드 테스트가 세 견본의 관리자 알림함을 새 이미지로 읽는다(S4-AC-72). 0.3.0 견본에는 소속 요청 항목이 있다 [소스: `deploy/upgrade/README.md`] |
| 확인 테스트 | 견본을 올린 뒤 관리자의 알림 목록이 200이고 있던 항목이 종류와 고객사 코드 그대로다 |
| 옮길 곳 | S4-AC-38, 72, 73 |

## 9. 받아들이는 것

- 담당자가 없는 문의에 고객이 댓글을 달면 알림함에는 아무에게도 가지 않는다. 웹훅과 "담당 없음" 보기가 맡는다(`acceptance.md` 5절 9).
- 멘션은 상담 쪽만 쓴다(`acceptance.md` 5절 1).
- 메일 한 주소에 한 시간 50통의 상한(MAIL-6)은 4b에 있다. 그때까지는 새 메일 여섯이 상한 없이 나간다. 한 일에 한 사람이 받는 메일은 한 통이다.
- 알림함 항목은 보관 기간 없이 쌓인다. 7번의 영구 삭제가 문의의 항목을 지운다.
