# 4번 묶음 수용 기준: 대화와 알림

> `roadmap.md` 6절 4번의 EARS 수용 기준이다. 묶음이 끝나면 `design/archive/4-talk/`로 간다(D-27).
> 전체 경로다. 개인정보 흐름(고객에게 가는 알림함과 메일, 멘션 후보), 고객사 경계(알림함과 멘션 후보라는 새 옆길), 마이그레이션(V12), 공개 계약(포털 알림 API, 새 오류 코드)을 건드린다. 사전 부검은 같은 폴더의 `premortem.md`에 쓴다(C-3).
> 꼴은 앞 묶음과 같다. 괄호 안은 근거다. 규칙 ID의 글은 같은 폴더 `rules.md`와 앞 묶음의 `rules.md`에 있다. 기준 ID는 `S4-AC-nn`이다.
> 관계있는 결정(`adr.md`): D-12, D-18, D-24, D-39, D-41, D-43, D-44, D-49. 새 결정은 없다. 위협 모델: TM-02, TM-07, TM-08, TM-24, TM-30, TM-37.
> 기준 한 줄에는 밖에서 보이는 동작 하나만 적는다. 만드는 법은 설계(`design.md`)에 둔다.
> 상태: **메인이 정함, 사용자 확인 전**(2026-10-12). 사용자가 남은 묶음의 설계를 메인의 추천대로 진행하라고 맡겼다. 규칙에 없던 것을 메인이 넣은 곳은 5절에 모았다.

## 1. 넣는 것과 미루는 것

앞 묶음이 이미 만든 것: 댓글 달기와 목록, 공개·내부 구분, `CLOSED` 문의의 댓글 거절(CMT-1·2·4), 댓글 첨부 올리기(서버), 메일 넷(초대, 비밀번호 재설정, 상담 쪽 공개 댓글, 대리 등록), 웹훅 여섯, 보내기 대기와 루프(MAIL-2~5), 관리자 알림함(운영 경보 둘과 소속 요청, 콘솔 API 셋). 알림함 화면은 두 앱 모두 없다.

roadmap이 4번에 둔 것을 둘로 나눈다. 이 묶음(4a)은 사람이 쓰는 대화와 알림이고, 4b는 보내기의 운영이다.

## 2. 수용 기준

"상담 쪽"은 상담원과 관리자다. 상담원에 관한 기준은 배정된 고객사의 문의에만 해당한다. "올린 고객"은 문의의 올린 사람이다. "볼 수 있다"는 `docs/use/permissions.md`의 범위(RULE-02, RULE-03, ISSUE-4)다. "담당자"는 문의의 담당자 칸에 있는 계정이다.

### 2.1 댓글 고치기

| ID | 기준 |
|---|---|
| S4-AC-01 | When 댓글을 쓴 사람이 그 댓글의 내용을 고치면, the system shall 저장하고 고친 시각을 남겨 고친 댓글을 준다. 길이와 글자 규칙은 달기와 같다(1~4,000자). (CMT-3, CMT-1) |
| S4-AC-02 | If 쓴 사람이 아닌 사람이 볼 수 있는 댓글을 고치려 하면, then the system shall 403으로 답한다. 관리자도 남의 댓글은 고치지 못한다. (CMT-3, COM-2) |
| S4-AC-03 | If 고객이 내부 댓글을, 또는 누구든 볼 수 없는 문의의 댓글이나 없는 댓글이나 다른 문의의 댓글 ID를 고치거나 지우려 하면, then the system shall 404로 답하고 아무것도 바꾸지 않는다. (CMT-2, COM-1, RULE-01) |
| S4-AC-04 | If 문의가 `CLOSED`이면, then the system shall 댓글 고치기를 400 `ISSUE_CLOSED`로 답한다. (CMT-4) |
| S4-AC-05 | If 그 고객사 소속에서 빠진 올린 고객이 자기 댓글을 고치거나 지우려 하면, then the system shall 403으로 답한다. (PROJ-4) |
| S4-AC-06 | When 보낸 내용이 지금 내용과 같으면, the system shall 200으로 답하고 고친 시각을 바꾸지 않는다. (5절 4) |
| S4-AC-07 | The system shall 댓글 응답에 고친 시각(고친 적이 없으면 `null`)을 준다. 공개인지 내부인지는 고칠 수 없다. (CMT-3, D-44) |
| S4-AC-08 | If 지운 댓글을 고치려 하면, then the system shall 400 `COMMENT_DELETED`로 답한다. (COM-7, 5절 5) |
| S4-AC-09 | The system shall 댓글 고치기를 댓글 달기와 같은 요청 수 제한(한 계정에 60초 동안 30건)에 함께 센다. (COM-8, 5절 6) |

### 2.2 댓글 지우기

| ID | 기준 |
|---|---|
| S4-AC-10 | When 쓴 사람이나 관리자가 댓글을 지우면, the system shall 내용을 비우고 지운 표시, 지운 시각, 지운 사람을 남긴다. 댓글 목록에서 그 댓글은 제자리에 지운 댓글로 남고 수에도 그대로 센다. (CMT-3, COM-7) |
| S4-AC-11 | If 상담원이 남의 댓글을, 올린 고객이 상담 쪽의 댓글을, 또는 동료 고객이 올린 고객의 댓글을 지우려 하면, then the system shall 403으로 답한다. (CMT-3, COM-2) |
| S4-AC-12 | When 이미 지운 댓글을 다시 지우면, the system shall 같은 응답을 주고 지운 시각과 지운 사람을 바꾸지 않는다. (PROJ-4와 같은 꼴) |
| S4-AC-13 | While 문의가 `CLOSED`여도, the system shall 댓글 지우기를 받는다. (5절 7) |
| S4-AC-14 | When 댓글을 지우면, the system shall 그 댓글에 붙은 첨부도 같은 요청에서 지운다(첨부의 지우기 흔적 그대로). 문의에 붙은 첨부와 다른 댓글의 첨부는 그대로다. (CMT-3, ATT-5) |
| S4-AC-15 | The system shall 포털의 지운 댓글에 쓴 사람(상담 쪽이면 "지원팀" 표시)과 지운 시각만 주고, 지운 사람은 주지 않는다. 콘솔에는 지운 사람을 계정 ID, 이름, 역할로 준다. (ANON-1, D-49) |
| S4-AC-16 | When 댓글을 지우면, the system shall 그 댓글 때문에 생긴 알림함 항목을 함께 지우고, 아직 나가지 않은 그 댓글의 메일을 보내지 않는다. (MAIL-4, 5절 8) |
| S4-AC-17 | The system shall 상담 쪽의 첫 공개 댓글이 지워져도 문의의 첫 응답 시각을 그대로 둔다. (ISSUE-10) |
| S4-AC-18 | The system shall 지운 댓글의 내용을 어느 응답에도 주지 않는다. 검색, 알림함, 메일, 웹훅에서도 그렇다. (COM-7, PII-1) |

### 2.3 멘션

| ID | 기준 |
|---|---|
| S4-AC-19 | When 상담 쪽이 댓글을 달면서 멘션할 계정을 1~10명 주면, the system shall 댓글과 함께 저장하고 콘솔의 댓글 응답에 멘션된 사람을 계정 ID, 이름, 역할로 준다. 같은 계정을 두 번 주면 한 번으로 친다. (MNT-1) |
| S4-AC-20 | If 멘션할 계정이 그 문의를 볼 수 있는 `ACTIVE` 계정 가운데 대상(관리자, 그 고객사에 배정된 상담원, 공개 댓글이면 올린 고객)이 아니면, then the system shall 까닭과 관계없이 같은 400과 `fields`의 `UNKNOWN_VALUE`로 답하고 댓글을 만들지 않는다. 자기 자신, 내부 댓글에서의 올린 고객, 다른 고객, 배정되지 않은 상담원, 정지·수락 전 계정, 없는 계정이 모두 그렇다. (MNT-1, INVITE-5) |
| S4-AC-21 | If 멘션이 10명을 넘으면, then the system shall 400과 `fields`의 `TOO_MANY`로 답한다. (MNT-1, 5절 5) |
| S4-AC-22 | When 상담 쪽이 한 문의의 멘션 후보를 공개 댓글용이나 내부 댓글용으로 요청하면, the system shall S4-AC-20의 대상을 계정 ID, 이름, 역할로 준다. 요청한 사람 자신은 빠지고, 올린 고객은 공개 댓글용에만 있다. 이메일은 주지 않는다. (MNT-2) |
| S4-AC-23 | If 상담원이 볼 수 없는 문의의 멘션 후보를 요청하면, then the system shall 404로 답한다. (COM-1, RULE-03, TM-02) |
| S4-AC-24 | When 쓴 사람이 댓글을 고치면서 멘션 목록을 보내면, the system shall 목록을 그것으로 바꾸고, 새로 더해진 사람에게만 알린다. 그대로 남은 사람과 빠진 사람에게는 알리지 않는다. 목록을 보내지 않으면 멘션은 그대로다. (MNT-2) |
| S4-AC-25 | The system shall 포털의 댓글 요청에 멘션 칸을 두지 않고, 포털의 댓글 응답에 멘션된 사람을 넣지 않는다. 계약 스냅샷이 이것을 고정한다. (ANON-1, TM-07, 5절 1) |
| S4-AC-26 | When 멘션된 사람이 뒤에 그 문의를 볼 수 없게 되면(배정 빠짐, 정지), the system shall 댓글의 멘션 목록에는 그대로 두되 그 사람의 알림함 목록에서는 그 항목을 숨긴다. (PROJ-4, INBOX-3) |

### 2.4 알림함에 넣기

"알림 표"는 `rules.md` 2절의 표다. 이 묶음이 넣는 줄은 아래 기준에 모두 있다.

| ID | 기준 |
|---|---|
| S4-AC-27 | When 상담 쪽이 공개 댓글을 달면, the system shall 올린 고객의 알림함에 항목 하나를 넣는다. 내부 댓글은 넣지 않는다. (알림 표, INBOX-1, TM-08) |
| S4-AC-28 | When 올린 고객이 댓글을 달면, the system shall 담당자의 알림함에 항목 하나를 넣는다. (알림 표, D-12) |
| S4-AC-29 | When 상담 쪽이 문의를 `RESOLVED`나 `CLOSED`로 바꾸거나 재오픈하면, the system shall 올린 고객의 알림함에 그 일의 항목 하나를 넣는다. `CONFIRMED`와 `IN_PROGRESS`로 가는 것은 넣지 않는다. (알림 표) |
| S4-AC-30 | When 올린 고객이 문의를 종료하거나(해결 확인 포함) 재오픈하면, the system shall 담당자의 알림함에 그 일의 항목 하나를 넣는다. (알림 표, D-12) |
| S4-AC-31 | When 상담 쪽이 담당자를 정하거나 바꾸면, the system shall 새 담당자의 알림함에 항목 하나를 넣는다. 담당자를 비우면 아무에게도 넣지 않고, 전 담당자에게도 넣지 않는다. 담당 일괄 비우기(S3-AC-69)도 넣지 않는다. (알림 표) |
| S4-AC-32 | When 상담 쪽이 대리 등록하면, the system shall 올린 고객의 알림함에 항목 하나를 넣는다. (알림 표) |
| S4-AC-33 | When 댓글에 멘션되면(달 때, 고치며 새로 더해질 때), the system shall 멘션된 사람의 알림함에 항목 하나를 넣는다. (알림 표, MNT-2) |
| S4-AC-34 | The system shall 일을 일으킨 사람 자신에게는 항목을 넣지 않는다. 자기를 담당자로 정한 것, 담당자가 자기 문의에 한 일이 그렇다. (INBOX-2) |
| S4-AC-35 | When 한 요청에서 같은 사람이 멘션과 댓글 알림을 함께 받게 되면, the system shall 멘션 항목 하나만 넣는다. (INBOX-2) |
| S4-AC-36 | The system shall 항목을 넣는 순간에 `ACTIVE`가 아니거나 그 문의를 볼 수 없는 계정에게는 넣지 않는다. 담당자가 정지됐거나 배정에서 빠져 있으면 담당자에게 가는 항목은 생기지 않는다. (INBOX-2, ISSUE-11, 5절 9) |
| S4-AC-37 | The system shall 항목을 바꾼 내용과 같은 트랜잭션에 저장한다. 요청이 실패하면(400, 403, 404, 409) 항목이 없고, 같은 값으로 바꾼 요청(같은 담당자, 같은 내용)도 항목이 없다. (INBOX-1) |
| S4-AC-38 | The system shall 지금 있는 관리자 항목(운영 경보, 소속 요청)을 그대로 넣고 그대로 준다. (OPS-1, S2-AC-39) |

### 2.5 알림함 읽기

| ID | 기준 |
|---|---|
| S4-AC-39 | When 로그인한 사람이 자기 알림함 목록을 요청하면, the system shall 자기 항목만 최신순으로 COM-4로 쪽 나눠 준다. 포털과 콘솔에 각각 있다. (INBOX-3) |
| S4-AC-40 | The system shall 문의의 항목에 종류, 문의 키와 지금 제목, 고객사 코드, 댓글 ID(없으면 `null`), 일으킨 사람, 만든 시각, 읽은 시각(없으면 `null`)을 준다. 제목은 항목을 만든 뒤 고쳐졌으면 고친 제목이다. (INBOX-1, D-44) |
| S4-AC-41 | The system shall 포털의 항목에서 일으킨 사람을 "지원팀" 표시로만 주고, 상담 쪽 사람의 이름, 이메일, 계정 ID를 넣지 않는다. 콘솔의 항목에는 일으킨 사람을 계정 ID, 이름, 역할로 준다. (ANON-1, INBOX-1, TM-08) |
| S4-AC-42 | The system shall 지금 볼 수 없는 문의의 항목을 목록과 안 읽은 수에서 뺀다. 다시 볼 수 있게 되면(배정을 되돌림) 다시 나온다. (INBOX-3, TM-02, RULE-01, RULE-03) |

## 4. 테스트를 쓸 때 지킬 것

- 기준 하나에 테스트는 동작 하나꼴로 쓴다. "누가 무엇을 받는가"(S4-AC-27~36, 48~50)는 일과 받는 사람의 표를 매개변수 테스트로 돈다. 도움 코드는 `support/`, `issue`, `notify` 패키지에 이미 있는 것을 쓴다.
- "메일이 없다"는 뒤에 온 다른 메일을 기다린 뒤에 센다(`MemberMailTest`의 꼴). 고정 대기를 쓰지 않는다.
- 알림함 테스트는 자기가 만든 문의의 항목만 센다(같은 앱과 DB를 나눠 쓴다). 안 읽은 수는 새로 만든 계정으로 본다.
- "까닭과 관계없이 같은 400"(S4-AC-20)은 경우마다 상태 코드와 본문 전체를 견준다.
- 60초 다시 받기(S4-AC-64)는 가짜 시계로 본다. 한 번에 긴 시간을 옮기지 않는다(3번 C-11의 흔들린 테스트).
- 웹 테스트의 가짜 응답은 계약 파일의 설명과 맞춘다(3번 C-11 규칙). 지운 댓글의 `content`, 고친 적 없는 댓글의 `editedAt`, 포털 항목의 일으킨 사람이 계약대로인지 본다.
- 메일의 글은 스냅샷으로 고정하되, 오류 문구나 순서 같은 우연한 값은 고정하지 않는다.
- 앞 묶음의 잠긴 테스트 가운데 이 묶음의 기준과 부딪히는 것은 계약 탭 뒤의 테스트 탭이 맞춘다. 지금 아는 것은 `MembershipRequestMailTest`의 "관리자에게 메일 없음"(S4-AC-75) 하나다. 문의의 상태를 바꾼 뒤 고객의 메일 수를 세는 테스트가 더 있는지 그 탭이 찾는다.
