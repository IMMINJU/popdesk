## 1. 넣는 것과 미루는 것

8a가 만든 것: 정책과 버전, 문의마다 두 시계(첫 응답, 해결)와 확정(`MET`·`MISSED`·`NONE`), 돌고 있는 목표의 경고·기한 시각, 상태 판정(`SlaClocks.state`), 정책 버전이 오르면 도는 다시 계산 작업 `sla-recalculate`(1분), 사람의 쓰기가 옛 버전 문의를 먼저 지금 버전으로 따라잡는 것(`SlaWrite`), 우선순위가 바뀌면 그 문의만 바로 다시 계산. 알림, "알렸음" 표시, 첫 응답 확정 시각은 없다.

| 기능 | 8b에 넣는 것 | 미루는 것 |
|---|---|---|
| SLA-5 | 시간이 지나 `warning`·`breached`가 된 목표를 한 번씩 알림(알림함, 넘김은 메일과 웹훅도), "알렸음" 표시와 낮추기, 다시 계산 요약 | – |
| SLA-7, STATS-4 | 고객사마다 기간(7·30·90일) 안에 확정된 목표의 중앙값과 지킴 수 | 기간을 날짜로 고르기, 상담원별 통계 |
| 화면 | C-7 SLA 알림 다섯 종류, C-5 기간과 SLA 칸 둘 | 포털은 바뀌지 않는다 |

## 2. 수용 기준

말의 뜻:

- "알림 단계"는 `sla-recalculate` 작업의 회차가 하는 일 가운데 하나다(5절 1). "알린다"는 알림함 항목을 넣고 메일·웹훅을 보내기 대기에 넣는 것이다(메일이 실제로 닿는 때는 보내기 루프와 MAIL-6을 따른다).
- "목표의 단계"는 시계가 돌고 있을 때만 있다: 목표가 있으면 `ok` < `warning` < `breached`, 목표가 없으면(그 우선순위의 목표가 비었거나 정책이 꺼짐) "목표 없음"이고 셈에서는 `ok`와 같다. 멈춘 시계(확정, 휴지통)는 단계가 없다.
- "알렸음 표시"는 목표마다 `null`, `WARNING`, `BREACHED` 가운데 하나다(5절 2).
- "받는 상담 쪽"은 S8B-AC-03의 사람들이다.
- "다시 계산"은 정책 버전이 올라 문의의 시계를 지금 버전으로 옮기는 일이다. 작업이 하든, 작업보다 먼저 사람의 쓰기가 따라잡든 같다(5절 5).

### 2.1 시간이 지나 바뀐 상태의 알림

| ID | 기준 |
|---|---|
| S8B-AC-01 | When 알림 단계가 SLA 대상 문의(휴지통이 아니고, 계산 버전이 지금 정책 버전)의 돌고 있는 목표 하나가 `warning`이고 그 목표의 알렸음 표시가 `null`인 것을 찾으면, the system shall 받는 상담 쪽 각자의 알림함에 항목 하나(첫 응답이면 `SLA_RESPONSE_WARNING`, 해결이면 `SLA_RESOLUTION_WARNING`)를 남기고 표시를 `WARNING`으로 한다. 메일과 웹훅은 보내지 않는다. (SLA-5, 알림 표) |
| S8B-AC-02 | When 알림 단계가 돌고 있는 목표 하나가 `breached`이고 알렸음 표시가 `BREACHED`가 아닌 것을 찾으면, the system shall 받는 상담 쪽과 `ACTIVE` 관리자 전부(겹치는 사람은 한 번) 각자에게 알림함 항목 하나(`SLA_RESPONSE_BREACHED`·`SLA_RESOLUTION_BREACHED`)와 메일 한 통을 남기고, 웹훅이 켜져 있으면 웹훅 하나를 넣고, 표시를 `BREACHED`로 한다. 표시가 `null`이었어도(경고를 건너뛰고 넘김) 경고 항목은 따로 남기지 않는다. 두 목표가 같은 회차에 넘김이면 목표마다 따로 한다. (SLA-5, 알림 표, 5절 4) |
| S8B-AC-03 | The system shall 받는 상담 쪽을 이렇게 정한다: 담당자가 있고 `ACTIVE`이며 지금 그 문의를 볼 수 있으면 담당자 한 사람. 아니면 그 고객사에 배정된 `ACTIVE` 상담원 전부. 그것도 없으면 경고는 `ACTIVE` 관리자 전부(넘김은 이미 관리자 전부가 받는다). 고객 계정은 어떤 경우에도 받지 않는다(그 고객사의 고객이 고객사 구성원이어도). 항목의 `actor`는 `null`이다. (ISSUE-11, 알림 표, 5절 3) |
| S8B-AC-04 | The system shall 한 목표의 한 단계를 한 번만 알린다: 경고 시각이나 기한이 지난 뒤 회차가 여러 번 돌아도 그 목표·그 단계의 항목은 받는 사람마다 하나, 메일은 한 통, 웹훅은 하나다. 표시는 단계가 없는 동안(멈춤, 휴지통) 그대로 남는다. 그래서 `BREACHED`로 알린 해결 목표가 재오픈 뒤에도 넘김이면 다시 알리지 않는다. (SLA-5, 5절 2) |
| S8B-AC-05 | If 문의가 휴지통에 있으면, then the system shall 그 문의를 알리지 않는다. 휴지통에서 꺼낸 뒤 그 목표가 경고·넘김이고 그 단계가 표시되지 않았으면 다음 회차에 알린다. 멈춘(확정한) 목표와 목표 없음은 알리지 않는다. (SLA-5) |
| S8B-AC-06 | When 목표가 경고 시각이나 기한을 지나면, the system shall 그 뒤 2분 안에 알린다. 다시 계산을 기다리는 문의(S8B-AC-09)와 다른 쓰기가 잡고 있던 문의는 빼고, 작업이 1분마다 돌고 실패하지 않는 동안이다. (SLA-5) |
| S8B-AC-07 | The system shall 알렸음 표시를 쓸 때 문의의 `version`과 `updatedAt`을 바꾸지 않고 문의 이력에 남기지 않는다. (8a 5절 14, 8a 설계 0절 9) |
| S8B-AC-08 | When 시계를 다시 쓰는 일(우선순위 바꾸기, 휴지통에서 꺼내기, 재오픈, 다시 계산)로 돌고 있는 목표의 단계가 표시보다 앞이 되면, the system shall 같은 쓰기에서 표시를 지금 단계로 낮춘다(`ok`와 목표 없음이면 `null`, `warning`이면 `WARNING`). 그 뒤 다시 그 단계가 되면 다시 알린다. (SLA-5, 5절 13) |
| S8B-AC-09 | If 정책이 바뀌어 문의의 기한이 늘었으면, then the system shall 옛 경고 시각이나 옛 기한이 지나도 그 문의를 알리지 않고 새 기한으로 알린다(옛 버전으로 계산된 문의는 다시 계산된 뒤에 본다). (SLA-5, 5절 1) |
| S8B-AC-10 | When 사람이 우선순위를 바꿔 목표의 단계가 뒤로 가면(예: 높게 바꿔 바로 넘김), the system shall 그것을 다시 계산 요약에 넣지 않고 S8B-AC-01·02대로 하나씩 알린다. 바꾼 사람이 받는 사람이어도 받는다(INBOX-2의 "자기가 일으킨 일"이 아니다). (SLA-5, 5절 6) |
| S8B-AC-11 | When 상담원이 고객사 배정에서 빠지거나 문의를 볼 수 없게 되면, the system shall 그 사람의 SLA 항목을 목록과 안 읽은 수에서 감춘다(있는 INBOX-3대로). 모두 읽음은 SLA 항목도 읽음으로 한다. (INBOX-3, TM-64) |

### 2.2 다시 계산 요약

| ID | 기준 |
|---|---|
| S8B-AC-12 | The system shall 다시 계산으로 바뀐 것을 문의 단위로 센다. 문의의 단계는 돌고 있는 두 목표 가운데 뒤의 것이다(8a 5절 12). 다시 계산 직전 시계와 직후 시계를 그 시각으로 판정해, "새로 넘김"은 뒤가 `breached`이고 앞이 아닌 것, "새로 곧 넘김"은 뒤가 `warning`이고 앞이 `ok`이거나 목표 없음이던 것, "벗어남"은 뒤가 앞보다 앞 단계인 것이다(목표가 없어진 것 포함). 수는 바뀜의 횟수다: 정책이 두 번 바뀌는 동안 한 문의가 넘김이 됐다가 벗어나면 둘 다 센다. (SLA-5, 5절 7) |
| S8B-AC-13 | When 다시 계산으로 문의가 "새로 넘김"이나 "새로 곧 넘김"으로 세어지면, the system shall 그 문의의 목표 가운데 단계가 뒤로 간 것의 표시를 새 단계로 올린다(하나씩 알리지 않는다). 세어지지 않은 문의의 표시는 올리지 않아, 그 목표가 경고·넘김이면 S8B-AC-01·02대로 하나씩 알린다(예: 첫 응답이 이미 넘김으로 알려진 문의의 해결 목표가 다시 계산으로 곧 넘김이 되면, 문의 단계는 그대로라 세지 않고 해결 경고를 하나씩 알린다. 해결 목표는 첫 응답보다 짧을 수 없어 거꾸로는 생기지 않는다). (SLA-5, 5절 8) |
| S8B-AC-14 | When 작업의 회차가 지금 정책 버전보다 낮은 돌고 있는 문의를 하나도 남기지 않으면(다시 계산이 끝남), the system shall 그때까지 모인 세 수 가운데 하나라도 0이 아니면 `ACTIVE` 관리자 전부의 알림함에 `SLA_RECALCULATED` 항목 하나를 남긴다. 여러 회차에 걸친 다시 계산도, 그 사이 정책이 또 바뀐 것도 한 건으로 묶는다. 셋이 모두 0이면 남기지 않는다. 메일과 웹훅은 없다. 시간대가 바뀌어 시스템이 올린 버전도 같다. (SLA-5, INBOX-1, 5절 9) |
| S8B-AC-15 | The 콘솔 알림 응답 shall 새 칸 `slaSummary`(`{becameBreached, becameWarning, released}`, `SLA_RECALCULATED`일 때만 값, 다른 종류는 `null`)를 준다. `SLA_RECALCULATED` 항목의 `issue`, `actor`, `companyCode`, `commentId`, `task`, `linkedIssue`는 `null`이다. (INBOX-1, D-43) |

### 2.5 통계

| ID | 기준 |
|---|---|
| S8B-AC-21 | When 상담 쪽이 통계를 읽으면(`GET /api/console/stats`), the system shall 매개변수 `days`(7, 30, 90, 없으면 30)를 받는다. 다른 값이면 400 `INVALID_INPUT`(칸 `days`). 있는 수(전체, 열림, 처리 중, 해결, 종료)는 `days`와 관계없이 지금 상태를 센다. (STATS-4, 5절 10) |
| S8B-AC-22 | The system shall 고객사 항목마다 새 칸 `sla`를 준다: 지금 정책이 꺼져 있으면 `null`, 켜져 있으면 `{firstResponse, resolution}`이고 각각 `{medianMinutes, met, missed}`다. 한 응답에서 모든 항목이 같이 `null`이거나 같이 값이다. (STATS-4, SLA-7) |
| S8B-AC-23 | The system shall `met`·`missed`를 그 고객사의 SLA 대상 문의(휴지통 제외) 가운데 그 목표가 지금부터 `days`×24시간 전 이후에 확정된 것으로 센다(UTC 시각의 차이, TIME-1). `NONE`은 세지 않는다. 재오픈으로 확정이 지워진 해결 목표는 다시 확정될 때 그 시각으로 한 번만 센다. (SLA-3, SLA-7, 5절 11) |
| S8B-AC-24 | The system shall `medianMinutes`를 같은 문의들의 센 업무 시간(초)의 아래 중앙값(값이 짝수 개면 가운데 둘 가운데 작은 것)을 분으로 내림해 준다. 첫 응답은 응답으로 확정된 것만 중앙값에 넣는다: 첫 응답 없이 해결·종료로 확정된 것은 뒤에 재오픈해 응답이 달려도 빼고, `met`·`missed`에는 넣는다. 셀 문의가 없으면 `null`이다. (SLA-7, 5절 12) |
| S8B-AC-25 | If 상담원이 통계를 읽으면, then the system shall 있는 대로 배정된 고객사만 주고 SLA 칸도 그 고객사의 문의만 센다(고객사 A에 배정된 상담원은 B의 중앙값과 수를 받지 않는다). (STATS-2, TM-62) |
| S8B-AC-26 | The 콘솔 C-5 shall 정책이 켜져 있으면(항목의 `sla`가 `null`이 아님) 기간 고르기와 칸 둘("첫 응답 SLA", "해결 SLA")을 `screens.md` 2절대로 보이고, 꺼져 있으면 7b 화면 그대로다. 기간을 바꾸면 다시 읽고, 늦게 온 앞 기간의 답은 버리고, 다시 읽기에 실패하면 앞 기간의 수를 새 기간 아래 두지 않는다. (STATS-4) |

### 2.6 마이그레이션, 작업, 성능

`process.md` C-10대로 고객사 경계, 권한, 개인정보, 마이그레이션, 공개 계약에 걸린 기준만 일부러 틀린 구현, 숨긴 E2E, 변이 테스트를 받는다.

## 6. 테스트 쓰는 법 (C-5)

8a 테스트의 꼴을 그대로 쓴다.

- 시간은 함께 쓰는 테스트 시계(`TestClock`)를 옮기고, 회차는 `SlaSteps.recalculateNow`처럼 `GET /api/console/system/status`의 `cleanupJobs`에서 `sla-recalculate`의 마지막 회차 시각이 바뀌기를 기다린다. 작업을 바로 돌리는 경로는 없고 만들지 않는다.
- SLA 테스트는 8a처럼 따로 띄운 앱(`@TestPropertySource`)에서 돈다. 정책은 설치에 하나다.
- 받는 사람 수와 항목 수는 자기가 만든 문의 키로만 센다.
- 메일은 GreenMail, 막을 때는 `SmtpGate.hold()`. 웹훅은 있는 테스트용 받는 쪽.
- 다시 계산 실패(S8B-AC-28)는 7b `CleanupStall`처럼 다른 DB 연결에서 `sla_recalc_report`를 잠가 만든다.
- 여러 회차에 걸친 요약(5천 건 넘게)은 잠그는 테스트로 쓰지 않고 숨긴 E2E나 C-10 성능 실행에서 본다.
