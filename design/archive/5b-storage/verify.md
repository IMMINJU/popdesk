# 5b 묶음(첨부 저장소 disk와 s3) 검증 (C-10)

2026-10-14. 메인이 정리했다.

> **GitHub Actions의 10월분을 다 써서 CI 없이 이 PC에서만 봤다(2절).** 커밋은 `origin/main`에 올리지 않았다. 릴리스는 5번 묶음과 묶어 0.5.0으로, 11월에 CI가 돌아온 뒤 낸다.

## 1. 구현 탭이 끝났고 맡은 테스트는 모두 통과한다

- 구현 탭 하나(`s5b-i-server`)가 일곱 걸음을 커밋했고 메인이 main에 cherry-pick했다(`5816435`~`6b31986`, 구현 브랜치와 트리가 같다).
- `start` 패키지의 새 네 클래스(`DiskStorageTest` 9, `S3StorageTest` 20, `StorageStartCheckTest` 23, `StorageSwitchTest` 7)는 정해진 순서와 무작위 순서에서 한 번씩 모두 통과했다.
- deploy 태그의 새 네 클래스(명령, compose의 S3 키, root 소유 폴더, s3의 10MB 16개)는 새 이미지로 7개가 첫 실행에서 모두 통과했다.
- `pending.txt`가 비었다.
- 순수 계산 셋(`StoragePaths`, `BucketLocation`, `S3KeyCheck`)의 단위 테스트는 구현이 합쳐진 뒤 테스트 쪽이 주석과 설계만 보고 썼다(`76ab408`, 336개).

이 PC에서 돌리지 않은 것: trivy(0.5.0 릴리스 때 CI에서), 웹 단계.

## 3. 숨긴 E2E

`StorageFlowTest`(10단계, 숨긴 저장소 `f5c1668`): 10개 통과, 3분 24초.

- 첫 실행에서 1~8단계가 통과하고 9단계가 실패했다. 테스트는 `db`로 돌아가며 S3 키를 지우면 로그가 `S3_BUCKET`도 빠졌다고 말하기를 기대했다. 옛 `s3` 파일의 버킷은 행의 자리에 적혀 있어 `S3_BUCKET`은 닿는 데 필요하지 않다(S5B-AC-10, 22, 23). 테스트 쪽이 기준을 다시 읽고 확인한 뒤 그 단언만 고쳤다. 9단계의 뒷부분과 10단계는 고치지 않고 통과했다.
- 숨긴 E2E에서 구현 탓으로 나온 것은 없다.

## 4. 메인이 브라우저로 본 것

진짜 서버(`popdesk:test`), Mailpit과 S3 대역(versitygw)을 붙인 설치 하나. 견본은 API로 넣었다(고객사, 상담원, 고객, 본문 이미지 둘이 든 문의).

| 한 것 | 결과 |
|---|---|
| 버킷 없이 `s3`로 띄움(버킷 만들기가 실패했다) | 뜨지 않았다. 로그: `The s3 storage pd-click/popdesk cannot be used for new files: … 404 NoSuchBucket. popdesk did not start.` 앞에 `S3_ENDPOINT is an http address` 경고 |
| 버킷을 만들고 다시 띄움 | 떴다. `New s3 storage pd-click/popdesk: … left its marker` 줄과 버킷의 `popdesk/.popdesk-storage` |
| P-5 문의 화면(고객, 1280 밝게) | 본문 이미지 둘(2000px, 320px)이 그려졌다 |
| 한글 이름 2.6MB 파일을 "첨부 올리기"로 | 목록에 이름과 크기. 내려받은 해시가 같다. 범위 요청 206과 `Content-Range`. `Location` 없음. 버킷에는 `popdesk/{ID}` 이름으로만 있다 |
| 같은 설치를 `disk`로 바꿔 다시 띄움 | 떴다. 볼륨에 표지. s3의 파일 셋이 그대로 읽히고 해시가 같다 |
| 댓글에 WebP 이미지를 넣어 보냄 | 그려졌다. 볼륨에 `{앞 두 글자}/{ID}`로만 있다 |
| `popdesk attachments check` | `disk /data/attachments: checked 2, …`, `s3 pd-click/popdesk: checked 3, …`, 끝 코드 0 |

콘솔의 오류와 경고는 없었다. 앱 로그에 `ERROR` 줄(다시 띄운 뒤)과 이메일 주소는 없었다.

본 것 하나: 볼륨의 `disk` 파일 둘 가운데 하나는 DevTools의 `fill`이 편집기 글을 덮어써 묶이지 못한 임시 이미지다. 24시간 뒤 정리 작업이 지운다. 명령은 `stored`인 임시 이미지도 센다.

## 7. 하지 않은 것

- `S3StorageTest`의 문턱 24(정리 작업이 저장소에 닿지 못할 때 연결 수, S5B-AC-35)를 실제 숫자로 재지 않았다. 테스트가 숫자를 찍지 않는다. 통과는 했다.
- `heavy.sh`가 종료 신호를 받으면 잠금만 풀고 실행은 계속 도는 것으로 보인다는 보고가 있었다(실행 둘이 잠깐 겹쳤을 수 있다). 확인하지 않았다.
- 실제 AWS S3로는 보지 않았다(대역은 versitygw).
