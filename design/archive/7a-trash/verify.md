## 5. 성능

같은 설치에 문의 10만 건을 SQL로 넣고(고객사 50, 그중 1,004건은 휴지통, 2만 건은 `RESOLVED`) `analyze` 뒤 HTTP로 15번씩 잰 중앙값(앞 두 번 뺌). 두 번 잰 값을 같이 적는다.

| 첫 쪽(20건) | 중앙값 | 6a(같은 데이터 꼴) |
|---|---|---|
| 관리자, 검색 없음 | 89, 89 ms | 82 ms |
| 상담원, 검색 없음 | 152, 146 ms | 122 ms |
| 관리자 `sort=dueDate` | 106, 89 ms | 82 ms |
| 상담원 `sort=dueDate` | 144, 152 ms | 96 ms |
| 관리자 `status=RESOLVED` | 29, 44 ms | |
| 관리자 휴지통 1쪽, 50쪽 | 18 / 31, 18 / 16 ms | |

- 상담원 첫 쪽이 기준(150 ms) 언저리다. 쿼리 계획은 6a 때와 같다(문의 표를 처음부터 끝까지 읽고 담당 고객사로 거른다). `deleted_at is null`이 줄마다 칸 하나를 더 읽어 쪽 쿼리와 건수 쿼리에 10~15 ms씩 더한다(psql에서 40 대 25 ms). 7a를 막지 않고 넘긴다(9절).
- 자동 종료의 업그레이드 뒤 첫 실행: 해결된 지 7일 지난 문의 2만 건을 한꺼번에 기한으로 만들고 기록을 지워 바로 돌게 했다. 4초 뒤 첫 종료가 보였고 39초 안에 2만 건을 모두 닫았다(남은 0, 이력 2만 줄). 그동안 1초마다 잰 관리자 목록 36번은 모두 200, 중앙값 99 ms, 가장 긴 것 186 ms.
- 그때 고객에게 가는 종료 메일 2만 통이 대기에 들어갔다. 견본의 보고자가 모두 한 고객이라 받는 사람마다의 한도에 걸려 7,207통이 `failed`로 남았고, 앱 로그에 그 경고가 18,770줄 쌓였다. 실제 설치에서도 해결된 문의가 많은 고객은 업그레이드 뒤 첫 10분에 종료 메일을 몰아 받는다(9절 릴리스 노트).

## 7. 메인이 코드로 본 것

C-7 점검에서 테스트로 다 잡지 못한다고 정한 것:

- 시스템 영구 삭제(`TrashService.purgeDue`): 대상은 잠그지 않고 고르고, 문의마다 트랜잭션에서 `lockTrashedByIds`로 잠근 뒤 휴지통에 있는지와 `TrashTimes.due`를 다시 본다. 고르는 선(`deletedUntil`)과 다시 보는 선(`due`)이 같아 같은 문의를 끝없이 다시 고르지 않는다.
- 보내기 직전 확인: `NotificationDirectory.find`가 `deleted_at is null`로 읽고, `MailSender`·`WebhookSender`는 문의가 없으면 행을 버린다(`Attempt.dropped`).
- 파일 지우기는 커밋 뒤: `purge`와 `purgeDue` 모두 `transactions.run` 밖에서 `removePurgedFiles`를 부른다. 실패는 행을 `purging`으로 두고 첨부 정리가 끝낸다.
- 자동 종료(`IssueAutoClose`): 잠그는 조건과 조건부 UPDATE의 조건이 같은 상수(`DUE_FOR_CLOSING`)라 묶음 반복이 끝난다.
- 남는 틈: 시스템 영구 삭제에서 한 문의가 계속 실패하면 그 회차의 나머지도 멈춘다(정리 작업 실패로 남는다). `architecture.md` 잠금 절에 적었다.
