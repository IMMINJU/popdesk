# 7a 묶음 수용 기준: 휴지통과 자동 종료

> `roadmap.md` 7번의 앞 조각이다(5절 1). 묶음이 끝나면 `design/archive/7a-trash/`로 간다(D-27).
> 전체 경로다. 로드맵은 7번을 "기본"으로 적었으나, 이 묶음은 마이그레이션(문의에 칸 넷), 개인정보(영구 삭제는 쓴 내용을 지우는 길이다), 고객사 경계(지운 문의가 모든 읽기에서 빠져야 한다), 공개 계약(새 경로, 감사 종류, 이력 칸)을 건드린다(5절 2). 사전 부검은 같은 폴더의 `premortem.md`다.
> 규칙 ID의 글은 같은 폴더 `rules.md`에 있다. 기준 ID는 `S7A-AC-nn`이다.
> 관계있는 결정(`adr.md`): D-10, D-20, D-43, D-44, D-49, D-57. 위협 모델: TM-37(보낼 때 다시 확인), TM-49(다시 보내기), TM-60(새, 지운 문의가 어딘가에 남아 보임), TM-61(새, 영구 삭제와 복구가 겹침).
> 상태: **메인이 정함, 사용자 확인 전**(2026-10-15). 규칙에 없던 것을 메인이 넣은 곳은 5절에 모았다.

## 1. 넣는 것과 미루는 것

앞 묶음이 이미 만든 것: 보기 범위 한 곳(`IssueScope.SQL`)과 그것을 쓰는 읽기·잠금, 상태 전이(조건부 UPDATE), 해결 시각(`resolved_at`), 첨부 지우기(`purging` 뒤 커밋 다음에 파일), 정리 작업 틀(`Housekeeping`, `CleanupJob`, 기록), 감사 로그, 이력, 보내기 직전 확인(받는 사람이 문의를 볼 수 있는지). 6c의 연결(볼 수 없는 연결까지 세는 검사). 휴지통과 자동 종료는 없다.

## 2. 수용 기준

"지운 문의"는 휴지통에 있는 문의다. "영구 삭제한 문의"는 영구 삭제가 끝난 문의다. 둘 다 아닌 문의를 "산 문의"라 쓴다.

### 2.1 지우기

| ID | 기준 |
|---|---|
| S7A-AC-01 | When 관리자가 볼 수 있는 문의를 지우면(`DELETE /api/console/issues/{key}`), the system shall 그 문의를 휴지통으로 옮기고(지운 시각과 사람) 204로 답한다. 문의의 내용과 그 아래의 것(댓글, 첨부, 작업, 연결, 라벨, 담당자)은 그대로 둔다. 상태는 어느 것이든 지울 수 있다. (TRASH-1) |
| S7A-AC-02 | If 상담원이 지우려 하면, then the system shall 403 `FORBIDDEN`으로 답한다(관리자 전용 경로, 대상보다 먼저 본다). 고객은 있는 콘솔 경로와 같은 답(포털 호스트 404, 콘솔 호스트 401)이다. (TRASH-1, D-49) |
| S7A-AC-03 | When 지운 문의의 키로 문의나 그 아래 경로(댓글, 첨부와 그 파일, 이력, 작업, 기록, 연결, 라벨, 마감일, 담당자, 상태, 멘션 후보)를 부르면, the system shall 콘솔과 포털 모두 없는 문의와 같은 404로 답한다(관리자 포함). 이미 지운 문의를 다시 지우는 것도 404다. 휴지통 경로(`/api/console/trash/{key}…`)는 이 기준에 들지 않는다. 지운 문의를 만든 요청을 같은 `Idempotency-Key`로 다시 보내면 404다. (TRASH-1, COM-1, ISSUE-12) |
| S7A-AC-04 | The system shall 지운 문의를 모든 목록과 검색(콘솔·포털 문의 목록, 검색어, 필터, 쪽의 전체 수), 내 작업, 알림함(목록과 안 읽은 수), 남은 담당 수(배정 빼기·정지 앞의 수), 라벨이 붙은 문의 수에서 뺀다. 담당 비우기(ACCT-7)는 지운 문의의 담당자와 작업 담당자를 비우지 않는다. (TRASH-1, 5절 6) |
| S7A-AC-05 | The system shall 지운 문의와 이어진 연결을 상대 문의의 연결 목록과 이력에서 숨긴다(지운 문의는 아무도 볼 수 없는 문의다). 숨은 연결도 잇기 검사와 개수에는 든다. (LINK-2, LINK-7) |
| S7A-AC-06 | When 문의를 지우거나 복구하거나 영구 삭제하면, the system shall 그 문의의 이력에 칸 `TRASH` 항목을 남긴다(지울 때 뒤 값 `TRASHED`, 복구할 때 전 값 `TRASHED`, 영구 삭제할 때 전 값 `TRASHED` 뒤 값 `PURGED`. 한 사람은 관리자, 시스템이 영구 삭제하면 0). 지우기와 복구는 문의의 `version`을 올린다. (HIST-1, 5절 7) |
| S7A-AC-07 | When 관리자가 문의를 지우거나 복구하거나 바로 영구 삭제하면, the system shall 감사 로그에 한 항목(`ISSUE_DELETED`, `ISSUE_RESTORED`, `ISSUE_PURGED`)을 남긴다. 대상은 `{type: "COMPANY", code, issueKey}`, 바뀐 값은 없다(`changes`는 `null`. 계약과 앞 감사 항목의 꼴, 2026-10-16 메인이 고침). 시스템이 한 영구 삭제는 남기지 않는다. (AUDIT-1, 5절 8) |

### 2.2 휴지통에 있는 동안

| ID | 기준 |
|---|---|
| S7A-AC-10 | The system shall 지운 문의에 대한 알림(알림함, 메일, 웹훅)을 보내지 않는다. 지우는 요청이 그 문의의 보내기 대기 행(기다리는 것, 다시 보낼 것, `failed`)을 모두 지운다. 그래서 복구해도 보내지 않는다. 지우기와 같은 때 보내기 직전 확인을 이미 지난 한 통은 나갈 수 있다(받아들인다). 보내기 직전 확인은 문의가 휴지통에 있으면 보내지 않고 행을 지운다(웹훅 포함). (TRASH-2, MAIL-4, TM-37, TM-49, 5절 13) |
| S7A-AC-11 | The system shall 지운 문의를 자동 종료하지 않는다. (TRASH-1, STATUS-5) |
| S7A-AC-12 | When 문의 쓰기(고치기, 상태, 댓글, 첨부, 작업, 연결 등)와 지우기가 같은 때 오면, the system shall 어떤 한 순서로 한 것과 같은 결과를 준다(지운 뒤에 그 문의가 바뀌지 않는다. 쓰기가 먼저면 지운 문의에 그 쓰기가 남는다). 첨부 지우기와 상태 바꾸기도 든다. (STATUS-7) |

### 2.3 휴지통 목록과 복구

| ID | 기준 |
|---|---|
| S7A-AC-20 | When 관리자가 휴지통 목록을 읽으면(`GET /api/console/trash`), the system shall 지운 문의를 지운 시각이 늦은 순으로 준다. 항목마다 키, 제목, 고객사(코드와 이름), 상태, 지운 시각, 지운 사람, 영구 삭제 예정 시각(지운 시각 + 30일)이 있다. 영구 삭제한 문의는 없다. 쪽 나누기는 COM-4다. 상담원은 403이다. (TRASH-2) |
| S7A-AC-21 | When 관리자가 지운 문의를 복구하면(`POST /api/console/trash/{key}/restore`), the system shall 문의를 산 문의로 되돌리고 200으로 콘솔 문의를 준다. 내용, 댓글, 첨부, 작업과 기록, 연결, 라벨, 담당자, 마감일, 상태가 지우기 전과 같다. 그 문의의 알림함 항목도 다시 보인다. (TRASH-2) |
| S7A-AC-22 | When `RESOLVED` 문의를 복구하면, the system shall 자동 종료 기준 시각을 복구 시각으로 한다. 해결 시각(`resolvedAt`)은 바꾸지 않는다. (TRASH-2, STATUS-5) |
| S7A-AC-23 | If 휴지통에 없는 문의(산 문의, 영구 삭제한 문의, 없는 키)를 복구하거나 영구 삭제하려 하면, then the system shall 404로 답한다. (TRASH-2) |
| S7A-AC-24 | The system shall 복구할 때 그 문의와 이어진 문의의 행을 ID 차례로 함께 잠그고, 연결이 LINK-2(연결 50개, 중복 사슬)를 어기는지 다시 보고, 어기면 복구하지 않고 409 `RESTORE_LINK_CONFLICT`로 걸리는 연결의 상대 키를 준다. 휴지통 동안의 잇기 검사가 숨은 연결을 세므로 HTTP로는 이 상태를 만들 수 없다. 단위 테스트로 본다. (TRASH-2, 5절 9) |

### 2.4 영구 삭제

| ID | 기준 |
|---|---|
| S7A-AC-30 | When 관리자가 지운 문의를 바로 영구 삭제하면(`DELETE /api/console/trash/{key}`), the system shall 204로 답하고 그 문의의 쓴 내용을 지운다: 제목과 내용(빈 글), 댓글과 멘션, 첨부(올리는 중인 것 포함, 파일까지), 작업과 기록, 연결, 라벨 붙임, 그 문의의 알림함 항목과 다른 문의의 연결 알림 가운데 이 문의를 가리키는 것, 보내기 대기의 행, 문의 만들기의 `Idempotency-Key` 행. 이력의 `TITLE`·`CONTENT` 항목의 전·뒤 값을 비운다. 문의 행(키, 고객사, 상태, 시각)과 이력 항목은 남는다. (TRASH-3) |
| S7A-AC-31 | When 지운 지 30일이 지나면, the system shall 1시간마다 도는 정리 작업 "휴지통 영구 삭제"로 S7A-AC-30과 같이 영구 삭제한다. 30일이 안 된 문의는 지우지 않는다. 작업은 돈 시각과 지운 수를 정리 작업 기록(C-18)에 남긴다. (TRASH-3, OPS-2) |
| S7A-AC-32 | The system shall 영구 삭제한 문의를 어디서도 보이지 않는다(문의와 그 아래 경로 404, 휴지통 목록에도 없다). 다른 문의 이력의 `LINK` 항목은 상대가 보기 범위 밖이라(영구 삭제한 문의도 `deleted_at`이 있다) 보이지 않는다. (TRASH-3, 5절 10) |
| S7A-AC-33 | The system shall 영구 삭제한 문의의 첨부 파일을 커밋한 뒤 지운다. 저장소에서 파일을 지우지 못하면 첨부 정리 작업이 나중에 마저 지우고 행도 지운다. 첨부 행은 남기지 않는다. (TRASH-3, ATT-10) |
| S7A-AC-34 | When 복구와 영구 삭제(사람이든 시스템이든)가 같은 때 오면, the system shall 어떤 한 순서로 한 것과 같은 결과를 준다(복구된 문의가 비지 않는다. 비운 문의가 복구되지 않는다). (TRASH-2, TRASH-3, TM-61) |
| S7A-AC-35 | The system shall 지운 문의와 영구 삭제한 문의의 순번을 다시 쓰지 않는다(다음 문의는 다음 번호다). (TRASH-4) |
| S7A-AC-36 | The system shall 영구 삭제한 문의의 제목, 내용, 댓글 글, 기록 글, 첨부 파일 이름을 DB 어디에도 남기지 않는다(감사 로그 제외. 감사 항목은 키만 담는다). (TRASH-3, PII) |

### 2.5 자동 종료

| ID | 기준 |
|---|---|
| S7A-AC-40 | When 자동 종료 기준 시각에서 7일이 지난 산 `RESOLVED` 문의가 있으면, the system shall 10분마다 도는 정리 작업 "문의 자동 종료"로 `CLOSED`로 바꾼다. 바꾼 사람은 시스템(계정 0)이고 이력에 남는다. 7일이 안 된 것과 다른 상태는 그대로다. 작업은 돈 시각과 닫은 수를 정리 작업 기록에 남긴다. (STATUS-5, OPS-2) |

| S7A-AC-42 | When 자동 종료와 고객의 다시 열기(또는 상담 쪽의 상태 바꾸기)가 같은 때 오면, the system shall 어떤 한 순서로 한 것과 같은 결과를 준다(다시 연 문의를 닫지 않는다). (STATUS-5, STATUS-7) |
| S7A-AC-43 | When 자동 종료로 닫히면, the system shall 상담 쪽이 닫을 때와 같은 알림을 보낸다(올린 고객에게 `ISSUE_CLOSED` 알림함과 메일, 팀 웹훅 `ISSUE_CLOSED`). 6c의 연결 알림(`LINKED_ISSUE_CLOSED`)도 보낸다. 한 사람은 시스템이라 콘솔 알림 항목의 `actor`는 `null`이다. (STATUS-5, LINK-6, 5절 11) |

## 4. 테스트를 쓸 때 지킬 것

- 지운 문의의 404는 앞 묶음이 만든 모든 아래 경로를 매개변수 하나로 돈다. 계약 파일의 콘솔·포털 operation 가운데 `{key}`가 든 것을 모두 모으는 꼴(`boundary.BoundaryList`)을 쓴다.
- 30일, 7일, 10분, 1시간은 앱 시계(`TestClock.advance`)로 넘기고, 정리 작업이 돈 것은 `CleanupRecords`로 기다린다(`support/README.md`). 고정 대기를 쓰지 않는다.
- S7A-AC-36은 DB를 보는 테스트 도움으로 그 문의의 글이 든 행이 없는지 본다(스키마를 보는 예외). 지어낸 표시 글(예: 테스트마다 다른 난수 글)을 제목, 내용, 댓글, 기록, 첨부 이름에 넣고 DB 전체 글 칸에서 찾는다.
- 정리 작업과의 같은 때(S7A-AC-34, 42): DB를 보는 테스트 도움이 따로 연 연결로 그 문의 행을 `FOR UPDATE`로 잡아 둔 채 앱 시계를 넘겨 작업이 그 행에서 기다리게 하고, 그동안 복구(또는 다시 열기)를 보낸 뒤 잡은 것을 푼다. 단언은 끝난 상태다: 복구가 이겼으면 문의가 산 채로 내용이 그대로이고, 영구 삭제가 이겼으면 복구가 404다. 둘 사이의 섞인 상태(산 문의인데 내용이 빔)가 없어야 한다. 작업은 한 스레드에서 차례로 돌므로 잡아 둔 동안 다른 정리 작업도 멈춘다. 잡는 시간을 짧게 한다.
- 휴지통 경로(`/trash/{key}`, `/trash/{key}/restore`)는 S7A-AC-03의 404 훑기에서 뺀다.
- 감사 종류 이름과 대상 꼴은 해시에 들어간다. 이 문서의 글자 그대로다. 잠긴 웹 테스트가 감사 종류 묶음의 차례를 본다(6b `acceptance.md` 4절). 문의 셋은 "고객사" 묶음에 넣는다.
- 관리자 옆 메뉴를 그대로 견주는 잠긴 테스트(6b에서 고친 `layout.inbox.test.tsx`, `adminOnly.1b.test.tsx`)는 이 묶음의 테스트 탭이 "휴지통"을 넣어 맞춘다(자리는 `screens.md` 2절).
- C-18 정리 작업 목록을 그대로 견주는 잠긴 테스트가 있으면 같은 탭이 맞춘다.
