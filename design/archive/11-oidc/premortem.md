# 11 묶음 사전 부검

> OIDC 로그인을 내놓고 석 달 뒤 크게 잘못됐다고 치고, 무엇이 그렇게 만들었을지 적는다. 막는 것은 기준 ID로 단다. 프로젝트 사전 부검(`design/premortem.md`) 113·130·153줄과 위협 모델 TM-15·TM-47을 이어받는다.

## 1. 남의 계정으로 들어갔다

- 제공자 관리자가 자기 쪽 사용자의 이메일을 우리 관리자 이메일로 바꾸고 로그인했다. → 묶음이 있으면 (`iss`, `sub`)로만 맞춘다(S11-AC-15). 묶음이 없는 관리자 계정은 여전히 이메일로 맞으므로, 제공자를 믿는다는 것을 운영 문서에 적는다(S11-AC-37).
- 확인하지 않은 이메일을 주는 제공자(자가 가입을 받는 곳)로 들어왔다. → `email_verified`가 JSON 참일 때만(S11-AC-16). 문자열 `"true"`는 받지 않는다.
- 공격자가 자기 제공자 계정으로 받은 코드를 피해자 브라우저에 밀어 넣어, 피해자가 공격자 계정으로 로그인해 문의를 썼다(로그인 CSRF). → 쿠키와 `state` 묶기(S11-AC-04, 11).
- 돌아오기 주소의 코드가 로그나 `Referer`로 새어 다시 쓰였다. → PKCE, 로그인 요청 한 번만, 로그에 코드 없음, `no-referrer`(S11-AC-09, 25 [소스: CSP와 `Referrer-Policy`는 이미 모든 응답에]).
- 익명화한 계정에 묶음이 남아 같은 이메일로 다시 초대한 사람이 옛 계정에 들어갔다. → S11-AC-29.
- 서명을 보지 않는 디코더(`alg: none`)를 썼다. → `NimbusJwtDecoder`와 JWKS, 일부러 틀린 구현으로 확인(S11-AC-10).

## 2. 들어가야 할 사람이 못 들어갔다

- 제공자가 멈춘 동안 앱이 다시 떠 뜨지 못했다. → 뜰 때 제공자에 접속하지 않는다(S11-AC-02).
- 클라이언트 비밀이 만료되자 상담원 전원이 못 들어왔다. → 비밀번호 로그인과 비밀번호 찾기가 남는다(S11-AC-22, D-65). C-18에 실패 종류가 보인다(S11-AC-34).
- 제공자에서 사람을 다시 만들어 `sub`가 바뀌었고, 그 사람은 늘 실패 화면만 봤다. → 관리자가 묶음을 푼다(S11-AC-27).
- 호스트 시계가 2분 어긋나 모든 토큰이 실패했다. → 60초 허용, 운영 문서의 시계 맞추기(S11-AC-10, 37). 그 밖은 C-18의 `ID_TOKEN` 실패로 드러난다.
- Microsoft Entra ID는 `email_verified`를 주지 않아 아무도 처음 묶이지 못했다. → 운영 문서에 적는다(S11-AC-37). 고칠 길(설정으로 확인 생략, `userinfo`)은 넘긴 일이다(`acceptance.md` 5절 12).
- 초대를 받고 7일이 지난 사람이 OIDC로도 못 들어와 문의했다. → 같은 실패 화면에 "초대받은 이메일인지 확인하거나 관리자에게 문의하세요"(`screens.md`), 관리자는 초대를 다시 보낸다.
- OIDC로만 들어오던 사람을 정지했다 다시 켜려 하자 "수락 전"이라고 거절됐다. → 켤 때 쓸 수 없는 비밀번호 값을 둔다(S11-AC-23).

## 3. 다른 곳으로 보내졌다

- 로그인 링크에 `next=//evil.example`을 붙여 돌린 피싱이 OIDC 뒤 바깥 사이트로 보냈다. → S11-AC-05.

## 4. 운영자가 상태를 몰랐다

- 제공자 오류가 쌓여도 아무도 몰랐다. → C-18의 실패 수와 마지막 종류(S11-AC-30, 34). 경보는 두지 않았다(비밀번호 길이 남는다, `acceptance.md` 5절 10).
