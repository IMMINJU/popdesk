## 1. 표 (V16)

```
issue_link(id bigint generated by default as identity primary key,
           tenant_id bigint not null,
           low_issue_id uuid not null references issue(id),
           high_issue_id uuid not null references issue(id),
           type text not null check (type in ('DUPLICATE_OF','RELATED')),
           duplicate_issue_id uuid,                -- DUPLICATE_OF: 중복인 쪽. RELATED: null
           created_by bigint not null references account(id),
           created_at timestamptz not null,
           check (low_issue_id < high_issue_id),
           check ((type = 'RELATED' and duplicate_issue_id is null)
               or (type = 'DUPLICATE_OF' and duplicate_issue_id is not null
                   and duplicate_issue_id in (low_issue_id, high_issue_id))),
           unique (low_issue_id, high_issue_id))
create index issue_link_high_idx on issue_link(high_issue_id);
create unique index issue_link_one_original_idx on issue_link(duplicate_issue_id) where duplicate_issue_id is not null;

alter table notification add column linked_issue_id uuid;
```

- `tenant_id`와 ID의 꼴은 V14·V15와 같다.
- uuid의 크기 비교는 Postgres의 `uuid` 차례(바이트 차례)다. 잠금 차례(0절 1)도 같은 비교를 쓴다(Java `UUID.compareTo`는 부호 있는 비교라 다르다. 차례는 SQL의 `order by id`로 정한다).
- 끊으면 행을 지운다. 흔적은 이력에 있다.
- 휴지통이 생기면(7번) 영구 삭제가 연결 행을 지운다. 이 묶음은 외래 키를 `on delete cascade`로 두지 않는다(6b와 같다).
- `deploy/upgrade/make-sample.py`가 S6C-AC-60의 행을 API로 채운다.

## 2. 경로

계약 탭(C-4)이 `conventions.md`의 꼴과 견줘 정한다. 메인의 초안:

| 하는 일 | 초안 | 답 |
|---|---|---|
| 목록 | `GET /api/console/issues/{key}/links` | 200 `IssueLinks{items: IssueLink[]}` |
| 잇기 | `POST /api/console/issues/{key}/links` `{issueKey, type}` | 201 `IssueLink` |
| 끊기 | `DELETE /api/console/issues/{key}/links/{otherKey}` | 204 |

- `IssueLink`: `type`(`DUPLICATE_OF`·`DUPLICATED_BY`·`RELATED`, 이 문의에서 본 것), `issue{key, title, status, companyCode, companyName}`, `createdBy`(사람), `createdAt`. 연결 ID는 주지 않는다(두 문의로 정해진다).
- 목록은 쪽을 나누지 않는다(50개가 끝이다). 차례는 연결 ID 차례(이은 차례).
- `IssueHistoryEntry`에 `oldLink`·`newLink`(`{type, issue{key, title}}` 또는 `null`)를 더한다. `LINK` 항목은 `oldValue`·`newValue`가 `null`이다. 칸 이름 설명에 `LINK`를 더한다.
- `Notification`에 `linkedIssue`(`{key, title}` 또는 `null`)를 더하고 `kind`에 `LINKED_ISSUE_RESOLVED`, `LINKED_ISSUE_CLOSED`를 더한다.
- 새 오류 code: `LINK_TO_SELF`(400), `LINK_DUPLICATE_CHAIN`(400), `LINK_LIMIT_EXCEEDED`(400), `LINK_EXISTS`(409). 요청 수 제한 표에 "문의 잇기와 끊기: 60"을 더한다. 그 밖은 있는 code다(`ISSUE_CLOSED`, `INVALID_INPUT`의 `REQUIRED`·`UNKNOWN_VALUE`).
- 상대 키(`issueKey`, `{otherKey}`)가 키 꼴이 아니면 없는 문의와 같은 404다(400이 아니다. 경로의 키와 같다).
- 검사 차례는 S6C-AC-14다(`conventions.md` "Order of checks"). `issueKey`가 없으면 상대를 찾을 수 없으므로 그 `REQUIRED`만 상대의 404보다 앞이다.

## 3. 쓰기의 차례와 잠금

| 쓰기 | 차례 |
|---|---|
| 잇기 | 요청 수 → 이 문의 ID(404) → `issueKey` 있음(400) → 상대 문의 ID(404) → `type`(400) → 같은 문의면 400 `LINK_TO_SELF` → 두 행을 ID 차례로 잠금(보기 범위 조건 포함, 하나라도 없으면 404) → 이 문의 `CLOSED`면 400 → 두 문의 사이 연결(409) → 중복이면 사슬 검사(400) → 두 문의의 연결 수(각 50, 400) → INSERT → 두 문의의 이력 `LINK` 항목 |
| 끊기 | 요청 수 → 두 키로 문의 ID(404) → 두 행을 ID 차례로 잠금 → 연결 행(없으면 404) → 이 문의 `CLOSED`면 400 → DELETE → 두 문의의 이력 항목 |
| 상태가 `RESOLVED`·`CLOSED`가 됨 | 지금의 `move()` 안, `notifications.statusChanged` 다음에 같은 트랜잭션에서 그 문의의 연결을 읽어 상대 문의마다 담당자를 정한다(4절). 연결 쪽 행을 잠그지 않는다. 연결 읽기는 상태를 바꾼 사람의 보기 범위로 거르지 않는다(고객이 닫아도 알림이 가야 한다) |

- 사슬 검사(중복이 될 문의 D, 원본 O): O에 나가는 `DUPLICATE_OF`가 있다(O가 이미 중복), D에 들어오는 `DUPLICATE_OF`가 있다(D가 이미 원본), D에 나가는 `DUPLICATE_OF`가 있다(D에 원본이 이미 있다). 셋 가운데 하나면 400. 두 행을 잠근 뒤라 같은 때의 잇기가 이 검사를 피하지 못한다. A→B와 B→C가 같은 때 오면 B 행을 둘 다 잡으려 하므로 차례가 선다.
- 잠금 안에서 쓴 연결은 두 문의 행이 잠긴 동안만 바뀐다. 연결을 바꾸는 쓰기는 잇기와 끊기뿐이고, 둘 다 두 행을 잠근다(7a의 영구 삭제가 셋째가 된다. 휴지통의 문의만 다루고 잇기가 닿지 않는다). 그래서 연결 수와 사슬 검사는 그 두 문의에 대해 맞다.
- `architecture.md` 잠금 순서 표에 위 두 줄을 C-10에서 더한다.
- 연결 서비스는 `helpdesk/link`(새)에 둔다. `link` → `issue`의 공개 타입(`IssueRepository`의 잠금, `IssueHistoryRepository`)을 쓴다. 상태가 바뀔 때의 알림은 `issue` 쪽이 `helpdesk`의 인터페이스(새, "이 문의와 이어진 문의 ID들")로 묻고 `link`가 구현한다(6b의 열린 작업 수와 같은 꼴, `PackageCyclesTest`).
- 이력의 `LINK` 항목은 `IssueHistoryRepository.insertChanged`에 `Field.LINK`를 더해 쓴다.

## 4. 알림

- `IssueNotifications.statusChanged` 다음에 `linkedStatusChanged(actor, issue, to)`(이름은 구현 탭이 정함)를 부른다. `to`가 `RESOLVED`나 `CLOSED`일 때만 한다.
- 받는 사람: 이어진 문의마다 그 담당자. 빼는 것은 S6C-AC-32다. 볼 수 있는지는 둘을 본다: 담당자가 자기 문의를 볼 수 있는가(앞 `tell()`이 보는 것), 바뀐 문의를 볼 수 있는가(새로) [소스: `IssueNotifications.tell` 191-205줄, `sees` 207-209줄].
- 항목: `inbox.add`에 `linkedIssueId`를 받는 메서드 하나를 더한다(6b `addAboutTask`와 같은 꼴) [소스: `IssueInbox.java` 49, 61줄]. 메일은 없다.
- 같은 받는 사람에게 같은 종류, 같은 두 문의(`issue_id`, `linked_issue_id`)의 안 읽은 항목이 있으면 넣지 않는다(S6C-AC-35).
- 알림함을 읽을 때: 연결 항목은 읽는 사람이 `linked_issue_id`의 문의도 지금 볼 수 있을 때만 나온다. 목록(`listInboxIssues`)과 안 읽은 수(`Shown.SQL`)가 같은 조건을 쓴다. 바뀐 문의의 키와 제목은 `InboxFacts`(있는 것)에 묻는다.
- 상태가 바뀔 때 이어진 문의가 50개면 항목이 50개까지 생긴다. 받아들인다(한 요청 안의 INSERT 50개).

## 5. 이력 읽기

- `IssueHistoryRepository`의 `SELECT`에 `LINK` 항목의 상대 문의를 붙인다: `left join issue li on li.id = case when h.field = 'LINK' then split_part(coalesce(h.new_value, h.old_value), ':', 2)::uuid end`(값이 uuid가 아닌 행이 캐스트에 닿지 않게 `ASSIGNEE`처럼 CASE로) [소스: `IssueHistoryRepository.java` 60-75줄].
- 거르기: `and (h.field is distinct from 'LINK' or ({li에 대한 보기 범위 조건}))`. `CREATED` 항목은 `field`가 `null`이라 `<>`로 쓰면 상담원에게서 빠진다(C-1~3 검토에서 찾음). 지금의 `IssueScope.SQL`은 문의 별칭이 `i`로 박혀 있으므로, 별칭을 받는 꼴을 하나 더한다(구현 탭이 정함). `list`와 `count`가 같은 조건을 쓴다.
- 상대 문의가 없어지는 길은 지금 없다(영구 삭제는 7번). 7번에서 영구 삭제가 연결 이력의 상대를 어떻게 보일지 정한다.

## 10. 구현 지시서에 넣을 것 (C-5, C-7에서)

- 서버: 두 문의 행은 ID 차례로 잠근다. 잠그는 문장에 보기 범위를 넣는다. 차례는 SQL `order by id`로 정한다(Java `UUID.compareTo`를 쓰지 않는다).
- 서버: 사슬 검사 셋(설계 3절)과 한도는 잠근 뒤 한다. 볼 수 없는 연결도 센다. 수와 사슬은 `issue_link`만 읽고 `issue`를 보기 범위로 붙이지 않는다(7a에서 범위가 휴지통의 문의를 빼도 숨은 연결을 세야 한다).
- 서버: 이력 값은 ID만 담는다. 읽을 때 상대를 보기 범위로 SQL 안에서 거른다(`list`와 `count`).
- 서버: 연결 알림은 받는 사람이 두 문의를 모두 볼 수 있을 때만, 읽을 때도 둘 다 다시 본다.
