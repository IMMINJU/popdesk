# 6c 묶음 사전 부검

> 0.6.0을 낸 지 한 달 뒤 문의 연결 때문에 사고가 났다고 치고, 무엇이 그랬을지 거꾸로 적는다. 막는 것은 기준 ID나 설계 절로 단다.
> 상태: **메인이 정함, 사용자 확인 전**(2026-10-15).

## 1. 다른 고객사 문의가 배정되지 않은 상담원에게 보였다

- 연결 목록이 상대 문의의 보기 범위를 거르지 않아, A사만 맡은 상담원이 A사 문의 화면에서 B사 문의의 키, 제목, 고객사 이름을 봤다.
- 이력에 "B-7 {제목}과 관련 문의로 이었습니다"가 남아, 연결 목록에서는 숨긴 B사 문의가 이력으로 보였다. 키와 제목을 감춰도 "볼 수 없는 문의와 연결함"이 남아 연결이 있다는 것이 드러났다.
- B사 문의가 해결되자 A사 문의의 담당자(B사를 맡지 않음)에게 "연결된 문의를 해결했습니다: B-7 {제목}"이 갔다. 보낼 때는 볼 수 있었는데 그 뒤 배정에서 빠져, 알림함을 열 때 제목이 보였다.
- 상대 키로 잇기를 시도해 404와 400의 차이로 B사에 그 번호의 문의가 있는지 알아냈다.

막는 것: 연결 목록과 이력의 `LINK` 항목은 상대를 보기 범위로 SQL 안에서 거른다(S6C-AC-12, 22, 설계 5절). 이력 값은 ID만 담는다(S6C-AC-20). 알림은 받는 사람이 두 문의를 모두 볼 때만 남고, 읽을 때도 둘 다 다시 본다(S6C-AC-32, 33). 볼 수 없는 상대는 없는 문의와 같은 404이고, 404는 입력 검사보다 먼저다(S6C-AC-02, 설계 2절). 넷 모두 C-7의 틀린 구현으로 본다.

## 2. 고객이 연결을 봤다

- 포털 문의 응답이 콘솔 타입을 같이 써서 연결이 실렸다.
- 연결된 문의가 해결될 때 고객 메일에 "관련 문의 B-7도 해결되었습니다"가 들어갔다.

막는 것: 포털 타입은 바뀌지 않는다. 연결 알림은 담당자의 알림함뿐이고 메일이 없다(S6C-AC-31, 41). 숨긴 E2E가 고객의 응답과 메일함까지 본다.

## 3. 원본이 둘이 되거나 사슬이 생겼다

- A를 B의 중복으로, B를 C의 중복으로 같은 때 이어 둘 다 검사를 지나갔다.
- A를 B의 중복으로 이은 뒤, 다른 사람이 A를 C의 중복으로 이었다(규칙의 두 경우만 봤다).
- 같은 두 문의를 양쪽 화면에서 같은 때 이어 연결이 둘 생겼다.

막는 것: 두 문의 행을 ID 차례로 잠근 뒤 검사한다. 사슬 검사는 세 경우를 본다(설계 3절, S6C-AC-05, 08). DB의 유니크 둘(두 문의 쌍, 중복 쪽)이 잠금을 빠뜨린 코드도 막는다(설계 0절 2).

## 4. 잇기가 서로 기다리다 멈췄다

- A 화면에서 B를, B 화면에서 A를 같은 때 이었다. 각자 경로의 문의를 먼저 잠가 서로를 기다렸고, DB가 하나를 끊어 500이 났다.
- 잠금 차례를 Java `UUID.compareTo`로 정해 SQL의 차례와 달랐다.
- 앱이 교착을 한 번 다시 해 답은 201과 409로 왔고, 테스트가 이것을 놓쳤다.

막는 것: 차례는 SQL의 `order by id`로 한 문장 안에서 잡는다(설계 0절 1, 10절). S6C-AC-08이 반대 차례의 두 요청을 되풀이해 보내고 DB의 교착 수를 본다. 담당 비우기(여러 문의를 한 UPDATE로 잠금)와 잇기의 교착은 다시 하기로 받아들인다(설계 0절 1).

## 5. 이력과 알림이 끝없이 늘었다

- 잇고 끊기를 되풀이해 두 문의의 이력이 수천 줄이 됐다.
- 연결 50개인 문의를 해결과 다시 열기로 오가며 알림을 쏟았다.

막는 것: 잇기·끊기의 요청 수 제한(S6C-AC-09). 연결 알림은 `RESOLVED`·`CLOSED`가 될 때만이고, 같은 소식의 안 읽은 항목이 있으면 새로 남기지 않는다(S6C-AC-35). 상태 바꾸기에는 요청 수 제한이 없다.

## 5-1. 바뀐 시각으로 연결이 드러났다

- 잇기가 두 문의의 `updated_at`을 바꿔, A사만 맡은 상담원과 A사 고객이 "보이는 이력은 없는데 방금 바뀐 문의"를 봤다.

막는 것: 잇기와 끊기는 `version`도 `updatedAt`도 바꾸지 않는다(S6C-AC-23).

## 6. 앞 테스트와 화면이 깨졌다

- `IssueHistoryEntry`와 `Notification`에 칸이 늘어 견본을 그대로 견주는 앞 테스트가 깨졌다.
- C-4가 연결 목록을 하나 더 불러, 가짜 서버에 그 핸들러가 없는 앞 테스트가 오류 띠를 봤다.
- 연결 구역의 "끊기"가 이름으로 단추를 찾는 앞 테스트와 겹쳤다.

막는 것: 테스트 탭이 계약 뒤 같은 커밋에서 견본과 가짜 서버를 맞춘다(`acceptance.md` 4절). 단추 이름을 "{키} 연결 끊기"로 둔다.

## 7. 받아들이는 것

- 사슬 검사와 한도의 400은 보는 사람이 볼 수 없는 연결이 있다는 것을 드러낼 수 있다(어느 문의인지는 아니다, `acceptance.md` 5절 13).
- 연결 알림과 잇기가 같은 때 오면, 막 이은 문의의 담당자가 알림을 받을 수도 못 받을 수도 있다(상태 바꾸기는 연결 쪽을 잠그지 않는다).
- 문의의 상태는 연결 때문에 바뀌지 않는다(LINK-5). 중복을 이어 놓고 닫지 않은 문의가 남을 수 있다.
- 휴지통에 간 문의의 연결은 7번 전까지 없다(휴지통이 없다).
- 닫힌 상대 문의의 이력에도 잇기와 끊기 항목이 남는다(`acceptance.md` 5절 4).
