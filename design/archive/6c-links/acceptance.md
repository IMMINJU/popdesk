> `roadmap.md` 6번의 셋째 조각이다(6a 수용 기준 5절 1). 묶음이 끝나면 `design/archive/6c-links/`로 간다(D-27).

## 1. 넣는 것과 미루는 것

앞 묶음이 이미 만든 것: 문의와 상태 전이(고객도 종료와 다시 열기를 한다), 보기 범위(`IssueScope`), 문의 행 잠금(STATUS-7), 문의 이력(HIST, 칸 이름에 CHECK가 없어 새 칸을 더할 수 있다), 알림함(읽을 때 지금 볼 수 있는 문의의 항목만 보인다). 연결은 표도 코드도 없다. 휴지통(TRASH)과 자동 종료(STATUS-5)는 아직 없다(7번).

## 2. 수용 기준

"상담 쪽"은 관리자와 상담원이다. "볼 수 있는"은 RULE-03이다(관리자는 모든 문의, 상담원은 배정된 고객사의 문의). "이 문의"는 경로의 문의, "상대"는 요청의 `issueKey`가 가리키는 문의다. 연결의 종류는 이 문의에서 본 것으로 셋이다: `DUPLICATE_OF`(이 문의가 상대의 중복), `DUPLICATED_BY`(상대가 이 문의의 중복), `RELATED`(관련, 방향 없음). 저장은 규칙대로 `DUPLICATE_OF`와 `RELATED` 둘이고, `DUPLICATED_BY`는 같은 연결을 반대쪽에서 본 이름이다(5절 2).

### 2.1 잇기

| ID | 기준 |
|---|---|
| S6C-AC-01 | When 상담 쪽이 볼 수 있는 두 문의를 이으면(`issueKey`, `type`), the system shall 연결 하나를 만들고 이 문의에서 본 연결을 201로 준다. 연결에는 종류, 상대 문의(키, 제목, 상태, 고객사 코드와 이름), 이은 사람과 시각이 있다. 두 문의의 고객사가 달라도 된다. (LINK-1) |
| S6C-AC-02 | If 이 문의나 상대를 볼 수 없으면(없는 키, 키 꼴이 아닌 값, 배정되지 않은 고객사의 문의), then the system shall 없는 문의와 같은 404로 답하고 아무것도 만들지 않는다. 상대를 볼 수 없을 때의 답은 상대가 없을 때와 몸까지 같다. (LINK-1, TM-42) |
| S6C-AC-03 | If `issueKey`가 없거나 `null`이거나 빈 글(앞뒤 공백을 자른 뒤)이면, then the system shall 400 `INVALID_INPUT`(필드 `issueKey`, `REQUIRED`)으로 답한다. `type`이 없거나 `null`이면 `REQUIRED`, 셋 가운데 하나가 아니면 `UNKNOWN_VALUE`다(필드 `type`). If 상대가 이 문의면, then 400 `LINK_TO_SELF`다. (LINK-2) |
| S6C-AC-04 | If 두 문의 사이에 이미 연결이 있으면(종류와 방향과 관계없이), then the system shall 409 `LINK_EXISTS`로 답하고 아무것도 바꾸지 않는다. (LINK-2) |
| S6C-AC-05 | If 중복으로 이을 때 원본이 될 문의가 이미 다른 문의의 중복이거나, 중복이 될 문의가 이미 원본(들어오는 `DUPLICATE_OF`가 있다)이거나 이미 다른 문의의 중복이면, then the system shall 400 `LINK_DUPLICATE_CHAIN`으로 답하고 아무것도 바꾸지 않는다. `RELATED`는 이 검사를 받지 않는다. (LINK-2, 5절 3) |
| S6C-AC-06 | If 이 문의나 상대에 연결이 이미 50개면, then the system shall 400 `LINK_LIMIT_EXCEEDED`로 답한다. 개수는 보는 사람이 볼 수 없는 연결까지 센다. (LINK-2, TM-59) |
| S6C-AC-07 | If 이 문의가 `CLOSED`면, then the system shall 잇기와 끊기를 400 `ISSUE_CLOSED`로 답한다. 상대는 `CLOSED`여도 된다(새 문의를 닫힌 옛 문의의 중복으로 잇는다). (STATUS-7, 5절 4) |
| S6C-AC-08 | When 같은 두 문의에 같은 때 여러 잇기가 오거나, 중복 사슬을 만들 잇기가 같은 때 오거나(A를 B의 중복으로, B를 C의 중복으로), 한도를 넘게 될 잇기가 같은 때 오면, the system shall 어떤 한 순서로 한 것과 같은 결과를 준다(연결은 하나, 사슬 없음, 50개를 넘지 않음). 서로 반대 차례로 같은 두 문의를 잇는 요청이 함께 와도 DB의 교착(deadlock)이 생기지 않는다. (LINK-2, STATUS-7) |
| S6C-AC-09 | If 한 계정이 60초 안에 잇기와 끊기를 60번 넘게 하면, then the system shall 429로 답한다. 404·400·409로 끝난 요청도 센다(세기는 다른 검사보다 먼저다). (COM-8, TM-59, 5절 5) |
| S6C-AC-14 | The system shall 잇기의 검사를 이 차례로 한다: 요청 수(429) → 이 문의(404) → `issueKey` 있음(400 `REQUIRED`) → 상대(404) → `type`(400) → 자기 자신(400 `LINK_TO_SELF`) → 이 문의 `CLOSED`(400) → 이미 연결(409) → 사슬(400) → 한도(400). 끊기는 요청 수 → 이 문의(404) → 상대(404) → 연결(404) → `CLOSED`(400)다. 그래서 상대를 볼 수 없으면 `type`이 틀려도 404다. (`conventions.md` "Order of checks", TM-42) |

### 2.2 끊기와 목록

| ID | 기준 |
|---|---|
| S6C-AC-10 | When 상담 쪽이 이 문의와 상대의 연결을 끊으면(`DELETE …/links/{상대 키}`), the system shall 연결을 지우고 204로 답한다. 어느 쪽 문의에서 끊어도 같다. 끊은 뒤에는 두 문의를 다시 이을 수 있다. (LINK-1) |
| S6C-AC-11 | If 상대를 볼 수 없거나(잇고 난 뒤 그 고객사 배정에서 빠진 경우 포함) 두 문의 사이에 연결이 없으면, then the system shall 404로 답하고 연결을 그대로 둔다. (LINK-1, TM-42) |
| S6C-AC-12 | When 상담 쪽이 문의의 연결 목록을 읽으면, the system shall 상대를 볼 수 있는 연결만 이은 차례로 준다. 볼 수 없는 연결은 항목도 개수도 응답에 없다. 이 문의를 볼 수 없으면 404다. 배정에서 빠졌다가 다시 배정되면 그 연결이 다시 나온다. (LINK-4, TM-41) |
| S6C-AC-13 | The system shall 연결의 종류를 보는 쪽에서 준다: A를 B의 중복으로 이으면 A의 목록에는 `DUPLICATE_OF` B, B의 목록에는 `DUPLICATED_BY` A다. `DUPLICATED_BY`로 이은 것은 반대로 `DUPLICATE_OF`로 이은 것과 같다. (LINK-1, 5절 2) |

### 2.3 이력

| ID | 기준 |
|---|---|
| S6C-AC-20 | When 잇거나 끊으면, the system shall 두 문의의 이력에 칸 `LINK` 항목을 하나씩 남긴다(같은 트랜잭션). 이은 것은 뒤 값, 끊은 것은 전 값에 그 문의에서 본 종류와 상대 문의의 ID만 담는다(키와 제목을 담지 않는다. DB를 보는 테스트 도움으로 저장 값에 상대의 키와 제목이 없는지만 본다). 한 사람은 요청한 사람이다. (LINK-7, HIST-1·2) |
| S6C-AC-21 | When 상담 쪽이 이력을 읽으면, the system shall `LINK` 항목에 상대 문의(키, 제목)와 종류를 사람이 읽을 칸(`oldLink`·`newLink`)으로 주고, 전·뒤 값 글은 비운다(`ASSIGNEE`의 사람 칸과 같은 꼴). (LINK-7, 5절 6) |
| S6C-AC-22 | If 보는 사람이 상대 문의를 볼 수 없으면, then the system shall 그 `LINK` 항목을 이력에서 뺀다. 쪽 나누기의 전체 수에도 들지 않는다. 다시 볼 수 있게 되면(배정되면) 다시 나온다. 그 문의의 다른 항목(`CREATED`, 다른 칸)은 그대로 나온다. (LINK-7, TM-41, 5절 7) |
| S6C-AC-23 | The system shall 잇기와 끊기로 두 문의의 `version`도 `updatedAt`도 바꾸지 않는다(콘솔과 포털 응답 모두). 다른 고객사와의 연결이 바뀐 시각으로 드러나지 않게 한다. (TM-41, 5절 8) |

### 2.4 상태와 알림

| ID | 기준 |
|---|---|
| S6C-AC-30 | The system shall 중복으로 이어도 어느 문의의 상태도 바꾸지 않는다. (LINK-5) |
| S6C-AC-31 | When 문의가 `RESOLVED`나 `CLOSED`가 되면(상담 쪽이 바꾸든 고객이 닫든), the system shall 그 문의와 이어진 다른 문의마다 그 담당자에게 알림함 항목 하나(`LINKED_ISSUE_RESOLVED`, `LINKED_ISSUE_CLOSED`)를 남긴다. 항목의 문의는 담당자의 문의이고, 바뀐 문의는 항목의 새 칸(`linkedIssue`: 키와 제목)이다. 메일과 웹훅은 보내지 않는다. `RESOLVED`에서 `CLOSED`로 가면 다시 남긴다. (LINK-6, 10절 표) |
| S6C-AC-32 | The system shall 다음 담당자에게는 남기지 않는다: 바뀐 문의를 볼 수 없는 사람, 자기 문의를 더는 볼 수 없는 사람(배정에서 빠짐), `ACTIVE`가 아닌 사람, 상태를 바꾼 사람 자신, 담당자가 없는 문의, 자기 문의가 `CLOSED`인 사람. 같은 사람이 이어진 문의 둘의 담당자면 문의마다 하나다. (LINK-6, TM-41, 5절 9) |
| S6C-AC-35 | If 받는 사람에게 같은 종류, 같은 두 문의의 안 읽은 연결 항목이 이미 있으면, then the system shall 새 항목을 남기지 않는다(해결과 다시 열기를 오가도 항목이 쌓이지 않는다). 읽은 뒤에는 다시 남긴다. (TM-59, 5절 14) |
| S6C-AC-33 | When 알림함을 읽으면, the system shall 연결 항목을 읽는 사람이 두 문의를 모두 지금 볼 수 있을 때만 보이고, 바뀐 문의의 키와 제목은 읽을 때의 것을 준다. 안 읽은 수도 같다. (INBOX-2, TM-41) |
| S6C-AC-34 | The system shall 다른 알림 종류에 `linkedIssue`를 `null`로 준다. 문의가 해결·종료될 때의 앞 알림(올린 고객, 담당자)은 그대로다. (D-44) |

| S6C-AC-41 | 포털 문의 응답이 콘솔 타입을 써서 연결이 실린다 |

## 4. 테스트를 쓸 때 지킬 것

- 고객사 경계의 부정 테스트는 고객사 둘(A, B), 둘 다에 배정된 상담원(잇는 사람), A에만 배정된 상담원(보는 사람)으로 쓴다. 다른 고객사 사이의 연결이 이 묶음의 중심이다.
- 알림은 자기가 만든 문의로만 센다. 알림함의 안 읽은 수는 자기 계정만 본다.
- 이력 항목의 종류와 값의 꼴(`DUPLICATE_OF:{uuid}` 같은 글)은 API로 보지 않는다. 테스트는 `oldLink`·`newLink`와 칸 이름 `LINK`만 본다(설계 1절의 저장 꼴은 구현이 바꿀 수 있다).
- 잠긴 앞 테스트: `IssueHistoryEntry`의 칸을 그대로 견주는 테스트가 있으면 `oldLink`·`newLink`(다른 칸에서 `null`)가 더해져도 맞게 테스트 탭이 맞춘다(C-4 뒤 `grep -rn "oldPerson" server/src/test web/*/src`로 찾는다). 알림 항목 `Notification`에 `linkedIssue`가 더해지는 것도 같다.
- 웹 가짜 서버(`console.ts`)의 기본 핸들러에 빈 연결 목록(`items: []`)을 더한다. C-4가 요청을 하나 더 보낸다(`process.md` C-4).
- 콘솔 C-4의 잠긴 테스트가 이름으로 찾는 단추("바꾸기", "담당자 바꾸기", "작업 담당자 바꾸기")와 겹치지 않게, 연결 구역의 단추는 "문의 잇기", "{키} 연결 끊기"다.
- 같은 때의 테스트(S6C-AC-08)는 A→B와 B→A 잇기를 함께 보내는 것을 여러 번(20쌍쯤) 되풀이하고, 앞뒤로 DB를 보는 테스트 도움으로 `pg_stat_database.deadlocks`가 늘지 않았는지 본다. 앱은 교착이 나면 트랜잭션을 한 번 다시 하므로(`conventions.md` "Retrying on lock") 답만 봐서는 잡히지 않는다. 사슬의 같은 때(A→B와 B→C)는 DB 제약이 막지 않으므로 이것도 여러 번 되풀이한다. 그래도 겹치지 않은 회차는 못 잡으므로 C-7 점검이 잠금 차례를 코드로도 본다.
- 연결 50개(S6C-AC-06, 08)를 만들려면 문의 51개와 잇기 50번이 든다. 문의 올리기(계정마다 60초에 10번)와 잇기(60번)의 제한은 앱 시계를 넘겨 지나가거나 계정을 여럿 쓴다. 연결 행을 DB에 바로 넣지 않는다(픽스처는 API로).
- 상태를 `RESOLVED`나 `CLOSED`로 바꾸는 길은 앞 묶음의 도움(`IssueFlow.moveTo`, `changeStatus`, 고객 종료)을 쓴다.
