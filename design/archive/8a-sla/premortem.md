# 8a 묶음 사전 부검

> 0.8.0을 낸 지 한 달 뒤 SLA 기한 때문에 사고가 났다고 치고, 무엇이 그랬을지 거꾸로 적는다. 막는 것은 기준 ID나 설계 절로 단다.
> 상태: **메인이 정함, 사용자 확인 전**(2026-10-16).

## 1. 기한이 틀렸다

- 금요일 17시에 올라온 문의의 4시간 목표가 토요일 새벽으로 잡혔다(업무 시간 밖을 셌다).
- 서머타임이 시작하는 날 기한이 한 시간 어긋났다(벽시계 구간을 고정 오프셋으로 바꿨다).
- 업무 시간을 정한 요일이 없을 때 계산이 끝나지 않아 등록 요청이 멈췄다.

막는 것: 업무 시간 계산을 순수 클래스 하나에 두고 경계·서머타임·24시간을 단위 테스트와 변이 테스트로 본다(설계 2절, 7절). 목표 한도와 "모든 요일이 비면 24시간"으로 끝나는 것을 보장한다(5절 6, 7). 기한 계산 5 ms 기준(S8A-AC-42, 주 단위로 건너뜀). 숨긴 E2E가 업무 시간 밖 등록을 본다.

## 2. 다시 계산이 값을 망쳤다

- 정책을 바꾼 뒤 작업이 돌기 전에 상담원이 첫 응답을 했는데, 작업이 읽어 둔 옛 값으로 덮어 첫 응답이 다시 돌았다.
- 작업이 늦게 돌아, 바꾼 때부터가 아니라 작업이 돈 때부터 새 업무 시간으로 셌다. 인스턴스가 재시작해 같은 문의를 두 번 계산해 센 시간이 두 배가 됐다.
- 지난 날짜를 쉬는 날로 넣었더니 이미 넘긴 문의가 "지킴"이 됐다.

막는 것: 버전을 바꾸지 않는 행으로 쌓고 버전의 시작 시각을 경계로 센다(5절 2, S8A-AC-20, 23). 작업은 `where 계산 버전 = 읽은 버전` 조건부 UPDATE, 다른 쓰기는 문의 행 잠금(설계 0절 4, S8A-AC-21). 센 시간은 줄이지 않는다(S8A-AC-22).

## 3. 고객이 SLA를 봤다

- 포털 문의 응답에 콘솔 DTO가 섞여 `sla` 칸이 나갔다. 포털 목록이 `sort=slaDue`를 받아 순서로 기한을 짐작할 수 있었다.
- 고객이 우선순위를 바꿔 기한을 당기거나 늦출 수 있다는 것을 몰랐다(받아들인다. 우선순위 고치기는 규칙이 고객에게 허락했다).

막는 것: 포털 DTO는 따로 있고 매개변수는 허용 목록이다(S8A-AC-33, TM-63). 고객이 바꾼 우선순위도 같은 다시 계산을 탄다(S8A-AC-17).

## 4. 목록이 느려졌다

- `sla=breached`가 문의 표를 처음부터 끝까지 읽었다. 상담원 목록은 이미 150 ms 언저리라 넘었다.
- 다시 계산 작업이 2만 건을 한 트랜잭션으로 잠가 목록과 쓰기가 기다렸다.

막는 것: 이른 기한과 경고 시각을 칸으로 저장하고 부분 색인 셋(기한, 경고, 다시 계산 대상. 설계 0절 3, 1절). 작업은 500건 묶음, `skip locked`(설계 4절). 성능 기준 S8A-AC-40, 41.

## 5. 정책을 고친 사람이 사라졌다

- 관리자 둘이 같은 때 고쳐 앞 사람의 쉬는 날이 없어졌다.
- 시간대만 바꾼 운영자가 버전이 왜 올랐는지 몰랐다.

막는 것: `version`을 보내고 다르면 409(5절 9, S8A-AC-03). 감사 로그(S8A-AC-06). 화면의 상태 줄이 시스템이 바꾼 버전을 "시간대가 바뀌어"로 적는다(`screens.md` 1절).
