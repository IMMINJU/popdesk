| 정리 작업 | 24시간이 지난 `issue_idempotency` 행 지우기. 한 시간마다 | S3-AC-46 |

- `CREATED` 이력 행은 `field`와 두 값 칸이 모두 `null`이다. 제목을 값에 넣지 않는다(잠긴 `notify.NoWebhookTest`가 "등록 뒤 제목이 든 행은 하나"를 본다. 테스트 쪽 탭이 알림).
- V10은 앱의 서비스 클래스를 부르지 않고 마이그레이션 안에 글자 뽑기를 둔다. 나중에 앱의 뽑는 법이 바뀌어도 나간 마이그레이션은 그대로다(D-24). 앱과 마이그레이션이 같은 결과를 내는지는 구현 탭의 단위 테스트가 한 번 견준다.
- 표 둘이 늘어나므로 `deploy/upgrade/make-sample.py`가 채운다(S3-AC-90). 이력은 상태를 바꾸고 담당자를 정하면 생긴다. 등록 키는 키를 붙인 등록 한 번으로 생긴다.
- 옛 이미지는 이 스키마에서 뜨지 않는다(D-46). 릴리스 노트에 되돌릴 수 없는 마이그레이션과 `pg_trgm`을 적는다(D-24).
- 검색어가 한두 글자면 색인을 타지 않고 훑는다. 10만 건에 2초, 한국어는 4초쯤이다 [실험 4]. 받아들이고 요청 수 제한으로만 막는다. 수십만 건에서 느려지면 그때 최소 글자 수를 정한다.
- 10만 건에서 색인은 293 MB, 표는 535 MB다 [실험 4]. 릴리스 노트에 DB가 커진다고 적는다.
- DB의 ctype이 `C`이면 한글에서 트라이그램이 나오지 않아 한국어 검색이 늘 훑는다 [실험 4]. 결과는 맞다. compose 설치는 `en_US.utf8`이라 걸리지 않는다. `docs/operate/`의 바깥 DB 안내에 적는다.
- 등록이 `issue_history`에 한 줄을 넣으므로 "등록 뒤 더해진 행은 문의 행뿐"이라고 단언하는 잠긴 테스트(`notify.NoWebhookTest`)는 요구가 바뀐 것이다. 테스트 쪽 탭이 맞춘다 [실험 5].

## 2. 문의를 바꾸는 요청의 꼴

한 트랜잭션이고 차례는 `architecture.md`의 잠금 순서를 따른다.

| 요청 | 차례 |
|---|---|
| 상태 변경, 종료, 재오픈 | ① 범위 안에서 문의를 읽는다(없으면 404) ② 권한(403) ③ `UPDATE issue SET status …, version = version + 1 WHERE id = ? AND status = ?(읽은 값)`. 재오픈은 조건에 종료 시각의 14일을 넣는다 ④ 바뀐 행이 0이면(그사이 다른 요청이 상태를 바꿨다) 다시 읽어 전이를 처음부터 다시 판정한다. 지금 상태에서 되는 전이면 ③을 다시 하고, 안 되면 400이다. 같은 때 온 "접수 → 확인"과 "접수 → 종료"는 확인이 먼저 되면 종료가 "확인 → 종료"로 다시 판정되어 둘 다 된다(S3-AC-51의 "어떤 한 순서의 결과". 점검 탭이 짚음). 다시 하기는 몇 번으로 끊는다 ⑤ 이력과 웹훅 대기 행을 넣는다 |
| 고치기 | ① 읽기 ② 권한 ③ 문의 행을 `FOR NO KEY UPDATE`로 잠그고 `version`과 `CLOSED`를 다시 본다(409, 400) ④ 바뀐 칸만 UPDATE하고 `search_text`를 다시 만든다 ⑤ 바뀐 칸마다 이력 |
| 담당자 | ① 읽기 ② 문의 행 잠금 ③ 새 담당자가 자격이 있는지 같은 트랜잭션에서 본다 ④ UPDATE와 이력, 웹훅 |
| 담당 비우기 | 배정 빼기나 정지의 트랜잭션 안에서 `UPDATE issue SET assignee_id = NULL … WHERE assignee_id = ? AND status <> 'CLOSED' [AND company_id = ?] RETURNING id`. 돌아온 문의마다 이력을 넣는다. 문의 행을 하나씩 잠그지 않는다(조건부 UPDATE다, STATUS-7) |

- 닫힌 문의에 옛 `version`으로 고치면 400 `ISSUE_CLOSED`가 먼저다(409가 아니다).
- 고치기 본문의 모르는 칸은 무시한다(등록과 같다). 빈 `Idempotency-Key` 머리글은 틀린 키다(400).
- 배정되지 않은 상담원의 그 고객사 열린 담당 수는 0이다(404가 아니다. 관리자가 묻는 것이고 고객사와 계정은 있다).
- 상태 변경은 `version`을 받지 않는다(ISSUE-6). 고치기만 받는다. 그래서 상태가 바뀐 뒤의 고치기는 409가 된다. 화면은 최신 값을 다시 읽어 보인다(S3-AC-81).
- 전이 표는 한 곳(상태 enum의 함수 하나)에 둔다. 콘솔 화면의 버튼은 서버가 준 "지금 되는 전이" 목록으로 그린다 [추론: 계약 탭이 응답에 넣을지 화면이 표를 따로 가질지 정한다. 메인의 추천은 서버가 주는 것이다. 표가 두 곳에 있으면 어긋난다].
- "올린 고객이고 소속이 남아 있는가"는 댓글이 이미 본다 [소스: `CommentService`]. 고치기, 재오픈이 같은 함수를 쓰고, 종료만 소속을 보지 않는다(S3-AC-54).
- 고객의 요청은 포털 타입으로만 받는다. 포털의 고치기 타입에는 제목, 내용, 우선순위, `version`만 있다(S3-AC-23, D-41).

## 3. 목록의 필터와 검색

- 필터는 `IssueScope.SQL` 뒤에 `AND`로만 붙인다 [소스: 범위는 모든 읽기에 붙는 한 조건이다]. 범위를 대신하거나 `OR`로 잇는 조건을 만들지 않는다(S3-AC-06, 10). 건수(`totalElements`)도 같은 조건으로 센다.
- "담당자가 볼 수 없음"은 SQL 조건 하나다: 담당자가 있고, 그 계정이 `ACTIVE`가 아니거나, 상담원인데 `company_agent`에 그 고객사의 행이 없다. 목록과 상세의 표시, 필터가 같은 조건을 쓴다.
- 검색어가 있으면 검색 조건으로 먼저 좁힌 뒤 정렬한다(좁힌 결과를 `MATERIALIZED` CTE로 두는 꼴). 그냥 `ORDER BY created_at DESC LIMIT 20`을 붙이면 계획기가 최신순 색인을 거꾸로 훑어 10만 건에서 2.1초가 걸렸다 [실험 4]. 잠긴 테스트로는 보지 않는다(쿼리의 글자를 고정하면 구현을 묶고, 테스트 DB는 작아서 계획이 다르다. 테스트 탭이 따져 봄). 구현 탭이 문의 10만 건에서 세 글자 이상의 검색이 1초 안인지 한 번 재서 보고하고 메인이 `verify.md`에 적는다.
- 검색은 `search_text ILIKE ? ESCAPE '\'`다. 검색어의 `%`, `_`, `\`는 계정 검색과 같은 함수로 바꾼다 [소스: `AccountRepository`]. 계정 검색에는 `ESCAPE` 절이 없어 DB 기본값에 기대고 있다. 같이 붙인다.
- 검색어는 로그에 남기지 않는다(S3-AC-92). 앱에는 접근 로그도 쿼리 문자열을 적는 코드도 없다 [계약 탭이 확인].
- 요청 수 제한(S3-AC-15)은 `q`가 있을 때만 센다. 문의 목록과 계정 목록이 한 통을 쓴다.

## 4. 등록 키

1. 키가 있으면 먼저 `(계정, 키)`를 읽는다. 있으면 내용의 해시를 견줘 같으면 그 문의를 201로, 다르면 409로 답하고 끝낸다. 첨부를 받기 전이다.
2. 없으면 지금처럼 등록한다. 업무 트랜잭션 안에서 새 행들을 넣는 자리(잠금 순서 3)에 키 행을 넣는다. 유니크에 걸리면(같은 때 온 다른 요청이 먼저 커밋함) 트랜잭션을 되돌리고 1로 돌아가 답한다.
3. 순번(잠금 순서 4)은 키 행 뒤에 받는다. 그래서 진 쪽은 순번을 쓰지 않는다(S3-AC-44).

- 해시에 넣는 값: 고객사 코드, 제목(자른 뒤), 내용, 우선순위(기본값을 채운 뒤), 비공개 여부, 대리 등록이면 고객 계정 ID와 받은 경로. 값을 정해진 차례로 이어 SHA-256을 낸다.
- 진 쪽이 미리 올린 첨부(`pending`)는 정리 작업이 지운다(첫 묶음의 실패한 등록과 같다, S0-AC-63).
- 키와 해시는 로그에 남기지 않는다.

## 5. 대리 등록과 메일

- 포털 등록과 같은 서비스 함수(`IssueService.prepare`, `file`)를 쓰고, 올린 사람과 만든 사람, 받은 경로만 다르게 넘긴다 [소스: 경로는 지금 `PORTAL`로 박혀 있다].
- 고객의 자격(그 고객사 소속, `ACTIVE`, 고객 역할)은 등록 트랜잭션 안에서 본다.
- 고객을 고르는 목록은 새 경로(`…/companies/{code}/reporters`)다. 있던 소속 고객 목록은 관리자 전용 그대로다(`acceptance.md` 5절 12).
- 콘솔 대리 등록의 본문도 포털처럼 256 KB에서 413이다(`conventions.md`).
- `popdesk restore`의 `pg_restore`에 `--no-comments`를 더한다(S3-AC-93). 확장의 주인이 아닌 사용자는 `COMMENT ON EXTENSION`에서 실패한다 [실험 2].
- 메일은 `STAFF_COMMENT`와 같은 길이다: 대기 행에 받는 계정과 문의만 두고, 제목과 주소는 보낼 때 읽고, 보내기 직전에 `IssueVisibility`로 다시 본다 [소스].
- 메일의 글은 `MailText`에 한국어와 영어로 더한다. 문의 제목은 메일 제목에 들어가고(첫 묶음의 댓글 메일과 같다) 내용은 넣지 않는다.

## 6. 쓸 컴포넌트와 토큰

- 새 토큰은 없다.
- 새 공용 컴포넌트 하나: `SearchField`(검색 입력. 이름표, 지우기 버튼, 입력을 멈춘 뒤에 알림). 콘솔 구성원 목록이 직접 짠 지연 입력 [소스: `C10MemberList.tsx`의 `SEARCH_DELAY_MS`]을 이것으로 바꾼다.
- 있는 것을 쓴다: `Select`, `CheckboxGroup`(상태 여러 개), `DataTable`, `Dialog`, `ConfirmDialog`, `StatusBadge`, `PriorityPicker`, `MarkdownEditor`, `RelativeTime`, `Avatar`, `Alert`, `Toast`, `Pagination`.
- 있던 공용 컴포넌트의 props는 깨지 않는다. `StatusBadge`와 `ISSUE_STATUS_WORDS`에는 다섯 상태의 말이 이미 있다 [소스: `words.ts`]. 그 말을 그대로 쓴다.
- 필터를 주소에 싣는 법은 감사 로그 화면의 것을 따른다 [소스: `C12AuditLog.tsx`의 `readFilters`, `writeFilters`].
