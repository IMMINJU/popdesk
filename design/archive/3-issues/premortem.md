# 3번 묶음 사전 부검

> 3번 묶음(문의)을 내고 석 달 뒤 일이 틀어졌다고 가정하고, 어떻게 틀어졌을지와 막을 장치를 적는다. 고객사 경계, 마이그레이션, 공개 계약을 건드려서 전체 경로다(`process.md`).
> 표시: [소스]는 레포의 코드나 마이그레이션에서 본 것, [추론]은 확인하지 않은 판단이다.
> 장치는 `acceptance.md`와 `design.md`에 옮겼다. 묶음이 끝나면 이 파일은 `design/archive/3-issues/`로 간다.
> 상태: **메인이 정함, 사용자 확인 전**(2026-10-12). 묶음이 끝나 `design/archive/3-issues/`로 옮겼다(2026-10-12).

## 1. 고객이 검색으로 다른 고객사의 문의를 알아냈다

| 항목 | 내용 |
|---|---|
| 장면 | A사 고객이 검색어를 바꿔 가며 목록의 건수(`totalElements`)를 봤다. 경쟁사 이름을 넣자 건수가 0이 아니었다. 문의는 한 줄도 안 보였지만 그런 글이 있다는 것은 알았다 |
| 원인 | 목록은 범위로 거르는데 건수를 세는 SQL은 필터만 붙였다. 또는 검색 조건을 `OR`로 이어 범위 조건이 풀렸다 |
| 막는 법 | 필터와 검색은 범위 조건 뒤에 `AND`로만 붙이고, 목록과 건수가 같은 조건을 쓴다(`design.md` 3절). 볼 수 없는 고객사 코드로 거르면 오류가 아니라 빈 목록이다(S3-AC-02, 08) |
| 확인 테스트 | B사 문의에만 있는 낱말로 A사 고객과 A사에만 배정된 상담원이 찾으면 항목이 없고 건수가 0이다. 동료의 비공개 문의에만 있는 낱말도 같다. C-7 점검 탭이 건수 SQL에서 범위를 뺀 틀린 구현을 넣어 테스트가 잡는지 본다 |
| 옮길 곳 | S3-AC-06, 10, 88 |

## 2. 상담원이 맡지 않은 고객사의 사람을 봤다

| 항목 | 내용 |
|---|---|
| 장면 | A사에만 배정된 상담원이 담당자 후보와 대리 등록의 고객 목록 주소에 B사 코드를 넣어 B사의 고객 이름과 이메일을 받았다 |
| 원인 | 새 읽기 길 둘(후보, 소속 고객)이 "상담 쪽이면 된다"만 봤다. 소속 고객 목록은 지금 관리자만 부른다 [추론: 계약 탭이 확인] |
| 막는 법 | 두 길 모두 고객사를 상담원의 배정 범위 안에서 먼저 찾는다. 범위 밖은 없는 코드와 같은 404다(S3-AC-27, 40). 대리 등록에서 고른 고객이 그 고객사 소속인지는 서버가 다시 본다(S3-AC-33) |
| 확인 테스트 | 배정되지 않은 상담원의 후보·고객 목록·대리 등록이 404다. A사 문의에 B사 고객을 올린 사람으로 넣으면 400이다. 경계 테스트 목록에 새 엔드포인트가 모두 있다 |
| 옮길 곳 | S3-AC-27, 33, 34, 40, 88 |

## 3. 고객의 화면에 담당자와 대리 등록한 상담원이 나왔다

| 항목 | 내용 |
|---|---|
| 장면 | 포털의 문의 응답에 담당자 이름이 실렸다. 대리 등록 메일에는 상담원의 이름이 "○○ 님이 문의를 올렸습니다"로 나갔다 |
| 원인 | 콘솔 타입에 칸을 더하면서 포털 타입을 같이 넓혔다. 메일의 글이 만든 사람의 이름을 썼다 |
| 막는 법 | 포털과 콘솔의 타입은 따로다(D-41). 포털에는 "지원팀이 대신 올렸다"는 표시 하나만 더한다(S3-AC-36). 첫 묶음의 계약 테스트가 포털 타입에 담당자·이력·첫 응답 같은 이름 조각이 없는지 본다 [소스: `PortalIssueContractTest`의 `STAFF_ONLY`]. 메일은 "지원팀"만 쓴다(S3-AC-37) |
| 남는 것 | 포털에 주는 표시의 이름이 그 테스트의 금지 조각(`createdby`)에 걸리면 계약 탭이 다른 이름을 고른다 |
| 확인 테스트 | 대리 등록하고 담당자를 정한 문의로, 포털 응답(목록, 상세)과 메일 본문 전체에서 그 상담원의 이름, 이메일, 계정 ID를 찾아 없다(첫 묶음 S0-AC-98의 꼴) |
| 옮길 곳 | S3-AC-29, 36, 37 |

## 4. 두 사람이 같은 때 누른 일이 이력을 틀리게 남겼다

| 항목 | 내용 |
|---|---|
| 장면 | 상담원 둘이 같은 문의를 같은 때 "해결"로 바꿨다. 이력에 "처리 중 → 해결"이 두 번 남고 웹훅도 두 번 갔다. 다른 날에는 고객이 종료한 직후에 달린 댓글이 닫힌 문의에 붙었다 |
| 원인 | 상태를 읽고 검사한 뒤 조건 없이 UPDATE했다. 댓글이 문의 행을 잠그기 전에 상태를 읽었다 |
| 막는 법 | 상태 변경은 읽은 상태를 조건에 넣은 UPDATE이고 바뀐 행이 0이면 이력을 남기지 않는다(`design.md` 2절). 문의 아래 쓰기는 문의 행을 잠그고 상태를 다시 본다 [소스: 첫 묶음의 댓글과 첨부가 이미 그렇게 한다] |
| 확인 테스트 | 같은 전이 둘을 같은 때 보내면 하나는 200, 하나는 400이고 이력과 웹훅 대기 행이 한 건이다(S3-AC-51). 종료와 댓글을 같은 때 보내면 닫힌 뒤의 댓글이 없다(S3-AC-52) |
| 옮길 곳 | S3-AC-51, 52, 63 |

## 5. 뒤로 가기 한 번에 문의가 둘 생겼다

| 항목 | 내용 |
|---|---|
| 장면 | 통신이 느린 곳에서 고객이 등록을 눌렀다. 응답이 늦어 화면이 다시 보냈고 같은 문의가 둘 생겼다. 다른 설치에서는 키를 붙였는데도 둘이 생겼다. 두 요청이 같은 때 와서 둘 다 "키 없음"을 읽었다 |
| 원인 | 키를 읽기만 하고 유니크로 막지 않았다. 또는 화면이 다시 보낼 때 새 키를 만들었다 |
| 막는 법 | 키 행은 (계정, 키)가 기본 키이고 등록 트랜잭션 안에서 넣는다. 진 쪽은 순번을 받기 전에 되돌린다(`design.md` 4절). 화면은 폼을 열 때 키를 만들고 입력을 고칠 때만 새로 만든다(S3-AC-84) |
| 남는 것 | 키가 없는 요청(다른 클라이언트)은 막지 못한다. 요청 수 제한(60초에 10건)이 전부다 |
| 확인 테스트 | 같은 키의 등록 둘을 같은 때 보내면 문의가 하나이고 순번이 하나만 오른다(S3-AC-44). 다른 계정의 같은 키는 새로 만든다(S3-AC-43). 화면 테스트: 실패 뒤 다시 보낸 요청의 키가 같다 |
| 옮길 곳 | S3-AC-41~47, 84 |

## 6. 올린 뒤 앱이 뜨지 않았다

| 항목 | 내용 |
|---|---|
| 장면 | 관리형 Postgres를 쓰는 설치가 0.3.0으로 올렸다. 앱의 DB 사용자가 확장을 만들 수 없어 V9가 실패했고, 로그에는 SQL 오류 한 줄뿐이라 무엇을 해야 하는지 몰랐다. 다른 설치는 문의가 많아 V10이 20분 걸렸고 그동안 상태 확인이 실패해 오케스트레이터가 컨테이너를 계속 다시 띄웠다 |
| 원인 | `CREATE EXTENSION`의 권한. 마이그레이션 시간 |
| 막는 법 | V9가 확장에서 실패하면 뜨지 않고 확장 이름과 칠 명령(`CREATE EXTENSION pg_trgm;`을 DB 관리자로)을 로그에 남긴다(S3-AC-91). `docs/operate/`의 업그레이드 안내와 릴리스 노트에 적는다. V10은 나눠서 채우고 걸리는 시간을 실험으로 재서 릴리스 노트에 적는다(`design.md` 7절 4). 마이그레이션 동안의 상태 확인은 첫 묶음의 `start_period` 안내 그대로다 [소스: `architecture.md` 기동 순서] |
| 남는 것 | 확장 자체가 설치되지 않은 Postgres(아주 줄인 이미지). 같은 안내가 나가고, 설치하는 사람이 Postgres 쪽에 패키지를 넣어야 한다 |
| 확인 테스트 | 확장을 만들 수 없는 사용자로 띄우면 뜨지 않고 로그에 안내가 있다. 0.1.0과 0.2.0 견본이 올라오고 있던 문의가 검색된다(S3-AC-89) |
| 옮길 곳 | S3-AC-89, 91, `design.md` 7절 1·2·4 |

## 7. 담당 비우기가 엉뚱한 문의까지 비웠다

| 항목 | 내용 |
|---|---|
| 장면 | 관리자가 상담원을 A사 배정에서 빼며 "담당 비우기"를 골랐다. 그 상담원이 B사에서 맡은 문의의 담당까지 비워졌다. 다른 날에는 정지가 "마지막 관리자"로 거절됐는데 담당은 이미 비워져 있었다 |
| 원인 | 비우는 UPDATE에 고객사 조건이 빠졌다. 비우기와 정지가 다른 트랜잭션이었다 |
| 막는 법 | 배정 빼기의 비우기는 그 고객사 조건을 넣는다. 비우기는 배정 빼기·정지와 같은 트랜잭션이고 검사가 모두 지난 뒤에 한다(`design.md` 2절). 화면에 보인 수와 비운 수는 같은 조건으로 센다 |
| 남는 것 | 수를 본 뒤 비우기 전에 누가 문의를 더 맡기면 화면의 수와 비운 수가 다르다. 비운 수는 감사 항목에 남는다(S3-AC-72) |
| 확인 테스트 | 두 고객사에서 담당인 상담원을 한 고객사에서 빼며 비우면 다른 고객사의 담당은 그대로다. 거절된 정지 뒤 담당이 그대로다(S3-AC-71). 닫힌 문의의 담당은 그대로다(S3-AC-70) |
| 옮길 곳 | S3-AC-68~72 |

## 8. 맡은 사람이 없어진 문의를 아무도 몰랐다

| 항목 | 내용 |
|---|---|
| 장면 | 관리자가 비우기를 고르지 않고 상담원을 정지했다. 그 사람이 맡은 문의는 목록에 담당자 이름이 그대로 보여 아무도 손대지 않았다 |
| 원인 | 담당자 칸은 그대로 둔다(PROJ-4). 볼 수 없는 담당자를 가려 보는 길이 없었다 |
| 막는 법 | 목록과 상세가 "담당자가 볼 수 없음"을 글자로 표시하고 그것만 거르는 필터를 둔다(S3-AC-04, 28, 78). 정지와 배정 빼기의 대화상자가 담당인 문의 수를 먼저 보인다(S3-AC-85) |
| 남는 것 | 알림은 없다. SLA 넘김 알림이 배정 상담원 전부에게 가는 것은 8번 묶음이다 |
| 확인 테스트 | 담당자를 정지하면 그 문의가 필터에 나오고, 풀면 사라진다(S3-AC-31) |
| 옮길 곳 | S3-AC-04, 28, 31, 78, 85 |

## 9. 고친 글이 조용히 사라졌다

| 항목 | 내용 |
|---|---|
| 장면 | 고객이 내용을 길게 고치는 동안 상담원이 우선순위를 바꿨다. 고객이 저장하자 409가 났고 화면이 최신 값으로 폼을 덮어 고객이 쓴 글이 사라졌다 |
| 원인 | 충돌 뒤 화면이 폼을 서버 값으로 다시 채웠다 |
| 막는 법 | 409이면 입력을 그대로 두고 최신 값을 옆에 보인다. 다시 저장하면 새 `version`으로 보낸다(S3-AC-81, UX-10). 상태 변경도 `version`을 올리므로 고치는 중에 상태가 바뀌어도 409다(`design.md` 2절) |
| 남는 것 | 상태만 바뀌었는데도 409가 난다. 규칙(ISSUE-6)이 "문의 행이 바뀔 때마다"로 정했다. 화면이 "무엇이 바뀌었는지"를 보여 다시 저장하게 한다 |
| 확인 테스트 | 화면 테스트: 409 뒤 입력칸의 글이 그대로이고 다시 저장하면 새 `version`이 간다. 서버 테스트: 옛 `version`은 아무것도 바꾸지 않는다(S3-AC-19) |
| 옮길 곳 | S3-AC-19, 81 |

## 10. 로그에 검색어와 문의 내용이 남았다

| 항목 | 내용 |
|---|---|
| 장면 | 고객이 주민번호로 자기 문의를 찾았다. 요청 로그가 쿼리 문자열을 그대로 남겼다. 이력 표에 제목과 내용의 전·뒤 값이 통째로 들어 있는 것도 내보내기 때 드러났다 |
| 원인 | 검색어가 주소에 실린다. 이력이 글을 두 벌 더 가진다 |
| 막는 법 | 앱은 검색어를 로그에 남기지 않는다(S3-AC-92). 앞단 프록시의 액세스 로그는 설치하는 사람의 것이라 `docs/operate/`에 "검색어가 주소에 실린다"고 적는다. 이력의 제목·내용 값은 영구 삭제 때 비운다(TRASH-3, 7번 묶음). 이력은 상담 쪽만 본다(S3-AC-64, 65) |
| 남는 것 | 프록시 로그. 검색을 POST로 바꾸면 없어지지만 주소에 필터를 싣는 것(S3-AC-76)과 맞지 않는다. 받아들인다 |
| 확인 테스트 | 검색과 고치기 뒤 앱 로그에 그 낱말이 없다(원문, 퍼센트 인코딩, JSON 이스케이프 세 꼴. 받은 줄 수를 먼저 본다) |
| 옮길 곳 | S3-AC-92 |

## 11. 대리 등록 메일이 엉뚱한 사람에게 갔다

| 항목 | 내용 |
|---|---|
| 장면 | 상담원이 고객을 잘못 골라 비공개 문의를 대리 등록했다. 제목에 다른 사람의 사정이 적힌 메일이 그 고객에게 갔다 |
| 원인 | 사람의 실수다. 올린 사람을 바꾸는 길도 없다 |
| 막는 법 | 대리 등록 화면이 보내기 전에 고객의 이름과 이메일을 함께 보인다(`screens.md`). 메일에는 내용을 넣지 않는다(S3-AC-37). 잘못 올린 문의는 상담원이 종료하고 다시 올린다 |
| 남는 것 | 제목은 메일에 들어간다(첫 묶음의 댓글 메일과 같다). 잘못 올린 문의를 지우는 것은 7번 묶음의 휴지통이다. 그때까지는 종료만 된다 |
| 확인 테스트 | 메일 본문에 문의 내용이 없다 |
| 옮길 곳 | S3-AC-37, `screens.md` |
