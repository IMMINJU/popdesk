## 2. 1~2자 검색이 느려진 것

- 시간당 p95: 1~2자 검색 90 ms(시작) → 620 ms(9시간) → 1,750 ms(24시간). 3자 검색 48~64 ms, 목록 46~51 ms.
- 원인: 검색어를 아는 계획(custom plan)에서 통계가 "거의 모든 문의가 이 글자를 가진다"고 하면, 계획기가 조각 색인 대신 순차 읽기를 고르고 `issue_search_grams()`를 행마다 부른다. 함수 비용이 기본값이라 계획기는 이 함수를 싸게 본다. 앱이 보낸 질의 그대로 `in`(문의 97%)이 1,760 ms였고, 같은 질의의 값을 모르는 계획은 17 ms였다.
- 검색어를 스칼라 서브쿼리로 감싸면 늘 색인을 탄다. b9 DB에서 `in`, `s`, `프` 모두 17 ms, `zz` 0.8 ms. Claude 서브에이전트 교차검증도 같은 결론이었다(함수 COST 마이그레이션은 거의 모든 행이 맞을 때 양쪽에 같은 비용이 붙어 고쳐지지 않는다).
- b10 묶음으로 고친다(`../../slices/b10-search-plan/plan.md`). 쿼리 시간 제한이 없는 것은 backlog 마-7.
