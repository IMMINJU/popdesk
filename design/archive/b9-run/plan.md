# b9 계획: 운영처럼 하루 돌려 본다

> 2026-10-23. 상태: **메인이 정함, 사용자 확인 전**. 0.6.0을 운영자가 하는 순서대로 이 PC에 깔고, TLS 프록시, 정해 둔 백업, 부하를 붙여 하루 돌린다. 끝에 백업으로 복원해 걸린 시간(RTO)을 잰다.
> 제품 코드는 바꾸지 않는 것이 목표다. 돌리다 문제가 나오면 그때 묶음을 따로 연다.

## 1. 왜 하나

- 지금까지의 확인은 테스트가 만든 설치를 몇 분 쓰고 지우는 것이었다. 몇 시간 이상 켜 둔 설치에서만 보이는 것(힙이 계속 느는지, 정리 작업이 겹치는지, 로그가 쌓이는 속도, 백업이 커지는 속도)은 본 적이 없다.
- D-33은 RTO를 견본 데이터로 재서 문서에 적으라고 한다. 아직 잰 값이 문서에 없다(`process.md` D절 "남은 것").
- 백업 문서는 손으로 한 번 하는 법만 있다. 정해 둔 시간에 돌리고 오래된 것을 지우는 법이 없다.

## 3. 메인이 정한 것

| # | 정한 것 | 까닭 | 버린 것 |
|---|---|---|---|
| 1 | 부하 도구는 `deploy/soak/`에 Python 표준 라이브러리로 둔다 | 업그레이드 도구(`deploy/upgrade/`)와 같은 꼴이라 누구나 다시 돌릴 수 있다. 결과를 읽는 사람이 같은 숫자를 다시 낼 수 있어야 한다 | k6, Locust(설치가 더 든다) |
| 2 | 관측은 Grafana 묶음(`compose.obs.yml`)을 쓰지 않고 부하 도구가 한 시간마다 지표와 `docker stats`를 파일에 적는다 | 그 묶음은 메모리 1.5GB가 더 든다. 이 PC는 16GB이고 하루 내내 켜 둔다 | `compose.obs.yml` |
| 3 | 백업 일정은 문서의 예시와 스크립트로 둔다. 이 PC에는 cron이 없어 같은 스크립트를 한 시간마다 부르는 반복문으로 대신한다 | 운영자 대부분은 리눅스 호스트의 cron이나 systemd 타이머를 쓴다. 앱 안에 백업 일정을 넣는 것은 새 설정과 계약이라 이 묶음 범위 밖이다 | 앱 안의 백업 작업 |
| 4 | 부하는 사람 쪽 API로만 건다(포털과 콘솔). DB에 직접 넣지 않는다 | 쓰기 경로의 색인 갱신, 알림, 메일, 감사 기록이 모두 돌아야 한다 | SQL로 채우기 |
| 5 | 이 묶음은 기본 경로다. 문서와 개발 도구만 바뀌고 제품 코드, 스키마, 공개 계약은 바뀌지 않는다. Caddy를 Compose에 붙이는 파일을 레포에 더하게 되면 그때 공개 계약으로 보고 다시 정한다 | | |

## 4. 순서

1. 탭 하나가 `deploy/soak/`(부하 도구와 기록)와 백업 스크립트를 쓴다. 메인은 짧게 돌려 본다(10분).
2. 0.6.0 이미지가 ghcr에 오른 뒤 메인이 설치하고 하루 돌린다.
3. 끝나면 RTO를 재고 문서를 고치고 `verify.md`에 적는다.
