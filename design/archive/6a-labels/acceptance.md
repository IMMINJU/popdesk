# 6a 묶음 수용 기준: 라벨과 마감일

> `roadmap.md` 6절 6번의 첫 조각이다. 6번을 셋으로 가른다: 6a(라벨, 마감일, 문의 목록), 6b(작업과 내 작업), 6c(문의 연결). 5절 1. 묶음이 끝나면 `design/archive/6a-labels/`로 간다(D-27).
> 전체 경로다. 마이그레이션(표 둘, 문의에 칸 하나), 고객사 경계(다른 고객사의 라벨을 붙이기, 배정되지 않은 고객사의 라벨 읽기), 공개 계약(새 경로, 목록의 새 매개변수, 이력의 새 `field`, 설정 키 `POPDESK_TIMEZONE`의 동작)을 건드린다. 사전 부검은 같은 폴더의 `premortem.md`다.
> 규칙 ID의 글은 같은 폴더 `rules.md`에 있다. 기준 ID는 `S6A-AC-nn`이다.
> 관계있는 결정(`adr.md`): D-10, D-13, D-41, D-42, D-43, D-44, D-57. 위협 모델: TM-55(새, 상담원이 다른 고객사의 라벨을 보는 것), TM-56(새, 라벨 한도).
> 상태: **메인이 정함, 사용자 확인 전**(2026-10-14). 규칙에 없던 것을 메인이 넣은 곳은 5절에 모았다.

## 1. 넣는 것과 미루는 것

앞 묶음이 이미 만든 것: 문의와 상태 전이, 담당자, 문의 행 잠금(STATUS-7), 이력(`field`에 CHECK 없음), 콘솔 목록(필터 `status`·`companyCode`·`assignee`·`reporter`·`q`, 정렬은 올린 시각 하나), 포털 목록이 `label` 매개변수를 400으로 거절하는 것, `Clock` 빈, `POPDESK_TIMEZONE`을 읽는 곳 하나(시험 메일, 틀린 값은 조용히 UTC). 라벨과 마감일은 표도 코드도 없다.

## 2. 수용 기준

"상담 쪽"은 관리자와 상담원이다. "볼 수 있는"은 RULE-03이다(관리자는 모든 문의, 상담원은 배정된 고객사의 문의). "오늘"은 요청을 받은 시각을 `POPDESK_TIMEZONE`의 날짜로 바꾼 것이다.

### 2.1 라벨 관리

| ID | 기준 |
|---|---|
| S6A-AC-01 | When 관리자가 고객사에 라벨을 만들면(이름, 색), the system shall 만들고 ID·이름·색을 준다. 색을 보내지 않으면 `#808080`이다. (LBL-1) |
| S6A-AC-02 | If 이름이 앞뒤 공백을 자르고 NFC로 맞춘 뒤 1~30자가 아니면, then the system shall 400 `INVALID_INPUT`으로 답한다. 만들기와 고치기 모두다. (LBL-1, COM-1) |
| S6A-AC-03 | If 같은 고객사에 대소문자만 다른 같은 이름이 있으면, then the system shall 409로 답한다. 다른 고객사의 같은 이름은 된다. 고치기에서 자기 이름의 대소문자만 바꾸는 것은 된다. (LBL-1) |
| S6A-AC-04 | If 색이 `#`과 16진 여섯 자리가 아니면, then the system shall 400으로 답한다. 소문자로 보낸 색은 대문자로 맞춰 저장하고 준다. (LBL-1, 5절 4) |
| S6A-AC-05 | When 관리자가 라벨의 이름이나 색을 고치면, the system shall 고친다. 붙어 있는 문의에는 새 이름과 색으로 보인다. 이력에 남은 옛 이름은 바꾸지 않고, 고친 일도 이력에 남기지 않는다. (LBL-1, 5절 6) |
| S6A-AC-06 | When 관리자가 라벨을 지우면, the system shall 지우고 붙어 있던 문의에서 뗀다. 문의 이력에 남기지 않는다. (LBL-3) |
| S6A-AC-07 | If 관리자가 아닌 사람이 라벨을 만들거나 고치거나 지우면, then the system shall 403 `FORBIDDEN`으로 답한다. 계약의 403 설명에 "admins only"가 있다. (LBL-1, `AdminOnlyContractTest`) |
| S6A-AC-08 | If 고객사가 `ARCHIVED`면, then the system shall 라벨 만들기를 그 고객사에 무엇을 더할 때와 같은 400으로 답한다. 고치기와 지우기는 된다. (permissions.md "Nothing can be added to an `ARCHIVED` company", 5절 5) |
| S6A-AC-09 | If 고객사에 라벨이 이미 200개면, then the system shall 만들기를 400으로 답한다. (TM-56, 5절 3) |
| S6A-AC-10 | When 상담 쪽이 고객사의 라벨 목록을 읽으면, the system shall 그 고객사의 라벨을 이름순(대소문자 무시)으로 준다. 라벨마다 ID·이름·색·붙은 문의 수가 있다. (LBL-2, 5절 7) |
| S6A-AC-11 | If 상담원이 배정되지 않은 고객사의 라벨 목록을 읽거나 그 고객사의 라벨을 붙이려 하면, then the system shall 없는 고객사·없는 문의와 같은 404로 답한다. (RULE-03, TM-55) |
| S6A-AC-12 | If 경로의 고객사와 라벨의 고객사가 다르면, then the system shall 고치기와 지우기를 없는 라벨과 같은 404로 답한다. (LBL-1, TM-55) |

### 2.2 문의에 붙이기와 떼기

| ID | 기준 |
|---|---|
| S6A-AC-20 | When 상담 쪽이 볼 수 있는 문의에 그 고객사의 라벨을 붙이면, the system shall 붙이고 그 문의의 라벨 목록을 준다. 이미 붙어 있으면 그대로 200이고 이력을 남기지 않는다. (LBL-2) |
| S6A-AC-21 | When 상담 쪽이 문의에서 라벨을 떼면, the system shall 떼고 그 문의의 라벨 목록을 준다. 붙어 있지 않던 라벨(지워진 라벨 포함)이면 그대로 200이고 이력을 남기지 않는다. (LBL-2) |
| S6A-AC-22 | If 붙이려는 라벨이 다른 고객사의 것이거나 없는 ID면, then the system shall 붙이지 않고 400으로 답한다. 두 경우의 상태 코드와 본문이 같다. (LBL-2, TM-55) |
| S6A-AC-23 | If 문의가 `CLOSED`면, then the system shall 붙이기와 떼기를 400 `ISSUE_CLOSED`로 답한다. 종료와 같은 때 온 붙이기는 종료 뒤에 처리되면 붙지 않는다. (LBL-2, STATUS-7) |
| S6A-AC-24 | If 문의에 라벨이 이미 20개면, then the system shall 붙이기를 400으로 답한다. (TM-56, 5절 3) |
| S6A-AC-25 | If 붙이기와 그 라벨의 지우기가 같은 때 오면, then the system shall 어떤 한 순서로 처리한 결과와 같게 한다: 라벨이 지워지고 문의에 남지 않는다. 붙이기의 답은 200이나 S6A-AC-22의 400이고 500이 아니다. (LBL-3, STATUS-7) |
| S6A-AC-26 | When 문의를 재오픈하면, the system shall 라벨과 마감일을 그대로 둔다. (STATUS-4) |

### 2.3 마감일

| ID | 기준 |
|---|---|
| S6A-AC-30 | When 상담 쪽이 볼 수 있는 문의에 마감일(`YYYY-MM-DD`)을 정하면, the system shall 적고 문의를 준다. 오늘이나 그 뒤의 날짜면 된다. (DUE-1) |
| S6A-AC-31 | If 마감일이 오늘보다 이전이거나, 날짜 꼴이 아니거나(시각이 붙은 값, 없는 날 `2026-02-30`), then the system shall 400으로 답한다. (DUE-1, `conventions.md` 시각 절) |
| S6A-AC-32 | When 상담 쪽이 마감일을 지우면, the system shall 지운다. 없을 때 지워도 200이고 이력을 남기지 않는다. (DUE-1) |
| S6A-AC-33 | If 문의가 `CLOSED`면, then the system shall 정하기와 지우기를 400 `ISSUE_CLOSED`로 답한다. (DUE-1, STATUS-7) |
| S6A-AC-34 | The system shall "오늘"을 `POPDESK_TIMEZONE`으로 정한다. 같은 때 같은 날짜를 보내도 시간대가 다른 설치는 다르게 답할 수 있다(예: UTC 12시에 보낸 UTC의 오늘은 `Pacific/Kiritimati`(UTC+14)에서 오늘 이전이라 400이다). (TIME-1, D-10) |
| S6A-AC-35 | When 정해 둔 마감일이 날이 지나 오늘보다 이전이 되면, the system shall 마감일을 그대로 두고 응답에 지났다는 값(`overdue: true`)을 준다. 지난 마감일을 같은 날짜로 다시 정하는 것은 S6A-AC-31의 400이다. (DUE-1, 5절 8) |
| S6A-AC-36 | When 이미 정해진 날짜와 같은 날짜로 정하면, the system shall 그대로 200이고 이력을 남기지 않는다. (HIST-1) |

### 2.4 고객에게 보이지 않는다

| ID | 기준 |
|---|---|
| S6A-AC-40 | The system shall 포털의 어떤 응답(문의, 문의 목록, 알림함, 그 밖의 포털 경로)과 고객에게 가는 메일에도 라벨과 마감일을 넣지 않는다. (LBL-4, DUE-1, RULE-04, D-41) |
| S6A-AC-41 | If 고객이 콘솔의 라벨·마감일 경로를 부르면, then the system shall 있는 콘솔 경로가 고객에게 답하는 것과 같은 상태와 code로 답한다(포털 호스트에서 404, 콘솔 호스트로 옮긴 쿠키로 401). 처음에 403이라 적은 것은 틀렸다(C-5 테스트 탭이 찾음). (D-43) |
| S6A-AC-42 | The system shall 포털 목록의 `label`과 `sort` 매개변수를 지금처럼 400 `UNKNOWN_PARAMETER`로 답한다. (D-41) |

### 2.5 콘솔 문의 목록

| ID | 기준 |
|---|---|
| S6A-AC-50 | The system shall 콘솔 목록과 문의 응답에 라벨(ID·이름·색, 이름순)과 마감일과 `overdue`를 준다. (LBL-2, DUE-1) |
| S6A-AC-51 | When 목록 요청이 `label`(라벨 ID)을 주면, the system shall 그 라벨이 붙은 문의만 준다. 여러 번 주면 그 가운데 하나라도 붙은 문의다(`status`와 같다). 다른 필터와는 모두 맞아야 한다. (ISSUE-5) |
| S6A-AC-52 | If `label`이 없는 ID거나 호출한 사람이 볼 수 없는 고객사의 라벨이면, then the system shall 빈 목록을 준다. ID 꼴이 아니면 400이다. (permissions.md "A filter … gives an empty list") |
| S6A-AC-53 | When 목록 요청이 `sort=dueDate`를 주면, the system shall 마감일이 이른 순으로, 마감일이 없는 것은 뒤에, 같은 날은 지금의 순서(올린 시각 최신, 번호)로 준다. `sort`가 없거나 `createdAt`이면 지금 순서 그대로다. 그 밖의 값은 400 `UNKNOWN_VALUE`다. `q`와 함께 쓸 수 있다. (C-3 "기한순 정렬", 5절 9) |
| S6A-AC-54 | The system shall 필터와 정렬을 바꿔도 쪽 나누기(COM-4)와 `totalElements`를 지금처럼 맞게 준다. 같은 마감일과 같은 시각의 문의가 쪽을 넘어 빠지거나 겹치지 않는다. (COM-4) |
| S6A-AC-55 | The system shall 문의 10만 건에서 검색 없는 첫 쪽(상담원, 관리자)과 `sort=dueDate`의 첫 쪽을 150 ms 안에 준다. 3번 묶음과 같은 방법으로 C-10에서 잰다(`archive/3-issues/verify.md` 4절). 테스트로 고정하지 않는다. (3번에서 넘긴 일) |

### 2.6 이력과 알림

| ID | 기준 |
|---|---|
| S6A-AC-60 | When 라벨을 붙이거나 떼면, the system shall 문의 이력에 `field` `LABEL`로 남긴다. 붙이면 새 값이, 떼면 옛 값이 그때의 라벨 이름이다. (HIST-1, 5절 6) |

| S6A-AC-63 | The system shall 라벨과 마감일의 바뀜으로 알림함·메일·웹훅을 보내지 않는다. (10절 표에 줄이 없다) |

### 2.7 설치 시간대

| ID | 기준 |
|---|---|
| S6A-AC-70 | If `POPDESK_TIMEZONE`이 빈 값(`POPDESK_TIMEZONE=`)이거나 받는 값이 아니면, then the system shall 요청을 받지 않는다: 프로세스는 돌고, 설정 이름과 받는 값을 로그에 적고, 상태 검사는 unhealthy로 남는다. `POPDESK_LOCALE`이 틀릴 때와 같다. (4번에서 넘긴 일, 5절 10) |

## 4. 테스트를 쓸 때 지킬 것

- 시간대: S6A-AC-34는 시간대가 UTC에서 먼 설치 둘로 본다: `Pacific/Kiritimati`(UTC+14)와 `Pacific/Pago_Pago`(UTC-11). 설치마다 테스트가 앱의 시계(테스트 시계, `TestClock`)를 그 시간대의 날짜가 UTC 날짜와 다른 시각으로 옮기고(Kiritimati는 UTC 12:30, Pago_Pago는 UTC 05:30) 그 시간대의 오늘을 셈해, 오늘은 200이고 하루 전은 400인지 본다(C-5 테스트 탭이 정함). "오늘을 UTC로 정하는" 틀린 구현은 UTC 10시 이후에는 Kiritimati에서 하루 전을 받아 걸리고, UTC 11시 전에는 Pago_Pago의 오늘을 거절해 걸린다. 그래서 하루 어느 때든 둘 가운데 하나가 잡는다. 시계를 옮기므로 두 클래스가 각각 늘 잡는다. 앱 시계가 멈춰 있어 요청 사이에 날짜가 바뀌지 않는다.
- 고객사 경계의 부정 테스트는 고객사 둘(A, B)과 A에만 배정된 상담원으로 쓴다.
- 이력 값과 순서는 자기가 만든 문의로만 센다.
- 잠긴 웹 테스트 `C3IssueList.test.tsx` 79~80줄이 라벨·마감일 칸이 없다고 단언한다. 이 묶음의 테스트 탭이 그 줄을 맞춘다(SLA 칸이 없다는 단언은 둔다).
- 오류 문구나 라벨 목록의 순서처럼 우연한 값은 기준이 정한 것만 고정한다(이름순은 기준이 정했다).
