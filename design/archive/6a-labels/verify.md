## 5. 목록 성능 (S6A-AC-55)

같은 설치에 문의 10만 건을 SQL로 넣고(고객사 50, 내용 약 2,000자, 마감일 있는 것 2만, 라벨 붙은 행 6만) `analyze` 뒤 HTTP로 7번씩 잰 중앙값(앞 두 번 뺌). 앱이 띄울 때 마이그레이션한 DB다(서버 탭은 SQL 파일만 넣은 DB로 쟀다).

| 첫 쪽(20건) | 중앙값 | 가장 짧은 것 – 가장 긴 것 |
|---|---|---|
| 관리자, 검색 없음 | 82 ms | 66 – 104 |
| 상담원, 검색 없음 | 122 ms | 100 – 312 |
| 관리자 `label` | 20 ms | 20 – 45 |
| 상담원 `label` | 32 ms | 20 – 44 |
| 관리자 `sort=dueDate` | 82 ms | 70 – 92 |
| 상담원 `sort=dueDate` | 96 ms | 94 – 121 |
| 관리자 `status` + `sort=dueDate` | 35 ms | 33 – 52 |
| 관리자 `q`(10만 건 모두 맞음) + `sort=dueDate` | 182 ms | 160 – 183 |

- 기준(검색 없는 첫 쪽과 `sort=dueDate`의 첫 쪽, 150 ms)을 넘지 않는다. HTTP 시간이라 로그인 확인과 건수 쿼리까지 든다. 상담원 첫 번 312 ms는 첫 요청이다.
- 검색은 기준 밖이다. 모두 맞는 낱말이라 가장 나쁜 경우다(3번 묶음에서 2만 건 맞는 낱말이 0.55초였다).
- 색인은 더하지 않았다(서버 탭이 쿼리를 "쪽을 먼저 고른 뒤 사람과 잇는" 꼴로 바꿨다. 관리자 첫 쪽이 SQL로 251 → 24 ms).
