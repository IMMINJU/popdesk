# popdesk 위협 모델

> 계속 고쳐 쓰는 정본이다(D-27). 무엇을 지키고, 누가 어디서 공격할 수 있으며, 무엇으로 막는지 적는다. 보안 질문지에 답할 때 이 문서의 표를 그대로 쓴다.
> 권한 규칙 자체는 `docs/use/permissions.md`, 결정과 이유는 `adr.md`에 있다. 묶음이 전체 경로(`process.md` C)에 걸리면 이 문서를 다시 연다.

## 1. 지킬 것은 고객사 경계, 계정, 내부 정보, 감사 기록이다

| 자산 | 깨지면 생기는 일 |
|---|---|
| 고객사 사이의 경계 (RULE-01) | A사 고객이 B사의 문의·댓글·첨부·사람 이름을 본다. 제품을 쓸 수 없게 되는 사고다 |
| 내부 정보 (RULE-04) | 내부 댓글, 작업 기록, 담당자, 라벨이 고객에게 보인다 |
| 계정과 세션 | 남의 계정으로 로그인한다. 관리자 계정이면 설치 전체를 가져간다 |
| 초대 링크 | 링크를 손에 넣은 사람이 계정을 차지한다 |
| 첨부 파일 | 다른 고객사의 파일을 받거나, 올린 파일이 다른 사람 브라우저에서 스크립트로 돈다 |
| 감사 로그 | 누가 권한을 바꿨는지 숨긴다 |
| 비밀값 (DB·SMTP·IMAP 비밀번호, S3 키, OIDC 비밀, 웹훅 주소) | 바깥 시스템까지 넘어간다 |
| 개인정보 (PII-1) | 이메일·이름·문의 내용이 로그나 내보내기 파일로 샌다 |

전제: 설치 하나에 지원팀 하나다(D-17, D-18). 팀 사이 경계는 지금 지키지 않는다. 앱 인스턴스는 하나다(D-23).

## 2. 데이터는 이렇게 흐르고, 신뢰 경계는 다섯 곳이다

```
 [고객 브라우저]          [상담원·관리자 브라우저]
       │ portal.<호스트>          │ console.<호스트>
═══════╪══════════════════════════╪═══════════ B1 인터넷 ↔ 설치처
       ▼                          ▼
   ┌──────────────────────────────────┐
   │  리버스 프록시 (설치처가 둔다, TLS 끝) │
   └──────────────────────────────────┘
                   │ http
═══════════════════╪═══════════════════════ B2 프록시 ↔ 앱
                   ▼
   ┌──────────────────────────────────┐
   │ popdesk 앱                         │
   │  helpdesk 모듈 ── notification 모듈 │──┐
   └──────────────────────────────────┘  │
                   │ JDBC                 │
═══════════════════╪══════════════════════╪═ B3 앱 ↔ DB·저장소
                   ▼                      │
          [PostgreSQL]  [disk 폴더 또는 S3] │
                                          │
══════════════════════════════════════════╪═ B4 앱 ↔ 바깥 서비스
                                          ▼
     SMTP(보내기) · IMAP(받기) · 웹훅 · 감사 사본 · OIDC 제공자

 B5 고객 포털 ↔ 상담 콘솔: 같은 앱이지만 호스트와 쿠키가 다르다(D-7)
```

| 경계 | 들어오는 것 | 믿지 않는 이유 |
|---|---|---|
| B1 | 로그인, API 요청, 첨부, 마크다운 본문 | 누구나 보낼 수 있다. 로그인한 고객도 다른 고객사를 노릴 수 있다 |
| B2 | 프록시가 넘긴 요청과 `X-Forwarded-*` | 앱 포트가 프록시를 거치지 않고 열려 있으면 머리글을 위조할 수 있다 |
| B3 | DB 행, 저장소 파일 | DB를 고칠 수 있는 사람은 앱 검사를 거치지 않는다 |
| B4 | 받은 메일, OIDC 토큰, 웹훅 응답 | 메일의 보낸 사람은 위조할 수 있다. 바깥 서비스가 멈추거나 느릴 수 있다 |
| B5 | 고객 화면에서 실행된 스크립트, 포털 호스트로 온 API 요청 | 고객 화면에 XSS가 생겨도 상담 쪽 권한으로 요청을 보내면 안 된다. 포털 호스트는 `/api/console/**`을 받지 않는다(D-43) |

## 3. 암호화는 이 위치에서 한다

### 전송 구간

| 구간 | 방식 | 맡는 쪽 |
|---|---|---|
| 브라우저 ↔ 리버스 프록시 | TLS. 운영 문서가 TLS 1.2 이상과 HSTS를 권한다 | 설치처 (D-40) |
| 리버스 프록시 ↔ 앱 | http. 같은 호스트나 내부망에 둔다 | 설치처 |
| 앱 ↔ Postgres | compose 내부망에서는 평문. DB를 밖에 두면 JDBC `sslmode=verify-full` | 설치처 (D-40) |
| 앱 ↔ SMTP·IMAP | 포트가 465(SMTP)·993(IMAP)이면 암묵적 TLS, 그 밖이면 STARTTLS를 요구하고 서버가 지원하지 않으면 연결하지 않는다. 평문은 `SMTP_ALLOW_PLAINTEXT`·`IMAP_ALLOW_PLAINTEXT`를 켤 때만 쓰고, 켜져 있으면 시작할 때 경고 로그 (D-51) | popdesk 설정 |
| 앱 ↔ 웹훅·감사 사본 주소 | 주소가 `https`면 TLS. `http`도 받되 시작할 때 경고 로그(주소는 빼고) (D-51) | 설치처가 주소를 정한다 |
| 앱 ↔ S3 | `S3_ENDPOINT`가 없으면 AWS의 https. `S3_ENDPOINT`가 `https`면 TLS. `http`도 받되 시작할 때 경고 로그 (D-51) | 설치처가 주소를 정한다 |
| 앱 ↔ OIDC 제공자 | https (OIDC 규격) | Spring Security |

### 저장 구간

| 데이터 | 저장 방식 | 맡는 쪽 |
|---|---|---|
| 비밀번호 | Argon2id 해시 (AUTH-5) | popdesk |
| 초대 토큰 | 32바이트 난수, DB에는 SHA-256 해시만 (INVITE-2) | popdesk |
| 세션 | Spring Session JDBC. 세션 ID가 DB에 평문으로 있다. DB를 읽을 수 있으면 세션을 가로챌 수 있다 | popdesk, 남은 위험(5절) |
| 감사 로그 | 평문 + 항목마다 SHA-256 해시 사슬 (AUDIT-6). 해시는 고친 흔적을 찾는 용도이고 내용을 숨기지 않는다 | popdesk |
| 문의·댓글·계정 | 평문. 앱 단 암호화는 하지 않는다. 디스크 암호화는 설치처가 한다 | 설치처 |
| 첨부 (`db`) | `bytea` 평문 | 설치처의 디스크 암호화 |
| 첨부 (`disk`) | 볼륨의 파일. 파일 이름은 만든 ID이고 올린 이름을 경로에 쓰지 않는다 | 설치처의 디스크 암호화 |
| 첨부 (`s3`) | 버킷 설정의 서버 쪽 암호화 | 설치처 |
| 백업 (`pg_dump`) | 평문 파일. 운영 문서가 백업 암호화를 권한다 | 설치처 |
| 비밀값 | 환경변수나 `*_FILE`로 받는다. DB에 넣지 않고, 기본값이 없고, 로그에 남기지 않는다 | popdesk, 설치처 |

## 4. 위협마다 막는 장치와 그것을 확인하는 테스트

### 4.1 다른 고객사의 데이터를 보는 것 (가장 중요)

| ID | 위협 | 막는 장치 | 확인 |
|---|---|---|---|
| TM-01 | 고객이 다른 고객사 문의 ID나 키를 넣어 읽는다 | 고객사 범위를 저장소 계층의 조회 조건에 넣는다. 범위 밖은 404 (COM-1) | 기능마다 A사·B사 부정 테스트 |
| TM-02 | 목록·검색·통계·알림함·멘션 후보·이름 조회 같은 옆길로 새어 나간다 | 옆길마다 같은 범위 조건을 쓴다. 이름 조회는 ACCT-4 | 옆길마다 부정 테스트. 대응표(C-7)에 옆길을 줄로 적는다 |
| TM-03 | 메일 답장 제목의 `[B사 문의 키]`로 남의 문의에 댓글을 단다 | 보낸 사람이 그 문의를 볼 수 있을 때만 잇는다 (MAILIN-2) | 메일 받기 부정 테스트 |
| TM-04 | 고객사 담당자가 초대 응답으로 다른 고객사의 계정 유무를 알아낸다 | 새 이메일과 이미 있는 이메일의 응답을 같게 한다 (MGR-3) | 두 경우 응답이 같은지 비교하는 테스트 |
| TM-05 | 고객사 내보내기·계정 내보내기에 다른 고객사 데이터가 섞인다 | 관리자만 한다. 내보내기 조회도 같은 범위 조건 | 내보내기 부정 테스트 |
| TM-06 | 배정에서 빠진 상담원, 소속에서 빠진 고객, 담당자 지정이 풀린 고객이 세션이 끝날 때까지 계속 본다 | 배정·소속·담당자 표시를 세션에 담지 않고 요청마다 DB에서 읽는다 (AUTH-4) | 해제 직후 404·403 테스트 (세 경우 모두) |
| TM-33 | 남의 첨부 ID나 내부 댓글 첨부 ID를 본문 이미지로 내 글에 묶어 내려받는다 | 내가 올렸고, 묶이지 않았고, 만료 전인 임시 이미지만 묶는다. 묶인 첨부는 다시 묶지 않는다 (ATT-6) | A사 고객이 B사 첨부 ID로 묶는 부정 테스트, 내부 첨부를 공개 댓글에 묶는 테스트 |
| TM-34 | 남의 임시 이미지를 ID로 받는다 | 묶기 전에는 올린 사람만 읽는다. 첨부 ID는 추측할 수 없는 값 (ATT-7) | 다른 사람의 임시 이미지 404 테스트 |
| TM-35 | 고객사 담당자가 초대 뒤 소속 목록을 보고 계정 유무를 알아낸다 | 이미 있는 이메일의 소속 요청도 `INVITED` 행으로 같게 보인다. 다시 보내기·취소 거절도 같은 `code`. 초대 요청 수 제한 (MGR-3·4, COM-8) | 두 경우 목록 응답 비교 테스트 |
| TM-36 | 메일 받기의 `Message-ID`·`+코드`·안내 메일로 남의 문의나 다른 고객사 코드가 드러난다 | `Message-ID`는 난수. 볼 수 없는 문의는 답장으로 보지 않는다. 안내 문구는 하나이고 볼 수 없는 문의를 적지 않는다. 소속을 상태보다 먼저 본다 (MAILIN-2·3) | 메일 받기 부정 테스트 |
| TM-37 | 보내기 대기에 남은 메일이 휴지통에 간 문의나 소속에서 빠진 사람에게 나간다 | 보내기 직전에 다시 확인하고, 제목은 보낼 때 읽는다 (MAIL-4) | 넣은 뒤 휴지통·소속 해제하고 보내지 않는지 테스트 |
| TM-38 | 429가 나는지로 대상이 있는지 떠본다 | 요청 수는 대상을 찾기 전에 센다 (COM-8) | 없는 대상과 있는 대상의 429 시점이 같은지 테스트 |

### 4.2 내부 정보가 고객에게 보이는 것

| ID | 위협 | 막는 장치 | 확인 |
|---|---|---|---|
| TM-07 | 응답 JSON에 담당자·라벨·내부 댓글이 섞이거나, 고객 목록 요청의 담당자·라벨 필터로 내부 정보를 떠본다 | 고객용과 상담용 요청·응답 타입을 따로 둔다. 고객용 타입에는 그 칸과 필터가 없고, 들어오면 400 (ISSUE-5) | OpenAPI 스냅샷에서 고객용 타입의 칸과 파라미터 목록을 고정 |
| TM-08 | 알림 메일이나 웹훅에 내부 댓글이 실린다. 알림의 "일으킨 사람"으로 담당자를 알아낸다 | 고객에게 가는 알림은 공개 댓글에서만 만든다. 고객 쪽(포털 화면, 포털 API, 메일, 알림함)에는 상담 쪽 사람을 "지원팀"으로만 보이고, 포털 API 응답에 상담 쪽 사람의 이름·이메일·계정 ID를 넣지 않는다 (INBOX-1, D-49). 웹훅은 팀 채널이라 받는 쪽이 상담 쪽이다 | 메일·웹훅·알림함 스냅샷 테스트, 포털 응답에 상담 쪽 계정 정보가 없는 테스트 |
| TM-39 | 고객이 내부 댓글 첨부를 요청해 403과 404의 차이로 있는지 알아낸다 | 고객에게 내부 첨부는 목록에서 빠지고 404 (ATT-4) | 내부 첨부 404 테스트 |
| TM-41 | 다른 고객사 문의와의 연결이 고객에게, 또는 그 고객사에 배정되지 않은 상담원에게 드러난다(키, 제목, 개수, 이력 값, 해결 알림) | 고객용 응답·메일·내보내기에 연결 칸이 없다. 상담 쪽도 볼 수 있는 쪽만 보이고 개수도 숨긴다. 이력 값은 ID만 담고 그릴 때 범위를 다시 본다. 해결 알림은 볼 수 있는 담당자에게만 (LINK-3·4·6·7) | A사만 배정된 상담원이 B사 문의와의 연결을 못 보는 부정 테스트, 고객 응답 스냅샷 |
| TM-42 | 볼 수 없는 문의 키로 연결을 시도해 응답 차이로 그 문의가 있는지 알아낸다 | 두 문의를 다 볼 수 있어야 하고, 아니면 없는 문의와 같은 404 (LINK-1) | 연결 부정 테스트 |
| TM-43 | 비밀번호 찾기로 계정 유무를 알아내거나 남의 계정을 차지한다 | 응답은 계정이 있든 없든 같다. 토큰은 32바이트 난수, 해시만 저장, 1시간, 한 번. 요청 수 제한. 쓰면 그 계정의 세션을 모두 지운다 (D-47) | 같은 응답 테스트, 토큰 재사용 테스트 |
| TM-44 | 관리자 화면의 초대 링크 복사로 토큰이 화면·클립보드·스크린숏에 남는다 | SMTP가 꺼져 있을 때만 보인다. 링크는 만든 응답에서 한 번만 보인다. 토큰을 담거나 받는 모든 응답(초대, 링크 복사, 수락)에 `Cache-Control: no-store`를 붙이고, 컨트롤러가 `Cache-Control`을 따로 써서 이 값을 덮지 않는다. 토큰은 링크의 URL 조각(`#` 뒤)에만 두어 프록시 액세스 로그에 남지 않게 한다(INVITE-2). 만든 일을 감사 로그에 남기되 링크와 토큰은 넣지 않는다. 고객사 담당자는 쓰지 못한다(INVITE-6, D-47) | SMTP가 켜져 있으면 404인 테스트, 감사 로그에 토큰이 없는 테스트, 토큰을 담거나 받는 엔드포인트(초대, 링크 복사, 수락)마다 `no-store` 단언과 모든 `/api` 응답의 `no-store` 묶음 단언, E2E 뒤 액세스 로그에 토큰이 없는 테스트 |
| TM-47 | 비밀번호 찾기로 OIDC를 거치지 않고 들어온다. 메일함을 뺏긴 계정은 재설정 메일로 차지된다 | 지금도 OIDC를 켜도 비밀번호 로그인이 남는다(AUTH-6). 재설정을 마치면 세션을 모두 지우고 로그인 화면으로 보낸다(AUTH-7). 메일함 탈취는 메일을 쓰는 모든 서비스의 공통 한계로 받아들인다 | 재설정 뒤 기존 세션이 끊기는 테스트 |
| TM-50 | 비밀번호 찾기 요청의 `Host`를 바꿔 피해자에게 가는 재설정 링크를 공격자 주소로 만든다. 정지된 사람이 미리 받아 둔 링크를 쓴다 | 링크는 설정한 공개 주소로만 만든다. 토큰을 쓸 때 계정이 `ACTIVE`이고 그 앱의 계정인지 다시 본다. 초대 토큰과 재설정 토큰은 테이블이 달라 섞어 쓸 수 없다. 찾기 요청만으로는 비밀번호·세션·잠금이 바뀌지 않는다 (S1A 부검 2) | `Host`를 바꾼 요청의 메일 링크 검사, 토큰 종류 바꿔 내기, 정지 뒤 링크 쓰기 (S1A-AC-82~85) |
| TM-51 | 프로필 사진으로 서버를 죽인다(작은 파일이 큰 그림으로 풀림, 동시 올리기). 올린 내용이 브라우저에서 HTML로 읽힌다. 사진 주소로 다른 고객사에 누가 있는지 알아낸다 | 머리글에서 크기를 먼저 읽고 2,500만 픽셀 초과는 거절, 줄여서 풀기, 같은 때 둘까지. 저장과 응답은 서버가 다시 만든 PNG뿐이고 `nosniff`. 사진 조회는 이름 조회와 같은 범위 검사를 지나고 범위 밖과 없음은 같은 404 (D-52, D-53, S1A 부검 4) | 큰 그림 거절, `-Xmx384m` 동시 올리기, 저장 바이트의 EXIF 검사, 경계 부정 테스트 (S1A-AC-21·23·25~27·87·88) |

| TM-49 | 시스템 상태 화면의 `failed` 다시 보내기로 휴지통 문의나 볼 수 없게 된 사람에게 메일을 되살린다. 시험 메일 응답에 비밀값이 섞인다 | 다시 보낼 때도 MAIL-4·5의 확인을 다시 한다. 화면에 SMTP 비밀번호·웹훅 주소를 보이지 않는다(OPS-3) | 휴지통 문의의 `failed` 행 다시 보내기가 보내지 않는 테스트 |
| TM-45 | 관리자 복구 명령을 남이 쓴다 | 컨테이너 안에서만 돈다(HTTP 경로가 없다). 호스트에 들어올 수 있는 사람은 이미 DB와 비밀값을 가진 것으로 본다. 감사 로그에 남는다 (D-46) | 명령에 대응하는 HTTP 경로가 없다는 아키텍처 테스트 |
| TM-46 | 지표·상태 확인 경로로 내부 정보가 밖에 보인다 | actuator는 관리 포트(8081)에만 두고 compose는 그 포트를 열지 않는다 (D-45) | 8080으로 `/actuator/**`가 404인 테스트 |
| TM-40 | 고객사 내보내기 ZIP에 담당자·라벨·이력·내부 첨부·다른 고객사 소속이 들어가 고객사에 넘어간다 | 문의 칸은 고객용 응답과 같은 목록. 내부 댓글을 빼면 그 첨부도 뺀다. 계정은 이메일·이름만. 내려받기는 로그인한 관리자만 (PII-8) | 내보내기 파일 칸 목록 스냅샷 테스트 |

## 6. 정할 것

- OIDC를 켠 설치에서 상담 쪽의 비밀번호 로그인과 비밀번호 찾기를 끌 수 있게 할지(TM-47). 회사가 SSO만 쓰게 하려면 필요하다. OIDC 묶음(11번)을 시작할 때 정한다.

- 받은 메일의 보낸 사람 확인(TM-22). 제안: 메일 서버가 붙인 `Authentication-Results`에서 DMARC가 `fail`이면 버리고, 결과 머리글이 없으면 받되 지표를 남긴다. 메일 받기 묶음(12번)을 시작하기 전에 정한다.
- SMTP·IMAP의 TLS 기본값은 정했다(D-51). 465·993이면 암묵적 TLS, 그 밖이면 STARTTLS를 요구하고 서버가 지원하지 않으면 연결하지 않는다. 평문은 `SMTP_ALLOW_PLAINTEXT=true`, `IMAP_ALLOW_PLAINTEXT=true`로 따로 켤 때만 쓰고, 켜져 있으면 시작할 때 경고 로그를 남긴다.
- 웹훅·감사 사본 주소가 `http`이면 받고, 시작할 때 경고 로그를 남긴다(D-51).
