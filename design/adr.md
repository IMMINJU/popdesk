# popdesk 결정 기록 (ADR)

> 계속 고쳐 쓰는 정본이다. 정한 것과 그 이유, 버린 대안을 남긴다. 번호는 다시 쓰지 않는다. 결정을 뒤집을 때는 새 번호로 남기고 옛 항목에 "→ D-n"을 적는다.
> 이 파일의 "이전 판"은 사내에서 플랫폼 도그푸딩용으로 만든 solvesk를 말한다.

| ID | 날짜 | 결정 | 이유 | 버린 대안 |
|---|---|---|---|---|
| D-1 | 2026-10-08 | 설치형 오픈소스 헬프데스크를 새 레포로 처음부터 짠다. 이름은 popdesk, 라이선스는 Apache-2.0 | 남이 받아서 써 보는 것이 목적이다. Apache-2.0은 회사 안에서 써 보려는 사람의 법무 부담이 적고 특허 조항이 있다 | 기존 코드를 고쳐 쓰기(서비스·브로커가 도그푸딩용으로 많아 고치는 품이 더 든다) / AGPL-3.0(남이 닫힌 SaaS로 쓰는 것은 막지만 써 보는 문턱이 높다) / MIT(특허 조항이 없다) |
| D-2 | 2026-10-08 | 기능 범위는 이전 판과 같게 둔다: 문의, 공개·내부 댓글, 고객사, 초대 가입, 알림함, 메일, 첨부·본문 이미지, 멘션·라벨·마감일, 작업, 통계, 이력·휴지통·자동 종료·웹훅. 같은 날 검색 색인(D-13), 첨부 저장소 셋(D-14, 뒤에 D-19로 뒤집음), OIDC(D-15), 메일 받기(D-16)를 더했다 | 사람 결정 | 첫 판을 문의·댓글만으로 줄이기 |
| D-3 | 2026-10-08 | 레포 하나, 앱 하나(Spring Boot, Java 25), Postgres 하나. 기본 컨테이너는 `app`과 `db` 둘이다 | 설치하는 사람에게 컨테이너와 런타임 수가 곧 문턱이다. 개발 PC가 16GB라 테스트를 돌릴 여유도 필요하다. 이전 판의 서비스 분리는 제품 요구가 아니라 플랫폼 도그푸딩 때문이었다(이전 판 명세에 분리 이유가 없다) | 서비스 넷과 DB 셋을 그대로 두기 / Java 21(25가 지금 LTS다) |
| D-4 | 2026-10-08 | (→ D-18) 모든 업무 테이블에 `tenant_id`를 두고 모든 조회·쓰기를 팀으로 거른다. v1은 첫 실행 때 팀 1만 만들고, 팀을 만드는 API·화면은 두지 않는다 | 설치형 헬프데스크는 대부분 설치 하나에 조직 하나다. 하지만 나중에 칸을 더하려면 모든 쿼리를 고쳐야 하므로, 칸은 처음부터 둔다 | 팀 칸 없이 시작 / 여러 팀을 v1에서 열기 |
| D-5 | 2026-10-08 | 메시지 브로커를 두지 않는다. 메일·웹훅은 DB 보내기 대기 테이블(`FOR UPDATE SKIP LOCKED`, 최소 한 번 보내기, 24시간까지 다시 보내기)로 보낸다 | 이전 판에서 브로커는 통계 한 곳(Kafka)과 알림 한 곳(RabbitMQ)에만 쓰였고, 이벤트 순서도 보장하지 않았다. 같은 DB 안이면 바꾼 내용과 보낼 일을 한 트랜잭션에 묶을 수 있고, 이전 판에서 재시작 때 메일이 중복되던 문제(중복 거르기가 메모리에만 있었다)도 줄어든다 | Kafka·RabbitMQ 유지 / Spring Modulith 이벤트 저장소(기본값은 끝난 행이 쌓이고 다시 보내기를 직접 짜야 해서, 정해 둔 보내기 대기 방식보다 덜 정해져 있다) |
| D-6 | 2026-10-08 | 서버 모듈은 `helpdesk`와 `notification` 둘이다. 고객사는 문의와 같은 모듈에 두고, 통계는 문의 테이블을 바로 센다 | 고객사를 따로 두면 문의 번호를 다른 곳에서 받아야 해서 번호가 비고 재시도를 못 했다(이전 판). 통계는 상태별 건수뿐이라 목표 규모(하루 1,000건)에서 바로 세도 된다 | core·project·analytics·notification 넷으로 나누기 / 이벤트를 모아 통계 테이블을 따로 두기 |
| D-7 | 2026-10-08 | 두 포털은 앱 둘로 두고 공통 코드는 `web/packages`(ui, api, i18n)에 둔다. 서로 다른 호스트로 낸다 | 고객과 상담원은 기기와 밀도가 다르다. 이전 판에서 두 포털은 같은 경로의 파일 432개 중 329개가 같아, 공통 패키지가 없으면 중복이 다시 생긴다. 같은 호스트로 합치면 고객 화면의 XSS가 상담원 권한으로 요청을 보낼 수 있다 | 한 앱에서 역할별 라우트로 나누기 / 같은 호스트에 경로로만 나누기 |
| D-8 | 2026-10-08 | (→ D-14) 첨부 파일 내용은 DB에 두되 저장소 인터페이스 하나로 모은다 | 설치할 것이 늘지 않고 `pg_dump` 하나로 백업이 끝난다. 첨부가 커지면 디스크나 S3 호환 저장소로 바꿀 수 있게 길만 열어 둔다 | 처음부터 S3 호환 저장소(MinIO 컨테이너가 하나 더 는다) / 로컬 디스크(볼륨과 백업이 둘로 나뉜다) |
| D-9 | 2026-10-08 | 로그인은 서버 세션과 `HttpOnly` 쿠키로 한다. 탭을 닫으면 로그아웃되던 이전 판의 동작은 두지 않는다 | 앱이 하나라 여러 서비스가 검증하던 JWT가 필요 없다. 토큰을 브라우저 저장소에 두지 않으면 XSS가 토큰을 읽지 못한다 | JWT(액세스 1시간·갱신 8시간)와 탭 단위 저장 유지 |
| D-10 | 2026-10-08 | 시각은 UTC로 저장하고 오프셋을 붙여 준다. 날짜 판정은 `POPDESK_TIMEZONE`, 메일·서버 문구의 기본 언어는 `POPDESK_LOCALE`(기본 `en`)이고 메일은 받는 사람의 언어로 쓴다 | 오픈소스라 설치하는 곳의 시간대와 언어가 정해져 있지 않다 | 이전 판처럼 Asia/Seoul과 한국어로 고정 |
| D-11 | 2026-10-08 | 첫 관리자는 첫 실행 때 환경변수로 만든다 | 이전 판은 운영자가 DB 스크립트로 열었다. 받아서 써 보는 사람에게는 환경변수 둘이 더 쉽다 | DB 스크립트 / 첫 접속 때 설정 화면(공개된 채 떠 있는 동안 남이 먼저 차지할 수 있다) |
| D-12 | 2026-10-08 | 이전 판과 다르게 정한 작은 것들: 비밀번호 해시는 Argon2id, 고객사 코드는 영문 대문자·숫자 2~10자이고 팀 안에서 하나, 상담 쪽도 알림함에 고객의 댓글·종료·재오픈을 받고, 새 담당자는 메일도 받으며, 웹훅은 문의 등록·고객 댓글·상태 변경·담당자 변경에 나간다 | Argon2id가 지금 Spring Security의 권장이다. 코드는 문의 키(`ACME-7`)에 들어가므로 짧고 읽기 쉬워야 한다. 알림은 이전 판에서 상담 쪽이 멘션·담당 지정만 받아 고객의 답을 놓치기 쉬웠다 | 이전 판 값 그대로(PBKDF2, 코드 1~255자, 상담 쪽 알림은 멘션·담당만) |
| D-13 | 2026-10-08 | 검색은 `pg_trgm` GIN 색인과 `ILIKE`로 한다 | 들어 있는 글자를 찾는 지금 동작을 그대로 두면서 문의가 쌓여도 느려지지 않는다. 확장 하나라 컨테이너가 늘지 않는다 | Postgres 전문 검색(`tsvector`, 한국어 형태소 분석이 기본으로 없다) / Elasticsearch(컨테이너가 하나 늘고 메모리가 크다) |
| D-14 | 2026-10-08 | (→ D-19) 첨부 저장소는 `db`(기본)·`disk`·`s3` 셋을 v1에 둔다. 첨부 행마다 저장소를 적는다 | 받아 써 보는 사람은 설정 없이 `db`로 시작하고, 첨부가 커지면 설정만 바꾼다. 행마다 저장소를 적으면 바꿔도 이전 파일을 옮기지 않아도 된다 | `db` 하나만(D-8) / 바꿀 때 옮기는 도구를 먼저 만들기 |
| D-15 | 2026-10-08 | OIDC 로그인을 v1에 둔다. 기본은 콘솔에만 버튼을 두고, 계정은 새로 만들지 않고 이메일로 이미 있는 계정에 맞춘다 | 회사에서 써 볼 때 사내 로그인이 있으면 문턱이 낮다. 계정을 만들지 않아야 "초대로만 가입"(RULE-07)이 지켜진다 | 제공자 로그인으로 계정 자동 생성 / SAML(설정이 무겁다) |
| D-16 | 2026-10-08 | 메일로 문의 받기를 v1의 마지막 묶음에 둔다. 등록된 고객 메일만 받고 모르는 보낸 사람은 버린다(답장하지 않는다). 소속이 여럿이면 받는 주소의 `+코드`로 고객사를 고른다 | 헬프데스크 오픈소스는 메일이 주 채널인 경우가 많다. 모르는 사람을 받으면 계정이 저절로 생겨 RULE-07과 부딪히고, 위조된 보낸 사람에게 답장하면 남의 주소로 메일을 뿌리게 된다 | 모르는 보낸 사람으로 고객 계정 만들기 / 관리자가 검토하는 대기함(화면이 하나 는다, 필요하면 나중에) / 안내 답장 |
| D-17 | 2026-10-08 | 여러 팀 열기는 v1에서 뺀다 | 운영자 역할, 팀 관리 화면, 팀별 설정이 한꺼번에 늘어나는데, 처음 받아 쓰는 사람에게는 팀 하나면 된다. 칸은 이미 있다(D-18) | v1에 넣기 |
| D-18 | 2026-10-08 | 업무 테이블에 `tenant_id NOT NULL`(값은 1) 칸만 두고, 팀으로 거르는 일은 여러 팀을 열 때 한다. 칸이 빠지지 않게 CI 관문이 마이그레이션을 검사한다. 대신 고객사 경계(RULE-01)를 기능마다 부정 테스트로 지킨다 | 팀이 하나뿐이면 팀 거르기 코드는 검증할 방법이 거의 없고 틀려도 드러나지 않는다. 지금 실제로 지켜야 할 경계는 고객사 사이다. 쿼리를 저장소 계층에 모아 두면 나중에 거르기를 더하는 품이 작다 | 지금부터 모든 쿼리를 팀으로 거르기(D-4) / Postgres 행 수준 보안(RLS) |
| D-19 | 2026-10-08 | (→ D-38) 첨부는 DB(`bytea`)에만 두고 파일·문의·팀 단위 크기 상한을 건다. 디스크·S3는 "나중에"로 옮긴다. 저장소 인터페이스는 남긴다 | 사람 결정(진행 절차의 설계 단계). 첫 판은 `pg_dump` 하나로 백업이 끝나는 것이 낫다 | 저장소 셋을 v1에 두기(D-14) |
| D-20 | 2026-10-08 | 관리 작업과 로그인의 감사 로그를 둔다(AUDIT). 이전 판의 "감사 로그를 두지 않는다"를 뒤집는다 | 사람 결정(진행 절차의 설계 단계). 회사에서 써 보려면 누가 권한·소속을 바꿨는지 물을 수 있어야 한다. 고객사 경계가 깨졌을 때 원인을 찾을 근거도 된다 | 감사 로그 없음 / 모든 요청 기록(개인정보와 저장량이 커진다) |
| D-21 | 2026-10-08 | (파일 경로는 → D-43) API 계약은 코드에서 만든다(springdoc → `docs/integrate/openapi.json` 커밋 → TypeScript 클라이언트 생성). 묶음마다 컨트롤러 껍데기를 먼저 커밋한다 | 손으로 쓴 OpenAPI는 코드와 어긋나기 쉽다. 만든 파일을 커밋하고 CI가 차이를 보면 계약 변경이 리뷰에 드러난다 | 손으로 쓴 `openapi.yaml`에서 서버·클라이언트 생성(contract-first) |
| D-22 | 2026-10-08 | 구현은 진행 절차(`design/process.md`)를 따른다. 첫 묶음은 "포털 문의(첨부) → 콘솔 답변 → 메일 → 웹훅 → Grafana 지표"를 끝에서 끝까지 얇게 꿰는 묶음이다 | 메일, 웹훅, 지표처럼 위험한 연결을 처음에 한 번 다 꿰어 본다. 층별로 쌓으면 프런트를 붙일 때에야 API의 빈 곳이 드러난다 | 백엔드 → 프런트 → 관측 / 기능 묶음을 층별로 0~9단계로 쌓기 |
| D-23 | 2026-10-08 | 앱 인스턴스는 하나를 전제로 한다 | 목표 규모를 하나로 받는다. 요청 수 제한과 메일 받기 회차를 단순하게 둘 수 있다 | 처음부터 여러 인스턴스(공유 저장소가 필요하다) |
| D-24 | 2026-10-08 | 마이그레이션은 앞으로만 간다. 나간 파일은 고치지 않고 down은 두지 않는다. 되돌릴 수 없는 마이그레이션은 릴리스 노트에 표시한다 | 설치처마다 DB가 따로라 되돌리기를 믿을 수 없다. 대신 업그레이드 전 백업과 지난 릴리스에서 올라오는 업그레이드 테스트로 지킨다 | down 마이그레이션 |
