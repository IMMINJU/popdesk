# popdesk 로드맵

> popdesk가 누구의 어떤 문제를 풀고, 무엇을 지키며, 무엇을 하지 않는지(범위와 범위 밖), 그리고 기능 묶음의 순서를 적는다.
> 이유는 `adr.md`, 진행 방법은 `process.md`, 아직 묶음으로 옮기지 않은 세부는 `spec/`에 있다.
> 문서끼리 어긋나면 이 순서로 따른다: 이 문서 → ADR → 정본(OpenAPI, 공통 규약, 권한 모델, 위협 모델) → 진행 중인 묶음 → `spec/` 초안.

## 1. 무엇인가

popdesk는 설치형 헬프데스크에 이슈트래커를 합친 것이다. 지원팀 하나가 여러 고객사의 문의를 한곳에서 받고, 문의를 그대로 이슈로 삼아 작업으로 나눠 맡기고 진행을 쫓는다. 해결될 때까지의 대화와 작업 기록이 문의에 남는다(D-42).

- 받아서 바로 써 볼 수 있어야 한다. `docker compose up` 한 번에 앱 하나와 Postgres 하나가 뜬다(D-3).
- 설치 하나에 지원팀 하나다. 데이터에는 팀 구분 칸(`tenant_id`)만 두고, 팀으로 거르는 일은 여러 팀을 열 때 한다(D-18).
- 용어: "고객사"는 문의를 보내는 회사, "문의"는 고객이 올린 요청 하나다. 코드와 API에서는 고객사를 `project`, 문의를 `issue`로 부른다.

## 2. 사용자와 문제

| 역할 | 문제 | popdesk가 주는 것 |
|---|---|---|
| 고객 | 요청이 전달됐는지, 어디까지 처리됐는지 모르고, 대화 창구가 흩어져 있다 | 문의 상태를 보고 한곳에서 대화한다 |
| 고객사 담당자 | 우리 회사 사람을 넣고 빼려면 매번 지원팀에 부탁해야 한다 | 자기 고객사의 고객을 초대하고 소속에서 뺀다 |
| 상담원 | 무슨 문제였는지, 무엇을 했는지 되짚기 어렵다 | 문의마다 문제·대화·작업 기록이 한곳에 남는다 |
| 관리자 | 상담원의 문제에 더해 고객사와 구성원을 관리해야 한다 | 고객사·구성원·배정을 관리하고, 문의도 직접 처리한다 |
| 설치하는 사람 | 헬프데스크를 띄우는 데 컨테이너와 설정이 많다 | 앱 이미지 하나와 Postgres로 뜬다. 첫 관리자는 첫 실행 때 만든다 |

- 고객은 고객 포털을, 상담원·관리자는 상담 콘솔을 쓴다.
- 고객은 하나 이상의 고객사에 속한다. 상담원은 관리자가 배정한 고객사를 맡는다.
- 고객사 담당자는 따로 있는 역할이 아니라, 관리자가 고객사의 고객 가운데 지정한 사람이다.
- 문의는 고객이 포털이나 메일로 넣는다. 전화로 온 요청은 상담원이 고객 대신 올린다(대리 등록). 메신저 연동은 하지 않는다.

## 3. 핵심 시나리오

- SCN-01 고객이 포털에서 문의를 올린다(기본 공개, 비공개 선택). 진행 상태를 보고 상담원과 대화한다.
- SCN-02 고객이 같은 고객사 동료의 공개 문의를 보고 진행을 함께 확인한다.
- SCN-03 상담원이나 관리자가 담당자를 정한다. 담당자는 문의 아래 작업을 만들어 상담 쪽 사람에게 나눠 맡기고 마감일을 정한다. 작업을 맡은 사람은 조사한 것과 알아낸 것을 기록으로 쌓고, 끝나면 작업을 닫는다. 상담 쪽은 "내 작업"에서 맡은 일을 모아 본다.
- SCN-04 상담원이 지난 문의를 열면 무슨 문제였고, 무엇을 했고, 어떤 대화가 오갔는지 한 화면에서 본다.
- SCN-05 새 답변과 주요 상태 변화는 상대에게 알림함과 메일로 알린다.
- SCN-06 관리자가 고객사를 만들고 고객과 상담원을 초대 메일로 부른다.
- SCN-07 문의를 올린 고객은 언제든 종료할 수 있고, 상담원·관리자도 종료한다. 해결된 문의는 7일 뒤 자동으로 종료된다. 종료된 문의는 14일 안에 다시 열 수 있다.
- SCN-08 관리자가 고객사별 문의 건수를 상태별로 본다.
- SCN-09 등록된 고객이 지원 메일 주소로 메일을 보내면 문의가 생긴다. 알림 메일에 답장하면 같은 문의의 댓글로 이어진다.
- SCN-10 회사가 쓰는 로그인(OIDC)이 있으면 상담원·관리자는 그것으로 로그인한다.
- SCN-11 고객이 전화로 요청하면 상담원이 그 고객 이름으로 문의를 올린다. 고객은 알림을 받고 포털에서 이어 간다.
- SCN-12 관리자가 우선순위별 첫 응답·해결 목표 시간과 업무 시간을 정한다. 상담원은 목록에서 목표를 곧 넘길 문의를 먼저 보고, 넘기면 담당자에게 알림이 간다. 관리자는 고객사별 목표 달성률을 본다.
- SCN-13 관리자가 고객사의 고객 한 명을 담당자로 지정하면, 그 사람이 자기 회사 동료를 초대하고 소속에서 뺀다.
- SCN-14 관리자가 설치 전체의 표시 이름, 로고, 강조색을 정한다. 두 포털과 메일이 그것으로 보인다.
- SCN-15 여러 고객사가 같은 버그를 올리면 상담원이 문의끼리 중복·관련으로 잇는다. 원본 문의가 해결되면 이어진 문의의 담당자가 알림을 받고 각 고객에게 답한다. 고객은 연결을 보지 못한다.

## 4. 핵심 규칙

- RULE-01 고객사 격리: 한 고객사의 고객은 어떤 경로로도 다른 고객사의 문의·댓글·첨부·고객 이름을 보지 못한다. 이 경계는 기능마다 부정 테스트(A사 고객이 B사 문의를 못 본다)로 지킨다.
- RULE-02 고객이 보는 범위: 자기 고객사의 공개 문의와 자기가 올린 문의만 본다.
- RULE-03 상담 쪽이 보는 범위: 관리자는 모든 문의를, 상담원은 배정된 고객사의 문의를 공개·비공개 구분 없이 본다.
- RULE-04 내부 정보: 작업, 작업 기록, 내부 댓글, 담당자 이름, 문의 사이의 연결은 고객에게 어떤 경로(포털, API, 메일)로도 보이지 않는다. 연결된 다른 고객사의 문의는 상담 쪽에서도 볼 수 있는 사람에게만 보인다.
- RULE-05 한 문의, 한 기록: 문의 하나의 대화, 상태 변화, 작업은 그 문의에 모인다.
- RULE-06 흔적이 남는 변경: 문의·댓글·작업은 고치거나 지울 수 있지만 그랬다는 흔적은 남는다. 지운 문의는 30일 동안 되돌릴 수 있고, 그 뒤에는 쓴 내용만 지우고 흔적은 남긴다.
- RULE-07 초대로만 가입: 계정은 관리자나 고객사 담당자(자기 고객사의 고객만)의 초대 메일로만 생긴다. 첫 관리자만 설치하는 사람이 첫 실행 때 만든다.
- RULE-08 담당: 담당자는 상담원·관리자가 정한다. 담당이 아닌 상담원도 볼 수 있는 문의에 답하고 작업 기록을 남길 수 있다.
- RULE-09 종료와 재오픈: 올린 고객, 상담원, 관리자만 한다. 같은 고객사 동료는 볼 수만 있다.
- RULE-10 관리 작업은 남는다: 계정·역할·고객사·소속·배정·휴지통을 바꾼 일은 누가 언제 무엇을 바꿨는지 감사 로그에 남는다(D-20).
- RULE-11 개인정보: 무엇을 어디에 저장하는지 적어 둔다(지금은 `spec/features.md` 13절). 관리자는 한 사람의 정보를 내보내고, 계정을 익명으로 바꿀 수 있다(D-25).

## 5. 하지 않을 것

- NG-01 전화·메신저·문자 같은 외부 채널 연동. (메일 받기, 팀 알림용 웹훅 발신, 상담원의 대리 등록은 한다)
- NG-02 자가 가입. 계정은 초대로만 생긴다(RULE-07).
- NG-05 실시간 푸시(웹소켓)와 브라우저·OS 알림. 알림함과 메일로 알린다.
- NG-06 네이티브 앱, PWA, 오프라인 동작.
- NG-07 고객사별 브랜딩. 브랜딩은 설치 전체에 하나다.

## 7. 나중에

v1에는 넣지 않지만 막지 않는다. 할 때는 결정을 먼저 남긴다.

- 여러 팀 열기(D-17). 칸은 이미 있다(D-18). 열 때 함께 할 것: 모든 조회·쓰기에 팀 거르기 더하기(저장소 계층 한 곳), 팀 경계 부정 테스트, 팀 밖의 운영자 역할, 팀 관리 화면, 팀별 설정(웹훅, SMTP, 메일 받기, 첨부 한도), 이메일이 유일한 범위와 로그인 때 팀 고르기.
- SAML 로그인, SCIM으로 사용자 자동 등록·해제(D-32). 대기업 도입용이라 지금 목표(받아서 써 보기)와 멀고 품이 크다.
- 이슈트래커 쪽 나머지(D-42): 고객 없이 만드는 내부 이슈, 고객용 상태와 따로 두는 내부 상태 단계, 보드, 마일스톤·버전, 이슈 종류, GitHub·Jira 같은 바깥 트래커 연동.

앞 묶음에서 뒤 묶음으로 넘긴 것 가운데 아직 남은 것(끝난 묶음이 만든 것은 뺐다. 2026-10-14):

- 1b에서: 샌드박스에서 메일 받기를 끄는 것은 12번(메일 받기)에서 한다.
- 2번에서: 담당자의 초대에 하루 한도를 거는 일은 필요해지면 한다(`archive/2-manager/premortem.md` 4절).
- 3번에서: 라벨 필터와 작업 수는 6번, 자동 종료는 7번, SLA 칸과 필터는 8번, 이력의 익명화는 10번이다. 검색 없는 문의 목록이 10만 건에서 250~315 ms인 것은 6번에서 목록을 고칠 때 같이 본다(`archive/3-issues/verify.md` 8절).
- 4번에서: 정리 작업이 하루 넘게 돌지 않을 때의 경보는 7번, `POPDESK_TIMEZONE`의 틀린 값을 시작할 때 막는 것은 날짜 판정(마감일)이 들어오는 6번이다(`archive/4b-delivery/verify.md` 8절). 서버 패키지 순환은 `account` ↔ `company` 하나가 남았고 초대나 구성원을 고치는 묶음에서 본다(D-57). `@popdesk/app`으로 옮긴 파일 가운데 테스트와 변이 테스트를 아직 재지 않은 것이 있다.
- 5번에서: Storybook의 넘침 단언을 명령 줄에서 돌리는 실행기는 6번 묶음의 첫 웹 일로 넣는다(5b는 화면을 바꾸지 않는다. `archive/5b-storage/acceptance.md` 5절 12). 편집기의 새 문구를 `@popdesk/i18n`으로 옮기는 것은 영어 화면을 만들 때 한다(`archive/5-attachments/verify.md` 9절).
