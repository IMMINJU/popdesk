# popdesk 기능 (분해 대기 초안)

> 기능마다 누가 무엇을 할 수 있고 어떤 값을 지키는지 적는다. 테스트는 이 문서의 규칙 ID를 이름에 적는다.
> 정본이 아니다(D-27). 묶음을 시작할 때 그 묶음의 절을 EARS 수용 기준(`../slices/`)으로 옮기고 여기서 지운다. 권한은 고객사 권한 모델(`docs/use/permissions.md`)로 옮긴다. 0절은 공통 규약으로 옮겼다.
> API 경로와 응답 모양은 묶음마다 컨트롤러 껍데기로 먼저 정하고, springdoc이 만든 `docs/integrate/openapi-portal.json`·`openapi-console.json`이 그 계약이다(D-21, D-43).
> 글자 수 세는 법, NFC 정규화, 앞뒤 공백 자르기는 `docs/integrate/conventions.md`에 있다.

## 0. 공통

→ `docs/integrate/conventions.md`로 옮김(COM-1~8, 글자 수·NFC·공백 자르기, 시각, null의 뜻 제안).

아래 규칙은 아직 공통 규약에 없다. 공통 규약으로 옮기면 여기서 지운다(TIME-1은 시각 절로).

| ID | 규칙 |
|---|---|
| TIME-1 | 기간(24시간, 7일, 14일, 30일, 보관 기간)은 UTC 시각의 차이로 잰다. 서머타임이나 `POPDESK_TIMEZONE` 변경과 관계없이 같은 길이다. 설치 시간대로 날짜를 판정하는 것은 마감일(DUE-1, TASK-6)과 SLA 업무 시간·쉬는 날(SLA-2)뿐이다 |
| ANON-1 | 고객 쪽(포털 화면, 포털 API, 고객에게 가는 메일·알림함)에는 상담 쪽 사람(상담원·관리자)을 "지원팀"으로만 보인다. 댓글 작성자, 첨부를 올리거나 지운 사람, 대리 등록한 사람(ISSUE-9), 고객에게 보이는 일을 일으킨 사람 모두 그렇다. 포털 API 응답에는 상담 쪽 사람의 이름, 이메일, 계정 ID를 넣지 않는다. 상담 쪽이 한 것은 "상담 쪽"이라는 표시만 담고, 화면과 메일이 그것을 "지원팀"으로 쓴다. 고객이 쓴 것의 작성자(올린 고객, 같은 고객사 동료)는 그대로 보인다(D-49) |

## 1. 로그인과 계정 (AUTH, ACCT)

→ AUTH-1~5·7, ACCT-1~6·8은 `../archive/1a-people/rules.md`로, ACCT-7은 `../archive/3-issues/rules.md`로 옮김(3번 묶음). 아래는 11번 묶음의 것이다.

| ID | 규칙 |
|---|---|
| AUTH-6 | OIDC 로그인(설정이 있을 때, `OIDC_APPS`의 앱에만): 제공자가 준 `email`이 확인된 것(`email_verified`=true)이고 그 이메일의 계정이 있을 때만 로그인된다. 계정을 새로 만들지 않는다(RULE-07). 수락 전 계정이면 이때 `ACTIVE`가 된다(제공자가 이메일 주인임을 확인했으므로). 처음 맞출 때 제공자의 `iss`와 `sub`를 계정에 묶고, 그 뒤로는 그 값으로만 맞춘다(제공자 쪽에서 이메일이 바뀌어도 남의 계정에 맞지 않게). 정지 계정, 역할이 그 앱과 맞지 않는 계정(AUTH-1), 계정이 없는 이메일은 같은 실패 화면이다. 비밀번호 로그인도 함께 남는다. OIDC로 수락해 비밀번호가 없는 계정은 비밀번호 로그인이 일반 실패(AUTH-2)와 같고, 비밀번호 찾기(AUTH-7)로 비밀번호를 정할 수 있다(제공자가 멈추거나 클라이언트 비밀이 만료돼도 들어올 길이 남게) |

## 6. 첨부 (ATT)

→ ATT-6~8은 `../archive/5-attachments/rules.md`로, ATT-9는 `../archive/5b-storage/rules.md`로 옮김(5번, 5b 묶음).

| ID | 규칙 |
|---|---|
| ATT-1 | 문의나 댓글에 파일을 올린다. 올리는 사람은 그 문의에 댓글을 달 수 있는 사람이고, 댓글 첨부는 그 댓글을 쓴 사람만 붙인다. `CLOSED` 문의는 400이다 |
| ATT-2 | 파일 하나는 1바이트~10MB, 문의 하나의 공개 첨부(문의 첨부와 공개 댓글 첨부) 합은 50MB까지다. 내부 댓글 첨부는 이 합에 세지 않고 팀 총량 한도(ATT-3)에만 센다(고객이 400이 나는 지점으로 내부 첨부 크기를 짐작하지 못하게). 파일 이름은 1~255자다 |
| ATT-3 | 팀 전체 첨부 합이 `POPDESK_ATTACHMENT_QUOTA`(기본 10GB)를 넘게 되면 올리기가 400이다. 한도의 80%를 넘으면 경고 로그를 남기고 관리자 알림함에도 남긴다(OPS-1) |
| ATT-4 | 내려받기는 문의를 볼 수 있는 사람이 한다. 늘 `Content-Disposition: attachment`와 `X-Content-Type-Options: nosniff`로 내려준다. 고객에게 내부 댓글의 첨부는 없는 것과 같다(목록에서 빠지고, 내려받기는 404, CMT-2). 고객에게 상담 쪽이 올리거나 지운 첨부의 사람은 "지원팀"이다(ANON-1) |
| ATT-5 | 지우기는 올린 사람과 관리자가 하고 흔적을 남긴다(COM-7, 파일 내용은 지운다) |
| ATT-10 | 첨부 행의 파일 상태: `pending`(파일을 쓰는 중), `stored`, `purging`(파일을 지울 차례), `purged`. 올리기는 ① `pending` 행을 따로 커밋하고 ② 파일을 저장소에 쓰고 ③ 업무 트랜잭션에서 `stored`로 바꾼다. 지우기는 ① 행을 `purging`으로 바꿔 커밋하고 ② 저장소의 파일을 지우고 ③ 지워지면 행을 `purged`로 바꾸거나(흔적이 남는 지우기, ATT-5) 행을 지운다(영구 삭제, TRASH-3). 저장소에서 지우기가 실패해도 업무 요청은 성공한다 |
| ATT-11 | 첨부 정리 작업(하루 한 번): 만든 지 1시간이 지난 `pending` 행과 `purging` 행의 파일을 지우고 ATT-10의 ③을 한다. 파일이 이미 없으면 지운 것으로 본다. 저장소를 훑어 DB에 없는 파일을 찾아 지우는 방식은 쓰지 않는다(복원 직후처럼 DB가 뒤처진 때 살아 있는 파일을 지울 수 있다). 정리 작업마다 돈 시각과 지운 수를 남긴다(OPS-2) |

## 8. 작업 (TASK)

| ID | 규칙 |
|---|---|
| TASK-1 | 작업은 상담 쪽 전용이다. 고객은 403이고 어떤 경로로도 보이지 않는다(RULE-04) |
| TASK-2 | 문의 하나에 작업을 여러 개 만든다. 필드: 제목(1~100자), 상태(`OPEN`·`DONE`, 새로 만들면 `OPEN`), 담당자(비울 수 있다), 마감일(비울 수 있다). 상담 쪽 누구나 고친다. 지우기는 만든 사람과 관리자가 하고, 흔적을 남기며, 그 작업의 기록도 함께 지운다 |
| TASK-6 | 작업 담당자는 문의 담당자와 자격이 같다(ISSUE-7): `ACTIVE` 관리자, 또는 그 고객사에 배정된 `ACTIVE` 상담원. 마감일 규칙은 DUE-1과 같다. `DONE`이 되면 끝낸 시각과 사람을 남기고, `OPEN`으로 되돌리면 지운다 |
| TASK-7 | 내 작업: 상담 쪽은 자기가 담당인 작업을 모든 문의에 걸쳐 한 목록으로 본다. 기본은 `OPEN`만, 마감일이 빠른 순(마감일 없는 것은 뒤)이다. 지금 볼 수 있는 문의의 작업만 나오고, `CLOSED`·휴지통 문의의 작업은 빠진다. 쪽 나누기는 COM-4 |
| TASK-8 | 문의를 `RESOLVED`나 `CLOSED`로 바꿀 때 `OPEN` 작업이 있어도 막지 않는다. 화면은 남은 작업 수를 보이고 한 번 더 묻는다 |
| TASK-3 | 작업마다 기록을 시간순으로 쌓는다. 내용은 1~4,000자이고 상담 쪽 누구나 남긴다. 고치기는 쓴 사람만, 지우기는 쓴 사람과 관리자가 한다(흔적을 남긴다) |
| TASK-4 | 목록은 작업과 그 기록을 한 번에 오래된 순으로 준다. `CLOSED` 문의에서는 읽기만 된다 |
| TASK-5 | 작업의 상태·담당자·마감일이 바뀌면 그 작업의 기록에 시스템 항목(누가, 무엇을, 전·뒤 값)으로 남긴다. 문의 이력(HIST)에는 남기지 않는다. 알림은 작업 담당자가 바뀔 때 새 담당자에게만 간다(10절 표) |

## 8-1. 문의 연결 (LINK)

| ID | 규칙 |
|---|---|
| LINK-1 | 상담 쪽이 두 문의를 잇는다. 종류는 `DUPLICATE_OF`(이 문의는 저 문의의 중복)와 `RELATED`(관련, 방향 없음)다. 고객사가 달라도 된다. 잇고 끊는 사람은 두 문의를 모두 볼 수 있어야 한다(아니면 404) |
| LINK-2 | 두 문의 사이에는 종류와 방향과 관계없이 연결이 하나다(겹치면 409). 저장할 때 두 문의 ID를 (작은 ID, 큰 ID)로 맞춘 칸에 유니크 제약을 두고, `DUPLICATE_OF`의 방향은 따로 적는다. 자기 자신과는 잇지 못한다(400). 중복의 원본은 다른 문의의 중복이 아니어야 하고, 이미 원본인 문의(들어오는 `DUPLICATE_OF`가 있는 문의)는 중복이 될 수 없다(둘 다 400, 원본이 하나로 모이고 사슬이 생기지 않게). 문의 하나에 연결은 50개까지다. 연결을 만들 때 두 문의 행을 ID 순서로 잠근 뒤 검사한다(동시에 걸어 검사를 피하지 못하게). 검사와 개수는 휴지통에 있어 숨은 연결(LINK-7)까지 센다 |
| LINK-3 | 고객에게 연결은 없는 것과 같다(RULE-04). 고객용 응답, 메일, 고객사 내보내기에 넣지 않는다 |
| LINK-4 | 상담 쪽 화면은 연결된 문의 가운데 보는 사람이 볼 수 있는 것만 키·제목·상태·고객사로 보인다. 볼 수 없는 쪽은 개수도 보이지 않는다 |
| LINK-5 | 중복으로 이어도 상태는 저절로 바뀌지 않는다. 상담 쪽이 고객에게 공개 댓글로 알리고 직접 닫는다 |
| LINK-6 | 연결된 문의가 `RESOLVED`나 `CLOSED`가 되면, 이어진 다른 문의의 담당자에게 알림함으로 알린다(10절 표). 그 담당자가 바뀐 문의를 볼 수 없으면 보내지 않는다 |
| LINK-7 | 잇고 끊은 일은 양쪽 문의의 이력(HIST)에 남는다. 이력 값은 상대 문의의 ID만 담고, 화면은 볼 수 있을 때만 키와 제목을 보인다. 한쪽이 휴지통에 가면 연결이 숨고, 복구하면 다시 보이며, 영구 삭제하면 연결을 지운다 |

## 9. 이력과 휴지통 (HIST, TRASH)

→ HIST-1~3은 `../archive/3-issues/rules.md`로 옮김(3번 묶음). 아래는 7번 묶음의 것이다.

| ID | 규칙 |
|---|---|
| TRASH-1 | 문의 삭제는 관리자만 한다. 지우면 휴지통으로 간다: 모든 목록·검색·알림함에서 빠지고, 그 문의와 하위 경로는 404다. 자동 종료도 하지 않는다 |
| TRASH-2 | 관리자는 휴지통 목록을 보고(지운 시각, 지운 사람, 영구 삭제 예정 시각), 복구하거나 바로 영구 삭제한다. 복구하면 내용·댓글·첨부·작업·연결·담당자가 지우기 전 그대로 돌아온다. 다만 다음은 그대로가 아니다: 휴지통에 있던 동안 생겼을 알림(알림함·메일·웹훅)은 버리고 복구해도 보내지 않는다. SLA 시계는 휴지통에 있던 동안 멈춰 있었다(SLA-3). `RESOLVED` 문의의 자동 종료 기준 시각은 복구 시각으로 미룬다(STATUS-5). 복구는 문의 행을 잠그고 아직 휴지통에 있는지 본 뒤 한다. 복구할 때 연결 규칙(LINK-2)을 다시 보고, 어긋나면 복구하지 않고 409로 어느 연결이 걸리는지 알린다 |
| TRASH-3 | 지우고 30일이 지나면 시스템이 영구 삭제한다(1시간마다 돈다). 영구 삭제는 쓴 내용(제목은 "Deleted issue"/"삭제된 문의", 내용, 댓글, 첨부, 작업, 알림함 항목)을 지우고 문의 행(키, 고객사, 상태, 시각)과 이력의 흔적은 남긴다. 이력의 제목·내용 값도 비운다. 문의 하나를 한 트랜잭션으로 지운다: 문의 행을 잠그고 아직 휴지통에 있는지(사람이 지울 때) 또는 30일이 지났는지(시스템이 지울 때) 다시 본 뒤 지운다(같은 순간의 복구와 겹치지 않게). 첨부는 그 트랜잭션에서 `purging`으로만 바꾸고, 파일은 커밋한 뒤 지운다(ATT-10) |
| TRASH-4 | 문의 순번은 지워도 다시 쓰지 않는다 |

## 10. 알림 (INBOX, MAIL, HOOK)

→ 알림 표, INBOX-1~4, MAIL-1~5, HOOK-1은 `../archive/4-talk/rules.md`로 옮김(4번 묶음). 아래는 뒤 묶음의 것이다: 표의 줄은 6번(작업 담당자, 연결)과 8번(SLA), MAIL-7은 12번이다(MAIL-6은 `../archive/4b-delivery/rules.md`로 옮김). MAIL-1의 `Reply-To`와 MAIL-4의 휴지통 확인도 12번과 7번에서 채운다.

| 일 | 고객(올린 사람) | 상담 쪽 | 팀 웹훅 |
|---|---|---|---|
| SLA 목표의 80%가 지남 | – | 담당자(없거나 볼 수 없으면 그 고객사 배정 상담원 전부, ISSUE-11)에게 알림함 | – |
| SLA 목표를 넘김 | – | 담당자(없거나 볼 수 없으면 그 고객사 배정 상담원 전부)와 관리자 전부에게 알림함 + 메일 | 보냄 |
| SLA 재계산으로 상태가 바뀜 | – | 관리자 전부에게 요약 알림함 한 건 (SLA-5) | – |
| 작업 담당자가 바뀜 | – | 새 작업 담당자에게 알림함 + 메일 | – |
| 연결된 문의가 `RESOLVED`·`CLOSED`가 됨 | – | 이어진 문의의 담당자에게 알림함 (LINK-6) | – |

| ID | 규칙 |
|---|---|
| MAIL-7 | 보낸 알림 메일의 `Message-ID`(MAILIN-2)는 문의 ID와 함께 저장하고 보관 기간 표대로 지운다 |

## 11. 메일로 받기 (MAILIN)

설정(`IMAP_*`)이 있을 때만 켜진다. 메일로 들어온 일은 포털로 들어온 같은 일과 규칙이 같다(권한, 길이, 첨부 한도, 알림).

| ID | 규칙 |
|---|---|
| MAILIN-1 | 보낸 사람(`From`)이 `ACTIVE` 고객 계정일 때만 받는다. 모르는 주소, 상담 쪽 계정, 정지·수락 전 계정에서 온 메일은 버리고 로그 한 줄(주소는 가린다)과 지표만 남긴다. 답장하지 않는다(위조된 보낸 사람에게 메일을 뿌리지 않게) (D-16) |
| MAILIN-2 | 답장인 메일(알림 메일의 `Message-ID`를 가리키거나 제목에 `[문의 키]`가 있고, 어느 쪽이든 보낸 사람이 지금 볼 수 있는 문의)은 그 문의의 공개 댓글이 된다. 알림 메일의 `Message-ID`는 추측할 수 없는 난수로 짓는다. 볼 수 없는 문의를 가리키면 답장으로 보지 않는다. 제목에 볼 수 없는 문의 키가 있으면 새 문의도 만들지 않고 MAILIN-3의 안내 메일을 보낸다(전달받은 비공개 문의가 공개 문의로 새지 않게). 그 문의에 댓글을 달 수 없는 사람(CMT-1)이거나 `CLOSED` 문의면 댓글을 만들지 않고, 보낸 사람에게 이유와 포털 링크를 담은 안내 메일을 보낸다 |
| MAILIN-3 | 답장이 아닌 메일은 새 문의가 된다: 제목은 메일 제목(비면 "(제목 없음)"/"(no subject)"), 내용은 본문, 우선순위 `NORMAL`, 공개. 고객사는 받는 주소의 `+코드`(예: `support+ACME@…`)로 고르고, 없으면 보낸 사람의 소속이 하나일 때 그곳이다. 소속이 여럿인데 코드가 없거나, 코드가 소속이 아니거나, 고객사가 `ACTIVE`가 아니면 문의를 만들지 않고 안내 메일을 보낸다. 소속을 상태보다 먼저 보고, 안내 메일 문구는 이유와 관계없이 하나다(다른 고객사의 코드와 상태가 드러나지 않게). 안내 메일에는 받는 사람이 볼 수 없는 문의의 키와 제목을 넣지 않는다 |
| MAILIN-4 | 본문: `text/plain` 부분을 쓰고, 없으면 HTML을 글자로 바꾼다. 답장은 흔한 인용 구분선(`On … wrote:`, `-----Original Message-----`, `>` 인용) 아래를 잘라 낸다. 길이 한도(ISSUE-2, CMT-1)를 넘으면 한도까지 자르고 끝에 잘렸다고 적는다 |
| MAILIN-5 | 메일 첨부는 문의나 댓글의 첨부가 된다. 파일 규칙(ATT-2·3)에 맞지 않는 첨부는 빼고, 뺀 파일 이름을 본문 끝에 적는다 |
| MAILIN-6 | 같은 `Message-ID`는 한 번만 처리한다. 받은 메일 기록(`Message-ID`)은 문의·댓글을 만드는 트랜잭션에 함께 저장하고 유니크 제약을 둔다. `Message-ID` 머리글이 없으면 원문의 SHA-256을 대신 쓴다. 메일함 쪽 처리(처리됨 폴더로 옮기기)는 커밋한 뒤에 한다. 그래서 옮기기 전에 끊겨도 다음 회차는 기록을 보고 건너뛴다. 버린 메일(MAILIN-1·7)도 기록하고 옮긴다. 처리하다 앱이나 DB 오류가 나면 옮기지 않고 다음 회차에 다시 처리한다 |
| MAILIN-8 | 처리한 메일은 읽음 표시가 아니라 처리됨 폴더로 옮긴다(사람이 같은 메일함을 열어 읽음으로 만든 메일도 놓치지 않게). 읽는 대상은 받는 폴더의 모든 메일이다. 한 메일의 처리 시도는 5번까지이고, 넘으면 격리 폴더로 옮기고 지표를 올린다(폴더 이름은 설정 키로 정한다) |
| MAILIN-9 | 메일로 들어온 문의·댓글도 보낸 계정 단위로 포털과 같은 요청 수 제한(COM-8)을 받는다. 넘은 메일은 문의·댓글을 만들지 않고 격리 폴더로 옮기고 지표를 올린다(자동 응답 서버와 서로 답하며 문의가 쏟아지지 않게) |
| MAILIN-7 | 자동 응답(`Auto-Submitted`가 `no`가 아님, `Precedence: bulk`·`list`·`junk`)과 자기 자신(`MAIL_FROM`)이 보낸 메일은 버린다(메일이 서로 되돌아 도는 것을 막는다) |

## 12. 통계 (STATS)

| ID | 규칙 |
|---|---|
| STATS-1 | 상담 쪽이 고객사마다 문의 건수를 본다: 전체, 열림(`RECEIVED`+`CONFIRMED`), 처리 중, 해결, 종료. 휴지통의 문의는 세지 않는다 |
| STATS-2 | 관리자는 모든 고객사를, 상담원은 배정된 고객사만 본다. 열린 문의가 많은 순, 같으면 코드순이다 |
| STATS-3 | 문의 테이블을 바로 센다(이벤트를 모아 두지 않는다). 규모(`architecture.md` 7절)를 넘어 느려지면 그때 집계 테이블을 정한다 |
| STATS-4 | SLA가 켜져 있으면 고객사마다 기간(기본 최근 30일) 안의 첫 응답·해결 시간 중앙값과 목표 달성률을 함께 보인다(SLA-7) |

## 13. 개인정보 (PII)

| ID | 규칙 |
|---|---|
| PII-1 | 저장하는 개인정보: 계정의 이메일·이름·언어·프로필 사진(ACCT-8), 고객이 쓴 문의·댓글·첨부(내용에 무엇이 들지는 고르지 못한다), 감사 로그의 바꾼 사람과 바뀐 값, 받은 메일의 보낸 주소와 `Message-ID`. IP 주소는 저장하지 않는다(로그인 횟수 제한은 메모리에서만 센다) |
| PII-2 | 로그에는 이메일을 첫 글자 뒤로 가려서 남기고, 비밀번호·토큰·초대 링크·문의 내용은 남기지 않는다 |
| PII-3 | 내보내기: 관리자가 한 계정의 정보를 JSON 하나로 받는다. 계정 필드, 프로필 사진(있으면), 그 사람이 올린 문의(제목·내용·상태·시각), 쓴 댓글, 올린 첨부 목록(파일 내용은 빼고 이름·크기·시각)이 들어간다. 내보내기 자체를 감사 로그에 남긴다 |
| PII-4 | 익명화: 관리자가 계정을 익명으로 바꾼다. 이름은 "Deleted user"/"삭제된 사용자", 이메일은 `deleted-{id}@invalid`, 상태는 `SUSPENDED`가 되고 프로필 사진(ACCT-8)과 세션을 모두 지운다. OIDC 묶음(`iss`·`sub`, AUTH-6)을 지운다(같은 이메일로 다시 초대한 사람이 OIDC로 옛 계정에 들어가지 않게). 받은 메일 기록(MAILIN-6)의 보낸 주소를 비운다. 그 계정에 갈 메일 대기 행을 지운다(MAIL-5). 되돌릴 수 없다. 그 사람이 쓴 문의·댓글은 남고 작성자는 익명 이름으로 보인다. 자기 자신과 마지막 관리자는 익명화할 수 없다(400) |
| PII-5 | 익명화한 계정의 이메일은 다시 초대에 쓸 수 있다. 감사 로그에 남은 그 사람의 이전 이메일·이름도 익명 값으로 바꾼다(감사 로그 사슬은 AUDIT-6대로 다시 잇고, 바꾼 일 자체를 감사 로그에 남긴다). 감사 값에 사람을 넣을 때는 이름·이메일만 글자로 넣지 않고 계정 ID와 함께 구조로 넣는다(`{"accountId": 12, "name": "…", "email": "…"}`). 익명화는 계정 ID로 찾아 바꾼다(이름이 같은 다른 사람을 바꾸지 않게). 보내기 대기에 남은 감사 바깥 사본(AUDIT-9)도 익명 값으로 바꾼다. 이미 밖으로 나간 사본과 내보낸 파일에는 옛 값이 남는다고 `docs/operate/privacy.md`에 적는다 |
| PII-6 | 보관 기간(아래 표). 문의 자동 정리는 기본으로 꺼져 있고, `POPDESK_ISSUE_RETENTION`(예: `P1095D`)을 넣으면 종료되고 그 기간이 지난 문의를 하루 한 번 휴지통으로 옮긴다(그 뒤는 TRASH-3). 값이 `P90D`보다 짧으면 앱이 뜨지 않고 이유를 남긴다. 처음 켜진 날(꺼져 있다가 켜지거나 값이 짧아진 날)은 옮기지 않고 옮길 문의 수만 관리자 알림함에 남긴 뒤(OPS-1) 하루 기다렸다 옮긴다(값을 잘못 넣었을 때 되돌릴 시간을 둔다). 옮기기도 STATUS-7의 조건부 쓰기다(그 사이 재오픈된 문의는 옮기지 않는다) |
| PII-7 | 삭제 요청 처리 절차를 `docs/operate/privacy.md`에 적는다: ① 원하면 내보내기(PII-3) ② 계정 익명화(PII-4) ③ 그 사람이 올린 문의 가운데 지워야 할 것을 관리자가 지우고 영구 삭제(TRASH-2). 다른 사람이 쓴 글에 든 그 사람의 이름은 자동으로 찾지 않으므로, 검색으로 찾아 고치라고 적는다 |
| PII-8 | 고객사 내보내기: 관리자가 고객사 하나의 데이터를 ZIP 하나로 받는다. 문의, 공개 댓글, 첨부 파일, 소속 고객 계정(이메일·이름)이 들어간다. 내부 댓글·작업은 기본으로 빼고, 고를 때만 넣는다. 빼면 내부 댓글의 첨부도 빠진다. 문의 칸은 고객용 응답과 같은 목록이다(담당자, 라벨, 마감일, 이력, SLA, 대리 등록한 상담원은 넣지 않는다). 계정은 이메일·이름만 넣고 다른 고객사 소속은 넣지 않는다. 내려받기는 로그인한 관리자만 한다. 크면 백그라운드로 만들고 다 되면 알림함으로 알린다. 내려받기 링크는 24시간 뒤 지운다. 내보내기를 감사 로그에 남긴다. 목록은 읽기 전용 트랜잭션 하나(스냅샷 하나)로 읽어 시점이 섞이지 않게 한다. 내보내기 작업에는 상태(`running`·`done`·`failed`)가 있고 화면은 그 상태를 보인다. 실패하면 알림함으로 알린다. 앱이 다시 뜰 때 `running`으로 남은 작업은 `failed`로 바꾼다(관리자가 끝없이 기다리지 않게) |

| 데이터 | 보관 |
|---|---|
| 문의, 댓글, 첨부, 작업 | 지울 때까지. 지우면 휴지통 30일 뒤 영구 삭제(TRASH). 선택: 종료 뒤 `POPDESK_ISSUE_RETENTION`이 지나면 휴지통으로(PII-6) |
| 계정 | 익명화할 때까지(PII-4) |
| 감사 로그 | `POPDESK_AUDIT_RETENTION`(기본 365일, 최소 30일, AUDIT-4) |
| 알림함 항목 | 문의를 영구 삭제할 때 함께 지움 |
| 보내기 대기의 실패 행 | 7일 |
| 임시 본문 이미지 | 24시간 |
| 세션 | 로그인 뒤 8시간 |
| 받은 메일의 `Message-ID`(또는 원문 해시) | 90일 |
| 보낸 알림 메일의 `Message-ID` | 90일(지난 뒤의 답장은 제목의 `[문의 키]`로만 찾는다) |
| 비밀번호 재설정 토큰 | 쓰거나 만료(1시간)된 뒤 지움 |
| 등록의 `Idempotency-Key` | 24시간 |
| 고객사 내보내기 파일 | 24시간 |
| 앱 로그(표준 출력) | popdesk는 저장하지 않는다. 설치한 곳의 로그 수집기가 정한다 |

## 16. SLA

| ID | 규칙 |
|---|---|
| SLA-1 | 관리자가 우선순위마다 첫 응답 목표와 해결 목표를 정한다(업무 시간 기준 분 단위, 비우면 그 목표가 없다). 정책은 설치 전체에 하나다. 기본은 모두 비어 있어서 SLA가 꺼진 상태다. 정책에는 버전 번호가 있다. 목표, 업무 시간, 쉬는 날, `POPDESK_TIMEZONE` 가운데 하나라도 바뀌면 버전이 1 오른다(시간대는 앱이 뜰 때 지난 값과 견준다). 문의마다 기한을 계산한 정책 버전을 적는다 |
| SLA-2 | 업무 시간: 요일마다 시작·끝 시각(하루에 구간 하나), 쉬는 날 목록. 시간대는 `POPDESK_TIMEZONE`이다. 업무 시간이 비어 있으면 하루 24시간으로 센다 |
| SLA-3 | 시계: 문의가 올라온 시각부터 업무 시간만 센다. 첫 응답 시계는 `firstResponseAt`(ISSUE-10)에서 멈춘다. 해결 시계는 `RESOLVED`나 `CLOSED`가 되면 멈추고, 재오픈되면 이어서 센다(앞서 센 시간을 더한다). 휴지통에 있는 동안은 두 시계가 모두 멈춘다(TRASH-2). 시계가 멈출 때 그 목표의 `met`·`missed`를 확정한다. 해결 목표는 재오픈하면 확정을 지우고 다시 센다. 다음에 멈출 때 다시 확정하므로 한 문의는 달성률(SLA-7)에 한 번만 들어간다. 첫 응답 목표는 한 번 확정하면 바뀌지 않는다(ISSUE-10) |
| SLA-4 | 기한: 목표가 있는 문의마다 첫 응답 기한과 해결 기한을 계산해 저장한다. 우선순위가 바뀌면 그 문의를, 정책 버전이 오르면(SLA-1) 열린 문의 전부를 다시 계산한다. 다시 계산은 남은 기한만 바꾼다: 지금까지 센 업무 시간(누적)은 그대로 두고, 새 목표에서 누적을 뺀 남은 시간을 지금부터 새 업무 시간으로 센다(지난 날짜를 쉬는 날로 넣어도 이미 넘긴 것이 `ok`가 되지 않는다). 정책이 바뀌면 작업이 계산 버전이 낮은 열린 문의를 나눠서(한 번에 수백 건) 다시 계산한다. 행마다 `WHERE 계산 버전 < 새 버전` 조건부 UPDATE라서 다시 돌려도 결과가 같고, 중간에 죽으면 다음 회차가 이어 간다. 1분 작업(SLA-5)도 자기가 읽은 계산 버전을 조건에 넣어 옛 값으로 덮지 않는다. 서머타임이 있는 시간대로 테스트한다 |
| SLA-5 | 상태: 목표마다 `ok`, `warning`(목표 시간의 80%가 지남), `breached`(넘김), `met`(기한 안에 멈춤), `missed`(넘긴 뒤 멈춤). 1분마다 도는 작업이 `warning`·`breached`로 바뀐 문의를 찾아 한 번씩만 알린다(10절 표). 휴지통의 문의는 알리지 않는다. 다시 계산(SLA-4)으로 바뀐 상태는 하나씩 알리지 않고, 다시 계산이 끝나면 관리자에게 요약 알림함 한 건(넘김·곧 넘김이 된 수, 풀린 수)만 남긴다. 다시 계산으로 기한이 늘어 상태가 앞 단계로 돌아가면(`breached`→`warning`·`ok`, `warning`→`ok`) 지금 상태보다 뒤 단계의 "알렸음" 표시를 지운다. 그 뒤 다시 그 단계가 되면 다시 알린다 |
| SLA-6 | 상담 쪽 목록은 남은 시간을 보이고, "곧 넘김"과 "넘김"으로 거른다. 기한이 빠른 순으로 정렬할 수 있다. 고객에게는 SLA가 보이지 않는다 |
| SLA-7 | 통계(STATS-4): 고객사마다 기간 안에 멈춘 문의의 첫 응답·해결 시간 중앙값과 목표 달성률(`met` ÷ (`met`+`missed`))을 보인다 |
| SLA-8 | 정책을 처음 켜면 그때부터 올라오는 문의에만 기한을 붙인다. 이미 있던 문의에는 붙이지 않는다 |

## 17. 브랜딩 (BRAND)

| ID | 규칙 |
|---|---|
| BRAND-1 | 관리자가 설치 전체의 표시 이름(1~50자, 기본 "popdesk"), 로고, 강조색을 정한다. 고객사별 브랜딩은 없다(NG-07) |
| BRAND-2 | 로고는 PNG·JPEG·WebP, 512KB까지이고 파일 앞 바이트가 형식과 맞아야 한다. SVG는 받지 않는다(스크립트를 담을 수 있다). 밝은 테마용과 어두운 테마용을 따로 올릴 수 있고, 하나만 있으면 둘 다 그것을 쓴다 |
| BRAND-3 | 강조색은 `#RRGGBB` 하나다. 앱이 OKLCH 명도만 옮겨 밝은 테마와 어두운 테마의 `accent`를 하나씩 만들고, 만든 두 값이 각 테마 바탕에서 글자 대비 4.5:1 이상이어야 받는다(아니면 400, 화면은 만든 두 값과 대비를 함께 보인다). 강조색은 `accent` 무리(`accent`, `accent-hover`, `accent-subtle`, `on-accent`)만 바꾼다. 포커스 테두리 색, 상태 색, 오류 색은 바꾸지 않는다(D-50) |
| BRAND-4 | 로그인 화면, 두 포털의 머리, 브라우저 탭 제목, 메일의 보내는 이름과 머리에 표시 이름과 로고가 나온다. 메일 본문은 로고를 붙임 이미지로 넣지 않고 표시 이름 글자만 쓴다 |
| BRAND-5 | 브랜딩 값은 로그인 전에도 읽을 수 있는 공개 API로 준다(로그인 화면에 필요하다). 비밀 정보는 담지 않는다 |

## 18. 운영 경보와 시스템 상태 (OPS)

관측 도구는 선택이라 거기에만 기대지 않는다. 메일이 멈췄을 수 있으므로 경보는 메일이 아니라 관리자 알림함으로 남긴다.

| ID | 규칙 |
|---|---|
| OPS-1 | 운영 경보: 다음 일이 생기면 관리자 전부의 알림함에 항목을 남긴다. 보내기 대기에 `failed` 행이 생김(MAIL-6 포함), 한 채널의 보내기 실패가 한 시간 넘게 이어짐, 정리 작업(OPS-2) 하나가 하루 넘게 돌지 않음, 첨부 총량이 한도의 80%를 넘음(ATT-3), 문의 자동 정리가 처음 켜짐(PII-6), 내보내기 실패(PII-8). 같은 종류의 경보는 풀리기 전까지 하루에 한 건만 남긴다 |
| OPS-2 | 정리 작업(보내기 대기의 `failed` 행, 임시 이미지, 첨부 파일, 세션, 받은·보낸 메일의 `Message-ID`, 비밀번호 재설정 토큰, `Idempotency-Key`, 감사 로그 보관, 문의 자동 정리, 휴지통 영구 삭제)마다 마지막으로 돈 시각과 지운 수를 DB에 남기고 지표로도 낸다 |

→ OPS-3은 `../archive/4b-delivery/rules.md`로 옮김(4b 묶음). 메일 받기와 OIDC의 줄은 12번과 11번에서 채운다.
