# popdesk 기능 (분해 대기 초안)

> 기능마다 누가 무엇을 할 수 있고 어떤 값을 지키는지 적는다. 테스트는 이 문서의 규칙 ID를 이름에 적는다.
> 정본이 아니다(D-27). 묶음을 시작할 때 그 묶음의 절을 EARS 수용 기준(`../slices/`)으로 옮기고 여기서 지운다. 0절은 공통 규약(`docs/integrate/`)으로, 권한은 고객사 권한 모델로 옮긴다.
> API 경로와 응답 모양은 묶음마다 컨트롤러 껍데기로 먼저 정하고, springdoc이 만든 `docs/integrate/openapi.json`이 그 계약이다(D-21).
> 글자 수는 모두 유니코드 코드 포인트로 센다. 문자열 입력은 NFC로 정규화하고, 제목·이름처럼 한 줄인 값은 앞뒤 공백을 잘라서 저장한다.

## 0. 공통

| ID | 규칙 |
|---|---|
| COM-1 | 볼 수 없는 대상(다른 팀, 범위 밖, 없는 것, 휴지통에 있는 것)은 404다. 존재를 드러내지 않는다 |
| COM-2 | 볼 수는 있지만 할 권한이 없으면 403이다. 판정 순서는 로그인(401) → 대상 범위(404) → 권한(403) → 입력(400) → 상태(400·409)다. 역할만으로 막히는 연산은 대상과 관계없이 403이 먼저다 |
| COM-3 | 오류 응답은 `{code, message}`다. `code`는 화면이 문구를 고르는 키(예: `ISSUE_CLOSED`)이고 `message`는 `POPDESK_LOCALE` 언어의 기본 문구다. 예외 이름, 스택, SQL은 넣지 않는다 |
| COM-4 | 목록의 쪽 나누기: `page`(1부터), `size`(1~100, 기본 20). 응답은 `{items, page, size, totalElements, totalPages}`다. 마지막 쪽보다 큰 `page`는 빈 `items`다 |
| COM-5 | 검색어 `q`는 1~100자다. 대소문자를 무시하고 `%`·`_`는 보통 글자로 본다. 들어 있는 글자를 찾는다(단어 단위가 아니다). trigram 색인을 쓴다(D-13) |
| COM-6 | 본문(문의 내용, 댓글)은 마크다운 원문으로 저장한다. 화면은 허용 목록 방식으로 걸러서 그린다(스크립트, 이벤트 속성, `javascript:` 링크를 그리지 않는다) |
| COM-7 | "흔적을 남기고 지운다"는 행을 남기고 내용 칸을 비우며 `deleted`, 지운 시각, 지운 사람을 남긴다는 뜻이다. 목록에서 같은 자리에 "삭제됨"으로 보인다 |
| COM-8 | 요청 수 제한(계정마다 60초 창): 문의 등록 10회, 댓글 등록 30회, 첨부 올리기 30회, 검색어가 있는 목록 60회, 로그인 시도는 IP마다 20회. 넘으면 429와 `Retry-After`. 앱 메모리에서 센다 |

## 1. 로그인과 계정 (AUTH, ACCT)

| ID | 규칙 |
|---|---|
| AUTH-1 | 로그인은 이메일과 비밀번호로 한다. 이메일은 앞뒤 공백과 대소문자를 무시한다. 고객은 포털에서만, 상담원·관리자는 콘솔에서만 로그인한다. 다른 쪽에서 로그인하면 일반 실패와 같은 응답이다 |
| AUTH-2 | 실패 응답은 이메일이 없든, 비밀번호가 틀리든, 정지·잠김·수락 전 계정이든 같다(401). 응답 시간으로도 구별되지 않게 없는 계정도 비밀번호 해시를 한 번 계산한다 |
| AUTH-3 | 비밀번호가 5번 연속 틀리면 15분 잠근다. 잠긴 동안은 맞는 비밀번호도 실패다. 성공하면 횟수를 0으로 되돌린다. 관리자의 비밀번호 초기화는 잠금도 푼다 |
| AUTH-4 | 세션은 로그인하고 8시간 뒤 끝난다. 끝나면 화면은 로그인으로 돌아간다. 정지, 비밀번호 변경·초기화, 역할 변경 때 그 계정의 세션을 모두 지운다(비밀번호를 바꾼 본인의 지금 세션은 새로 발급한다) |
| AUTH-5 | 비밀번호는 Argon2id(Spring Security 기본 설정)로 저장한다. 규칙: 10~72자, 공백뿐이면 안 되고, 이메일과 같으면 안 된다 |
| AUTH-6 | OIDC 로그인(설정이 있을 때, `OIDC_APPS`의 앱에만): 제공자가 준 `email`이 확인된 것(`email_verified`=true)이고 그 이메일의 계정이 있을 때만 로그인된다. 계정을 새로 만들지 않는다(RULE-07). 수락 전 계정이면 이때 `ACTIVE`가 된다(제공자가 이메일 주인임을 확인했으므로). 정지 계정, 역할이 그 앱과 맞지 않는 계정(AUTH-1), 계정이 없는 이메일은 같은 실패 화면이다. 비밀번호 로그인도 함께 남는다 |
| ACCT-1 | 계정 필드: 이메일(설치 전체에서 하나, 소문자로 저장, 최대 100자), 이름(1~50자), 역할(`CUSTOMER`·`AGENT`·`ADMIN`), 상태(`INVITED`·`ACTIVE`·`SUSPENDED`), 언어(`ko`·`en`), 만든 시각 |
| ACCT-2 | 본인은 이름, 언어, 비밀번호(지금 비밀번호 확인)를 바꾼다 |
| ACCT-3 | 관리자는 계정 목록을 보고(역할·상태 필터, 이름·이메일 검색), 이름을 고치고, 역할을 `AGENT`↔`ADMIN` 사이에서 바꾸고, 정지·해제하고, 비밀번호를 초기화한다. 자기 자신의 정지와 역할 변경은 400이다. 고객 역할로 바꾸거나 고객에서 바꾸는 것은 400이다 |
| ACCT-4 | 이름 조회: 화면이 사람 이름을 보일 때 쓴다. 고객에게는 상담 쪽 사람, 자기 자신, 같은 고객사 고객의 이름만 보인다 |
| ACCT-5 | 첫 관리자: DB에 관리자가 없으면 첫 실행 때 `POPDESK_ADMIN_EMAIL`·`POPDESK_ADMIN_PASSWORD`로 `ACTIVE` 관리자를 만든다. 값이 없으면 앱이 뜨지 않고 무엇을 넣어야 하는지 로그에 남긴다 |

## 2. 초대 (INVITE)

| ID | 규칙 |
|---|---|
| INVITE-1 | 관리자가 이메일, 이름, 역할로 초대한다. 같은 이메일이 있으면 409다. 고객을 초대할 때는 소속 고객사를 하나 이상 함께 고른다 |
| INVITE-2 | 초대하면 `INVITED` 계정이 생기고 초대 메일이 나간다. 링크의 토큰은 32바이트 난수이고 DB에는 SHA-256 해시만 둔다. 7일 뒤 만료되고, 한 번 쓰면 끝난다 |
| INVITE-3 | 관리자는 수락 전 계정에 초대를 다시 보내거나(이전 링크는 무효) 취소한다(`SUSPENDED`가 되고 링크 무효). 다시 보내면 취소된 초대도 살아난다 |
| INVITE-4 | 링크를 연 사람이 비밀번호를 정하면 `ACTIVE`가 되고 바로 로그인된다. 없는·만료된·무효인 링크는 모두 같은 400이다 |
| INVITE-5 | 수락 전 계정은 로그인할 수 없고 담당자·멘션 대상·메일 받는 사람이 되지 않는다. 소속·배정·이름 수정은 된다 |

## 3. 고객사 (PROJ)

| ID | 규칙 |
|---|---|
| PROJ-1 | 관리자가 고객사를 만든다. 필드: 이름(1~100자), 코드(영문 대문자·숫자 2~10자, 팀 안에서 하나, 바꿀 수 없다), 회사명(1~100자), 상태 |
| PROJ-2 | 상태: `ACTIVE`, `SUSPENDED`, `ARCHIVED`. `ACTIVE`↔`SUSPENDED`, 둘 다 → `ARCHIVED`만 된다. `ARCHIVED`는 끝이다 |
| PROJ-3 | `ACTIVE`가 아닌 고객사에는 새 문의를 올릴 수 없다(400). 이미 있는 문의는 상태와 관계없이 그대로 다룬다. `ARCHIVED`에는 소속·배정을 더하거나 이름을 고칠 수 없다 |
| PROJ-4 | 관리자는 고객을 소속시키고 빼고, 상담원을 배정하고 뺀다. 같은 것을 다시 하면 그대로 200이다. 소속에서 빠진 고객도 자기가 올린 문의는 본다. 배정에서 빠진 상담원은 바로 그 고객사의 문의를 못 보고, 담당자 칸은 그대로 둔다 |
| PROJ-5 | 상담원은 자기가 배정된 고객사 목록을, 관리자는 전부를 본다. 고객은 자기 소속 고객사만 본다 |

## 4. 문의 (ISSUE)

| ID | 규칙 |
|---|---|
| ISSUE-1 | 고객은 소속 고객사에만 문의를 올린다(아니면 404). 상담원·관리자는 대리 등록(ISSUE-9)으로만 올린다 |
| ISSUE-2 | 입력: 고객사, 제목(1~200자), 내용(0~10,000자), 우선순위(`LOW`·`NORMAL`·`HIGH`·`URGENT`, 없으면 `NORMAL`), 비공개 여부(기본 공개), 본문 이미지(ATT-6) |
| ISSUE-3 | 새 문의: 키는 `{고객사 코드}-{순번}`(예: `ACME-7`, 고객사마다 1부터, 비지 않는다), 상태 `RECEIVED`, 올린 사람은 호출한 고객 |
| ISSUE-4 | 보는 범위: 고객은 RULE-02, 상담원·관리자는 RULE-03. 비공개 문의는 올린 고객과 상담 쪽만 본다 |
| ISSUE-5 | 목록은 최신순이다. 필터: 상태(여러 개), 고객사, 담당자(특정·나·없음), 올린 사람, 라벨, 검색어(제목과 내용의 화면 글자, 마크다운 기호와 링크 주소는 빼고 찾는다). 쪽 나누기는 COM-4 |
| ISSUE-6 | 수정: 제목, 내용, 우선순위. 올린 고객(자기 문의)과 상담 쪽이 한다. 같은 고객사 동료는 403이다. `CLOSED` 문의는 400이다 |
| ISSUE-7 | 담당자 지정은 상담 쪽만 한다. 담당자는 `ACTIVE` 관리자이거나, 그 고객사에 배정된 `ACTIVE` 상담원이다. 비울 수 있다 |
| ISSUE-8 | 고객에게 보이는 문의에는 담당자 칸이 없다(RULE-04) |
| ISSUE-9 | 대리 등록: 상담원(배정된 고객사만)과 관리자가 고객 한 명을 골라 그 사람 이름으로 문의를 올린다. 고객은 그 고객사에 소속된 `ACTIVE` 고객이어야 한다(아니면 400). 올린 사람은 그 고객이고, 실제로 만든 사람(`createdBy`)은 상담원으로 따로 남는다. 상담 쪽 화면은 "대리 등록: {상담원}"을 보이고, 고객 화면은 "지원팀이 대신 올림"으로 보인다. 받은 경로(`channel`)를 `PHONE`·`OTHER` 가운데 고르고, 포털은 `PORTAL`, 메일은 `EMAIL`이다. 고객에게 알림함과 메일로 알린다(10절) |
| ISSUE-10 | 첫 응답 시각: 상담 쪽의 첫 공개 댓글이 달린 시각을 `firstResponseAt`으로 남긴다. 대리 등록할 때 함께 쓴 공개 댓글은 첫 응답으로 치지 않는다. 한 번 남기면 그 댓글을 지워도 바꾸지 않는다. SLA(16절)와 통계가 쓴다 |

| RECEIVED | – | 됨 | 됨 | – | 됨 |
| CONFIRMED | – | – | 됨 | – | 됨 |
| IN_PROGRESS | – | – | – | 됨 | – |
| RESOLVED | – | – | 됨 | – | 됨 |

| ID | 규칙 |
|---|---|
| STATUS-1 | 위 표는 상담 쪽의 상태 변경이다. 표 밖의 전이와 같은 상태로의 전이는 400이다 |
| STATUS-2 | 고객 종료: 올린 고객은 `CLOSED`가 아닌 어느 상태에서든 `CLOSED`로 닫는다 |
| STATUS-3 | 해결 확인: 올린 고객이 `RESOLVED` 문의를 확인하면 `CLOSED`가 된다 |
| STATUS-4 | 재오픈: 올린 고객과 상담 쪽이 한다. `RESOLVED`, 또는 `CLOSED`이고 종료 뒤 14일이 지나지 않은 문의만 된다. `RECEIVED`로 돌아가고 해결·종료 시각을 지운다. 담당자·마감일·라벨은 그대로다 |
| STATUS-5 | 자동 종료: 해결되고 7일이 지난 `RESOLVED` 문의를 시스템이 `CLOSED`로 바꾼다. 10분마다 돈다. 바꾼 사람은 시스템(계정 0)이다 |
| STATUS-6 | `RESOLVED`가 되면 해결 시각을, `CLOSED`가 되면 종료 시각을 남긴다. `RESOLVED`에서 `CLOSED`가 아닌 상태로 가면 해결 시각을 지운다 |
| STATUS-7 | 같은 문의의 상태 변경은 하나씩 차례로 처리한다. 동시에 온 요청의 결과는 어떤 한 순서로 처리한 결과와 같다(조건부 UPDATE, 앱 메모리의 잠금에 기대지 않는다) |

## 5. 댓글과 멘션 (CMT, MNT)

| ID | 규칙 |
|---|---|
| CMT-1 | 공개 댓글은 올린 고객과 상담 쪽이 단다. 같은 고객사 동료는 403이다. 내부 댓글은 상담 쪽만 단다. 내용은 1~4,000자다 |
| CMT-2 | 고객에게는 내부 댓글이 없는 것과 같다(목록에서 빠지고, 고치기·지우기는 404) |
| CMT-3 | 고치기는 쓴 사람만 한다(관리자도 남의 댓글은 403). 고친 시각을 남긴다. 지우기는 쓴 사람과 관리자가 하고 흔적을 남긴다(COM-7). 댓글을 지우면 그 댓글의 첨부도 지운다 |
| CMT-4 | `CLOSED` 문의에는 댓글을 달거나 고칠 수 없다(400) |
| MNT-1 | 댓글에 멘션을 10명까지 넣는다. 대상은 그 문의를 볼 수 있는 `ACTIVE` 계정이다: 관리자, 그 고객사에 배정된 상담원, (공개 댓글이면) 올린 고객. 자기 자신은 빠진다. 대상이 아니면 400이다 |
| MNT-2 | 화면은 멘션 후보 목록을 받아 고른다. 고치기에서 멘션을 바꾸면 새로 더해진 사람에게만 알린다 |

## 6. 첨부 (ATT)

| ID | 규칙 |
|---|---|
| ATT-1 | 문의나 댓글에 파일을 올린다. 올리는 사람은 그 문의에 댓글을 달 수 있는 사람이고, 댓글 첨부는 그 댓글을 쓴 사람만 붙인다. `CLOSED` 문의는 400이다 |
| ATT-2 | 파일 하나는 1바이트~10MB, 문의 하나의 첨부 합은 50MB까지다. 파일 이름은 1~255자다 |
| ATT-3 | 팀 전체 첨부 합이 `POPDESK_ATTACHMENT_QUOTA`(기본 10GB)를 넘게 되면 올리기가 400이다. 한도의 80%를 넘으면 경고 로그를 남긴다 |
| ATT-4 | 내려받기는 문의를 볼 수 있는 사람이 한다. 늘 `Content-Disposition: attachment`와 `X-Content-Type-Options: nosniff`로 내려준다. 고객은 내부 댓글의 첨부를 받을 수 없다 |
| ATT-5 | 지우기는 올린 사람과 관리자가 하고 흔적을 남긴다(COM-7, 파일 내용은 지운다) |
| ATT-6 | 본문 이미지: 글을 저장하기 전에 이미지를 임시로 올려 ID를 받고, 본문에 `![설명](attachment:{id})`로 넣은 뒤, 글을 저장할 때 그 ID들을 함께 보내 묶는다. 형식은 PNG·JPEG·GIF·WebP만 받고 파일 앞 바이트가 형식과 맞아야 한다 |
| ATT-7 | 임시 이미지는 24시간 안에 묶어야 한다. 사람마다 묶지 않은 임시 이미지는 20개·50MB까지다. 만료된 것은 시스템이 10분마다 지운다 |
| ATT-8 | 첨부를 올리고, 묶고, 지울 때 문의 이력을 남긴다. 알림은 보내지 않는다 |
| ATT-9 | 파일 내용은 `POPDESK_STORAGE`의 저장소(`db`·`disk`·`s3`)에 둔다(D-38). 저장소가 달라도 위 규칙과 응답은 같다. 지우기(ATT-5)와 영구 삭제(TRASH-3)는 저장소의 파일도 지운다. 저장소에서 지우기가 실패하면 행은 지운 것으로 두고, 남은 파일은 정리 작업이 하루 한 번 다시 지운다. 목록 조회는 파일 내용을 읽지 않는다 |

## 7. 라벨과 마감일 (LBL, DUE)

| ID | 규칙 |
|---|---|
| LBL-1 | 라벨은 고객사마다 있다. 관리자가 만들고 고치고 지운다. 이름은 1~30자이고 같은 고객사 안에서 대소문자를 무시하고 하나다(겹치면 409). 색은 `#RRGGBB`, 없으면 `#808080`이다 |
| LBL-2 | 상담 쪽이 문의에 라벨을 붙이고 뗀다. 그 문의 고객사의 라벨만 붙는다(아니면 400). 이미 붙은 것을 붙이거나 없는 것을 떼면 그대로 200이다. `CLOSED` 문의는 400이다 |
| LBL-3 | 라벨을 지우면 붙어 있던 문의에서도 떨어진다. 이것은 문의 이력에 남기지 않는다 |
| LBL-4 | 고객에게는 라벨이 보이지 않는다 |
| DUE-1 | 상담 쪽이 마감일(날짜)을 정하거나 지운다. 오늘(`POPDESK_TIMEZONE` 기준)보다 이전 날짜는 400이다. `CLOSED` 문의는 400이다. 고객에게는 보이지 않는다 |

## 8. 작업 (TASK)

| ID | 규칙 |
|---|---|
| TASK-1 | 작업은 상담 쪽 전용이다. 고객은 403이고 어떤 경로로도 보이지 않는다(RULE-04) |
| TASK-2 | 문의 하나에 작업을 여러 개 만든다. 제목은 1~100자이고 상담 쪽 누구나 고친다. 지우기는 만든 사람과 관리자가 하고, 흔적을 남기며, 그 작업의 기록도 함께 지운다 |
| TASK-3 | 작업마다 기록을 시간순으로 쌓는다. 내용은 1~4,000자이고 상담 쪽 누구나 남긴다. 고치기는 쓴 사람만, 지우기는 쓴 사람과 관리자가 한다(흔적을 남긴다) |
| TASK-4 | 목록은 작업과 그 기록을 한 번에 오래된 순으로 준다. `CLOSED` 문의에서는 읽기만 된다 |
| TASK-5 | 작업과 기록은 알림을 보내지 않고 문의 이력에도 남기지 않는다(그 자체가 기록이다) |

## 9. 이력과 휴지통 (HIST, TRASH)

| ID | 규칙 |
|---|---|
| HIST-1 | 문의를 올리면 `CREATED` 한 건, 그 뒤 값이 실제로 바뀔 때마다 `CHANGED` 한 건을 남긴다. 항목: 바뀐 칸(상태, 담당자, 제목, 내용, 우선순위, 마감일, 라벨, 첨부, 삭제), 전 값, 뒤 값, 한 사람(시스템은 0), 시각 |
| HIST-2 | 같은 값으로 바꾸거나 거부된 요청은 남기지 않는다. 이력은 바꾼 내용과 같은 트랜잭션에 저장한다 |
| HIST-3 | 이력은 상담 쪽만 본다(고객 403). 오래된 순이다 |
| TRASH-1 | 문의 삭제는 관리자만 한다. 지우면 휴지통으로 간다: 모든 목록·검색·알림함에서 빠지고, 그 문의와 하위 경로는 404다. 자동 종료도 하지 않는다 |
| TRASH-2 | 관리자는 휴지통 목록을 보고(지운 시각, 지운 사람, 영구 삭제 예정 시각), 복구하거나 바로 영구 삭제한다. 복구하면 지우기 전 그대로 돌아온다 |
| TRASH-3 | 지우고 30일이 지나면 시스템이 영구 삭제한다(1시간마다 돈다). 영구 삭제는 쓴 내용(제목은 "Deleted issue"/"삭제된 문의", 내용, 댓글, 첨부, 작업, 알림함 항목)을 지우고 문의 행(키, 고객사, 상태, 시각)과 이력의 흔적은 남긴다. 이력의 제목·내용 값도 비운다 |
| TRASH-4 | 문의 순번은 지워도 다시 쓰지 않는다 |

## 10. 알림 (INBOX, MAIL, HOOK)

알릴 일은 "누구에게 무엇을"을 한 번 정하고 알림함·메일·웹훅이 그 결과를 쓴다.

| 일 | 고객(올린 사람) | 상담 쪽 | 팀 웹훅 |
|---|---|---|---|
| 문의가 올라옴 | – | – | 보냄 |
| 상담 쪽이 대리 등록함 | 알림함 + 메일 | – | 보냄 |
| SLA 목표의 80%가 지남 | – | 담당자(없으면 그 고객사 배정 상담원 전부)에게 알림함 | – |
| SLA 목표를 넘김 | – | 담당자와 관리자 전부에게 알림함 + 메일 | 보냄 |
| 상담 쪽이 공개 댓글을 담 | 알림함 + 메일 | – | – |
| 고객이 댓글을 담 | – | 담당자에게 알림함 | 보냄 |
| `RESOLVED`가 됨 | 알림함 + 메일 | – | 보냄 |
| 상담 쪽이나 시스템이 `CLOSED`로 바꿈 | 알림함 + 메일 | – | 보냄 |
| 고객이 종료하거나 해결을 확인함 | – | 담당자에게 알림함 | 보냄 |
| 상담 쪽이 재오픈 | 알림함 + 메일 | – | 보냄 |
| 고객이 재오픈 | – | 담당자에게 알림함 | 보냄 |
| 멘션됨 | 멘션된 사람에게 알림함 + 메일 | 멘션된 사람에게 알림함 + 메일 | – |
| 담당자가 바뀜 | – | 새 담당자에게 알림함 + 메일 | 보냄 |
| 초대·다시 보내기 | 초대받은 사람에게 메일 | 초대받은 사람에게 메일 | – |

| ID | 규칙 |
|---|---|
| INBOX-1 | 알림함 항목은 바꾼 내용과 같은 트랜잭션에 저장한다. 항목: 종류, 문의 키와 지금 제목, 댓글 ID(있으면), 일으킨 사람, 시각, 읽음 |
| INBOX-2 | 자기가 일으킨 일은 자기에게 알리지 않는다. 한 요청에서 같은 사람에게 멘션과 댓글 알림이 겹치면 하나만 남긴다. `ACTIVE`가 아닌 계정에는 남기지 않는다 |
| INBOX-3 | 자기 항목만 보고, 지금 그 문의를 볼 수 있는 것만 보인다. 최신순, 쪽 나누기는 COM-4. 안 읽은 수, 하나 읽음, 모두 읽음이 있다 |
| INBOX-4 | 화면은 안 읽은 수를 60초마다(탭이 보일 때만) 다시 받는다 |
| MAIL-1 | 메일은 받는 사람의 언어(ACCT-1)로 쓴다. 문의 링크는 받는 사람이 고객이면 포털, 아니면 콘솔 주소다. 메일 받기가 켜져 있으면 고객에게 가는 문의 알림 메일의 `Reply-To`는 `MAIL_INBOUND_ADDRESS`이고 제목에 `[문의 키]`가 있다 |
| MAIL-2 | 메일 제목에 들어가는 값의 줄바꿈은 공백으로 바꾼다. 받는 사람은 한 명이다 |
| MAIL-3 | SMTP 설정이 없으면 보내지 않고 로그 한 줄(받는 주소는 첫 글자 뒤를 가린다)을 남긴다. 초대 링크와 토큰은 어떤 로그에도 남기지 않는다 |
| HOOK-1 | 웹훅은 `NOTIFY_WEBHOOK_URL`에 `{"text": "..."}` JSON을 POST한다(Slack, Teams, Mattermost가 받는 모양). 주소는 비밀값이라 로그에 남기지 않는다 |
| MAIL-4 | 메일과 웹훅은 보내기 대기 테이블로 나간다(`architecture.md` 4절). 실패해도 요청은 성공하고, 24시간까지 다시 보낸다 |

## 11. 메일로 받기 (MAILIN)

설정(`IMAP_*`)이 있을 때만 켜진다. 메일로 들어온 일은 포털로 들어온 같은 일과 규칙이 같다(권한, 길이, 첨부 한도, 알림).

| ID | 규칙 |
|---|---|
| MAILIN-1 | 보낸 사람(`From`)이 `ACTIVE` 고객 계정일 때만 받는다. 모르는 주소, 상담 쪽 계정, 정지·수락 전 계정에서 온 메일은 버리고 로그 한 줄(주소는 가린다)과 지표만 남긴다. 답장하지 않는다(위조된 보낸 사람에게 메일을 뿌리지 않게) (D-16) |
| MAILIN-2 | 답장인 메일(알림 메일의 `Message-ID`를 가리키거나, 제목에 그 사람이 볼 수 있는 `[문의 키]`가 있는 메일)은 그 문의의 공개 댓글이 된다. 그 문의에 댓글을 달 수 없는 사람(CMT-1)이거나 `CLOSED` 문의면 댓글을 만들지 않고, 보낸 사람에게 이유와 포털 링크를 담은 안내 메일을 보낸다 |
| MAILIN-3 | 답장이 아닌 메일은 새 문의가 된다: 제목은 메일 제목(비면 "(제목 없음)"/"(no subject)"), 내용은 본문, 우선순위 `NORMAL`, 공개. 고객사는 받는 주소의 `+코드`(예: `support+ACME@…`)로 고르고, 없으면 보낸 사람의 소속이 하나일 때 그곳이다. 소속이 여럿인데 코드가 없거나, 코드가 소속이 아니거나, 고객사가 `ACTIVE`가 아니면 문의를 만들지 않고 안내 메일을 보낸다 |
| MAILIN-4 | 본문: `text/plain` 부분을 쓰고, 없으면 HTML을 글자로 바꾼다. 답장은 흔한 인용 구분선(`On … wrote:`, `-----Original Message-----`, `>` 인용) 아래를 잘라 낸다. 길이 한도(ISSUE-2, CMT-1)를 넘으면 한도까지 자르고 끝에 잘렸다고 적는다 |
| MAILIN-5 | 메일 첨부는 문의나 댓글의 첨부가 된다. 파일 규칙(ATT-2·3)에 맞지 않는 첨부는 빼고, 뺀 파일 이름을 본문 끝에 적는다 |
| MAILIN-6 | 같은 `Message-ID`는 한 번만 처리한다. 처리하다 앱이나 DB 오류가 나면 읽음으로 바꾸지 않고 다음 회차에 다시 처리한다 |
| MAILIN-7 | 자동 응답(`Auto-Submitted`가 `no`가 아님, `Precedence: bulk`·`list`·`junk`)과 자기 자신(`MAIL_FROM`)이 보낸 메일은 버린다(메일이 서로 되돌아 도는 것을 막는다) |

## 12. 통계 (STATS)

| ID | 규칙 |
|---|---|
| STATS-1 | 상담 쪽이 고객사마다 문의 건수를 본다: 전체, 열림(`RECEIVED`+`CONFIRMED`), 처리 중, 해결, 종료. 휴지통의 문의는 세지 않는다 |
| STATS-2 | 관리자는 모든 고객사를, 상담원은 배정된 고객사만 본다. 열린 문의가 많은 순, 같으면 코드순이다 |
| STATS-3 | 문의 테이블을 바로 센다(이벤트를 모아 두지 않는다). 규모(`architecture.md` 7절)를 넘어 느려지면 그때 집계 테이블을 정한다 |
| STATS-4 | SLA가 켜져 있으면 고객사마다 기간(기본 최근 30일) 안의 첫 응답·해결 시간 중앙값과 목표 달성률을 함께 보인다(SLA-7) |

## 13. 개인정보 (PII)

| ID | 규칙 |
|---|---|
| PII-1 | 저장하는 개인정보: 계정의 이메일·이름·언어, 고객이 쓴 문의·댓글·첨부(내용에 무엇이 들지는 고르지 못한다), 감사 로그의 바꾼 사람과 바뀐 값, 받은 메일의 보낸 주소와 `Message-ID`. IP 주소는 저장하지 않는다(로그인 횟수 제한은 메모리에서만 센다) |
| PII-2 | 로그에는 이메일을 첫 글자 뒤로 가려서 남기고, 비밀번호·토큰·초대 링크·문의 내용은 남기지 않는다 |
| PII-3 | 내보내기: 관리자가 한 계정의 정보를 JSON 하나로 받는다. 계정 필드, 그 사람이 올린 문의(제목·내용·상태·시각), 쓴 댓글, 올린 첨부 목록(파일 내용은 빼고 이름·크기·시각)이 들어간다. 내보내기 자체를 감사 로그에 남긴다 |
| PII-4 | 익명화: 관리자가 계정을 익명으로 바꾼다. 이름은 "Deleted user"/"삭제된 사용자", 이메일은 `deleted-{id}@invalid`, 상태는 `SUSPENDED`가 되고 세션을 모두 지운다. 되돌릴 수 없다. 그 사람이 쓴 문의·댓글은 남고 작성자는 익명 이름으로 보인다. 자기 자신과 마지막 관리자는 익명화할 수 없다(400) |
| PII-5 | 익명화한 계정의 이메일은 다시 초대에 쓸 수 있다. 감사 로그에 남은 그 사람의 이전 이메일·이름도 익명 값으로 바꾼다(감사 로그 사슬은 AUDIT-6대로 다시 잇고, 바꾼 일 자체를 감사 로그에 남긴다) |
| PII-6 | 보관 기간(아래 표). 문의 자동 정리는 기본으로 꺼져 있고, `POPDESK_ISSUE_RETENTION`(예: `P1095D`)을 넣으면 종료되고 그 기간이 지난 문의를 하루 한 번 휴지통으로 옮긴다(그 뒤는 TRASH-3) |
| PII-7 | 삭제 요청 처리 절차를 `docs/operate/privacy.md`에 적는다: ① 원하면 내보내기(PII-3) ② 계정 익명화(PII-4) ③ 그 사람이 올린 문의 가운데 지워야 할 것을 관리자가 지우고 영구 삭제(TRASH-2). 다른 사람이 쓴 글에 든 그 사람의 이름은 자동으로 찾지 않으므로, 검색으로 찾아 고치라고 적는다 |
| PII-8 | 고객사 내보내기: 관리자가 고객사 하나의 데이터를 ZIP 하나로 받는다. 문의, 공개 댓글, 첨부 파일, 소속 고객 계정(이메일·이름)이 들어간다. 내부 댓글·작업은 기본으로 빼고, 고를 때만 넣는다. 크면 백그라운드로 만들고 다 되면 알림함으로 알린다. 내려받기 링크는 24시간 뒤 지운다. 내보내기를 감사 로그에 남긴다 |

| 데이터 | 보관 |
|---|---|
| 문의, 댓글, 첨부, 작업 | 지울 때까지. 지우면 휴지통 30일 뒤 영구 삭제(TRASH). 선택: 종료 뒤 `POPDESK_ISSUE_RETENTION`이 지나면 휴지통으로(PII-6) |
| 계정 | 익명화할 때까지(PII-4) |
| 감사 로그 | `POPDESK_AUDIT_RETENTION`(기본 365일) |
| 알림함 항목 | 문의를 영구 삭제할 때 함께 지움 |
| 보내기 대기의 실패 행 | 7일 |
| 임시 본문 이미지 | 24시간 |
| 세션 | 로그인 뒤 8시간 |
| 받은 메일의 `Message-ID` | 90일 |
| 고객사 내보내기 파일 | 24시간 |
| 앱 로그(표준 출력) | popdesk는 저장하지 않는다. 설치한 곳의 로그 수집기가 정한다 |

## 14. 감사 로그 (AUDIT)

| ID | 규칙 |
|---|---|
| AUDIT-1 | 남기는 일: 초대·다시 보내기·취소(고객사 담당자가 한 것 포함), 정지·해제, 역할·이름 변경, 비밀번호 초기화, 익명화, 내보내기(계정·고객사·감사 로그), 고객사 만들기·고치기·상태 변경, 소속·배정 더하고 빼기, 고객사 담당자 지정·해제, SLA 정책·업무 시간 변경, 브랜딩 변경, 라벨 만들기·고치기·지우기, 문의 삭제·복구·영구 삭제(사람이 한 것). 로그인 성공·실패와 잠금도 남긴다 |
| AUDIT-2 | 항목: 일의 종류, 한 사람(시스템은 0), 대상(종류와 ID), 바뀐 값(전과 뒤, 비밀번호·토큰은 넣지 않는다), 시각. 바꾼 내용과 같은 트랜잭션에 저장한다(로그인 실패는 따로) |
| AUDIT-3 | 관리자만 본다. 최신순이고 일의 종류·한 사람·대상·기간으로 거른다. 쪽 나누기는 COM-4 |
| AUDIT-4 | 고치거나 지우는 API는 없다. `POPDESK_AUDIT_RETENTION`(기본 365일)이 지난 항목은 시스템이 하루 한 번 지운다 |
| AUDIT-5 | 문의 이력(HIST)과는 따로다. 문의의 상태·담당자 같은 업무 변경은 이력에만 남는다 |
| AUDIT-6 | 변조 탐지: 항목마다 `hash = SHA-256(앞 항목의 hash ‖ 이 항목의 정해진 JSON)`을 저장한다. 항목은 한 번에 하나씩 순서대로 붙인다(사슬이 갈라지지 않게). 보관 기간이 지나 앞 항목을 지울 때는 지운 마지막 항목의 hash를 사슬의 시작점으로 남긴다. 익명화(PII-5)로 값을 바꿀 때는 그 뒤 사슬을 다시 계산하고, 다시 계산했다는 항목을 남긴다 |
| AUDIT-7 | 관리자는 "무결성 확인"을 돌려 사슬이 처음 끊긴 항목을 본다. 이것은 고친 흔적을 찾아낼 뿐 막지는 못한다: DB를 고칠 수 있는 사람은 사슬 전체를 다시 쓸 수 있다. 그래서 AUDIT-9의 바깥 사본과 함께 쓰라고 문서에 적는다 |
| AUDIT-8 | 내보내기: 관리자가 거른 결과(AUDIT-3)를 CSV나 JSON Lines로 받는다. hash 칸도 함께 나가서 밖에서도 사슬을 확인할 수 있다. 내보내기 자체를 감사 로그에 남긴다 |
| AUDIT-9 | 바깥 사본(선택): `AUDIT_FORWARD_URL`이 있으면 항목마다 JSON 한 건을 그 주소로 POST한다. 보내기 대기 테이블로 나가므로 최소 한 번 보내기다(중복이 올 수 있어 항목 ID를 함께 보낸다). 받는 쪽은 SIEM이나 로그 수집기다 |

## 15. 고객사 담당자 (MGR)

| ID | 규칙 |
|---|---|
| MGR-1 | 관리자는 고객사의 소속 고객 가운데 누구든 그 고객사의 담당자로 지정하고 해제한다. 한 고객사에 여럿일 수 있다. 담당자 지정은 소속에 붙는 표시이고, 다른 고객사에서는 담당자가 아니다 |
| MGR-2 | 담당자는 포털에서 자기 고객사의 소속 고객 목록(이름, 이메일, 상태, 담당자 표시)을 본다 |
| MGR-3 | 담당자는 자기 고객사에 고객을 초대한다(이메일, 이름). 처음 보는 이메일이면 INVITE-2대로 초대 메일이 나가고 그 고객사에 소속된다. 이미 있는 이메일이면 계정을 건드리지 않고 관리자에게 "소속 요청"을 남긴다(관리자가 승인하면 소속된다). 두 경우 응답과 화면 문구는 같다("요청을 처리했습니다"). 다른 고객사의 계정이 있는지 드러내지 않기 위해서다(RULE-01) |
| MGR-4 | 담당자는 자기 고객사 소속에서 고객을 뺀다. 계정을 정지하거나 다른 고객사 소속을 바꾸지는 못한다. 자기 자신과 다른 담당자는 뺄 수 없다(관리자가 한다). 수락 전 고객의 초대를 다시 보내거나 취소할 수 있다(그 고객이 이 고객사에만 소속일 때만) |
| MGR-5 | 담당자는 문의를 보는 범위가 넓어지지 않는다(RULE-02 그대로). 동료의 비공개 문의는 보지 못한다 |
| MGR-6 | 관리자는 소속 요청 목록을 보고 승인하거나 거절한다. 담당자가 한 일은 모두 감사 로그에 남는다 |

## 16. SLA

| ID | 규칙 |
|---|---|
| SLA-1 | 관리자가 우선순위마다 첫 응답 목표와 해결 목표를 정한다(업무 시간 기준 분 단위, 비우면 그 목표가 없다). 정책은 설치 전체에 하나다. 기본은 모두 비어 있어서 SLA가 꺼진 상태다 |
| SLA-2 | 업무 시간: 요일마다 시작·끝 시각(하루에 구간 하나), 쉬는 날 목록. 시간대는 `POPDESK_TIMEZONE`이다. 업무 시간이 비어 있으면 하루 24시간으로 센다 |
| SLA-3 | 시계: 문의가 올라온 시각부터 업무 시간만 센다. 첫 응답 시계는 `firstResponseAt`(ISSUE-10)에서 멈춘다. 해결 시계는 `RESOLVED`나 `CLOSED`가 되면 멈추고, 재오픈되면 이어서 센다(앞서 센 시간을 더한다) |
| SLA-4 | 기한: 목표가 있는 문의마다 첫 응답 기한과 해결 기한을 계산해 저장하고, 우선순위나 정책이 바뀌면 열린 문의의 기한을 다시 계산한다. 쉬는 날·업무 시간을 바꾸면 열린 문의의 기한도 다시 계산한다 |
| SLA-5 | 상태: 목표마다 `ok`, `warning`(목표 시간의 80%가 지남), `breached`(넘김), `met`(기한 안에 멈춤), `missed`(넘긴 뒤 멈춤). 1분마다 도는 작업이 `warning`·`breached`로 바뀐 문의를 찾아 한 번씩만 알린다(10절 표) |
| SLA-6 | 상담 쪽 목록은 남은 시간을 보이고, "곧 넘김"과 "넘김"으로 거른다. 기한이 빠른 순으로 정렬할 수 있다. 고객에게는 SLA가 보이지 않는다 |
| SLA-7 | 통계(STATS-4): 고객사마다 기간 안에 멈춘 문의의 첫 응답·해결 시간 중앙값과 목표 달성률(`met` ÷ (`met`+`missed`))을 보인다 |
| SLA-8 | 정책을 처음 켜면 그때부터 올라오는 문의에만 기한을 붙인다. 이미 있던 문의에는 붙이지 않는다 |

## 17. 브랜딩 (BRAND)

| ID | 규칙 |
|---|---|
| BRAND-1 | 관리자가 설치 전체의 표시 이름(1~50자, 기본 "popdesk"), 로고, 강조색을 정한다. 고객사별 브랜딩은 없다(NG-07) |
| BRAND-2 | 로고는 PNG·JPEG·WebP, 512KB까지이고 파일 앞 바이트가 형식과 맞아야 한다. SVG는 받지 않는다(스크립트를 담을 수 있다). 밝은 테마용과 어두운 테마용을 따로 올릴 수 있고, 하나만 있으면 둘 다 그것을 쓴다 |
| BRAND-3 | 강조색은 `#RRGGBB`이고, 밝은·어두운 테마 바탕 모두에서 글자 대비 4.5:1 이상이어야 받는다(아니면 400, 화면은 대비 값을 함께 보인다). 강조색은 디자인 토큰 하나(`accent`)만 바꾼다. 상태 색과 오류 색은 바꾸지 않는다 |
| BRAND-4 | 로그인 화면, 두 포털의 머리, 브라우저 탭 제목, 메일의 보내는 이름과 머리에 표시 이름과 로고가 나온다. 메일 본문은 로고를 붙임 이미지로 넣지 않고 표시 이름 글자만 쓴다 |
| BRAND-5 | 브랜딩 값은 로그인 전에도 읽을 수 있는 공개 API로 준다(로그인 화면에 필요하다). 비밀 정보는 담지 않는다 |
