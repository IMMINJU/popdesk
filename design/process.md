CI의 `locked` 잡도 같은 검사를 한다(`--role any`: 한 커밋이 잠근 테스트와 운영 코드를 함께 고치면 실패). 푸시 하나에 여러 탭의 커밋과 메인의 잠금 커밋이 같이 실리므로 커밋마다 본다. 테스트 도구 설정(Stryker 등)과 의존성 파일은 운영 코드로 세지 않는다. 고친 것을 두 커밋으로 쪼개면 이 검사는 지나가므로, 그 경우는 잠금 목록과 합치기 전 `--role impl` 검사가 잡는다. CI는 검사 스크립트를 기준 커밋에서 가져와 돌린다. 바뀐 쪽이 자기를 판정하는 스크립트를 느슨하게 하지 못하게 하려는 것이다.

숨긴 E2E는 레포 밖 로컬 git 저장소(`C:\Users\minju\popdesk-holdout\`, 원격 없음)에 둔다. 같은 레포의 다른 브랜치는 탭 worktree가 `.git`을 같이 써서 `git log --all`로 보이므로 쓰지 않는다. C-10에서 메인이 합친 `main` 위에서 돌리고, 통과하면 레포로 옮겨 커밋한다. 그 뒤로는 보통 회귀 테스트다. 브라우저 없이 HTTP로만 도는 것(첫 묶음의 빈 설치 E2E)은 `server/src/test/java/io/popdesk/e2e/`에 `deploy` 태그로 두어 CI 이미지 잡이 돌리고, 브라우저로 도는 것은 `web/e2e/`에 둔다.

코드가 생기면 운영 코드 쪽 정적 검사를 붙인다(`.github/workflows/ci.yml` 주석 목록). 예외 삼키기, 쓰지 않는 코드, 새 중복, 인가 검사가 빠진 컨트롤러, 서비스 밖 `@Transactional`, 운영 코드의 `System.exit`·호출 스택 검사·`Thread.sleep`·테스트 프로필 빈 같은 것을 잡는다. 거짓 완료를 막는 Stop 훅(바뀐 모듈 테스트와 `trace.py`가 실패하면 끝내지 못하게)도 빌드 명령이 정해지면 구현 탭에 더한다.

### 단계마다 지킬 것

묶음을 닫으며(C-11) 더한 규칙을 단계별로 모았다.

#### C-1~3 설계

- 화면 초안을 쓰기 전에 그 화면에 이미 나간 문구와 이미 잠긴 테스트를 읽는다. 이미 나간 말은 그대로 쓰고, 초안이 잠긴 테스트와 부딪히지 않게 한다.
- 설계 문서에 확인하지 않은 동작을 적지 않는다. "이미 있다"고 적기 전에 계약 파일에서 찾고, 설정 키는 문서에 적힌 키를 읽는 코드가 있는지 본다. 있는 동작에 기대는 문장은 [소스]로 표시할 수 있을 때만 쓴다.
- 같은 때 온 요청의 결과를 설계에 적을 때는 기준의 문장("어떤 한 순서로 한 것과 같다")에서 끌어낸다.

#### C-4 계약

- 계약이 바뀌면 그 계약에 묶인 잠긴 테스트(계약 고정값, 경계 목록, 견본 값의 타입)를 테스트 쪽 탭이 같은 푸시에서 맞춘다. 그러지 않으면 CI가 실패한다.
- 계약을 합친 뒤에는 두 계약의 모든 operation을 훑는 앞 묶음의 테스트를 한 번 돈다: `project.NoStoreTest`, `ops.CheckOrderTest`, `ops.EndpointMappingsTest`, `boundary.BoundaryListTest`.
- 있는 표에 칸을 더하는 묶음은 표나 칸을 꼴로 찾는 테스트 도움(`grep -rln "db.tables()" server/src/test`)을 쓰는 클래스를 한 번 돌려 본다.
- 모든 화면이 부르는 요청(레이아웃이 보내는 것)이 늘면, 계약 뒤 테스트를 맞추는 탭이 앱의 기본 가짜 서버(`console.ts`, `portal.ts`)에 그 핸들러를 더한다. 빠지면 `App.test.tsx` 같은 앞 묶음의 테스트가 가끔 실패한다.

#### C-5 테스트

- 테스트는 다른 테스트가 먼저 돌았다는 것에 기대지 않는다. 같은 앱과 DB를 나눠 쓰는 테스트는 자기가 만든 데이터만 센다(주소나 키로 거른다). JVM 전체에 걸리는 설정은 도움 클래스의 static 초기화에 두지 않고 surefire `argLine`에 둔다.
- 요청을 보내는 화면과 대화상자마다 "닫히거나 대상이 바뀐 뒤에 온 답"을 버리는지 보는 테스트를 둔다.
- 테스트 도움 코드는 스키마에 "그런 표나 칸은 하나뿐"이라고 기대지 않고, 자기가 만든 행으로 표를 찾는다. 스키마 이름을 테스트의 추측에 맞추지 않는다.
- 웹 테스트의 가짜 응답은 계약 파일의 설명과 맞춘다.
- 테스트의 HTTP 클라이언트가 보낼 수 없는 입력은 경우로 쓰지 않는다. JDK의 `HttpClient`는 머리글의 비ASCII 글자를 `?`로 바꿔 보낸다.
- 테스트 견본의 지어낸 토큰은 `rst-`, `inv-`로 시작하게 쓴다. `.gitleaks.toml`이 그 꼴을 허용한다.
- 순수 계산(앱과 DB 없이 도는 클래스)의 단위 테스트는 구현이 합쳐진 뒤에 쓴다(2026-10-13 사람이 정함, 5번 묶음부터. 4b의 `MailLimit`과 서버 답 다듬기로 먼저 시험한다). 테스트 쪽 서브에이전트가 기준의 줄과 메서드 시그니처만 보고 쓰고 본문은 읽지 않는다. 구현한 쪽이 쓰지 않는다. C-10에서 변이 테스트로 잰다. 잠그는 HTTP 테스트는 그 계산을 한두 경우만 본다.

#### C-6 실패 확인과 잠금

- 테스트 탭이 남긴 결과 파일(JUnit XML, vitest JSON)을 C-6이 그대로 읽는다(2026-10-13 사람이 정함, 5번 묶음부터). 같은 테스트를 메인이 다시 돌리지 않는다. 탭이 합친 뒤 테스트 파일이 바뀌었으면 그 파일만 다시 돈다.
- deploy 태그 테스트도 `pending.txt`를 따른다. CI 이미지 잡이 `-Dtest=` 대신 태그로 테스트를 골라 제외 목록이 듣는다.
- `pending.txt`의 `web` 줄은 패키지를 가리지 않아, 같은 이름의 파일이 다른 패키지에 있으면 그것도 빠진다(예: `src/App.test.tsx`). 줄을 쓸 때 `git ls-files | grep`으로 겹치는 이름을 본다.

#### C-7 점검

- 점검은 웹 테스트의 본문도 읽는다. 전체 경로 묶음은 서버와 웹을 탭 둘로 나누고, 그 밖의 묶음도 시간이 모자라면 나눈다.
- 웹 점검은 한 구현이 함께 만족할 수 없는 단언 쌍과 틀린 화면이 통과하는 테스트를 찾는다.
- 웹 점검은 새 응답 스키마마다 픽스처의 칸이 계약의 설명대로인지 본다(어느 칸이 언제 `null`인가).
- 요청을 보내는 화면 가운데 "닫히거나 대상이 바뀐 뒤에 온 답"을 버리는지 보는 테스트가 빠진 화면을 찾는다.
- 일부러 틀린 구현은 센 검증을 받는 기준에만 쓴다(아래 C-10).
- 점검 탭의 지시서에 넣어 볼 틀린 구현의 목록을 메인이 미리 적는다(2026-10-13 사람이 정함, 5번 묶음부터). 점검의 일을 늘리지 않는다. 4b의 웹 점검은 틀린 화면 16가지 가운데 6가지가 통과하는 것을 찾았다.
- 점검은 서브에이전트로 옮겨 본다(5번 묶음에서 시험). 구현과 잠그는 테스트는 탭에 둔다. 훅이 서브에이전트에도 걸리는지 먼저 확인한다.

#### C-8 작업 분해와 탭 지시서

- 테스트 클래스를 구현 탭에 나눌 때 클래스가 직접 쓰는 픽스처만 보지 않는다. 같은 패키지의 도움 클래스와 바탕 클래스(`ConnectedAppTest`처럼 SMTP를 켠 것)가 쓰는 픽스처까지 모아 "가장 늦은 탭"에 둔다.
- 탭 지시서에는 문서를 통째로 읽으라고 적지 않고, 그 탭이 맡은 절, 기준 번호, 결정 번호를 적는다. 탭 보고는 결과 표, 정한 것, 질문만 쓰고 줄 번호 같은 세부는 `-detail.md`에 따로 둔다(2026-10-11 정함).
- 구현 탭의 지시서에는 "계약의 글이 구현과 어긋나면 고치지 말고 보고에 적는다"를 넣는다.
- 메인이 그 묶음에서 생길 순수 계산 클래스의 목록을 적는다(C-5의 단위 테스트와 C-10의 변이 테스트가 이 목록을 쓴다).
- 두 웹 앱이 같이 쓸 부분(훅, 도움 함수, 기능 조각)은 한 탭이 공용 패키지 `@popdesk/app`에 먼저 만들고 두 앱 탭이 가져다 쓴다(2026-10-13 사람이 정함, 5번 묶음부터). 합칠 기준은 "같은 지식이고 같이 바뀌는가"다. 화면은 앱에 둔다.
- 지시서에 "다시 쓰지 마라", "순환을 만들지 마라" 같은 글을 늘리지 않는다. 구조는 돌아가는 검사가 막고(막는 장치 표), 지시서에는 그 검사를 통과하는 법만 적는다.

#### C-9 구현

- 첫 구현 탭은 맡은 클래스를 먼저 한 번 돌려, 다른 탭의 코드가 있어야 통과하는 클래스를 메인에 알린다.
- 구현 탭은 보고를 `C:\Users\minju\.claude\popdesk\tasks\<탭 이름>-report.md`에 바로 쓴다. 훅이 worktree 밖 쓰기 가운데 이 파일만 허용한다.
- 구현 탭이 "이 테스트는 어떤 구현으로도 통과할 수 없다"고 알리면 메인이 테스트와 기준을 읽고 판정한다. 한두 줄이면 메인이 고치고 잠금 목록을 다시 쓴다(메인은 그 묶음의 테스트를 쓰지도 구현하지도 않았다). 더 크면 테스트 쪽 탭에 맡긴다. 구현 탭은 `git merge main`으로 받아 간다.
- 구현 탭 보고의 "메인이 볼 곳"과 질문은 보고를 받은 자리에서 정하고 고친다. C-10으로 미루지 않는다(2026-10-12 사람이 정함, 4번 묶음부터).
- 표를 더하는 구현 탭은 업그레이드 견본 생성기(`deploy/upgrade/make-sample.py`)가 그 표를 채우게 한다. 생성기는 빈 표가 있으면 실패한다.
- 계약 파일(`docs/integrate/openapi-*.json`)과 생성 클라이언트는 구현 쪽 훅이 커밋을 막는다. C-9 뒤에 계약의 설명을 고칠 일이 생기면 구현 탭이 컨트롤러를 고치고 파일을 다시 만들어 worktree에 둔 채 알리고, 메인이 diff를 읽고 올린다.
- 웹 구현 탭은 서버 구현과 같이 띄워 가짜 서버 위에서 화면을 만들고, 서버 구현이 합쳐지면 `git merge main`으로 받아 브라우저 확인을 한다(2026-10-12 사람이 정함, 4번 묶음부터). 탭은 `start-tab.ps1 -Browser`로 띄운다(탭마다 따로 쓰는 Chrome이 붙는다). 끝내기 전에 합친 코드로 이미지를 띄워 자기가 만든 화면을 폭 둘(콘솔 1280px과 820px, 포털 1280px과 360px)로 열고, 스크린샷과 브라우저 콘솔의 오류 유무를 보고에 붙인다. 서버 테스트와 같은 때에 설치를 띄우지 않는다.

#### 브라우저 확인 (C-9의 웹 구현 탭, C-10의 메인)

- 브라우저 확인용 설치는 이미지 덮어쓰기 파일을 꼭 붙인다(`services.app.image: popdesk:test`). 릴리스 compose 파일은 지난 릴리스 이미지를 가리킨다. 띄운 뒤 새 화면의 주소가 열리는지로 확인한다.
- 표가 있는 화면은 칸이 가장 넓어지는 데이터(배지가 붙은 줄, 긴 제목)를 넣고 본다.
- 공용 컴포넌트를 고친 뒤에는 그것을 쓰는 화면을 고치기 전과 같은 폭으로 다시 본다.
- 같은 모양 문제를 두 번째로 만나면 그 화면이 아니라 공용 규칙(공용 컴포넌트나 공용 CSS)으로 고친다(2026-10-12 사람이 정함, 4번 묶음부터).

#### C-10 검증

- 센 검증은 묶음 전체가 아니라 수용 기준에 건다(2026-10-11 사람이 맡겨 메인이 정함). 고객사 경계, 권한과 세션, 개인정보, 마이그레이션, 공개 계약에 걸린 기준만 C-7의 일부러 틀린 구현, 숨긴 E2E, 변이 테스트를 받는다. 나머지 기준은 테스트와 잠금, 자동 관문만 받는다. 어느 기준이 센 검증을 받는지는 `acceptance.md`에 ID로 적는다.
- 서버 PIT는 순수 계산 코드(사진 머리글 읽기, 감사 JSON처럼 앱을 띄우지 않고 도는 단위 테스트가 붙은 것)에만 쓴다(2026-10-11 사람이 정함). 앱과 DB를 띄우는 테스트가 붙는 코드는 C-7의 점검과 숨긴 E2E로 본다.
- 변이 테스트는 묶음마다 그 묶음이 고친 범위로 실제로 돈다(2026-10-13 사람이 정함. 3번과 4a에서는 돌지 않았다). 웹은 파일 하나로 먼저 돌려 변이 하나에 걸리는 시간을 재고, 30분을 넘을 것 같으면 그 파일을 보는 테스트만 돌게 범위를 줄인다(4b에서 두 파일 587개에 287분이 걸렸다). 살아남은 것 가운데 동작이 걸린 것은 `verify.md`에 표로 적고 테스트 쪽 일로 넘긴다.
- 변이 테스트 전체 실행은 릴리스 태그 때만 한다(2026-10-11 사람이 맡겨 메인이 정함). 그것도 30분을 넘으면 먼저 묻는다. PIT의 history 파일은 유료 플러그인이 있어야 해서 쓰지 않고, 대상 클래스를 명령줄로 준다.
- 웹 구현 탭이 브라우저를 봤어도 메인의 브라우저 확인은 그대로 한다(2026-10-12 사람이 정함, 4번 묶음부터). 구현한 쪽의 확인이 독립 확인을 갈음하지 않는다. 1280px과 820px, 밝게와 어둡게를 다 본다.
- "문서를 구현에 맞춘다"로 정하기 전에 그 동작이 ADR이나 정본 문서에 정해져 있는지 먼저 찾는다(`grep -n`으로 `adr.md`, `conventions.md`). 정해져 있으면 구현을 고친다.
- 구현 탭들이 보고에 적은 "계약의 글이 구현과 어긋난 곳" 목록을 메인이 여기서 처리한다.
- 테스트 속도는 따로 일정을 잡지 않는다(2026-10-11 사람이 맡겨 메인이 정함). 구현 탭이 기다리는 것은 클래스 하나(가운데 값 3초, 긴 것 40초)라 급하지 않다.
- 뒤에 따로 할 것(2026-10-12 사람이 정함, 4번 묶음부터): 웹 테스트의 견본을 계약 스키마로 검증하는 도움, Storybook 스토리를 실제 브라우저에서 돌려 폭마다 넘침을 단언하는 것(스토리 하나로 먼저 시험한다).

#### C-11 닫기

- 묶음을 닫는 커밋처럼 문서와 `pending.txt`의 자리만 바뀌는 푸시는 `[skip ci]`를 붙인다. `pending.txt`는 CI의 모든 잡을 깨운다.
- 묶음이 끝나면 `docker builder prune -af`로 빌드 캐시를 지운다.

### 이 PC에서 돌리기와 탭 같이 띄우기

- 구현 탭과 테스트 탭은 이 PC에서 서버 전체 테스트를 돌리지 않는다(2026-10-11 사람이 정함). 맡은 클래스와 그 패키지만 돌리고, 전체는 푸시 뒤 CI가 돈다. 다른 패키지의 테스트가 깨지는 것은 CI에서 알게 된다.
- 30분을 넘는 실행은 줄일 방법을 먼저 찾아 적용한 뒤 돌린다. 묻지 않아도 되고, 걸리는 시간을 알린다(사람이 정함. 2026-10-11에는 답을 받고 돌리기로 했다가 뒤에 바꿨다).
- 서버 탭 여럿을 같이 띄운다(2026-10-12 사람이 정함). 무거운 실행(Maven 테스트, 이미지 빌드, compose 설치)만 `bash /c/Users/minju/.claude/popdesk/heavy.sh <탭 이름> <명령…>`으로 감싸 한 번에 하나만 돌게 한다. vitest와 타입 검사는 감싸지 않는다. `heavy.sh`는 잠금을 얻은 뒤 빈 메모리 3GB를 기다렸다가 시작한다. 같은 파일을 두 탭이 고치지 않게 나누는 것은 그대로다.
- 같이 띄우는 세션은 메인 말고 둘까지고, 브라우저를 쓰는 탭은 한 번에 하나만 띄운다(2026-10-12 사람이 정함). 넷을 띄우고 이미지를 빌드하자 16GB에서 빈 메모리가 0.5GB까지 내려갔다. 빌드나 설치 뒤에는 Docker VM의 캐시를 비운다.
- Claude Code는 메모리가 모자라면 백그라운드 명령을 끊는다. 이때 셸만 끊기고 java는 남으므로, 끊겼다는 알림이 오면 남은 java와 테스트 컨테이너를 먼저 지운다. 오래 도는 실행은 앞에서(백그라운드가 아니게) 10분 안쪽으로 나눠 돌린다. Docker가 쥔 메모리는 컨테이너가 없을 때 VM의 파일 캐시를 비우면 돌아온다.
- 이미지를 빌드하거나 설치를 띄우기 전에 C 드라이브 남은 공간을 본다. 5GB 아래면 띄우지 않고 알린다.
- 이 PC에서 서버 탭과 웹 전체를 같이 돌리면 "파일의 첫 테스트가 첫 화면을 한 번의 기본 기다림으로 기다리는" 웹 테스트가 가끔 실패한다. 웹 구현 탭의 끝 실행이 그렇게 실패하면 그 파일만 다시 돌려 가른다. CI에서 한 번이라도 나면 `asyncUtilTimeout`을 올린다.
- deploy 태그 테스트를 골라 돌릴 때는 `-Dtest=… -Dtest.groups=deploy -Dtest.excludedGroups=openapi`를 쓴다. `-Dtest.groups=deploy`만 주면 기본 제외 목록에 `deploy`가 남아 0개가 돈다.
- 스크립트나 치환으로 파일을 고친 뒤에는 결과를 `grep`으로 확인하고 나서 고쳤다고 적는다. Windows의 Python `Path.write_text`는 LF 파일을 CRLF로 바꾸므로 `write_bytes`를 쓴다.
- 파이썬 스크립트를 bash의 heredoc에 쓰면 역슬래시 둘이 하나로 줄어든다. 역슬래시가 든 글은 Edit 도구로 고치거나 스크립트를 파일로 쓴다. 고친 뒤 `grep`이 "Binary file"이라고 답하면 NUL이 든 것이다.
- 탭을 닫기 전에 커밋 안 된 파일이 있는지 본다(`git status --short`). `stop-tab.ps1`은 폴더를 지운다.

### 메인 세션이 지킬 것

푸시와 CI:

- CI가 도는 푸시는 묶음에 한 번을 기본으로 하고, CI 결과가 필요할 때만 한다(2026-10-11 사람이 정함). 코드나 루트 파일이 든 커밋은 로컬 `main`에 모아 두고, 이 PC에서 돌리지 않는 것(서버 전체 테스트, 이미지·deploy 테스트)의 결과가 필요한 때에 올린다: 서버 구현을 다 합쳐 전체를 봐야 할 때, C-10 검증, 릴리스. 단계가 끝났다는 것만으로는 올리지 않는다. 비공개 레포라 Actions 시간이 한 달 2,000분(Free)이고 코드 푸시 한 번이 37분쯤을 쓴다.
- 문서만 바꾼 푸시는 1분쯤이라 묶지 않아도 된다. 다만 로컬에 안 올린 코드 커밋이 있으면 문서만 고친 커밋도 같이 기다린다(2026-10-11 사람이 정함).
- 묶어 둔 동안에는 메인이 합친 트리에서 바뀐 패키지의 테스트를 한 번 돌려 본다(2026-10-11 사람이 정함).
- 올리기 전에 이 PC에서 gitleaks(`docker run ghcr.io/gitleaks/gitleaks git … --log-opts=origin/main..HEAD`)를 돈다. 합친 `main`의 서버 전체 테스트는 이 PC에서 한 번에 끝까지 돌지 못한다(3번 묶음에서 메모리 부족으로 멈췄다). 고친 코드가 걸리는 패키지와 모든 엔드포인트를 훑는 클래스들을 10분 안쪽 묶음으로 나눠 돌리고, 전체는 CI가 돈다(사람이 정함).
- 합친 main의 서버 전체를 이 PC에서 못 돌렸으면, 탭들의 끝 실행이 어느 패키지를 같은 코드로 돌렸는지 세어 빠진 패키지를 `verify.md`에 적고 CI의 서버 잡으로 본다.
- 푸시할 때마다 `gh run watch`로 CI를 끝까지 본다. `design/`만 바꾼 푸시는 잡이 건너뛰어 초록으로 보이므로, 마지막 코드 푸시의 런이 초록인지 따로 본다.

그 밖에:

- 테스트를 돌릴 때는 출력을 늘 파일로 남긴다. `grep`으로만 흘려보내면 어느 테스트가 실패했는지 남지 않는다.
- 로그나 보고에서 "0건"을 세기 전에 받은 줄 수를 먼저 본다.
- 탭을 기다리는 동안 다음 묶음의 C-1~3을 쓴다(2026-10-12 사람이 정함).
- 메인 세션을 넘길 때 옛 세션을 닫는다. 옛 메인이 살아 있으면 탭의 보고가 두 곳으로 가고, 옛 메인이 DevTools 전용 Chrome을 쥐고 있어 새 메인의 브라우저가 열리지 않는다.

## D. 릴리스할 때

- 지난 릴리스 2~3개에서 올라오는 업그레이드 테스트(데이터를 채운 DB).
- 릴리스 노트: 바뀐 설정 키, 되돌릴 수 없는 마이그레이션 표시, "업그레이드 전에 백업하세요".
- SBOM은 CI가 만들어 릴리스마다 붙인다(D-29). 이미지 서명은 여력이 될 때. `SECURITY.md` 신고 경로는 처음부터.

### 지금은 태그와 견본만 남기고 이미지는 올리지 않는다 (2026-10-10 사람이 정함)

다른 곳에서 설치할 사람이 없어 ghcr에 올리기를 미뤘다. 0.1.0을 이 범위로 했고, 0.2.0, 0.3.0, 0.4.0도 같은 범위와 같은 순서로 했다(사람이 맡겨 메인이 정함. 0.3.0은 2번과 3번을, 0.4.0은 4a와 4b를 묶었다).

릴리스마다 하는 것:

- 태그(`v0.1.0`, `v0.2.0` 꼴).
- 태그의 코드로 이 PC에서 만든 이미지(amd64)로 trivy와 업그레이드 견본(`deploy/upgrade/samples/0.2.0/` 꼴). 새 견본은 `upgrade-test.py`로 옛 견본들과 함께 새 이미지에 올려 본다.
- 릴리스 노트(`docs/release-notes/0.1.0.md` 꼴).
- 업그레이드 테스트는 옛 태그(`v0.1.0`)를 다시 빌드한 이미지가 아니라 견본 덤프와 새 이미지로 돈다(`deploy/upgrade/README.md`).
- 베이스 이미지 다이제스트는 0.1.0에서 고정했다.

올리는 순서(Actions 시간을 아끼려는 것이다): 태그만 먼저 올려 전체 런 하나를 돌린다. 견본은 태그 커밋에 넣는다(`deploy/upgrade`는 이미지에 들어가지 않는다). 그 뒤 검증 기록 커밋은 `[skip ci]`를 붙여 `main`에 올린다. 브랜치 푸시와 태그 푸시는 따로 돌기 때문에 둘을 같이 올리면 런이 둘이다.

버전을 올릴 때 고치는 곳: `server/pom.xml`, `OpenApiConfig.CONTRACT_VERSION`(계약 파일과 생성 클라이언트를 다시 만든다), `deploy/compose.yml`의 이미지 태그, README 둘의 상태 줄, `docs/operate/upgrade.md`의 "다음 판" 제목(판 번호로 바꾸고 그 앵커를 가리키는 링크도 고친다), `deploy/upgrade/README.md`와 `samples/README.md`의 견본 줄. 0.3.0의 기록은 `archive/3-issues/verify.md` 9절에, 0.4.0의 기록은 `archive/4b-delivery/verify.md` 10절에 있다.

설치할 사람이 생기거나 레포를 공개할 때 하는 것:

- 릴리스 워크플로: amd64·arm64 빌드(D-45), ghcr에 올리기, SBOM(D-29), compose 파일을 릴리스에 붙이기.
- 올린 이미지로 trivy를 다시 돌리고, 견본에 `sample.repodigest`를 붙인다.
- RTO를 재서 `docs/operate/`에 적는다(D-33). 지금은 잰 값이 문서에 없다.
- 문서의 "popdesk is not released yet" 줄(`configuration.md`, `upgrade.md`, `conventions.md`, `permissions.md`)을 고친다.

### 묶음 폴더

진행 중인 묶음은 `design/slices/{번호}-{이름}/`에 둔다.

| 파일 | 내용 | 묶음이 끝나면 |
|---|---|---|
| `acceptance.md` | EARS 수용 기준(`When …, the system shall …` 꼴, 한국어로 써도 꼴은 지킨다). 기준마다 ID를 달고 대응표(C-7)에 쓴다. 기준 한 줄에는 밖에서 보이는 동작 하나만 적는다. 만드는 법(잠금 순서, 쓸 클래스)은 설계 문서에 적고 ArchUnit 같은 검사로 지킨다. 머리말에 이 묶음과 관계있는 결정 번호(ADR)를 적는다 | `archive/`로 |
| `premortem.md` | 사전 부검(전체 경로일 때만) | `archive/`로 |
| `screens.md` | 화면 상태 목록 | story로 옮기고 지운다 |
| `tasks.md` | 한 세션 크기의 작업 목록 | 지운다 |
| `questions.md` | 테스트 쪽이 테스트를 쓰다 만난 모호한 기준(C-5) | 답을 수용 기준에 옮기고 지운다 |
| `red-allow.txt`, `red.md` | 처음부터 통과해도 되는 테스트와 이유, 실패 확인 결과(C-6) | `archive/`로 |

묶음을 시작할 때 `design/spec/`에서 그 묶음의 절을 이 폴더로 옮기고, `spec/`에서는 지운다. `spec/`이 비면 폴더를 지운다.
