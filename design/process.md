# popdesk 진행 절차

> 무엇을 어떤 방법으로 만들고, 무엇으로 끝났다고 보는지 적는다. 무엇을 어떤 순서로 만드는지는 `roadmap.md`에 있다.

## A. 프로젝트에서 한 번

| 단계 | 할 일 | 상태 |
|---|---|---|
| 0 바탕 | 루트 안내 파일(README 영어·한국어, LICENSE, SECURITY, CONTRIBUTING, AI_POLICY, CODE_OF_CONDUCT, `AGENTS.md`와 그것을 가리키는 `CLAUDE.md`) — 끝남(행동 강령 연락처만 남음). `CODEOWNERS`(테스트·스냅샷·마이그레이션·권한 코드), CI 관문(아키텍처 규칙 `tenant_id NOT NULL`, 의존성·비밀값·라이선스 검사, SBOM, OpenAPI 차이), 시각 회귀 렌더 환경 Docker 고정, springdoc → TypeScript 클라이언트 생성, 디자인 토큰·공용 컴포넌트 | 안내 파일, `CODEOWNERS`, CI 첫 관문(비밀값, `tenant_id`, 바뀐 영역만 돌기 D-48)은 끝남. 행동 강령 연락처, 코드가 있어야 하는 관문(빌드·테스트·OpenAPI 차이·의존성·SBOM·이미지), 렌더 환경, 클라이언트 생성, 디자인 토큰은 할 일 |
| 1 되묻기 | 제품 범위와 범위 밖, 기능 묶음 목록과 순서 | 끝남: `roadmap.md` |
| 2 설계 | 결정 기록: 인스턴스 하나(D-23), `tenant_id` 칸만(D-18), 첨부 저장소 셋과 상한(D-38), 보내기 대기 재시도 규칙(D-39), TLS는 앞단 프록시(D-40), 마이그레이션은 앞으로만(D-24). 고객사 단위 권한 모델, 감사 로그(D-20), 개인정보 항목(D-25), 간단한 위협 모델. 위협 모델에는 보안 질문지에 답할 자료를 함께 둔다: 데이터 흐름도, 암호화 위치 표(전송 구간 TLS를 어디서 끝내는지, 저장 구간, 비밀번호·토큰 해시, 비밀값 보관), 신뢰 경계 | 끝남: `docs/use/permissions.md`, `threat-model.md`. 위협 모델 6절의 정할 것 둘(OIDC, DMARC)은 남음. 메일 TLS·웹훅 http는 D-51로 정함 |
| 3 사전 부검 | "업그레이드하다 데이터가 깨졌다", "A사가 B사 문의를 봤다" 같은 실패를 가정하고 막을 장치를 적는다 | 끝남: `premortem.md`. 정한 것은 ADR D-44~47과 spec으로 옮김 |
| 4 공통 규약 | 오류 응답 모양, 쪽 나누기, 시간대, null의 뜻. 공개 계약: 환경변수·설정 키, compose 서비스·포트·볼륨, 문서화된 REST API | 옮김 끝남: `docs/integrate/conventions.md`, `docs/operate/configuration.md`. null의 뜻(D-44)과 compose 계약(D-45)도 정함 |

## B. 첫 묶음 (끝에서 끝까지 얇게)

| | |
|---|---|
| 흐름 | 빈 설치 → 첫 관리자 → 고객 초대 → 고객 포털에서 문의(첨부 포함) → 콘솔에서 상담원 답변 → 보내기 대기로 메일 → 채널 웹훅 → Grafana에 지표 |
| 함께 붙일 관문 | A사·B사 고객 픽스처로 서로의 문의를 못 보는 부정 테스트 |
| | 빈 설치 `docker compose up` → 첫 관리자 계정까지 E2E |
| | 업그레이드 테스트 틀(데이터를 채운 옛 버전 DB를 새 버전으로 올린다). 실제로는 v0.1이 나간 뒤 v0.2부터 돈다 |
| 바닥 깔기 | C를 돌기 전에 한 번. 빌드 파일, 빈 Spring Boot 앱과 빈 모듈, pnpm 작업공간과 빈 앱·패키지, Testcontainers 기반, springdoc → OpenAPI 파일 → TypeScript 클라이언트 생성, 서버·웹 CI 잡. 테스트를 쓸 쪽도 구현할 쪽도 아닌 세션이 한다. 이게 있어야 C-5의 테스트가 돈다. 수용 기준이 정한 것(compose, 보안 설정, 마이그레이션, 관리 포트, `popdesk` 명령)은 넣지 않는다. 넣으면 C-6에서 그 테스트가 처음부터 통과한다 |
| 나눠 쓰기 | 수용 기준이 많아(104개) C-5와 C-7을 한 세션에 못 한다. C-8의 분해를 C-5 앞에서 한 번 더 해, 수용 기준 절(4.1~4.12) 단위로 테스트 세션을 나눈다 |

첫 묶음이 끝나면 v0.1로 태그한다.

## C. 묶음마다 반복

| 단계 | 할 일 | 맡는 쪽 |
|---|---|---|
| 1 되묻기 | 수용 기준, 포털·콘솔 화면 상태 | 사람과 메인 |
| 2 설계 | 쓸 토큰·컴포넌트, 새 결정 기록이 필요한지 | 사람과 메인 |
| 3 사전 부검 | 전체 경로 조건(아래)에 걸릴 때만 | 사람과 메인 |
| 4 계약 | 컨트롤러 껍데기(경로·요청·응답 타입만, 본문은 501)로 엔드포인트 추가 → `docs/integrate/openapi-portal.json`·`openapi-console.json`과 클라이언트 다시 생성, props·story 껍데기 | 구현 쪽 |
| 5 테스트 | 백엔드 API 테스트와 고객사 경계 부정 테스트, 프런트 role·axe 테스트, 구현하는 쪽에 보이지 않는 E2E 하나. 테스트 이름에 수용 기준 ID를 단다. HTTP와 생성된 클라이언트로만 시험하고 서버 내부 클래스는 참조하지 않는다(픽스처도 API로 만들고, 스키마 검사처럼 DB를 봐야 하는 것만 예외). 기준이 모호하면 추측하지 않고 질문 목록에 적고 멈춘다. 숨긴 E2E는 레포 밖 로컬 저장소 `C:\Users\minju\popdesk-holdout\`에 쓴다(아래 "막는 장치") | 테스트 쪽 |
| 6 실패 확인 | 구현 전에 테스트를 돌려 모두 실패하는지, 컴파일 오류나 컨테이너 기동 실패가 아니라 단언에서 실패하는지 본다. 처음부터 통과하는 테스트는 고친다. 통과하면 테스트 파일마다 해시를 적은 잠금 목록을 커밋한다 | 스크립트 |
| 7 점검 | 수용 기준 ↔ 테스트 ↔ story ↔ E2E 대응표(스크립트가 만든다: 모든 기준에 테스트가 있는지, 모든 테스트의 기준 ID가 있는지). 테스트를 쓰지도 구현하지도 않는 에이전트가 빠진 부정 사례, 상태 코드만 보는 약한 단언, 오류 문구·순서 같은 우연한 값을 고정한 단언을 찾는다. 같은 에이전트가 일부러 틀린 구현(예: 고객사를 거르지 않는 조회)을 짧게 써서 테스트가 잡는지 본다. 마지막에 사람이 테스트를 승인한다 | 점검 쪽, 사람 |
| 8 작업 분해 | 한 세션 크기로, 모델 → 서비스 → API → 화면. 작업 하나는 "이 테스트들을 통과시킨다"로 적는다 | 메인 |
| 9 구현 | 백엔드 먼저, 포털·콘솔은 실제 API 위에서. 테스트는 잠근 채(아래 "막는 장치"). 새 단위 테스트를 더하는 것은 된다. 같은 테스트가 여러 번 고쳐도 실패하면 멈추고, 테스트가 틀렸다고 보는 이유를 보고한다 | 구현 쪽 |
| 10 검증 | 실제 앱 대상 E2E(compose·Testcontainers), 숨긴 E2E, 변이 테스트(서버 PIT, 웹 Stryker, 바뀐 곳만), 소스에 픽스처 값을 박아 넣었는지 검사, 보안 검사, 시각 회귀, 웹훅 메시지 스냅샷, 핵심 흐름만 손으로 접근성 점검 | 스크립트, 사람 |
| 11 가드레일 고치기 | 이번 묶음에서 에이전트가 우회했거나 잘못 읽은 것을 훅·검사 스크립트·`AGENTS.md` 한 줄로 남긴다 | 메인 |

사람이 정하는 것은 1~3(되묻기, 설계, 사전 부검)과 새 결정 기록(ADR)이다. 7의 테스트 승인, 10의 사람 검증, 아래 표의 "사람이 본다"는 메인이 점검 결과를 보고 추천대로 정하고 무엇을 정했는지 사람에게 알린다(2026-10-09 사람이 정함).

### 막는 장치

글로 쓴 지침만으로는 테스트를 고치거나 끄는 일, 테스트 입력만 따로 처리하는 일을 막지 못한다. 스크립트는 `scripts/ci/`에 있고, 무엇을 잠그는지는 `lockrules.py` 한 곳에 적는다.

| 스크립트 | 단계 | 하는 일 |
|---|---|---|
| `check-test-style.py --all-strict` | 5 | `@Disabled`·`.skip`·`.only`, 늘 참인 단언, mock(`@MockBean`, `Mockito`, `vi.mock` 등), 고정 대기(`Thread.sleep` 등)를 실패로 본다. 바깥 시스템은 mock 대신 실제 대역(Testcontainers Postgres, GreenMail, MinIO, 테스트용 웹훅 받는 쪽, 고정 `Clock`)을 쓴다 |
| `check-red.py --allow design/slices/{묶음}/red-allow.txt --out design/slices/{묶음}/red.md` | 6 | 이번 묶음의 새 테스트 결과(JUnit XML)가 모두 단언 실패인지 본다. 바닥, 프레임워크 기본값, C-4 계약 껍데기(계약 파일, 공용 컴포넌트의 props와 접근성 마크업)가 이미 하는 일이라 처음부터 통과하는 테스트는 `red-allow.txt`에 `테스트 이름 \| 이유`로 적는다. 이유가 없거나 결과에 없는 이름이면 실패다. 허용한 통과는 `red.md`에 이유와 함께 남고 C-7에서 사람이 본다. C-4 껍데기 때문에 허용한 테스트는 C-10 변이 테스트를 꼭 돌린다 |
| `pending.py server\|web` | 5~9, CI | 묶음의 테스트는 구현보다 먼저 `main`에 들어가 일부러 실패한다. `design/slices/{묶음}/pending.txt`에 적은 테스트는 CI의 server·web 잡이 빼고 돌려, 나머지 테스트는 늘 통과해야 한다. 구현 탭이 병합되면 메인이 그 줄을 지운다. 이 파일은 관문이라 테스트 쪽·구현 쪽 모두 고치지 못한다 |
| `tests-lock.py write` | 6 | 테스트 파일마다 sha256을 `tests.lock`에 적는다 |
| `trace.py design/slices/{묶음} --search <숨긴 E2E 저장소>` | 7 | 대응표. 테스트 없는 기준과 없는 기준 ID를 실패로 본다 |
| `check-locked-paths.py --base main --role tests` | 테스트 쪽 합치기 | 테스트 쪽 브랜치가 테스트 경로 밖을 고쳤는지 본다 |
| `check-locked-paths.py --base main --role impl` | 구현 쪽 합치기 | 구현 쪽 브랜치가 잠근 테스트, 잠금 목록, 병합된 마이그레이션, 생성 계약 파일, 관문, 테스트 실행·린트 설정을 고쳤는지 본다. 빌드·의존성 파일이 바뀌면 사람이 보라고 알린다 |
| `tests-lock.py check`, `check-test-style.py` | 구현 쪽 합치기, CI | 잠근 테스트가 그대로인지 본다. 구현 쪽이 더한 단위 테스트의 mock·고정 대기는 경고만 한다 |
| `check-fixture-literals.py` | 10 | 잠근 테스트의 데이터 값이 운영 코드에 그대로 있으면 알린다. 사람이 읽고 판단한다 |

구현 쪽에는 세 겹을 둔다.

- 구현 탭은 `start-tab.ps1 -Role impl`로 띄운다. 그러면 PreToolUse 훅(`C:\Users\minju\.claude\popdesk\hooks\impl-guard.py`)이 붙는다. 훅은 위의 잠긴 경로로 가는 Edit·Write, worktree 밖 쓰기, 숨긴 E2E 저장소 접근, 쓰기로 보이면서 잠긴 경로를 적은 Bash를 거부한다. 규칙은 worktree가 아니라 원래 레포의 `lockrules.py`에서 읽는다. Bash 판정은 짐작이라 빠지는 것이 있다.
- C-6의 잠금 목록. 해시를 대조하므로 어떤 도구로 고쳤든 잡힌다.
- 합치기 전 검사. 메인은 로컬에서 fast-forward로 합치므로 GitHub의 `CODEOWNERS`가 막아 주지 않는다. 메인이 위 표의 합치기 검사를 돌린다. CI의 `locked` 잡도 같은 검사를 한다(`--role any`: 한 브랜치가 잠근 테스트와 운영 코드를 함께 고치면 실패). CI는 검사 스크립트를 기준 커밋에서 가져와 돌린다. 바뀐 쪽이 자기를 판정하는 스크립트를 느슨하게 하지 못하게 하려는 것이다.

숨긴 E2E는 레포 밖 로컬 git 저장소(`C:\Users\minju\popdesk-holdout\`, 원격 없음)에 둔다. 같은 레포의 다른 브랜치는 탭 worktree가 `.git`을 같이 써서 `git log --all`로 보이므로 쓰지 않는다. C-10에서 메인이 합친 `main` 위에서 돌리고, 통과하면 `web/e2e/`로 옮겨 커밋한다. 그 뒤로는 보통 회귀 테스트다.

코드가 생기면 운영 코드 쪽 정적 검사를 붙인다(`.github/workflows/ci.yml` 주석 목록). 예외 삼키기, 쓰지 않는 코드, 새 중복, 인가 검사가 빠진 컨트롤러, 서비스 밖 `@Transactional`, 운영 코드의 `System.exit`·호출 스택 검사·`Thread.sleep`·테스트 프로필 빈 같은 것을 잡는다. 거짓 완료를 막는 Stop 훅(바뀐 모듈 테스트와 `trace.py`가 실패하면 끝내지 못하게)도 빌드 명령이 정해지면 구현 탭에 더한다.

### 경로

- 가벼운 경로(한 문장으로 설명되는 변경): 5 → 6 → 9 → 10의 자동 관문.
- 기본 경로(기능 하나): C 전체, 3은 뺀다.
- 전체 경로: 아래 다섯 가지 중 하나라도 건드리면 크기와 관계없이 A의 2~4를 다시 연다.
  - 스키마 마이그레이션
  - 고객사 경계
  - 개인정보 흐름
  - 공개 계약(설정·compose·문서화된 API)
  - 공용 컴포넌트 API 깨기

## D. 릴리스할 때

- 끝난 묶음만 넣는다. `main`은 늘 통과 상태다.
- 지난 릴리스 2~3개에서 올라오는 업그레이드 테스트(데이터를 채운 DB).
- 릴리스 노트: 바뀐 설정 키, 되돌릴 수 없는 마이그레이션 표시, "업그레이드 전에 백업하세요".
- SBOM은 CI가 만들어 릴리스마다 붙인다(D-29). 이미지 서명은 여력이 될 때. `SECURITY.md` 신고 경로는 처음부터.
- RTO 실측 값(`docs/operate/`)을 다시 잰다(D-33).

### 묶음 폴더

진행 중인 묶음은 `design/slices/{번호}-{이름}/`에 둔다.

| 파일 | 내용 | 묶음이 끝나면 |
|---|---|---|
| `acceptance.md` | EARS 수용 기준(`When …, the system shall …` 꼴, 한국어로 써도 꼴은 지킨다). 기준마다 ID를 달고 대응표(C-7)에 쓴다 | `archive/`로 |
| `premortem.md` | 사전 부검(전체 경로일 때만) | `archive/`로 |
| `screens.md` | 화면 상태 목록 | story로 옮기고 지운다 |
| `tasks.md` | 한 세션 크기의 작업 목록 | 지운다 |
| `questions.md` | 테스트 쪽이 테스트를 쓰다 만난 모호한 기준(C-5) | 답을 수용 기준에 옮기고 지운다 |
| `red-allow.txt`, `red.md` | 처음부터 통과해도 되는 테스트와 이유, 실패 확인 결과(C-6) | `archive/`로 |

묶음을 시작할 때 `design/spec/`에서 그 묶음에 해당하는 절을 이 폴더로 옮기고, `spec/`에서는 지운다. `spec/`이 비면 폴더를 지운다.

2. 첫 묶음의 부정 테스트, 빈 설치 E2E, 업그레이드 테스트 틀.
