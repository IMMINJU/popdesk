# popdesk 진행 절차

> 무엇을 어떤 방법으로 만들고, 무엇으로 끝났다고 보는지 적는다. 무엇을 어떤 순서로 만드는지는 `roadmap.md`에 있다.

## A. 프로젝트에서 한 번

| 단계 | 할 일 | 상태 |
|---|---|---|
| 0 바탕 | 루트 안내 파일(README 영어·한국어, LICENSE, SECURITY, CONTRIBUTING, AI_POLICY, CODE_OF_CONDUCT, `AGENTS.md`와 그것을 가리키는 `CLAUDE.md`) — 끝남(행동 강령 연락처만 남음). `CODEOWNERS`(테스트·스냅샷·마이그레이션·권한 코드), CI 관문(아키텍처 규칙 `tenant_id NOT NULL`, 의존성·비밀값·라이선스 검사, SBOM, OpenAPI 차이), 시각 회귀 렌더 환경 Docker 고정, springdoc → TypeScript 클라이언트 생성, 디자인 토큰·공용 컴포넌트 | 안내 파일, `CODEOWNERS`, CI 첫 관문(비밀값, `tenant_id`, 바뀐 영역만 돌기 D-48)은 끝남. 행동 강령 연락처, 코드가 있어야 하는 관문(빌드·테스트·OpenAPI 차이·의존성·SBOM·이미지), 렌더 환경, 클라이언트 생성, 디자인 토큰은 할 일 |
| 1 되묻기 | 제품 범위와 범위 밖, 기능 묶음 목록과 순서 | 끝남: `roadmap.md` |
| 2 설계 | 결정 기록: 인스턴스 하나(D-23), `tenant_id` 칸만(D-18), 첨부 저장소 셋과 상한(D-38), 보내기 대기 재시도 규칙(D-39), TLS는 앞단 프록시(D-40), 마이그레이션은 앞으로만(D-24). 고객사 단위 권한 모델, 감사 로그(D-20), 개인정보 항목(D-25), 간단한 위협 모델. 위협 모델에는 보안 질문지에 답할 자료를 함께 둔다: 데이터 흐름도, 암호화 위치 표(전송 구간 TLS를 어디서 끝내는지, 저장 구간, 비밀번호·토큰 해시, 비밀값 보관), 신뢰 경계 | 끝남: `docs/use/permissions.md`, `threat-model.md`. 위협 모델 6절의 정할 것 둘(OIDC, DMARC)은 남음. 메일 TLS·웹훅 http는 D-51로 정함 |

| 4 공통 규약 | 오류 응답 모양, 쪽 나누기, 시간대, null의 뜻. 공개 계약: 환경변수·설정 키, compose 서비스·포트·볼륨, 문서화된 REST API | 옮김 끝남: `docs/integrate/conventions.md`, `docs/operate/configuration.md`. null의 뜻(D-44)과 compose 계약(D-45)도 정함 |

### 막는 장치

글로 쓴 지침만으로는 테스트를 고치거나 끄는 일, 테스트 입력만 따로 처리하는 일을 막지 못한다. 스크립트는 `scripts/ci/`에 있고, 무엇을 잠그는지는 `lockrules.py` 한 곳에 적는다.

| 스크립트 | 단계 | 하는 일 |
|---|---|---|
| `check-test-style.py --all-strict` | 5 | `@Disabled`·`.skip`·`.only`, 늘 참인 단언, mock(`@MockBean`, `Mockito`, `vi.mock` 등), 고정 대기(`Thread.sleep` 등)를 실패로 본다. 바깥 시스템은 mock 대신 실제 대역(Testcontainers Postgres, GreenMail, MinIO, 테스트용 웹훅 받는 쪽, 고정 `Clock`)을 쓴다 |
| `check-red.py --allow design/slices/{묶음}/red-allow.txt --out design/slices/{묶음}/red.md` | 6 | 이번 묶음의 새 테스트 결과(JUnit XML)가 모두 단언 실패인지 본다. 바닥, 프레임워크 기본값, C-4 계약 껍데기(계약 파일, 공용 컴포넌트의 props와 접근성 마크업)가 이미 하는 일이라 처음부터 통과하는 테스트는 `red-allow.txt`에 `테스트 이름 \| 이유`로 적는다. 이유가 없거나 결과에 없는 이름이면 실패다. 허용한 통과는 `red.md`에 이유와 함께 남고 C-7에서 사람이 본다. C-4 껍데기 때문에 허용한 테스트는 C-10 변이 테스트를 꼭 돌린다 |
| `pending.py server\|web` | 5~9, CI | 묶음의 테스트는 구현보다 먼저 `main`에 들어가 일부러 실패한다. `design/slices/{묶음}/pending.txt`에 적은 테스트는 CI의 server·web·이미지 잡이 빼고 돌려, 나머지 테스트는 늘 통과해야 한다. 구현 탭이 병합되면 메인이 그 줄을 지운다. 이 파일은 관문이라 테스트 쪽·구현 쪽 모두 고치지 못한다 |
| `tests-lock.py write` | 6 | 테스트 파일마다 sha256을 `tests.lock`에 적는다 |
| `trace.py design/slices/{묶음} --search <숨긴 E2E 저장소>` | 7 | 대응표. 테스트 없는 기준과 없는 기준 ID를 실패로 본다 |
| `check-locked-paths.py --base main --role tests` | 테스트 쪽 합치기 | 테스트 쪽 브랜치가 테스트 경로 밖을 고쳤는지 본다 |
| `check-locked-paths.py --base main --role impl` | 구현 쪽 합치기 | 구현 쪽 브랜치가 잠근 테스트, 잠금 목록, 병합된 마이그레이션, 생성 계약 파일, 관문, 테스트 실행·린트 설정을 고쳤는지 본다. 빌드·의존성 파일이 바뀌면 사람이 보라고 알린다 |
| `tests-lock.py check`, `check-test-style.py` | 구현 쪽 합치기, CI | 잠근 테스트가 그대로인지 본다. 구현 쪽이 더한 단위 테스트의 mock·고정 대기는 경고만 한다 |
| `check-fixture-literals.py` | 10 | 잠근 테스트의 데이터 값이 운영 코드에 그대로 있으면 알린다. 사람이 읽고 판단한다 |

구현 쪽에는 세 겹을 둔다.

- 구현 탭은 `start-tab.ps1 -Role impl`로 띄운다. 그러면 PreToolUse 훅(`C:\Users\minju\.claude\popdesk\hooks\impl-guard.py`)이 붙는다. 훅은 위의 잠긴 경로로 가는 Edit·Write, worktree 밖 쓰기, 숨긴 E2E 저장소 접근, 쓰기로 보이면서 잠긴 경로를 적은 Bash를 거부한다. 규칙은 worktree가 아니라 원래 레포의 `lockrules.py`에서 읽는다. Bash 판정은 짐작이라 빠지는 것이 있다.
- C-6의 잠금 목록. 해시를 대조하므로 어떤 도구로 고쳤든 잡힌다.
- 합치기 전 검사. 메인은 로컬에서 fast-forward로 합치므로 GitHub의 `CODEOWNERS`가 막아 주지 않는다. 메인이 위 표의 합치기 검사를 돌린다. CI의 `locked` 잡도 같은 검사를 한다(`--role any`: 한 커밋이 잠근 테스트와 운영 코드를 함께 고치면 실패). 푸시 하나에 여러 탭의 커밋과 메인의 잠금 커밋이 같이 실리므로 커밋마다 본다. 테스트 도구 설정(Stryker 등)과 의존성 파일은 운영 코드로 세지 않는다. 고친 것을 두 커밋으로 쪼개면 이 검사는 지나가므로, 그 경우는 잠금 목록과 합치기 전 `--role impl` 검사가 잡는다. CI는 검사 스크립트를 기준 커밋에서 가져와 돌린다. 바뀐 쪽이 자기를 판정하는 스크립트를 느슨하게 하지 못하게 하려는 것이다.

숨긴 E2E는 레포 밖 로컬 git 저장소(`C:\Users\minju\popdesk-holdout\`, 원격 없음)에 둔다. 같은 레포의 다른 브랜치는 탭 worktree가 `.git`을 같이 써서 `git log --all`로 보이므로 쓰지 않는다. C-10에서 메인이 합친 `main` 위에서 돌리고, 통과하면 레포로 옮겨 커밋한다. 그 뒤로는 보통 회귀 테스트다. 브라우저 없이 HTTP로만 도는 것(첫 묶음의 빈 설치 E2E)은 `server/src/test/java/io/popdesk/e2e/`에 `deploy` 태그로 두어 CI 이미지 잡이 돌리고, 브라우저로 도는 것은 `web/e2e/`에 둔다.

코드가 생기면 운영 코드 쪽 정적 검사를 붙인다(`.github/workflows/ci.yml` 주석 목록). 예외 삼키기, 쓰지 않는 코드, 새 중복, 인가 검사가 빠진 컨트롤러, 서비스 밖 `@Transactional`, 운영 코드의 `System.exit`·호출 스택 검사·`Thread.sleep`·테스트 프로필 빈 같은 것을 잡는다. 거짓 완료를 막는 Stop 훅(바뀐 모듈 테스트와 `trace.py`가 실패하면 끝내지 못하게)도 빌드 명령이 정해지면 구현 탭에 더한다.

### 첫 묶음 C-11에서 더한 규칙

첫 묶음에서 어긋났던 일과, 그래서 정한 것이다.

- 테스트는 다른 테스트가 먼저 돌았다는 것에 기대지 않는다. 같은 앱과 DB를 나눠 쓰는 테스트는 자기가 만든 데이터만 센다(주소나 키로 거른다). JVM 전체에 걸리는 설정은 도움 클래스의 static 초기화에 두지 않고 surefire `argLine`에 둔다. `MailQueueRowTest`가 다른 테스트의 메일까지 셌고(37b9c34), E2E가 먼저 돌자 Host 머리글 허용 설정이 듣지 않았다(e719e37).
- 요청을 보내는 화면과 대화상자마다 "닫히거나 대상이 바뀐 뒤에 온 답"을 버리는지 보는 테스트를 둔다(C-5). C-7 점검 쪽은 이 테스트가 빠진 화면을 찾는다. 첫 묶음에서는 이 테스트가 없어 다른 계정의 초대 링크가 보이는 결함(V-2)이 C-10 코드 읽기에서야 나왔다.
- 테스트 클래스를 구현 탭에 나눌 때(C-8) 클래스가 직접 쓰는 픽스처만 보지 않는다. 같은 패키지의 도움 클래스와 바탕 클래스(`ConnectedAppTest`처럼 SMTP를 켠 것)가 쓰는 픽스처까지 모아 "가장 늦은 탭"에 둔다. 첫 구현 탭은 맡은 클래스를 먼저 한 번 돌려, 다른 탭의 코드가 있어야 통과하는 클래스를 메인에 알린다.
- 구현 탭은 보고를 `C:\Users\minju\.claude\popdesk\tasks\<탭 이름>-report.md`에 바로 쓴다. 훅이 worktree 밖 쓰기 가운데 이 파일만 허용한다.
- deploy 태그 테스트도 `pending.txt`를 따른다. CI 이미지 잡이 `-Dtest=` 대신 태그로 테스트를 골라 제외 목록이 듣는다.
- 메인은 푸시할 때마다 `gh run watch`로 CI를 끝까지 본다. `design/`만 바꾼 푸시는 잡이 건너뛰어 초록으로 보이므로, 마지막 코드 푸시의 런이 초록인지 따로 본다. C-10에서는 이것을 보지 않아 이미지 잡이 여러 커밋 동안 실패했다.
- 탭 지시서에는 문서를 통째로 읽으라고 적지 않는다. 그 탭이 맡은 절, 기준 번호, 결정 번호를 적는다. 탭 보고는 결과 표, 정한 것, 질문만 쓰고 줄 번호 같은 세부는 `-detail.md`에 따로 둔다(2026-10-11, 읽을 글이 길어 메인 세션이 요약으로 넘어간 뒤 정함).
- 구현 탭과 테스트 탭은 이 PC에서 서버 전체 테스트를 돌리지 않는다. 맡은 클래스와 그 패키지만 돌리고, 전체는 푸시 뒤 CI가 돈다(2026-10-11 사람이 정함). 1a에서 서버 구현 탭 셋이 끝에 전체를 한 번씩 돌려 한 시간(18분, 20분, 23분)을 썼는데, 같은 것을 CI가 15분에 돈다. 다른 패키지의 테스트가 깨지는 것은 CI에서 알게 된다.
- PC를 30분 넘게 쓰는 실행은 띄우기 전에 걸리는 시간을 사람에게 알리고 답을 받는다(2026-10-11, 웹 Stryker를 8시간짜리로 띄운 뒤 정함).
- 스크립트나 치환으로 파일을 고친 뒤에는 결과를 `grep`으로 확인하고 나서 고쳤다고 적는다. Windows의 Python `Path.write_text`는 LF 파일을 CRLF로 바꾸므로 `write_bytes`를 쓴다.

### 1a 묶음 C-11에서 더한 규칙

1a에서 어긋났던 일과, 그래서 정한 것이다.

- 메인이 검증에서 "문서를 구현에 맞춘다"로 정하기 전에 그 동작이 ADR이나 정본 문서에 정해져 있는지 먼저 찾는다(`grep -n` 으로 `adr.md`, `conventions.md`). PATCH의 `null`을 구현에 맞추라고 지시했다가 구현 탭이 D-44와 어긋난다고 짚어 되돌렸다. 정해져 있으면 구현을 고친다.
- 화면 상태 초안(C-1)을 쓰기 전에 그 화면에 이미 나간 문구를 확인한다. 1a 초안이 "멈춤"을 "중지"로, 빠진 고객 안내를 새 문장으로 써서 잠긴 테스트 넷과 부딪쳤다. 이미 나간 말을 그대로 쓴다.
- 테스트 도움 코드는 스키마에 "그런 표나 칸은 하나뿐"이라고 기대지 않는다. 자기가 만든 행으로 표를 찾는다. "token 칸이 든 표는 초대 표 하나"라는 추측 때문에 구현 탭이 새 표의 칸 이름을 바꾸려 했다. 스키마 이름을 테스트의 추측에 맞추지 않는다.
- 계약(C-4)이 바뀌면 그 계약에 묶인 잠긴 테스트(계약 고정값, 경계 목록, 견본 값의 타입)를 테스트 쪽 탭이 같은 푸시에서 맞춘다. 그러지 않으면 CI가 빨개진다.
- 표를 더하는 구현 탭은 업그레이드 견본 생성기(`deploy/upgrade/make-sample.py`)가 그 표를 채우게 한다. 생성기는 빈 표가 있으면 실패한다. V5 뒤 `UpgradeHarnessTest`가 CI에서 그렇게 실패했다.
- 브라우저 확인용 설치는 이미지 덮어쓰기 파일을 꼭 붙인다(`services.app.image: popdesk:test`). 릴리스 compose 파일은 지난 릴리스 이미지를 가리킨다. 메인이 덮어쓰기 없이 띄워 0.1.0 화면을 볼 뻔했다. 띄운 뒤 새 화면의 주소가 열리는지로 확인한다.
- 이미지를 빌드하거나 설치를 띄우기 전에 C 드라이브 남은 공간을 본다(5GB 아래면 띄우지 않고 알린다). 1a에서 이미지를 여러 번 빌드하다 디스크가 가득 차 Docker가 멈췄다. 묶음이 끝나면 `docker builder prune -af`로 빌드 캐시를 지운다.
- 탭을 닫기 전에 커밋 안 된 파일이 있는지 본다(`git status --short`). `stop-tab.ps1`은 폴더를 지운다.
- 테스트 견본의 지어낸 토큰은 `rst-`, `inv-`로 시작하게 쓴다. `.gitleaks.toml`이 그 꼴을 허용한다.
- 코드가 든 푸시는 묶어서 한다(2026-10-11 사람이 정함). 탭이 끝날 때마다 푸시하지 않고, 서버 구현 탭을 다 합친 뒤 한 번, 웹 구현 탭을 다 합친 뒤 한 번처럼 단계마다 한 번 한다. 테스트 탭들(C-5)과 잠금(C-6)도 한 번에 올린다. 비공개 레포라 GitHub Actions 시간이 한 달에 정해져 있는데(Free 2,000분), 코드 푸시 한 번이 37분쯤을 쓰고 1a를 한 날 하루에 455분을 썼다(10월 8~11일 합 1,270분). 문서만 바꾼 푸시는 1분쯤이라 묶지 않아도 된다. 묶어 둔 동안에는 메인이 합친 트리에서 바뀐 패키지의 테스트를 한 번 돌려 본다.
- CI가 도는 푸시는 CI 결과가 필요할 때만 한다(2026-10-11 사람이 정함, 위 규칙을 더 줄인다). 코드나 루트 파일이 든 커밋은 로컬 `main`에 모아 두고, 이 PC에서 돌리지 않는 것(서버 전체 테스트, 이미지·deploy 테스트)의 결과가 필요한 때에 올린다: 서버 구현을 다 합쳐 전체를 봐야 할 때, C-10 검증, 릴리스. 단계가 끝났다는 것만으로는 올리지 않는다. 로컬에 안 올린 코드 커밋이 있으면 문서만 고친 커밋도 같이 기다린다.
- 변이 테스트(PIT)는 앱과 DB를 띄우는 통합 테스트와 맞지 않았다. 1a에서 25분을 써서 결과가 남은 것은 클래스 둘(변이 31개)뿐이고, 두 조각은 상한까지 한 건도 끝내지 못했다. 사람이 정했다(2026-10-11): 다음 묶음부터 서버 PIT는 순수 계산 코드(사진 머리글 읽기, 감사 JSON처럼 앱을 띄우지 않고 도는 단위 테스트가 붙은 것)에만 쓴다. 앱과 DB를 띄우는 테스트가 붙는 코드는 C-7의 점검과 숨긴 E2E로 본다.

### 검증의 세기와 걸리는 시간 (2026-10-11 사람이 맡겨 메인이 정함)

첫 묶음은 C-10 검증과 거기서 나온 수정에 37시간쯤 걸렸다(C-5~7은 4시간, C-9는 9시간). 가장 긴 것은 변이 테스트였다. 조사 보고(`tasks\popdesk-b1-report.md`, popdesk-e7이 전한 것)를 보고 정했다.

- 센 검증은 묶음 전체가 아니라 수용 기준에 건다. 고객사 경계, 권한과 세션, 개인정보, 마이그레이션, 공개 계약에 걸린 기준만 C-7의 일부러 틀린 구현, 숨긴 E2E, 변이 테스트를 받는다. 나머지 기준은 테스트와 잠금, 자동 관문만 받는다. 어느 기준이 센 검증을 받는지는 `acceptance.md`에 ID로 적는다.
- 변이 테스트 전체 실행은 릴리스 태그 때만 한다(CI를 바뀐 영역만 돌리는 D-48과 같은 꼴). 그것도 30분을 넘으면 먼저 묻는다. PIT의 history 파일은 유료 플러그인이 있어야 해서 쓰지 않고, 대상 클래스를 명령줄로 준다.
- 잰 값(2026-10-11): 푸시 한 번의 CI는 15분이다(서버 테스트 14분 26초, deploy 테스트 13분, 웹 4분이 같이 돈다). 이 PC에서 서버 전체는 16분 30초, 계약 파일 다시 만들기는 20~40초다. 서버 테스트는 앱을 58번, Postgres 컨테이너를 38번 띄우고 그것이 14분 가운데 3분 30초다. deploy의 `MissingAdminInstallTest` 하나가 4분 30초다.
- 테스트 속도는 따로 일정을 잡지 않는다. 구현 탭이 기다리는 것은 클래스 하나(가운데 값 3초, 긴 것 40초)라 급하지 않다. 컨테이너를 한 번만 띄우는 것과 위 테스트의 기다림 줄이기는 1a의 첫 테스트 탭이 도움 클래스를 `support/`로 모을 때 같이 보고, 앞뒤 시간을 잰다.

### 묶음 폴더

진행 중인 묶음은 `design/slices/{번호}-{이름}/`에 둔다.

| 파일 | 내용 | 묶음이 끝나면 |
|---|---|---|
| `acceptance.md` | EARS 수용 기준(`When …, the system shall …` 꼴, 한국어로 써도 꼴은 지킨다). 기준마다 ID를 달고 대응표(C-7)에 쓴다. 기준 한 줄에는 밖에서 보이는 동작 하나만 적는다. 만드는 법(잠금 순서, 쓸 클래스)은 설계 문서에 적고 ArchUnit 같은 검사로 지킨다. 머리말에 이 묶음과 관계있는 결정 번호(ADR)를 적는다 | `archive/`로 |
| `premortem.md` | 사전 부검(전체 경로일 때만) | `archive/`로 |
| `screens.md` | 화면 상태 목록 | story로 옮기고 지운다 |
| `tasks.md` | 한 세션 크기의 작업 목록 | 지운다 |
| `questions.md` | 테스트 쪽이 테스트를 쓰다 만난 모호한 기준(C-5) | 답을 수용 기준에 옮기고 지운다 |
| `red-allow.txt`, `red.md` | 처음부터 통과해도 되는 테스트와 이유, 실패 확인 결과(C-6) | `archive/`로 |

묶음을 시작할 때 `design/spec/`에서 그 묶음에 해당하는 절을 이 폴더로 옮기고, `spec/`에서는 지운다. `spec/`이 비면 폴더를 지운다.
